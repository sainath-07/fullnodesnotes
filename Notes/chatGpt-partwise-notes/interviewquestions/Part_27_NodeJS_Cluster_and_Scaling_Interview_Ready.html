NODE.JS INTERVIEW PREPARATION

Part 27 — Node.js Cluster & Scaling

Interview-ready notes, diagrams, and code/output questions for MAANG, product companies, and MNC interviews.

1. What is Node.js Cluster?

What: The Node.js cluster module lets one Node.js application create multiple worker processes that can share the same server port.

Why: A normal Node.js process mainly uses one JavaScript thread. Cluster can run several processes so work can be distributed across multiple CPU cores.

Layman example: Imagine one shop with one cashier. If customers increase, you open more cashier counters. Each counter is a separate worker process.

Primary process → creates workers → Worker 1 | Worker 2 | Worker 3 | Worker 4 → incoming requests distributed
Interview line: Cluster improves process-level utilization across CPU cores; it is not the same as making JavaScript itself multi-threaded.
2. Cluster Architecture

Primary process: Manages workers and cluster lifecycle.

Worker processes: Separate Node.js processes that run application code and can accept requests.

Process isolation: Each worker has its own memory and event loop. A worker crash does not directly corrupt another worker's memory.

Primary / Cluster Manager
↓
Worker 1    Worker 2    Worker 3    Worker 4
↓         ↓         ↓         ↓
Event Loop + Heap   Event Loop + Heap   Event Loop + Heap   Event Loop + Heap
3. Basic Cluster Code
const cluster = require("node:cluster"); const http = require("node:http"); const os = require("node:os"); if (cluster.isPrimary) { const workers = os.cpus().length; for (let i = 0; i < workers; i++) { cluster.fork(); } } else { http.createServer((req, res) => { res.end(`Handled by worker ${process.pid}`); }).listen(3000); }
How it works: The primary process forks workers. The workers start the server. Requests can then be distributed among workers.
4. Worker Failure and Restart

Workers can exit because of an application crash, an unexpected error, or another process-level failure. A production system can detect the exit and create a replacement worker.

cluster.on("exit", (worker, code, signal) => { console.log(`Worker ${worker.process.pid} stopped`); if (!worker.exitedAfterDisconnect) { console.log("Starting replacement worker"); cluster.fork(); } });
Important: Restarting a worker does not fix the underlying bug. If the same bug happens immediately, workers can repeatedly crash. Production systems should use sensible restart policies and monitoring.
5. Cluster vs Worker Threads
FeatureClusterWorker Threads
UnitProcessThread
MemorySeparate memory per processCan share memory using supported mechanisms such as SharedArrayBuffer
IsolationStronger process isolationLess isolated than separate processes
Main useRun multiple server processes / scale across coresMove CPU-heavy JavaScript work away from main thread
CommunicationIPC between processesMessage passing between threads
Remember: Cluster = multiple processes. Worker Threads = multiple threads inside a process.
6. Horizontal vs Vertical Scaling

Vertical scaling: Give one server more CPU, RAM, or other resources.

Horizontal scaling: Run more application instances across machines or containers.

Vertical → Server → more CPU/RAM
Horizontal → Load Balancer → App 1 | App 2 | App 3 | App 4

Why horizontal scaling is common: It can increase capacity and improve availability without depending on one large machine.

7. Reverse Proxy and Load Balancer
Client → Reverse Proxy / Load Balancer → Node.js Instance A
                                                → Node.js Instance B
                                                → Node.js Instance C

Reverse proxy: A server placed in front of application servers. It can handle routing, TLS termination, compression, caching, and other edge concerns.

Load balancer: Distributes requests among available application instances.

Interview point: Cluster is inside the Node.js application environment; a load balancer can distribute traffic across separate application instances and machines.
8. Stateless APIs and Sessions

A stateless API should not depend on one particular application instance storing the user's session in local memory.

Request → Load Balancer → Any healthy API instance → Shared DB / Cache / Token-based identity

If session data exists only in Worker A's memory, the next request sent to Worker B may not find it.

Common solutions: signed access tokens, or shared session storage such as Redis. The exact choice depends on the application and security requirements.

9. PM2 Concept

PM2 is a Node.js process manager commonly used to run and supervise production Node.js applications. It can manage multiple application processes, restart failed processes, and provide operational monitoring features.

Interview distinction: PM2 is a process manager. Node.js Cluster is a Node.js capability for managing worker processes. They can be used together, but they are not the same thing.
10. Interview Code / Output Questions
Q1. What is the output type of cluster.isPrimary?
const cluster = require("node:cluster"); console.log(typeof cluster.isPrimary);
Answer: "boolean"
Why: cluster.isPrimary tells whether the current process is the primary cluster process.
Q2. How many workers are created?
const cluster = require("node:cluster"); if (cluster.isPrimary) { for (let i = 0; i < 3; i++) { cluster.fork(); } }
Answer: 3 worker processes.
Why: The loop calls cluster.fork() three times.
Q3. What is the important mistake in this code?
const cluster = require("node:cluster"); cluster.fork(); cluster.fork(); console.log("server started");
Answer: There is no cluster.isPrimary guard. Each worker can also execute the top-level code and potentially create more workers, causing uncontrolled process creation.
Why: Cluster workers run the same entry file. The primary/worker branch prevents worker processes from running primary-only logic.
Q4. Which architecture is represented here?
Client ↓ Load Balancer ↓ App A | App B | App C
Answer: Horizontal scaling with load balancing.
Why: Multiple application instances receive traffic from a common load balancer.
Q5. Why can local in-memory sessions be a problem with multiple workers?
Worker A: sessions["u1"] = { loggedIn: true } Request 1 → Worker A Request 2 → Worker B
Answer: Worker B has a different process memory, so it cannot automatically see Worker A's session object.
Why: Cluster workers are separate processes with separate heaps. Shared state should be stored in a shared system or represented using a suitable token/session strategy.
Q6. Which is usually the better choice for a CPU-heavy JavaScript calculation inside one Node.js application?
function calculateLargeResult() { // CPU-heavy JavaScript work }
Answer: Worker Threads are often a suitable choice when the goal is to move CPU-heavy JavaScript work away from the main thread.
Why: Worker Threads let CPU-intensive JavaScript execute on another thread, keeping the main event loop more responsive.
Q7. What is wrong with this scaling assumption?
const workers = 100; for (let i = 0; i < workers; i++) { cluster.fork(); }
Answer: Creating a very large number of workers is not automatically better. It can increase memory usage and scheduling overhead.
Why: Each worker is a separate Node.js process with its own runtime and memory. Worker count should be chosen based on workload, CPU resources, memory, and measurement.
Q8. What does this event help detect?
cluster.on("exit", worker => { console.log("worker stopped:", worker.process.pid); });
Answer: It detects that a cluster worker process has exited.
Why: The primary process can use the event to perform cleanup, logging, health handling, or start a replacement worker when appropriate.
Q9. Why should a distributed API avoid storing important state only in process memory?
let cart = {}; // cart exists only inside this process
Answer: Another instance may receive the next request and will not have the same in-memory state.
Why: Horizontal scaling creates multiple application processes or machines. Shared state needs a shared storage or an appropriate stateless design.
Q10. What is the best interview answer for Cluster vs Worker Threads?
Cluster → multiple Node.js processes Worker Thread → multiple threads within a process
Answer: Use Cluster mainly for process-level scaling and running multiple server workers; use Worker Threads mainly for CPU-heavy work that should not block the main event loop.
Why: Processes provide stronger isolation and independent heaps, while worker threads are designed for parallel JavaScript execution within a Node.js process.
11. Common Developer Mistakes
Mistake 1: Thinking Cluster makes one JavaScript thread multi-threaded.
Correct: Cluster creates multiple processes.
Mistake 2: Creating too many workers.
Correct: More workers can increase memory and scheduling overhead.
Mistake 3: Keeping sessions only in local memory.
Correct: Use a stateless approach or shared session storage when requests can reach different instances.
Mistake 4: Assuming worker restart fixes application bugs.
Correct: Find and fix the root cause and use controlled restart/monitoring policies.
Mistake 5: Confusing a load balancer with Cluster.
Correct: A load balancer distributes traffic among instances; Cluster manages Node.js worker processes.

13. Quick Recap — Interview Ready
  • Cluster: multiple Node.js processes.
  • Primary: manages workers.
  • Worker: separate process with its own memory and event loop.
  • Scaling: vertical means bigger machine; horizontal means more instances.
  • Load balancer: distributes incoming traffic.
  • Reverse proxy: sits in front of application servers and can provide several edge functions.
  • Stateless API: any healthy instance should be able to handle a request without depending on local process state.
  • Worker Threads: useful for CPU-heavy JavaScript without blocking the main event loop.
  • PM2: process manager concept; not a replacement for understanding application architecture.
30-second interview answer: “Node.js Cluster allows an application to run multiple worker processes so server work can use multiple CPU cores. Each worker has its own memory and event loop. For larger systems, traffic can be distributed across multiple application instances using a load balancer. Cluster is different from Worker Threads: Cluster uses processes, while Worker Threads use threads and are especially useful for CPU-heavy JavaScript work.”
