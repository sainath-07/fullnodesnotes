Node.js + Express Interview Preparation

Part 30 — Production Node.js + Express ⭐⭐⭐

Learn how to prepare, run, secure, monitor, scale, and gracefully stop a Node.js + Express application in production.

1. What Does “Production” Mean?

Production is the real environment where users access your application. A production server must be reliable, secure, observable, and able to handle failures.

Code → Build/Deploy → Reverse Proxy → Node.js App → Database/Cache → Users
Logs + Metrics + Health Checks watch the system
Layman example: Development is your practice kitchen. Production is the restaurant serving real customers. You need safety checks, monitoring, backups, and a plan for problems.
2. Environment Configuration

Production settings should come from environment variables or a secure configuration system, not hard-coded values.

const port = process.env.PORT || 3000;
const dbUrl = process.env.DATABASE_URL;

Why? The same code can run in development, staging, and production with different settings.

NODE_ENV=production
PORT=8080
DATABASE_URL=...
JWT_SECRET=...
Common mistake: Never commit secrets such as database passwords, JWT secrets, or API keys to Git.

NODE_ENV: It is commonly set to development, test, or production. Do not assume that changing it automatically makes an application secure or optimized; your application and its dependencies must use the setting appropriately.

4. Process Management — PM2

A process manager helps keep the Node.js application running and can restart it after a crash. PM2 is a popular Node.js process manager.

pm2 start server.js --name api
pm2 status
pm2 logs api
pm2 restart api
pm2 save
Interview line: “A process manager keeps the application process under supervision and can restart or manage multiple Node.js instances.”
5. Graceful Shutdown — SIGTERM and SIGINT

Graceful shutdown means stopping the server carefully instead of immediately killing active work.

const server = app.listen(process.env.PORT || 3000);

function shutdown(signal) {
  console.log(`${signal} received`);
  server.close(() => {
    console.log("HTTP server closed");
    // close DB connections, queues, etc.
    process.exit(0);
  });
}

process.on("SIGTERM", () => shutdown("SIGTERM"));
process.on("SIGINT", () => shutdown("SIGINT"));
  • SIGTERM: commonly asks a process to terminate, often used by orchestrators and process managers.
  • SIGINT: commonly generated when you interrupt a foreground process, such as Ctrl+C.
Why? Immediate termination can interrupt requests, leave resources open, or lose work. Graceful shutdown gives the application time to finish what it safely can and close resources.
6. Docker Basics

Docker packages an application and its runtime dependencies into a container image so it can run consistently across environments.

FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
EXPOSE 3000
CMD ["node", "server.js"]
Dockerfile → Image → Container → Node.js + Express App

Interview focus: An image is the packaged template; a container is a running instance of that image.

7. Reverse Proxy & Nginx Concept

A reverse proxy receives client requests and forwards them to backend services. Nginx is commonly used for this job.

Browser → HTTPS / Nginx → Node.js :3000 → Database
  • TLS/HTTPS termination
  • Routing to backend services
  • Load balancing
  • Serving static files
  • Connection and request handling controls
Important: Node.js does not have to expose its internal port directly to the public internet when a reverse proxy sits in front of it.
8. HTTPS

HTTPS protects data exchanged between client and server using TLS. In many deployments, a reverse proxy or load balancer handles the TLS certificate and forwards traffic to the application.

Production rule: Do not send passwords, tokens, cookies, or sensitive data over plain HTTP in a real production application.
9. Logging & Monitoring

Production applications need evidence about what happened and whether the system is healthy.

  • Logs: events, warnings, errors, request IDs.
  • Metrics: latency, throughput, error rate, CPU, memory.
  • Monitoring: watches those signals and can alert the team.
app.get("/health", (req, res) => {
  res.status(200).json({ status: "ok" });
});

/health usually answers whether the process/service is alive. A /ready endpoint can represent whether the service is ready to receive traffic, such as after required dependencies are available.

10. Scaling
Vertical scaling: Give one machine more CPU/RAM.
Horizontal scaling: Run more application instances and distribute traffic.
Load Balancer → Instance 1
↘ Instance 2
↘ Instance 3

Stateless APIs make horizontal scaling easier because any instance can handle a request. Shared state such as sessions should be stored in an appropriate shared system when needed.

11. Caching

Caching stores reusable data so the application does not repeat expensive work every time.

  • Application cache such as Redis
  • HTTP cache headers
  • CDN cache for suitable static content
Common mistake: Caching data without a clear expiration or invalidation strategy can return stale information.
12. Security in Production
  • Use HTTPS.
  • Keep secrets outside source code.
  • Validate and sanitize input.
  • Use secure cookie settings where cookies are used.
  • Apply authentication and authorization correctly.
  • Use rate limiting where appropriate.
  • Set suitable request-size limits.
  • Keep dependencies updated.
  • Do not expose stack traces or secrets in production responses.
13. Deployment Flow
Git → CI/CD → Install Dependencies → Test → Build → Deploy → Reverse Proxy → Node.js → Monitoring

A good deployment process is repeatable. It should include tests, configuration management, health checks, logs, rollback planning, and safe shutdown behavior.

14. Production Checklist
  • Environment variables configured
  • Secrets protected
  • HTTPS enabled
  • Input validation enabled
  • Authentication/authorization checked
  • Request limits configured
  • Structured logging
  • Health/readiness checks
  • Monitoring and alerts
  • Graceful shutdown
  • Database backups/recovery plan
  • Deployment/rollback process
15. Quick Recap
  • NODE_ENV: communicates the application's environment.
  • PM2: process management and supervision.
  • SIGTERM/SIGINT: signals that can trigger controlled shutdown.
  • Docker: packages an application into a portable container image.
  • Nginx: can act as a reverse proxy and load balancer.
  • HTTPS: protects network traffic with TLS.
  • Monitoring: gives visibility into health and performance.
  • Scaling: increases capacity vertically or horizontally.
  • Caching: reduces repeated expensive work.
16. Interview-Ready Output / Code Questions

Q1. What is the output?

console.log(process.env.NODE_ENV || "development");
Answer: If NODE_ENV is not set, it prints development. If it is set, it prints its value.
Why: The || operator uses the right side when the environment variable is undefined or another falsy value.

Q2. Which shutdown message is printed first?

const server = app.listen(3000);

process.on("SIGTERM", () => {
  console.log("signal received");
  server.close(() => console.log("server closed"));
});
Answer: signal received is printed first. server closed is printed after the server finishes closing.
Why: The callback passed to server.close() runs after the server has stopped accepting new connections and existing connections have closed.

Q3. Find the production mistake.

const JWT_SECRET = "my-secret-123";
Answer: The secret is hard-coded in source code. It should come from a secure environment/configuration system.
Why: Source code can be copied, logged, or committed to a public repository. Environment/configuration management reduces this risk.

Q4. What happens here if the cache contains old data?

const cached = await redis.get("user:10");
if (cached) return res.json(JSON.parse(cached));
return res.json(await loadUserFromDB(10));
Answer: The API returns the cached value and does not query the database.
Why: The if (cached) branch returns immediately. This is why cache expiration and invalidation are important.

Q5. Which deployment design supports horizontal scaling?

Client → Load Balancer → API Instance A
                     → API Instance B
                     → API Instance C
Answer: This is horizontal scaling because multiple application instances share incoming traffic.
Why: Capacity is increased by adding more instances rather than making only one machine larger.

Q6. What is wrong with this health endpoint?

app.get("/health", async (req, res) => {
  await db.query("SELECT 1");
  res.json({ status: "ok" });
});
Answer: Nothing is automatically wrong, but it mixes liveness and dependency readiness. A separate readiness check may be better when the application must verify database availability before receiving traffic.
Why: A process can be alive while a dependency is unavailable. Separating /health and /ready gives clearer operational signals.

Q7. What is the production concern?

app.use((err, req, res, next) => {
  res.status(500).json({
    message: err.message,
    stack: err.stack
  });
});
Answer: Returning the stack trace to clients can expose internal implementation details.
Why: Stack traces can reveal file paths, code structure, libraries, or other information useful to attackers. Log detailed errors internally and return safe production messages.

Q8. Why is graceful shutdown important?

process.on("SIGTERM", async () => {
  await db.close();
  process.exit(0);
});
Answer: It gives the application an opportunity to close resources cleanly before exiting.
Why: Production platforms may stop or replace instances. Closing database connections, queues, and servers cleanly reduces interrupted work and resource problems.

Q9. Which setting is safer for production logs?

res.status(500).json({
  error: process.env.NODE_ENV === "production"
    ? "Internal server error"
    : err.message
});
Answer: Production receives a generic message while development can receive more useful error information.
Why: Clients usually do not need internal implementation details. Detailed information should be logged securely for developers and operators.

Q10. What is the main problem with this Docker command?

RUN npm install
Answer: For reproducible production/container builds, npm ci is often preferred when a lockfile exists.
Why: npm ci installs from the lockfile and is designed for clean, repeatable CI environments.
