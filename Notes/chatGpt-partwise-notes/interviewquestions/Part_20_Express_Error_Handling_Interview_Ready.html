Node.js + Express.js Interview Preparation

Part 20 — Express Error Handling ⭐⭐⭐

Understand how errors move through an Express application, how to return safe API responses, and how to design a production-ready error handler.

1. What is Error Handling?

Error handling means detecting a failure, passing it to the correct place, and sending a useful response without crashing the API.

Layman example: Think of a restaurant. If the kitchen cannot prepare an order, the waiter should handle the problem and tell the customer what happened. The whole restaurant should not close.
Why?

Without proper error handling, APIs can return confusing responses, expose sensitive information, or stop working unexpectedly.

How it works
Request → Route / Controller → Error occurs ↓ next(error) ↓ Express Error Middleware ↓ Log error → Build safe response → Client
2. Express Error Middleware

Express identifies error-handling middleware by its four parameters:

app.use((err, req, res, next) => {
  // handle error
});
Important: The four parameters must be present in this order: err, req, res, next.

When to use: Use centralized error middleware near the end of your middleware and route setup.

3. Passing Errors with next(error)
app.get("/users/:id", async (req, res, next) => {
  try {
    const user = await findUser(req.params.id);

    if (!user) {
      const err = new Error("User not found");
      err.statusCode = 404;
      return next(err);
    }

    res.json(user);
  } catch (err) {
    next(err);
  }
});

Calling next(err) tells Express to skip normal middleware and move toward error-handling middleware.

4. Synchronous vs Async Errors
Synchronous
app.get("/", (req, res) => {
  throw new Error("Failed");
});

Express can catch synchronous route errors automatically.

Async
app.get("/", async (req, res, next) => {
  try {
    await doWork();
    res.send("OK");
  } catch (err) {
    next(err);
  }
});

Async failures must be correctly propagated to the error handler. A wrapper can reduce repeated try/catch.

5. Custom Error Classes
class AppError extends Error {
  constructor(message, statusCode = 500, code = "INTERNAL_ERROR") {
    super(message);
    this.statusCode = statusCode;
    this.code = code;
    this.isOperational = true;
  }
}

throw new AppError("User not found", 404, "USER_NOT_FOUND");

Custom errors make application failures easier to classify and handle consistently.

Interview point: Keep application error metadata such as status code and error code separate from the raw internal exception.
6. HTTP Error Responses
SituationTypical Status
Validation failure400 Bad Request
Not authenticated401 Unauthorized
Not allowed403 Forbidden
Resource missing404 Not Found
Conflict409 Conflict
Unexpected server failure500 Internal Server Error

Choose the status code based on the meaning of the failure. Do not return 200 for every failure.

7. 404 Handling

A 404 route handler is normally placed after all valid routes:

app.use((req, res, next) => {
  const err = new AppError("Route not found", 404, "ROUTE_NOT_FOUND");
  next(err);
});

The request first gets a chance to match a real route. If nothing matches, the request reaches this middleware.

8. Global Error Handler
app.use((err, req, res, next) => {
  const status = err.statusCode || 500;

  console.error({
    message: err.message,
    stack: err.stack,
    path: req.originalUrl
  });

  res.status(status).json({
    success: false,
    error: {
      code: err.code || "INTERNAL_ERROR",
      message: status < 500
        ? err.message
        : "Internal server error"
    }
  });
});
Production rule: Do not send database errors, stack traces, passwords, tokens, or internal implementation details to clients.
9. Validation, Authentication, Authorization and Database Errors
  • Validation error: Client sent invalid input → usually 400.
  • Authentication error: Identity is missing or invalid → usually 401.
  • Authorization error: User is authenticated but lacks permission → usually 403.
  • Database error: Database operation failed → log technical details internally and return a safe response.
Input → Validation → Authentication → Authorization → Controller → Database ↓ ↓ ↓ ↓ 400 401 403 DB-safe error
10. Development vs Production Error Messages
Development
You may include more debugging information, stack traces, and detailed logs for developers.
Production
Return a simple safe message. Keep internal details in server logs.
11. Logging Errors

Logs should help developers understand what failed without exposing secrets.

console.error({
  message: err.message,
  stack: err.stack,
  method: req.method,
  url: req.originalUrl
});
Never log: passwords, access tokens, refresh tokens, session secrets, or other sensitive values.
12. Graceful API Failure

A graceful API failure means the server remains stable and gives the client a predictable response.

Failure ↓ Detect ↓ Propagate ↓ Log safely ↓ Choose HTTP status ↓ Return consistent JSON ↓ Keep server healthy

Interview Questions — Code Based ⭐⭐⭐

Q1. What is wrong with this middleware?
app.use((req, res, next, err) => {
  console.log(err);
  res.status(500).json({ message: err.message });
});
Answer: The parameter order is wrong. Express error middleware must use (err, req, res, next).
Why? Express uses the four-argument signature to recognize error-handling middleware.
Q2. What response is produced?
app.get("/test", (req, res, next) => {
  next(new Error("Database failed"));
});

app.use((err, req, res, next) => {
  res.status(500).json({ message: err.message });
});
Answer: The client receives HTTP 500 with JSON: {"message":"Database failed"}.
Why? next(error) skips normal middleware and sends the error to the registered error handler.
Q3. Find the problem in this async route.
app.get("/users", async (req, res) => {
  const users = await User.find();
  res.json(users);
});
Answer: If User.find() rejects, the error must be propagated to Express's error handler. Use a supported async error wrapper or try/catch with next(err).
Why? Promise rejection is different from a synchronous throw. Your application must make sure the rejection reaches the centralized error handler.
Q4. What is wrong with this error response?
app.use((err, req, res, next) => {
  res.status(500).json({
    error: err.stack,
    databaseUrl: process.env.DATABASE_URL
  });
});
Answer: It exposes sensitive configuration and internal stack information to the client. A production API should return a safe generic message and log technical details on the server.
Why? Stack traces and environment values can reveal implementation details and secrets that attackers could use.
Q5. What will happen when this route is requested?
app.get("/users/:id", (req, res, next) => {
  if (req.params.id === "0") {
    return next(new AppError("User not found", 404, "USER_NOT_FOUND"));
  }
  res.json({ id: req.params.id });
});
Answer: For /users/0, the request moves to the error middleware and should produce a 404 response if the global handler uses err.statusCode.
Why? return next(error) stops the current handler and transfers control to error handling.
Q6. What is the correct order?
app.get("/users", getUsers);

app.use((req, res, next) => {
  next(new AppError("Not found", 404));
});

app.use((err, req, res, next) => {
  res.status(err.statusCode || 500).json({
    message: err.message
  });
});
Answer: This is the correct general order: valid routes first, then the 404 middleware, then the global error middleware.
Why? A request should first get a chance to match a valid route. The 404 handler runs only when no route handles it, and the error handler comes afterward.
Q7. Choose the correct status code.
if (!req.user) {
  // user has not supplied valid authentication
}
Answer: Normally return 401 Unauthorized when the request lacks valid authentication.
Why? 401 indicates that the server cannot treat the client as authenticated. A 403 is normally used when the client is authenticated but not allowed to perform the operation.
Q8. Design a consistent error response.
// Requirements:
// 1. status code
// 2. success flag
// 3. machine-readable error code
// 4. safe message

// Write the response shape.
res.status(status).json({
  success: false,
  error: {
    code: err.code || "INTERNAL_ERROR",
    message: status < 500
      ? err.message
      : "Internal server error"
  }
});
Why? A stable response shape makes frontend handling easier. A machine-readable code is also more reliable than making the frontend parse human-readable messages.
Common Developer Mistakes
❌ Putting the error handler before the routes.
❌ Forgetting the four-argument error middleware signature.
❌ Sending err.stack or secrets in production responses.
❌ Returning HTTP 200 for failed operations.
❌ Forgetting to propagate async Promise failures.
❌ Logging passwords, JWTs, or database credentials.
❌ Returning different error JSON shapes from every endpoint.
Quick Recap
  • Error middleware uses (err, req, res, next).
  • Use next(error) to propagate an error.
  • Handle async Promise failures correctly.
  • Use appropriate HTTP status codes.
  • Keep the global error handler near the end.
  • Separate development debugging details from production responses.
  • Log technical information safely on the server.
  • Return a consistent, safe API error format.
Interview-Ready Points
Say this in an interview: “I use centralized Express error handling so controllers can propagate failures with next(error), while one error middleware converts errors into consistent HTTP responses and keeps internal details out of production.”
  • Know exactly why Express error middleware has four arguments.
  • Explain next(error) and error propagation.
  • Know the difference between 400, 401, 403, 404, 409 and 500.
  • Explain why async errors need correct Promise rejection handling.
  • Explain why stack traces and secrets must not be exposed.
  • Know the correct route → 404 → error-handler order.
  • Understand operational errors vs programmer errors.
  • Be able to design a consistent production error response.
