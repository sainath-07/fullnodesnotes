Part 10 — Event Loop & Async Node.js ⭐⭐⭐

Learn how Node.js executes JavaScript, handles asynchronous work and decides what runs next.

1. What is the Event Loop?

What: The Node.js event loop is the mechanism that lets JavaScript execution continue while asynchronous operations are handled by the runtime and operating system or Node.js facilities.

Why: It allows a Node.js process to handle many I/O operations without waiting synchronously for each one to finish.

Layman example: Imagine one receptionist handling many customers. The receptionist starts a long task, gives that task to another department, and immediately helps the next customer. When the result comes back, the receptionist handles it.

Q1 — Is Node.js completely single-threaded?

Answer: JavaScript execution in a Node.js process normally uses one main thread, but Node.js itself can use other threads and operating-system facilities for some asynchronous work. So “Node.js is single-threaded” is an oversimplification.

Q2 — Does the event loop make CPU-heavy JavaScript non-blocking?

Answer: No. A long CPU-heavy JavaScript operation runs on the main JavaScript thread and can block the event loop. The event loop helps most with asynchronous I/O, not with magically making CPU work fast.
2. Call Stack
function one() { two(); } function two() { console.log("two"); } one();

Q3 — What happens on the call stack?

Answer: one() is pushed onto the stack, then two() is pushed. two() finishes and is removed, then one() finishes and is removed.

Q4 — What happens if synchronous code never finishes?

Answer: The call stack remains busy, so the event loop cannot run other JavaScript callbacks. This blocks the process from making progress on other work.
3. Event Loop Phases

Node.js uses several event-loop phases. The simplified interview view is:

Timers: callbacks for timers whose thresholds have been reached.
Pending callbacks: certain deferred system-level I/O callbacks.
Poll: retrieves I/O events and runs many I/O callbacks.
Check: runs setImmediate() callbacks.
Close callbacks: handles close events such as socket close callbacks.
Timers → Pending Callbacks → Poll → Check → Close Callbacks → repeat

Q5 — In which phase does setImmediate() run?

Answer: Its callback runs in the check phase.

Q6 — What is the poll phase responsible for?

Answer: It processes many I/O-related events and can wait for new I/O when appropriate. The exact behavior depends on the state of the event loop and pending work.
4. setTimeout() vs setImmediate()
setTimeout(() => console.log("timeout"), 0); setImmediate(() => console.log("immediate"));

Q7 — Is the output always timeout, then immediate?

Answer: No. At top level, their relative order can vary because it depends on event-loop timing. Inside an I/O callback, setImmediate() is generally executed before a zero-delay timer scheduled there.
const fs = require("fs"); fs.readFile(__filename, () => { setTimeout(() => console.log("timeout"), 0); setImmediate(() => console.log("immediate")); });

Q8 — What is the expected ordering inside this I/O callback?

Answer: Typically immediate is printed before timeout, because the callback is running in the poll phase and the check phase follows it.
5. process.nextTick() and Microtasks ⭐⭐⭐⭐⭐

Node.js has a special process.nextTick() queue. Promise reactions and queueMicrotask() use the microtask queue. These queues are processed before the event loop continues to later phases, with Node-specific ordering details.

console.log("A"); process.nextTick(() => console.log("nextTick")); Promise.resolve().then(() => console.log("promise")); queueMicrotask(() => console.log("microtask")); console.log("B");

Q9 — What is the basic output order?

Answer: A, B, then Node's process.nextTick() callback, followed by the Promise/other microtasks. The exact interaction can depend on where the callbacks are scheduled, but nextTick has special priority in Node.js.

Q10 — Why can excessive process.nextTick() calls be dangerous?

Answer: If code continually schedules more nextTick() callbacks, the event loop can be prevented from reaching I/O and timer phases. This is a form of event-loop starvation.
6. Promise Callbacks and queueMicrotask()
console.log("start"); setTimeout(() => console.log("timer"), 0); Promise.resolve().then(() => console.log("promise")); queueMicrotask(() => console.log("microtask")); console.log("end");

Q11 — What is the important ordering?

Answer: Synchronous code prints first: start, end. Then the queued microtasks run in their scheduling order: promise, microtask. The timer callback runs later.

Q12 — Why does the timer not run immediately when delay is 0?

Answer: A zero delay is not a promise of immediate execution. It means the timer becomes eligible after its minimum threshold and still has to wait for the current stack and event-loop scheduling to allow its callback to run.
7. Async File System and HTTP
const fs = require("fs"); fs.readFile("data.txt", "utf8", (err, data) => { if (err) throw err; console.log(data); }); console.log("after readFile");

Q13 — Which is normally printed first?

Answer: Usually after readFile is printed before the file contents because the asynchronous file operation does not block the current JavaScript execution.

Q14 — Does async fs.readFile execute its callback on the same call stack immediately?

Answer: No. The file operation is started, the current JavaScript stack continues, and its callback is scheduled to run later after the operation completes.

Q15 — How does an HTTP server benefit from the event loop?

Answer: While one request is waiting for asynchronous I/O such as a database, file or network operation, Node.js can continue processing other ready work instead of synchronously waiting for that I/O.
8. Blocking vs Non-blocking Code
const fs = require("fs"); console.log("1"); const data = fs.readFileSync("data.txt", "utf8"); console.log("2");

Q16 — Why can readFileSync() be dangerous in a server request?

Answer: It blocks the JavaScript thread until the file operation finishes. During that time, the event loop cannot process other JavaScript callbacks, which can reduce server responsiveness.
fs.readFile("data.txt", "utf8", (err, data) => { console.log(data); }); console.log("continue");

Q17 — Why is this generally better for I/O-heavy server code?

Answer: The asynchronous API lets current JavaScript execution continue while the file operation is being completed, allowing the process to make progress on other work.
9. Event Loop Ordering — Output Questions ⭐⭐⭐⭐⭐

Q18 — Predict the output

console.log("1"); setTimeout(() => console.log("2"), 0); Promise.resolve().then(() => console.log("3")); console.log("4");
Answer: 1 → 4 → 3 → 2. Synchronous code runs first, then the Promise microtask, then the timer callback.

Q19 — Predict the output

process.nextTick(() => console.log("A")); Promise.resolve().then(() => console.log("B")); setImmediate(() => console.log("C")); console.log("D");
Answer: The reliable basic ordering is D first, then A before the Promise microtask B. The relative placement of C depends on the event-loop context, but it runs in the check phase rather than as synchronous code.

Q20 — What is wrong with this code?

function work() { while (true) { // heavy work } } work();
Answer: It creates an infinite synchronous loop. The call stack never becomes free, so the event loop cannot process timers, I/O callbacks or other JavaScript work.
10. Event Loop Starvation ⭐⭐⭐⭐⭐

What: Event-loop starvation happens when callbacks or synchronous work keep the JavaScript thread busy for too long, preventing other ready tasks from getting a chance to run.

function starve() { process.nextTick(starve); } starve(); setTimeout(() => { console.log("Will this run?"); }, 0);

Q21 — Why may the timer never get a chance to run?

Answer: The code continually fills the nextTick queue. Node.js keeps processing that high-priority queue, starving later event-loop phases where the timer would run.

Q22 — How can you avoid event-loop starvation from CPU-heavy work?

Answer: Avoid long synchronous loops on the main thread. Break work into smaller chunks when appropriate, use worker threads for CPU-heavy tasks, or move heavy computation to another service/process when suitable.
11. async/await and the Event Loop
async function test() { console.log("A"); await Promise.resolve(); console.log("B"); } console.log("C"); test(); console.log("D");

Q23 — Predict the output.

Answer: C → A → D → B. Calling test() runs synchronously until await. The continuation after await is scheduled asynchronously, so the outer synchronous code prints D before B.

Q24 — Does await block the Node.js thread?

Answer: No. await pauses the async function's continuation; it does not block the entire JavaScript thread while the awaited Promise is pending.
12. Common Developer Mistakes
  • Thinking “single-threaded” means Node.js can never use other threads.
  • Thinking setTimeout(fn, 0) means “run immediately.”
  • Assuming setTimeout(0) always runs before setImmediate().
  • Using synchronous filesystem APIs inside high-throughput server request paths.
  • Running large CPU-heavy loops on the main JavaScript thread.
  • Creating recursive process.nextTick() chains that starve the event loop.
  • Thinking async/await makes CPU-heavy work asynchronous.
  • Ignoring Promise rejection/error handling.
  • Memorizing one event-loop output without considering where the code is scheduled.

Golden interview answer: “Node.js executes JavaScript on a main thread with a call stack. When asynchronous I/O is started, Node.js can let the current JavaScript continue instead of synchronously waiting. The event loop coordinates timers, I/O and other callbacks through its phases. Promise microtasks and Node's nextTick queue are processed with higher priority than normal later-phase callbacks. Therefore, long synchronous work or excessive nextTick scheduling can block or starve the event loop.”
Fast memory trick: Sync code → queues/I/O → event-loop phases → callback → microtasks/nextTick handling → repeat.
14. Interview Tips
  • Do not say “Node.js has only one thread.” Say JavaScript execution uses a main thread, while Node.js can use OS facilities and a worker pool for some operations.
  • For output questions, first mark synchronous statements, then microtasks/nextTick, then timers/I/O/check callbacks based on context.
  • Always ask: “Where was this callback scheduled?” Top-level and inside an I/O callback can produce different ordering.
  • Know why readFileSync() can hurt server performance.
  • Know event-loop starvation and how worker threads can help CPU-heavy work.
