NODE.JS INTERVIEW PREPARATION

Part 26 — Worker Threads & Child Processes

Interview-ready notes, visual flows, and output-based coding questions for MAANG, FAANG and MNC interviews.

1. What Are Worker Threads?

What: Worker Threads allow JavaScript code to run in a separate thread inside the same Node.js process.

Why: Node.js normally runs JavaScript on one main thread. CPU-heavy work can block that thread. A worker can perform that CPU-heavy work separately so the main thread remains responsive.

Layman example: Imagine one cashier handling customers. If the cashier must calculate a huge report, every customer waits. A worker is like another employee doing the calculation while the cashier continues serving customers.

When to use: CPU-heavy JavaScript such as large calculations, image processing, parsing large data sets, compression, or cryptographic computation.

Main Thread → creates Worker → Worker performs CPU work → Worker sends result → Main Thread continues
2. Worker Threads — Core API

The worker_threads module provides Worker, parentPort, and messaging APIs.

const { Worker } = require("node:worker_threads");

const worker = new Worker("./worker.js");

worker.on("message", result => {
  console.log("Result:", result);
});

worker.on("error", err => {
  console.error(err);
});

worker.on("exit", code => {
  console.log("Worker exited:", code);
});
// worker.js
const { parentPort } = require("node:worker_threads");

parentPort.on("message", number => {
  const result = number * number;
  parentPort.postMessage(result);
});
3. postMessage() and parentPort
  • worker.postMessage(data) sends data from the main thread to the worker.
  • parentPort.on("message", ...) receives data inside the worker.
  • parentPort.postMessage(data) sends a result back to the parent.
  • Messages are not normal shared variables. Node.js uses structured cloning for message data.

4. Worker Lifecycle
new Worker() → online → message / error → exit
                             ↘ worker.terminate()
  • online: worker has started executing.
  • message: worker sends a message.
  • error: worker encounters an uncaught error.
  • exit: worker has stopped.
  • terminate(): parent requests that the worker stop.
Interview point: A worker is not automatically a magic solution for every slow operation. It is mainly useful when JavaScript itself is CPU-bound.
5. Child Processes

What: The child_process module starts another operating-system process.

Why: A child process is useful when Node.js needs to run another program, command, script, or isolated Node.js process.

Parent Node.js Process → Child OS Process
                             ↕ IPC / stdin / stdout / stderr

Layman example: Instead of asking another employee in the same office to help, you start a completely separate office with its own resources.

8. IPC — Inter-Process Communication

IPC means communication between separate execution contexts.

With fork(), the parent and child Node.js processes can communicate with send() and message events.

// parent.js
const { fork } = require("node:child_process");

const child = fork("./child.js");

child.on("message", message => {
  console.log("Parent received:", message);
});

child.send({ task: "calculate", value: 10 });
// child.js
process.on("message", message => {
  const result = message.value * message.value;
  process.send({ result });
});
9. Common Developer Mistakes
Using workers for I/O:
Database and network I/O usually does not need a worker. Node.js already handles asynchronous I/O efficiently.
Creating too many workers:
Workers have overhead. A huge number can cause CPU contention and memory pressure.
Ignoring worker errors:
Always handle error and exit events.
Shell injection:
Do not build shell commands from untrusted input.
Blocking the worker:
A worker has its own JavaScript thread, but CPU-heavy work can still block that worker.
Wrong abstraction:
Do not use child_process when a normal async API is enough.
10. Quick Recap
  • Node.js JavaScript normally executes on the main thread.
  • Worker Threads move CPU-heavy JavaScript work to separate threads.
  • postMessage() and parentPort are used for worker communication.
  • child_process creates separate OS processes.
  • spawn() is useful for streaming large process output.
  • exec() is convenient for shell commands but needs careful input handling.
  • execFile() runs an executable without normally involving a shell.
  • fork() starts a Node.js module with built-in IPC.
  • Workers are mainly for CPU-heavy JavaScript; child processes are useful for external programs and stronger process isolation.
11. Interview-Ready Questions
Try to answer each question before opening the answer.
Question 1 — Predict the output
const { Worker } = require("node:worker_threads");

console.log("A");

const worker = new Worker(`
  const { parentPort } = require("node:worker_threads");
  parentPort.postMessage("C");
`, { eval: true });

worker.on("message", msg => console.log(msg));

console.log("B");
Answer: The normal main-thread output starts with A, then B. The worker's C arrives asynchronously, so the common output is A B C.
Why: Creating a worker starts another execution context. The main thread continues instead of waiting for the worker message.
Question 2 — Is a Worker Thread required here?
app.get("/users", async (req, res) => {
  const users = await db.users.findMany();
  res.json(users);
});
Answer: Usually no. A worker is not needed merely because the operation is asynchronous.
Why: Database/network I/O is generally handled asynchronously by Node.js. Workers are primarily useful when JavaScript computation itself is CPU-heavy.
Question 3 — Find the problem
const { exec } = require("node:child_process");

const username = req.query.username;

exec(`grep ${username} users.txt`, (err, stdout) => {
  res.send(stdout);
});
Answer: The code is vulnerable to shell injection because untrusted input is inserted directly into a shell command.
Why: exec() uses a shell. Special shell characters in user input can change the command that gets executed. Prefer safe argument handling or APIs that avoid a shell.
Question 4 — Worker communication
// main.js
worker.postMessage(5);

// worker.js
parentPort.on("message", value => {
  parentPort.postMessage(value * 2);
});
Answer: The worker receives 5 and sends back 10.
Why: postMessage() sends the value to the worker. The worker's message listener receives it, calculates 5 × 2, and sends the result through parentPort.postMessage().
Question 5 — Which child_process API?

You need to run a long-running program that continuously produces a large amount of stdout. Which API is the better fit: exec() or spawn()?

Answer: spawn().
Why: spawn() exposes stdout/stderr as streams, making it suitable for large or continuous output. exec() buffers command output.
Question 6 — Worker or child process?

Your Node.js application needs to call an installed image-processing command-line program. Which approach is more appropriate?

Answer: A child process is usually the natural choice because the application needs to execute an external program.
Why: Worker Threads execute JavaScript in another thread. Child processes can launch operating-system programs and communicate with them.
Question 7 — Output ordering
console.log("start");

const { Worker } = require("node:worker_threads");

const worker = new Worker(`
  const { parentPort } = require("node:worker_threads");
  parentPort.postMessage("worker");
`, { eval: true });

worker.on("message", console.log);

console.log("end");
Answer: start is printed first, end is printed next, and worker arrives asynchronously afterward. So the expected order is start → end → worker.
Why: The main thread does not stop at new Worker(). It continues to the next statement while the worker starts separately.
Question 8 — fork() and IPC
// parent.js
const { fork } = require("node:child_process");
const child = fork("./child.js");

child.on("message", console.log);
child.send("hello");

// child.js
process.on("message", msg => {
  process.send(msg.toUpperCase());
});
Answer: The parent receives and prints HELLO.
Why: fork() starts another Node.js process with an IPC channel. The parent sends hello; the child converts it to uppercase and sends it back.
Question 9 — When should you NOT use workers?

An endpoint waits for a database query for 500 ms but uses almost no CPU. Should you move the query into a worker?

Answer: Usually no.
Why: Waiting on I/O is different from blocking the CPU with JavaScript. A worker adds overhead without solving the main problem.
Question 10 — CPU-heavy task
app.get("/calculate", (req, res) => {
  let total = 0;

  for (let i = 0; i < 5_000_000_000; i++) {
    total += i;
  }

  res.json({ total });
});
Answer: This CPU-heavy calculation can block the main JavaScript thread. A Worker Thread is a strong candidate for moving this computation away from the main thread.
Why: The loop performs a huge amount of synchronous JavaScript work. While it runs on the main thread, other JavaScript callbacks cannot get normal execution time. A worker can perform the calculation separately.
