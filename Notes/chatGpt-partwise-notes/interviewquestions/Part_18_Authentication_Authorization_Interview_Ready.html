Node.js + Express.js Interview Preparation

Part 18 — Authentication & Authorization ⭐⭐⭐

Learn how applications verify users, protect routes, and control what each user is allowed to do.

Interview goal: Do not only memorize JWT or bcrypt syntax. Be able to explain the complete flow from registration to a protected API and clearly separate authentication from authorization.

1. Authentication vs Authorization

Authentication — “Who are you?”

Authentication verifies the identity of a user.

Example: A user enters email and password. The server checks whether those credentials belong to the user.
Authorization — “What can you do?”

Authorization checks whether an authenticated user has permission to perform an action.

Example: A normal employee may read reports, while an admin may delete reports.
Layman example: Showing your ID at a building entrance is authentication. Being allowed into the server room is authorization.

2. Complete Authentication Flow

What: A typical application first creates an account, then verifies credentials during login, creates a token/session, and checks that identity on protected requests.

Why? The server should never trust a username or role sent directly by the browser. It must establish identity and then make authorization decisions from trusted server-side verification.

3. Registration and Password Hashing

Purpose: Passwords should not be stored as plain text. bcrypt creates a password hash that can be stored safely enough for normal application use.

const bcrypt = require("bcrypt");

const password = "MyPassword123";

const hash = await bcrypt.hash(password, 12);

console.log(hash);
// Store hash in the database, not the original password.
Answer: The original password is converted into a bcrypt hash before storage. The number 12 is the cost factor used here.
Why? If a database is exposed, plain-text passwords would immediately reveal user credentials. Hashing avoids storing the original password. Password hashing is one-way; during login we compare the supplied password against the stored hash.

4. Password Comparison During Login

const isValid = await bcrypt.compare(
  req.body.password,
  user.passwordHash
);

if (!isValid) {
  return res.status(401).json({ message: "Invalid credentials" });
}

res.json({ message: "Login successful" });
The submitted password is compared with the stored bcrypt hash. We do not decrypt the hash or compare two plain strings.
bcrypt knows how to use the salt and cost information stored in the hash and checks whether the supplied password produces a matching result.

5. JWT — Access Token

JWT stands for JSON Web Token. A signed JWT can carry claims such as a user ID and role. The server verifies the signature before trusting those claims.

const jwt = require("jsonwebtoken");

const token = jwt.sign(
  { userId: user._id, role: user.role },
  process.env.JWT_SECRET,
  { expiresIn: "15m" }
);
Header
Token metadata, such as the signing algorithm.
Payload
Claims such as user ID, role, and expiration.
Signature
Allows the server to detect token tampering.
Important: A JWT payload is normally readable by anyone who has the token. Do not put passwords, secrets, or sensitive data in the payload.

6. JWT Expiration and Refresh Tokens

An access token is normally short-lived. A refresh token can be used to obtain a new access token without forcing the user to log in again.

Login
→
Access token
→
API requests
→
Access token expires
→
Refresh token
→
New access token
Interview point: Short access-token lifetime limits the window in which a stolen access token can be used. Refresh-token handling needs stronger protection and a revocation/rotation strategy in production systems.

7. Protected Route + Authorization Middleware

function authenticate(req, res, next) {
  const token = req.headers.authorization?.split(" ")[1];

  if (!token) {
    return res.status(401).json({ message: "Login required" });
  }

  try {
    req.user = jwt.verify(token, process.env.JWT_SECRET);
    next();
  } catch {
    return res.status(401).json({ message: "Invalid or expired token" });
  }
}

function requireAdmin(req, res, next) {
  if (req.user.role !== "admin") {
    return res.status(403).json({ message: "Forbidden" });
  }
  next();
}

app.delete("/users/:id", authenticate, requireAdmin, deleteUser);
Flow: The request first passes authentication. If the JWT is valid, the decoded user information is placed on req.user. Then authorization checks the role. Only an admin reaches deleteUser.
Why 401 vs 403? 401 means the request does not have valid authentication. 403 means the identity is known, but the user is not allowed to perform that action.

8. Cookies and Security Attributes

AttributePurpose
HttpOnlyPrevents JavaScript from reading the cookie through document.cookie.
SecureSends the cookie only over HTTPS.
SameSiteControls when the browser sends the cookie in cross-site requests and helps reduce CSRF risk.
 
res.cookie("refreshToken", token, {
  httpOnly: true,
  secure: true,
  sameSite: "strict",
  maxAge: 7 * 24 * 60 * 60 * 1000
});
Common mistake: Putting long-lived authentication tokens in normal JavaScript-readable storage without understanding the XSS risk. Cookie strategy depends on the application architecture and CSRF protections.

9. Code-Based Interview Questions

Q1. What is the output?
const token = jwt.sign(
  { userId: 10, role: "admin" },
  "secret",
  { expiresIn: "1s" }
);

setTimeout(() => {
  try {
    console.log(jwt.verify(token, "secret"));
  } catch (err) {
    console.log(err.name);
  }
}, 1500);
It prints TokenExpiredError.
The token expires after one second, but verification happens after about 1.5 seconds.
Q2. What is wrong with this login code?
if (req.body.password === user.passwordHash) {
  return res.json({ message: "Login successful" });
}
The code compares a plain password directly with a bcrypt hash. It should use bcrypt.compare().
A bcrypt hash is not the original password. Password verification must use the hashing library's comparison function.
Q3. What status code should this middleware return?
function adminOnly(req, res, next) {
  if (req.user.role !== "admin") {
    return res.status(403).json({ message: "Forbidden" });
  }
  next();
}
403 Forbidden.
The user is already authenticated, but does not have the required permission.
Q4. What happens if authenticate middleware does not call next()?
The next middleware or route handler will not execute, so the request can remain pending if no response is sent.
Express moves through middleware when a middleware sends a response or calls next(). Forgetting both can leave the request hanging.
Q5. Is this JWT payload secret?
{
  userId: 25,
  role: "admin"
}
No. JWT payload data should be treated as readable, not secret.
JWT signing protects integrity. It does not automatically encrypt the payload.
Q6. Which middleware order is correct?
app.get("/admin", requireAdmin, authenticate, handler);

// OR

app.get("/admin", authenticate, requireAdmin, handler);
The second order is correct: authenticate → requireAdmin → handler.
requireAdmin needs req.user, which is normally created by authentication middleware.

10. Common Developer Mistakes

  • Storing plain-text passwords.
  • Putting passwords or secrets inside JWT payloads.
  • Using a weak or hard-coded JWT secret.
  • Using very long-lived access tokens without a reason.
  • Confusing 401 with 403.
  • Checking only authentication and forgetting authorization.
  • Forgetting to call next() in middleware.
  • Trusting a role sent directly by the client.
  • Ignoring token expiration and verification errors.
  • Using cookies without understanding HttpOnly, Secure, SameSite and CSRF protection.

11. Quick Recap

  • Authentication: verifies identity.
  • Authorization: checks permissions.
  • bcrypt: hashes and verifies passwords.
  • JWT: signed token carrying claims.
  • Access token: normally short-lived.
  • Refresh token: helps obtain a new access token.
  • 401: authentication is missing or invalid.
  • 403: authenticated but not allowed.
  • HttpOnly: JavaScript cannot read the cookie.
  • Secure: cookie is sent only over HTTPS.
  • SameSite: controls cross-site cookie sending.

12. Interview-Ready Answers

Q: Explain authentication and authorization.
Authentication verifies who the user is. Authorization decides what that authenticated user is allowed to do.

Q: Why hash passwords?
We should not store original passwords. A password hashing algorithm such as bcrypt stores a derived hash and lets the server verify a password without storing the original value.

Q: Explain JWT.
A JWT contains a header, payload and signature. The server verifies the signature and validates claims such as expiration before trusting the token.

Q: 401 vs 403?
401 means valid authentication is missing or failed. 403 means the user is authenticated but does not have permission.
