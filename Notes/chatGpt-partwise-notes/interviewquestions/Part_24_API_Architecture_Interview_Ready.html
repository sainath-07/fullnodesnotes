Part 24 — API Architecture

MVC, controllers, services, repositories, dependency injection, configuration, errors, logging and scalable Express structure.

Interview goal: Explain not only how an Express API works, but where each piece belongs, why responsibilities should be separated, and how the structure can grow without becoming difficult to maintain.
1. What is API Architecture?

What: API architecture is the way we organize routes, middleware, business logic, database access, errors, configuration and shared utilities.

Why: A small application can work with a few files. A large application needs clear boundaries so developers can change one part without breaking unrelated parts.

Layman example: Think of a restaurant. The waiter takes the order, the kitchen prepares it, the store provides ingredients, and the manager handles rules. One person should not do every job.

Client → Middleware → Route → Controller → Service → Repository / Model → Database
Interview line: “A scalable API separates transport concerns from business logic, data access, configuration, and cross-cutting concerns such as logging and error handling.”
2. MVC — Model, View, Controller

In an API, MVC is commonly adapted because there may be no server-rendered View.

  • Model: Represents database data and data-access behavior.
  • Controller: Handles HTTP input and creates the HTTP response.
  • View: In a traditional web app, produces the UI. In a JSON API, the controller commonly returns JSON instead.
Request → Controller → Model / Service → JSON Response
Important: MVC is an architectural pattern, not a requirement that every Express project must follow exactly the same folder structure.
3. Controller Responsibility

A controller should mainly deal with HTTP concerns: reading params/body/query, calling the appropriate service, and sending a response.

// user.controller.js
async function getUser(req, res, next) {
  try {
    const user = await userService.getUserById(req.params.id);

    if (!user) {
      return res.status(404).json({ message: "User not found" });
    }

    res.status(200).json({ data: user });
  } catch (err) {
    next(err);
  }
}

Avoid: putting large business rules and many database queries directly inside controllers.

4. Service Layer

The service layer contains business rules and coordinates application operations.

// user.service.js
async function registerUser(input, userRepository) {
  const existing = await userRepository.findByEmail(input.email);

  if (existing) {
    throw new Error("Email already exists");
  }

  const hashedPassword = await hashPassword(input.password);

  return userRepository.create({
    ...input,
    password: hashedPassword
  });
}

Why: The same business operation may be used by more than one controller, job or other application entry point. Keeping it in a service reduces duplication.

5. Repository Pattern

A repository provides a focused interface for data access.

// user.repository.js
const userRepository = {
  findById(id) {
    return User.findById(id);
  },

  findByEmail(email) {
    return User.findOne({ email });
  },

  create(data) {
    return User.create(data);
  }
};
Controller → Service → Repository → Database

Benefit: Database-specific code stays in one place. This can make testing and future data-access changes easier.

6. Separation of Concerns
LayerMain responsibilityShould avoid
RouteMap HTTP path and method to handlersBusiness logic
MiddlewareCross-cutting/request processingUnrelated database workflows
ControllerHTTP input/outputLarge business rules
ServiceBusiness logicExpress-specific response handling
RepositoryData accessHTTP response logic
UtilityReusable generic helperHidden business workflows
7. Dependency Injection

What: Dependency injection means giving a function or class the dependencies it needs instead of creating them internally.

function createUserService({ userRepository, passwordHasher }) {
  return {
    async register(input) {
      const existing = await userRepository.findByEmail(input.email);

      if (existing) {
        throw new Error("Email already exists");
      }

      const password = await passwordHasher.hash(input.password);
      return userRepository.create({ ...input, password });
    }
  };
}

const userService = createUserService({
  userRepository,
  passwordHasher
});

Layman example: Instead of a chef buying their own oven every time, the restaurant gives the chef an oven. The chef can now work with different ovens for testing or different environments.

8. Configuration Management

Configuration contains values that change between environments, such as database URLs, ports and external service settings.

// .env
PORT=5000
DATABASE_URL=...
JWT_SECRET=...

// config.js
module.exports = {
  port: Number(process.env.PORT) || 3000,
  databaseUrl: process.env.DATABASE_URL,
  jwtSecret: process.env.JWT_SECRET
};
Security: Do not commit real secrets to source control. Validate required environment variables when the application starts.

Interview point: Choose structure based on project size and team needs. The goal is discoverability and clear responsibility, not simply having many folders.
10. Error Architecture
// AppError.js
class AppError extends Error {
  constructor(message, statusCode) {
    super(message);
    this.statusCode = statusCode;
    this.isOperational = true;
  }
}

// service
if (!user) {
  throw new AppError("User not found", 404);
}

// global error middleware
app.use((err, req, res, next) => {
  const status = err.statusCode || 500;

  res.status(status).json({
    success: false,
    message: err.isOperational
      ? err.message
      : "Internal server error"
  });
});
Route → Controller → Service throws → Error middleware → Consistent response

Production rule: Do not expose stack traces, secrets, database credentials or internal implementation details to API clients.

11. API Response Architecture

A consistent response shape makes frontend and client code easier to maintain.

// success
{
  "success": true,
  "data": {
    "id": "123",
    "name": "Sam"
  }
}

// error
{
  "success": false,
  "message": "Validation failed",
  "errors": [
    { "field": "email", "message": "Invalid email" }
  ]
}

There is no single universal response format. The important point is consistency across your API.

12. Logging Architecture

Logging records useful events for debugging, monitoring and incident investigation.

logger.info("User created", {
  userId: user.id
});

logger.error("Database operation failed", {
  operation: "findUser",
  error: err.message
});
  • Use structured logs in larger systems.
  • Include request IDs/correlation IDs when possible.
  • Never log passwords, tokens or other sensitive secrets.
13. Code-Based Interview Questions
Q1. What architectural problem is shown here?
app.post("/users", async (req, res) => {
  const existing = await User.findOne({ email: req.body.email });

  if (existing) {
    return res.status(409).json({ message: "Already exists" });
  }

  const hash = await bcrypt.hash(req.body.password, 10);
  const user = await User.create({
    email: req.body.email,
    password: hash
  });

  res.status(201).json(user);
});
Answer: The route contains routing, business logic, password processing, database access and response handling all in one place. Move business rules into a service and data access into a repository/model layer.
This makes the route harder to test, reuse and maintain. Separation of concerns keeps each layer focused.
Q2. What should the controller do here?
async function createUser(req, res, next) {
  try {
    const user = await userService.createUser(req.body);
    res.status(201).json({ data: user });
  } catch (err) {
    next(err);
  }
}
Read HTTP input, call the service, choose the HTTP status/response shape, and forward errors. It should not contain the main business workflow.
The controller is an HTTP adapter. Keeping it thin prevents business logic from becoming tightly coupled to Express.
Q3. Why is this service easier to test?
function createOrderService({ orderRepository, paymentService }) {
  return {
    async createOrder(input) {
      const order = await orderRepository.create(input);
      await paymentService.charge(order.total);
      return order;
    }
  };
}
Its dependencies are supplied from outside. Tests can pass fake repository and payment implementations.
This is dependency injection. The service does not create concrete dependencies itself, so tests can isolate business logic.
Q4. What is the problem with this error middleware?
app.use((err, req, res, next) => {
  res.status(500).json({
    error: err.stack
  });
});
Returning err.stack to clients can expose internal implementation details. Use a safe production message and log the detailed error on the server.
Stack traces may reveal file paths, library details and other information useful to attackers. Clients normally need a safe message, not internal debugging information.
Q5. What is wrong with this configuration?
const jwtSecret = "my-super-secret-key";
const dbUrl = "mongodb://admin:password@server";
Secrets and environment-specific configuration are hard-coded in source code. Use environment variables or a secure secret manager.
Source code can be copied, logged or accidentally committed. Separating configuration from code reduces this risk and makes deployment configuration easier.
Q6. Which layer should normally contain this rule?
if (order.total > 10000 && !user.isVerified) {
  throw new AppError("Verification required", 403);
}
Usually the service/business layer, assuming this is an application business rule rather than a simple request validation rule.
Business rules should not depend on one HTTP route. A service can be reused by other entry points while keeping the rule in one place.
Q7. What does this repository abstraction provide?
const userRepository = {
  findById(id) {
    return User.findById(id);
  }
};
It gives the service a focused interface for user data access and keeps database-specific code outside the service.
The service can depend on an interface-like contract rather than knowing every database detail. This can improve testing and maintainability.
Q8. What is the better design for this route?
// Design A
router.get("/users/:id", async (req, res) => {
  // 100 lines of validation,
  // business logic and DB code
});

// Design B
router.get("/users/:id", validateUserId, userController.getUser);
Design B is generally better. Keep validation in validation middleware, HTTP handling in the controller, business rules in the service, and data access in the repository/model layer.
It makes each part smaller and easier to test, reuse and change.
14. Common Developer Mistakes
  • Putting all logic inside route handlers.
  • Making controllers responsible for database details and business rules.
  • Creating a service layer that only renames repository methods without adding business value.
  • Creating too many abstractions for a tiny application.
  • Mixing configuration, secrets and business logic.
  • Returning raw internal errors to clients.
  • Logging passwords, JWTs or sensitive personal data.
  • Making every helper a global utility even when it belongs to one feature.
  • Using dependency injection as ceremony without a testing or design benefit.
  • Choosing a folder structure by fashion instead of project needs.
15. Quick Recap
  • Routes: map HTTP requests to handlers.
  • Middleware: handles cross-cutting request processing.
  • Controllers: handle HTTP input/output.
  • Services: contain business logic.
  • Repositories: isolate data access.
  • Models: represent database structures/access mechanisms.
  • Dependency injection: supplies dependencies from outside.
  • Configuration: keeps environment-specific values outside business code.
  • Error architecture: centralizes error conversion and safe responses.
  • Logging: records useful operational information without exposing secrets.
  • Scalable structure: grows by keeping responsibilities and boundaries clear.
