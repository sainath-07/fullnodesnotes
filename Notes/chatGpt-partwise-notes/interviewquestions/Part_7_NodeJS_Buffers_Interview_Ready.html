Part 7 — Buffers ⭐⭐⭐

Understand how Node.js stores and handles binary data.

1. What is a Buffer?

What: A Node.js Buffer is a fixed-size sequence of bytes used to work with binary data.

Why: Files, network packets, images, audio, video and other data are ultimately handled as bytes. A JavaScript string is designed for text, while a Buffer is designed for raw bytes.

Layman example: Think of a Buffer as a box containing small 8-bit pieces of data. A string is the readable text you interpret from those pieces.

Text / File / Network data → bytes → Buffer → decode using an encoding → String / useful data

Q1 — Why does Node.js need Buffer when JavaScript already has strings?

Answer: Strings are for text. Buffers let Node.js efficiently handle raw binary bytes, which are common in files, streams and network communication.
2. Buffer.from()

Buffer.from() creates a Buffer from existing data such as a string, array of bytes, or another Buffer.

const buf = Buffer.from("Hello"); console.log(buf); console.log(buf.toString());

Q2 — What does Buffer.from("Hello") contain?

Answer: It contains the UTF-8 encoded bytes representing Hello. buf.toString() converts those bytes back into text.

Q3 — Is Buffer.from("Hello") the same type as "Hello"?

Answer: No. "Hello" is a string. Buffer.from("Hello") returns a Buffer object containing bytes.
3. Buffer.alloc() vs Buffer.allocUnsafe() ⭐⭐⭐
const safe = Buffer.alloc(5); console.log(safe); const unsafe = Buffer.allocUnsafe(5); console.log(unsafe);

Q4 — What is the important difference?

Answer: Buffer.alloc(5) creates a 5-byte Buffer initialized to zero. Buffer.allocUnsafe(5) can be faster because initialization is skipped, so the buffer may contain old memory contents until you overwrite it.

Q5 — Why can allocUnsafe() be dangerous?

Why: If you expose or use bytes before fully overwriting them, they may contain stale memory data. Use alloc() when you need initialized memory and use allocUnsafe() only when you understand the performance trade-off and immediately initialize the bytes.
4. Buffer Encoding

Encoding defines how text is converted to bytes and how bytes are decoded back into text.

  • UTF-8: common text encoding.
  • Hex: represents each byte using hexadecimal characters.
  • Base64: represents binary data as text characters, often useful when binary data must travel through text-based systems.
const text = "Hi"; console.log(Buffer.from(text, "utf8")); console.log(Buffer.from(text).toString("hex")); console.log(Buffer.from(text).toString("base64"));

Q6 — What are the likely outputs?

Buffer containing bytes 48 69 4869 SGk=
Why: UTF-8 encodes H as 0x48 and i as 0x69. Hex displays those bytes as 48 69; Base64 encodes the same bytes as SGk=.

Q7 — Does changing the display encoding change the underlying bytes?

Answer: The encoding used for conversion or display determines how bytes are interpreted or represented. A Buffer itself stores bytes, not “hex characters” or “Base64 characters” as its underlying data.
5. Buffer length and Unicode
const a = Buffer.from("A"); const b = Buffer.from("😀"); console.log(a.length); console.log(b.length); console.log("😀".length);

Q8 — What is the output?

1 4 2
Why: Buffer.length counts bytes. The UTF-8 representation of 😀 uses 4 bytes. JavaScript string length counts UTF-16 code units, so 😀 has length 2.
6. String ↔ Buffer Conversion
const buf = Buffer.from("Node.js"); const text = buf.toString("utf8"); const again = Buffer.from(text); console.log(text); console.log(Buffer.compare(buf, again));

Q9 — Output?

Node.js 0
Why: The bytes are decoded into the same text and then encoded again. Buffer.compare() returns 0 when the buffers contain equal bytes.

Q10 — When should you use toString()?

Answer: When the bytes represent text and you need to decode them into a JavaScript string. Always choose the correct encoding for the data.
7. Buffer Comparison and Concatenation
const a = Buffer.from("Hello"); const b = Buffer.from(" World"); const c = Buffer.concat([a, b]); console.log(c.toString());

Q11 — Output?

Hello World
Why: Buffer.concat() creates a new Buffer containing the bytes of the supplied buffers in order.

Q12 — Does Buffer.concat() mutate the original buffers?

Answer: No. It creates a new Buffer. The input Buffers remain separate.
8. Buffer and Files

File APIs can read or write binary data using Buffers. If you omit an encoding in relevant Node.js file APIs, the returned data can be a Buffer.

const fs = require("fs"); fs.readFile("photo.png", (err, data) => { if (err) throw err; console.log(Buffer.isBuffer(data)); console.log(data.length); });

Q13 — Why is Buffer useful for an image?

Answer: An image is binary data, not ordinary text. A Buffer can hold its raw bytes without trying to interpret them as characters.
9. Buffer and Streams ⭐⭐⭐

Streams process data in chunks. Those chunks are commonly Buffers for binary streams.

Large file
↓
Readable Stream
↓
Buffer chunk → Buffer chunk → Buffer chunk
↓
Writable Stream / HTTP response

Q14 — Why are streams and Buffers commonly used together?

Answer: A stream can process data piece by piece instead of loading an entire large resource into memory. Buffers provide a byte container for those chunks.

Q15 — Why can streaming a large file be better than readFile()?

Answer: readFile() generally loads the whole file into memory. A stream can process smaller chunks, reducing memory pressure for large data.
10. Buffer and HTTP
const http = require("http"); const server = http.createServer((req, res) => { const chunks = []; req.on("data", chunk => { chunks.push(chunk); }); req.on("end", () => { const body = Buffer.concat(chunks); console.log(body.toString("utf8")); res.end("OK"); }); }); server.listen(3000);

Q16 — What is happening here?

Answer: The HTTP request body arrives as chunks. The chunks are collected, joined with Buffer.concat(), and decoded as UTF-8 text.
11. MAANG / FANG / MNC Output Questions ⭐⭐⭐

Q17 — Buffer mutation

const b = Buffer.from("abc"); b[0] = 65; console.log(b.toString());
Abc
Why: Buffer elements represent byte values. 65 is the UTF-8/ASCII byte for uppercase A.

Q18 — Slice shares memory

const b = Buffer.from("hello"); const part = b.subarray(0, 2); part[0] = 72; console.log(b.toString()); console.log(part.toString());
Hello He
Why: subarray() creates a view over the same underlying memory. Changing the view can change the original Buffer.

Q19 — Buffer.isBuffer()

console.log(Buffer.isBuffer("abc")); console.log(Buffer.isBuffer(Buffer.from("abc")));
false true
Why: The first value is a string; the second is a Buffer.

Q20 — Buffer length vs string length

const s = "é"; const b = Buffer.from(s); console.log(s.length); console.log(b.length);
1 2
Why: JavaScript string length counts UTF-16 code units, while UTF-8 Buffer length counts bytes. é uses two UTF-8 bytes.

Q21 — Base64 round trip

const encoded = Buffer.from("Hello").toString("base64"); const decoded = Buffer.from(encoded, "base64").toString("utf8"); console.log(encoded); console.log(decoded);
SGVsbG8= Hello
Why: The first step converts bytes into Base64 text; the second decodes that Base64 representation back into bytes and then UTF-8 text.

Q22 — alloc output

const b = Buffer.alloc(3); b[1] = 7; console.log([...b]);
[0, 7, 0]
Why: Buffer.alloc(3) initializes all three bytes to zero.

Q23 — compare()

const a = Buffer.from("a"); const b = Buffer.from("b"); console.log(Buffer.compare(a, b));
-1
Why: Buffer.compare() returns a negative value when the first Buffer sorts before the second. It returns 0 for equal and a positive value when the first sorts after the second.

Q24 — String vs Buffer interview question

Answer: A String represents text and is interpreted as characters. A Buffer represents raw bytes. Use strings for text and Buffers when working with binary data such as files, sockets, streams and HTTP payload chunks.
12. Common Developer Mistakes
  • Trying to treat binary data as normal text.
  • Forgetting to specify the correct encoding when converting bytes to text.
  • Assuming Buffer.length means number of visible characters.
  • Using allocUnsafe() without initializing the buffer before using its contents.
  • Loading huge binary files completely into memory when a stream would be more suitable.
  • Assuming Base64 is encryption. It is an encoding, not security.
  • Forgetting that Buffer views such as subarray() can share memory.
  • Concatenating many chunks inefficiently instead of using appropriate Buffer/stream APIs.
