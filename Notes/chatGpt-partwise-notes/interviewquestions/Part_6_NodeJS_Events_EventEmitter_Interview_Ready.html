Part 6 — Events & EventEmitter ⭐⭐⭐

Learn how Node.js uses events to communicate between parts of an application.

1. Event-Driven Programming

What: Event-driven programming means code reacts when an event happens instead of constantly checking whether something happened.

Why: It fits Node.js well because many operations are asynchronous: network requests, files, streams and other I/O can finish later.

Layman example: A doorbell is an event. You do not keep asking the doorbell whether someone pressed it. When it rings, you react.

Event happens → Event is emitted → Listener receives event → Listener function runs

Q1 — Is Node.js an “EventEmitter architecture”?

Answer: No. Node.js uses a non-blocking, event-driven architecture. EventEmitter is one important API used to implement event-based communication inside Node.js applications.
2. What is EventEmitter?

EventEmitter is a class from Node.js's built-in events module. It allows an object to emit named events and allows functions to listen for those events.

const EventEmitter = require("events"); const emitter = new EventEmitter(); emitter.on("login", () => { console.log("User logged in"); }); emitter.emit("login");
emitter.emit("login")
↓
Node finds listeners for "login"
↓
listener function executes

Q2 — What is the purpose of EventEmitter?

Answer: It provides a simple mechanism for registering listeners and notifying them when named events occur.
3. emit() and on()

on() registers a listener. emit() triggers an event.

const { EventEmitter } = require("events"); const bus = new EventEmitter(); bus.on("message", (text) => { console.log("Received:", text); }); bus.emit("message", "Hello");

Q3 — Output?

Received: Hello
Why? The second argument to emit() is passed to the listener as its parameter.

Q4 — Does on() execute the listener immediately?

Answer: No. on() registers the listener. The listener runs when the matching event is emitted.
4. once() — Run a Listener Only Once
const { EventEmitter } = require("events"); const emitter = new EventEmitter(); emitter.once("connected", () => { console.log("Connected"); }); emitter.emit("connected"); emitter.emit("connected");

Q5 — Output?

Connected
Why? once() automatically removes that listener after its first execution.

Q6 — When is once() useful?

Answer: When an event should be handled only once, such as one-time initialization, first connection, or a one-time setup event.
5. off() / removeListener()

off() removes a previously registered listener. removeListener() is the corresponding API name commonly used for the same operation.

const { EventEmitter } = require("events"); const emitter = new EventEmitter(); function handler() { console.log("Hello"); } emitter.on("test", handler); emitter.off("test", handler); emitter.emit("test");

Q7 — Output?

Answer: Nothing is printed because the listener was removed before emit().

Q8 — Can you remove an anonymous listener using a newly created identical function?

Answer: No. Listener removal depends on the same function reference that was registered.
6. removeAllListeners() and listenerCount()
const { EventEmitter } = require("events"); const emitter = new EventEmitter(); function a() {} function b() {} emitter.on("data", a); emitter.on("data", b); console.log(emitter.listenerCount("data")); emitter.removeAllListeners("data"); console.log(emitter.listenerCount("data"));

Q9 — Output?

2 0
Why? Two listeners were registered. removeAllListeners("data") removes all listeners for that event.

Q10 — What is the danger of removeAllListeners()?

Answer: It can remove listeners registered by other parts of the application. Use it carefully, especially on shared emitters.
7. Multiple Listeners and Execution Order ⭐⭐⭐
const { EventEmitter } = require("events"); const emitter = new EventEmitter(); emitter.on("start", () => console.log("A")); emitter.on("start", () => console.log("B")); emitter.on("start", () => console.log("C")); emitter.emit("start");

Q11 — Output?

A B C
Why? EventEmitter normally calls listeners synchronously in the order in which they were registered.

Q12 — Are EventEmitter listeners automatically parallel?

Answer: No. Emitting an event does not automatically make listeners run in parallel. Normal listeners are called synchronously, in registration order.
8. Event Arguments
const { EventEmitter } = require("events"); const emitter = new EventEmitter(); emitter.on("user", (name, age) => { console.log(name, age); }); emitter.emit("user", "Sam", 25);

Q13 — What reaches the listener?

Sam 25
Why? Arguments supplied after the event name in emit() are passed to the listener in the same order.
9. EventEmitter Error Handling ⭐⭐⭐

The special "error" event is important. If an EventEmitter emits "error" without an appropriate error listener, Node.js treats it as an uncaught exception and the process can terminate.

const { EventEmitter } = require("events"); const emitter = new EventEmitter(); emitter.on("error", (err) => { console.log("Handled:", err.message); }); emitter.emit("error", new Error("Database failed"));

Q14 — Output?

Handled: Database failed

Q15 — What is the interview trap with "error"?

Answer: Unlike ordinary event names, an unhandled "error" event is special. You should attach an error listener when an emitter may emit errors.
10. Custom Events

You can create your own event names. This is useful for application-level communication.

const { EventEmitter } = require("events"); class OrderService extends EventEmitter { createOrder(order) { console.log("Saving order..."); this.emit("orderCreated", order); } } const service = new OrderService(); service.on("orderCreated", (order) => { console.log("Send email for:", order.id); }); service.createOrder({ id: 101 });

Q16 — Why use a custom EventEmitter class?

Why? It can keep event-based communication close to a domain object, such as orders, notifications or application services, instead of placing unrelated event logic everywhere.
11. EventEmitter Memory Warnings

Node.js warns when too many listeners are added for the same event. The default maximum is commonly 10 listeners per event, and exceeding it produces a warning rather than automatically proving there is a memory leak.

const { EventEmitter } = require("events"); const emitter = new EventEmitter(); for (let i = 0; i < 11; i++) { emitter.on("data", () => {}); }

Q17 — Does MaxListenersExceededWarning always mean there is a memory leak?

Answer: No. It is a warning that often indicates listeners may be accumulating unexpectedly. It should be investigated, but it is not proof of a leak.

Q18 — What common coding pattern causes this warning?

Answer: Repeatedly registering listeners inside a function without removing them or registering them only once.
12. EventEmitter + async Functions ⭐⭐⭐
const { EventEmitter } = require("events"); const emitter = new EventEmitter(); emitter.on("task", async () => { await Promise.resolve(); console.log("listener"); }); console.log("before"); emitter.emit("task"); console.log("after");

Q19 — Predict the output

before after listener
Why? The async listener starts synchronously, reaches await, and suspends. The code after emit() continues. The continuation after the resolved promise runs as a microtask.

Q20 — Does emit() wait for an async listener to finish?

Answer: No. EventEmitter.emit() does not automatically await promises returned by async listeners.

Q21 — Can an async listener's rejected promise automatically be caught by emit()?

Answer: Do not assume that ordinary emit() awaits or handles a listener's returned promise. Async listener errors need an intentional error-handling strategy.
13. Tricky MAANG / FANG / MNC Questions

Q22 — Listener added during emission

const { EventEmitter } = require("events"); const e = new EventEmitter(); e.on("go", () => { console.log("A"); e.on("go", () => console.log("B")); }); e.emit("go"); e.emit("go");
A A B
Why? On the first emission, only the listener that was already registered for that emission runs. The new listener is available for the next emission. On the second emission there are two listeners.

Q23 — once() and listenerCount()

const e = new EventEmitter(); function work() {} e.once("ready", work); console.log(e.listenerCount("ready")); e.emit("ready"); console.log(e.listenerCount("ready"));
1 0
Why? The once listener exists until its first execution, then it is removed.

Q24 — Same event, two listeners

e.on("x", () => console.log("first")); e.on("x", () => console.log("second")); e.emit("x");
first second
Interview point: Registration order matters for normal synchronous listeners.
14. Common Developer Mistakes
  • Thinking on() runs a callback immediately.
  • Assuming emit() waits for async listeners.
  • Forgetting to remove listeners that are repeatedly registered.
  • Using removeListener() with a different function reference.
  • Using removeAllListeners() on a shared emitter without considering other consumers.
  • Ignoring the special "error" event.
  • Assuming many listeners automatically execute in parallel.
  • Increasing the listener limit to hide a warning instead of finding why listeners accumulate.
