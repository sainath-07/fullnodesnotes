Part 29 — Logging & Monitoring

Interview-ready teaching notes and code/output questions for MAANG, product companies, and MNC interviews.

1. What is Logging?

What: Logging means recording useful information about what an application is doing.

Why: Logs help developers understand requests, errors, warnings, important business events, and production failures.

Layman example: A security guard writes down who entered a building, when they entered, and what unusual event happened. Application logs provide a similar history for software.

Request → Application → Log event → Log storage → Developer / Monitoring system
Interview line: Logging tells us what happened. Monitoring tells us whether the system is healthy and how it is behaving over time.
2. Why Do We Need Logging?
  • Find production bugs.
  • Understand failed requests.
  • Track important application events.
  • Measure request behavior and response time.
  • Investigate security or operational problems.
  • Understand what happened before an error.
Good production log: It should contain enough context to understand an event without exposing passwords, tokens, or other sensitive information.
3. Logging Levels
LevelMeaningTypical use
fatalVery serious failureApplication cannot continue
errorSomething failedDatabase/API/application error
warnSomething needs attentionRetry, degraded dependency
infoNormal important eventServer started, request completed
debugDetailed debugging informationDevelopment/troubleshooting
traceVery detailed diagnostic informationDeep troubleshooting
Common mistake: Do not log everything at error. The level should communicate the seriousness of the event.
4. console vs Winston vs Pino
ToolBest understanding
consoleSimple built-in logging. Useful for basic debugging.
WinstonFlexible logging library with transports, levels, and formatting.
PinoHigh-performance structured logger commonly used in Node.js services.
console.log("Server started"); console.error("Database connection failed");

Why use a logging library? Production applications often need structured output, log levels, transports, timestamps, correlation IDs, and centralized log collection.

5. Structured Logs

A structured log stores information as fields rather than only as a sentence.

{ "level": "info", "message": "request completed", "method": "GET", "path": "/users", "statusCode": 200, "durationMs": 18, "requestId": "req-123" }
Why? Machines can search and filter structured fields easily. For example, you can find all requests where statusCode >= 500.
6. Request Logging

Request logging records useful HTTP information such as method, path, status, duration, and a request/correlation ID.

Incoming Request → Request ID → Handler → Response → Log status + duration
GET /users status: 200 duration: 21ms requestId: req-123

Interview focus: Logging request duration helps identify slow endpoints.

7. Error Logging

Error logs should provide enough context to investigate the failure.

{ "level": "error", "message": "Database query failed", "requestId": "req-123", "route": "/orders", "errorCode": "DB_TIMEOUT" }
Never blindly log secrets: passwords, access tokens, session secrets, API keys, and sensitive personal data should not be written to logs.
8. Correlation IDs / Request IDs

A correlation ID is an identifier that connects related logs belonging to the same request or distributed operation.

Client Request
↓
requestId = abc-123
↓
API → Service → Database / External API
↓
All related logs contain abc-123
requestId: "abc-123" API log → abc-123 Service log → abc-123 Payment log → abc-123
Interview line: Correlation IDs are especially useful in distributed systems because one user request may cross multiple services.
9. What is Monitoring?

Monitoring continuously observes application health and behavior.

Application → Metrics / Logs / Health Checks → Monitoring System → Alert → Developer

Important signals include:

  • Request rate
  • Error rate
  • Response latency
  • CPU usage
  • Memory usage
  • Database health
  • Availability
10. Metrics
MetricQuestion it answers
Request rateHow much traffic are we receiving?
Error rateHow many requests are failing?
LatencyHow long are requests taking?
CPUIs the process using too much CPU?
MemoryIs memory usage growing unexpectedly?
AvailabilityIs the service reachable and healthy?
Interview tip: A common production view is the relationship between traffic, errors, and latency.
11. Health Check — /health

A health endpoint provides a simple signal that the application process is alive and able to respond.

app.get("/health", (req, res) => { res.status(200).json({ status: "ok" }); });

Use: Load balancers, orchestration systems, or monitoring systems can call the endpoint.

12. Readiness — /ready

Readiness is different from simple liveness. A service may be running but not ready to receive traffic because an important dependency is unavailable.

/health → "Is the process alive?"

/ready → "Can this instance safely receive traffic?"
app.get("/ready", async (req, res) => { const databaseReady = await checkDatabase(); if (!databaseReady) { return res.status(503).json({ status: "not_ready" }); } res.json({ status: "ready" }); });
Interview point: Returning 503 Service Unavailable can tell infrastructure that the instance is temporarily unable to serve traffic.
13. Application and Performance Monitoring

Application monitoring looks at application behavior. Performance monitoring focuses on latency, throughput, CPU, memory, database calls, and slow operations.

Request → Controller → Service → Database / External API → Response ↓ Latency + errors + resource metrics
Useful production question: "Is the application slow, or is one of its dependencies slow?"
14. Production Debugging

A practical production debugging process:

  1. Identify the time window.
  2. Check error rate and latency.
  3. Search logs using the request/correlation ID.
  4. Find the failing route or dependency.
  5. Check database, CPU, memory, and external services.
  6. Compare with recent deployments or configuration changes.
  7. Fix safely and verify the metrics afterward.
Alert → Metrics → Correlation ID → Logs → Root cause → Fix → Verify
15. Code / Output-Based Interview Questions
Q1. What does this logging code do?
console.log("Server started"); console.error("Database connection failed");
Answer: Both messages are written to the process output; the second uses the error output stream.
Why: console.log is commonly used for normal messages, while console.error communicates an error. In production, a structured logger is usually preferred for richer context and routing.
Q2. Which log level is more appropriate?
try { await saveOrder(order); } catch (err) { logger.???("Order save failed", { err }); }
Answer: error
Why: A failed database/application operation is an error condition and should be searchable as an error rather than a normal info event.
Q3. Why is this structured log easier to search?
logger.info({ method: "GET", path: "/users", statusCode: 200, durationMs: 18, requestId: "abc-123" }, "request completed");
Answer: It stores important values as fields.
Why: Monitoring and log systems can filter fields such as statusCode, durationMs, and requestId without parsing a sentence.
Q4. What problem does the requestId solve?
requestId: "abc-123"
Answer: It lets us connect related logs for the same request or distributed operation.
Why: A single request may create logs in middleware, controllers, services, and external-service calls. The same ID makes those logs much easier to trace.
Q5. What is the likely issue with this health check?
app.get("/health", async (req, res) => { await database.connect(); res.json({ status: "ok" }); });
Answer: The health endpoint is performing a potentially expensive connection operation on every health request.
Why: Health checks can be called frequently by infrastructure. They should be lightweight. Dependency readiness checks can be handled separately, such as through a readiness endpoint or an appropriate cached/controlled check.
Q6. What should /ready return when a required database is unavailable?
if (!databaseReady) { return res.status(???).json({ status: "not_ready" }); }
Answer: 503 Service Unavailable.
Why: The process may still be alive, but it is not ready to safely serve traffic. A 503 response communicates temporary service unavailability to infrastructure.
Q7. Which metric helps identify slow requests?
{ statusCode: 200, durationMs: 1840 }
Answer: Request latency or response duration.
Why: durationMs represents how long the request took. A rising latency metric can reveal slow application code or slow dependencies.
Q8. What is dangerous about this log?
logger.info({ email: user.email, password: user.password, token: req.headers.authorization });
Answer: It logs sensitive credentials and authentication data.
Why: Passwords, access tokens, API keys, and similar secrets should not be logged. Logs are often copied to centralized systems and retained for a long time.
Q9. What does this flow help a developer investigate?
Alert ↓ Metrics ↓ requestId ↓ Logs ↓ Database / external API ↓ Root cause
Answer: It provides a structured production debugging path.
Why: Metrics show that something is wrong, a correlation ID narrows the investigation to one operation, and logs/dependency data help identify the root cause.
Q10. What is the key difference between /health and /ready?
GET /health GET /ready
Answer: /health generally answers whether the process is alive; /ready answers whether the instance is ready to receive traffic.
Why: A running process can still be unable to serve requests correctly because a required dependency is unavailable. Separating liveness and readiness prevents infrastructure from treating both conditions as the same.
16. Common Developer Mistakes
Mistake 1: Logging secrets.
Never log passwords, JWTs, API keys, session secrets, or sensitive authentication headers.
Mistake 2: Using only plain text logs.
Structured fields make production searching and filtering much easier.
Mistake 3: Logging every request without useful context.
Include useful fields such as method, route, status, duration, and request/correlation ID.
Mistake 4: Confusing liveness with readiness.
A process can be alive but unable to serve traffic because a required dependency is unavailable.
Mistake 5: Ignoring log volume.
Very large debug logs can increase storage cost, slow investigation, and create noise.
Mistake 6: Looking only at logs.
Production diagnosis should combine logs, metrics, health checks, traces/correlation information, and infrastructure signals when available.

18. Quick Recap — Interview Ready
  • Logging: Records useful application events.
  • Log levels: Communicate event importance such as info, warn, and error.
  • Winston: Flexible Node.js logging library.
  • Pino: High-performance structured logger.
  • Structured logs: Store searchable fields instead of only text.
  • Request logging: Records request context, status, and often duration.
  • Correlation ID: Connects related logs across an operation.
  • Metrics: Measure behavior such as request rate, errors, latency, CPU, and memory.
  • /health: Usually checks whether the process is alive/healthy.
  • /ready: Checks whether the instance is ready to receive traffic.
  • Monitoring: Observes application health and behavior over time.
  • Production debugging: Combine metrics, IDs, logs, and dependency information to find the root cause.
30-second interview answer: “Logging records what happened inside an application, while monitoring continuously tells us how the system is behaving. In Node.js production systems I prefer structured logs with levels, request IDs, status codes, and latency. Tools such as Winston or Pino can provide production-grade logging. I also expose health and readiness endpoints, monitor metrics such as error rate and latency, and use correlation IDs to trace a request across services. During production debugging, I combine metrics and logs rather than relying on a single signal, and I never log secrets.”
