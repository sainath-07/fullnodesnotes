Node.js + Express.js Interview Preparation

Part 25 — Performance & Scalability ⭐⭐⭐

Interview-ready notes and code-based questions for MAANG, FANG and MNC-style interviews.

1. What are Performance and Scalability?

Performance means how quickly and efficiently one application handles work.

Scalability means how well the application continues to work when users, requests or data increase.

User requests → Load Balancer → Node.js instances → Cache / Database → Response
Layman example: Performance is how quickly one cashier serves a customer. Scalability is how easily you can open more checkout counters when the queue grows.
Why / Purpose

Good performance improves response time and user experience. Good scalability prevents one server from becoming a bottleneck as traffic grows.

When to think about it

When traffic, database load, CPU usage, memory usage or response time starts increasing.

2. Core Concepts — What, Why and How
Blocking operations

A long synchronous operation keeps JavaScript execution busy and prevents the event loop from handling other work.

const fs = require("fs"); const data = fs.readFileSync("large.txt");

Better: prefer asynchronous APIs for normal I/O.

CPU-heavy tasks

Large calculations can keep the JavaScript thread busy. Use worker threads for suitable CPU-bound work.

const { Worker } = require("node:worker_threads");
Worker threads

Run CPU-heavy JavaScript work in another thread so the main event loop can remain responsive.

Cluster

Run multiple Node.js processes so work can use multiple CPU cores. Each worker is a separate process.

Horizontal vs Vertical scaling

Vertical: give one machine more CPU/RAM. Horizontal: add more application instances.

Caching

Keep frequently used data closer to the application so repeated requests do not always hit the database.

Redis

A fast in-memory data store often used for caching, counters, sessions and other low-latency use cases.

HTTP caching

Use response headers such as Cache-Control and ETag where appropriate so clients or intermediaries can reuse responses.

Compression

Compress suitable HTTP responses to reduce network transfer size. Compression costs CPU, so measure it.

Streaming

Send large data in chunks instead of loading the complete payload into memory first.

Pagination

Return a limited part of a large result set instead of sending every record at once.

Database indexing

Indexes can make lookups much faster, but they use storage and can add write/update cost.

Connection pooling

Reuse a controlled set of database connections instead of opening a new connection for every request.

Rate limiting

Limit how many requests a client can make in a time window to protect the API.

Load balancing

Distribute incoming traffic across healthy application instances.

Memory leaks

Memory that is still reachable but no longer useful can accumulate and increase memory usage.

Performance profiling

Measure CPU, memory, event-loop delay, database time and request latency before optimizing.

4. Interview Questions — Code Based
Q1. What is wrong with this Node.js API?
app.get("/report", (req, res) => { const result = fs.readFileSync("./large-report.json", "utf8"); res.json(JSON.parse(result)); }); app.get("/health", (req, res) => { res.send("OK"); });

Question: Why can /health become slow while /report is running?

Answer: readFileSync() is synchronous. It blocks the JavaScript thread while the file is read. During that time, the event loop cannot process the /health request normally.
Why? Node.js can handle many I/O operations efficiently when they are asynchronous, but synchronous work keeps the main JavaScript execution path busy.
Q2. How would you fix the blocking file operation?
app.get("/report", async (req, res, next) => { try { const result = await fs.promises.readFile( "./large-report.json", "utf8" ); res.json(JSON.parse(result)); } catch (err) { next(err); } });

Question: Explain why this version is safer for the event loop.

Answer: The promise-based file API does not use a synchronous file read. While the I/O is being handled, Node.js can continue processing other work.
Why? The goal is not simply “async is always faster.” The goal is to avoid unnecessarily blocking the main JavaScript execution path.
Q3. When should you use worker_threads?
const { Worker } = require("node:worker_threads"); const worker = new Worker("./heavy-work.js"); worker.on("message", result => { console.log(result); });

Question: Why can a worker thread help with a CPU-heavy calculation?

Answer: A worker can perform CPU-heavy JavaScript work outside the main JavaScript execution thread, allowing the main event loop to remain more responsive.
Why? CPU-heavy JavaScript can occupy the main thread for a long time. Moving suitable computation to a worker separates that work from request handling.
Q4. Identify the scalability strategy.
Internet | Load Balancer | +---------+---------+ | | Node #1 Node #2

Question: Is this vertical or horizontal scaling? What does the load balancer do?

Answer: This is horizontal scaling because multiple application instances are running. The load balancer distributes incoming requests among available instances.
Why? Horizontal scaling increases capacity by adding machines/processes/instances rather than making only one machine larger.
Q5. Find the database performance problem.
app.get("/users", async (req, res) => { const users = await User.find({ email: req.query.email }); res.json(users); });

Question: If email is queried very frequently on a huge collection, what database-level improvement might you consider?

Answer: Consider an appropriate database index on the queried field, after checking the query pattern and measuring the result.
Why? An index can avoid scanning every document/row for many lookup patterns. However, indexes are not free; they add storage and write/update overhead.
Q6. What is wrong with opening a new DB connection per request?
app.get("/orders", async (req, res) => { const db = await connectToDatabase(); const orders = await db.query("SELECT * FROM orders"); await db.close(); res.json(orders); });

Question: Why is a connection pool usually a better design for a busy API?

Answer: A pool maintains a controlled number of reusable database connections. Requests can borrow and release connections instead of repeatedly creating new ones.
Why? Creating connections has cost. A pool reduces repeated setup work and prevents uncontrolled connection creation.
Q7. How can caching reduce database load?
const cached = await redis.get("product:42"); if (cached) { return res.json(JSON.parse(cached)); } const product = await Product.findById(42); await redis.setEx( "product:42", 60, JSON.stringify(product) ); res.json(product);

Question: Explain the request flow and one important risk.

Answer: First check Redis. If data exists, return it without querying the database. If not, query the database, store the result temporarily, and return it. A major risk is stale data if cache invalidation is not designed correctly.
Why? Frequently requested data can be served from memory faster than repeatedly performing the same database query. The trade-off is cache consistency and invalidation complexity.
Q8. Why is pagination important?
app.get("/products", async (req, res) => { const page = Number(req.query.page) || 1; const limit = Math.min(Number(req.query.limit) || 20, 100); const skip = (page - 1) * limit; const products = await Product.find() .skip(skip) .limit(limit); res.json(products); });

Question: Why is returning 1,000,000 products in one response a bad idea?

Answer: A huge result can consume database resources, server memory, CPU, network bandwidth and client memory. Pagination limits the amount of data processed and transferred per request.
Why? Performance is affected by the entire request path: database → Node.js → network → browser. Pagination controls the size of that work.
Q9. What performance issue can this create?
const cache = new Map(); app.get("/user/:id", async (req, res) => { const user = await getUser(req.params.id); cache.set(req.params.id, user); res.json(user); });

Question: If user IDs are continuously different, what memory problem could happen?

Answer: The Map can grow continuously because entries are never removed. If the process keeps receiving new IDs, memory usage can grow significantly. This can become a memory leak or unbounded cache.
Why? Objects stored in a reachable Map remain reachable, so garbage collection cannot remove them just because they are no longer useful to the application.
Q10. Rate limiting and scalability
POST /login POST /login POST /login ... POST /login // thousands of attempts

Question: Why should a login API use rate limiting?

Answer: Rate limiting reduces abuse such as brute-force attempts and helps protect server resources. In a multi-instance deployment, the rate-limit state often needs a shared store or infrastructure-aware design.
Why? An in-memory counter inside one Node.js process does not automatically coordinate limits across several instances. A shared store such as Redis can be used when appropriate.
5. Common Developer Mistakes
  • Using synchronous file-system or crypto operations inside request paths without a good reason.
  • Doing CPU-heavy calculations on the main event-loop thread.
  • Adding indexes everywhere without checking query patterns and write cost.
  • Creating a new database connection for every request.
  • Using an unlimited in-memory cache.
  • Sending huge API responses instead of using pagination or streaming.
  • Adding caching without an invalidation or expiry strategy.
  • Scaling horizontally without considering shared sessions, cache state and database limits.
  • Compressing everything without measuring CPU and network trade-offs.
  • Optimizing before measuring the actual bottleneck.

7. Quick Recap
Remember: Node.js performance is strongly connected to keeping the event loop responsive, avoiding unnecessary CPU/blocking work, and controlling I/O and memory.
  • Blocking: delays other JavaScript work.
  • Workers: useful for CPU-heavy tasks.
  • Horizontal scaling: add instances.
  • Cache: reduce repeated expensive work.
  • Pagination/streaming: control large data transfer.
  • Indexes: speed suitable database queries.
  • Pooling: reuse controlled database connections.
  • Rate limiting: control abusive or excessive traffic.
  • Profiling: measure before changing code.
8. Final Interview Checklist

Be ready to explain these without memorizing definitions:

  • Why can synchronous code block Node.js?
  • When would you choose worker threads?
  • Cluster vs worker threads?
  • Horizontal vs vertical scaling?
  • Why use Redis?
  • What makes cache invalidation difficult?
  • Why are database indexes useful and what is their cost?
  • Why use connection pooling?
  • How does pagination improve API performance?
  • What is a memory leak in Node.js?
  • Why is rate limiting important?
  • What does a load balancer solve?
  • How would you investigate a slow API?
Strong interview answer pattern: First identify the bottleneck → measure it → explain the trade-off → choose the smallest suitable optimization → measure again.
