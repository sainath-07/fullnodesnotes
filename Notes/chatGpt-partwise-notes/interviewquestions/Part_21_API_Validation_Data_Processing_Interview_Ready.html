Node.js + Express.js Interview Preparation

Part 21 — API Validation & Data Processing ⭐⭐⭐

Learn how to validate request data before it reaches your business logic or database.

1. What is API Validation?

API validation checks whether data sent by a client has the correct type, shape, format, and values.

Layman example: A security guard checks your ticket before allowing you into an event. Validation checks the request before your application accepts it.
Why?

Clients can send missing, incorrect, unexpected, or dangerous data. Validation protects application logic and keeps stored data consistent.

How it works
Client Request ↓ Read body / query / params ↓ Validation + type checks ↓ Sanitize / normalize when needed ↓ Valid? ── No ──→ 400 response │ Yes ↓ Controller / Service ↓ Database

Interview point: Never assume data is valid just because your frontend validates it. The API is a trust boundary and must validate server-side.
3. Required and Optional Fields
// Conceptual schema
{
  name:     required string,
  email:    required valid email,
  age:      optional integer,
  phone:    optional string
}

Required means the field must be present and valid. Optional means the field may be absent, but if supplied it still needs validation.

Important: Optional does not mean “accept anything.”
4. Type Checking

Type checking confirms that data is the type your application expects.

{
  age: 25,        // number
  active: true,   // boolean
  name: "Sam"     // string
}

A common API problem is receiving values such as "25" where the application expects a number. Decide explicitly whether your validation layer should coerce or reject such values.

5. Nested Validation
{
  "name": "Sam",
  "address": {
    "city": "Hyderabad",
    "zip": "500001"
  }
}

Nested validation checks fields inside objects and arrays, not only top-level fields.

user ├── name └── address ├── city └── zip
6. Sanitization

Validation asks: “Is this data acceptable?”

Sanitization asks: “Can this data be safely normalized or cleaned before use?”

// Example idea
"  Sam  "  →  "Sam"
Security note: Sanitization is not a replacement for parameterized database queries, output encoding, authentication, authorization, or other security controls.
7. Schema Validation Libraries
Joi

A popular schema validation library with a readable schema API.

Zod

A TypeScript-friendly schema validation library that can validate and infer types from schemas.

express-validator

A validation/sanitization approach designed around Express request fields and middleware chains.

// Zod example
import { z } from "zod";

const userSchema = z.object({
  name: z.string().min(2),
  email: z.email(),
  age: z.number().int().positive().optional()
});
Interview answer: The exact library is less important than understanding schemas, validation boundaries, errors, and consistent middleware design.
8. Validation Middleware
function validateUser(req, res, next) {
  const result = userSchema.safeParse(req.body);

  if (!result.success) {
    return res.status(400).json({
      success: false,
      error: {
        code: "VALIDATION_ERROR",
        details: result.error.issues
      }
    });
  }

  req.body = result.data;
  next();
}

app.post("/users", validateUser, createUser);

Validation middleware keeps controllers focused on business logic.

9. Validation Error Responses
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request data is invalid",
    "fields": [
      { "field": "email", "message": "Invalid email" },
      { "field": "age", "message": "Must be a positive integer" }
    ]
  }
}

A consistent format makes frontend error handling much easier.

10. Custom Validation

Use custom validation when a business rule cannot be expressed by a simple type or format check.

// Example rule
// startDate must be before endDate

if (startDate >= endDate) {
  return next(new AppError(
    "startDate must be before endDate",
    400,
    "INVALID_DATE_RANGE"
  ));
}

Keep complex business rules in a suitable validation/service layer rather than spreading them across controllers.

Interview Questions — Code Based ⭐⭐⭐

Q1. What is wrong with this validation?
app.post("/users", (req, res) => {
  const { email } = req.body;

  if (!email) {
    return res.status(200).json({
      message: "Email is required"
    });
  }

  createUser(req.body);
});
Answer: It returns HTTP 200 for invalid input and does not validate the email format or handle the result/error from createUser(). A validation failure should normally use 400 and stop execution.
Why? HTTP status codes communicate the result to clients. A malformed request should not look like a successful request.
Q2. What is the bug?
function validate(req, res, next) {
  if (!req.body.email) {
    next(new Error("Email required"));
  }

  next();
}
Answer: It can call next() twice. When email is missing, the first next(error) is followed by normal next().
Why? After propagating an error, return immediately so the normal request flow does not continue.
Q3. What does this validation check?
const schema = z.object({
  name: z.string().min(2),
  age: z.number().int().positive()
});
Answer: It requires name to be a string with at least 2 characters and age to be a positive integer.
Why? The schema describes both the expected data type and the allowed value constraints.
Q4. Body vs Params vs Query
POST /users/42?notify=true

{
  "name": "Sam"
}
Answer: 42 is a route parameter (req.params.id), true is a query value (req.query.notify), and "Sam" is request-body data (req.body.name).
Why? These are different input locations and should be validated independently because they serve different purposes.
Q5. What is the validation problem?
const limit = req.query.limit;

if (limit > 100) {
  return res.status(400).json({
    message: "Too large"
  });
}
Answer: Query values arrive as strings in normal Express request parsing. The code should validate and deliberately parse/coerce the value, for example ensuring it is a valid integer and within an allowed range.
Why? Explicit type handling prevents unexpected values such as non-numeric input from reaching pagination or database logic.
Q6. Fix the nested validation idea.
const schema = z.object({
  name: z.string(),
  address: z.object({
    city: z.string(),
    zip: z.string()
  })
});
Answer: This is already a nested schema. It validates name, then validates address.city and address.zip. A production schema can add rules such as minimum lengths, regex patterns, or required/optional fields.
Why? Nested objects need nested schemas; checking only the top-level object does not guarantee that child properties are valid.
Q7. What should the middleware do after invalid input?
function validate(req, res, next) {
  const result = schema.safeParse(req.body);

  // complete this
}
if (!result.success) {
  return res.status(400).json({
    success: false,
    error: {
      code: "VALIDATION_ERROR",
      details: result.error.issues
    }
  });
}

req.body = result.data;
next();
Why? Invalid requests must stop before business logic. Using validated data also prevents controllers from working with an unchecked input object.
Q8. Validation or authorization?
DELETE /users/42

// user is logged in
// user tries to delete another user's account
Answer: This is primarily an authorization problem. The request can be syntactically valid, but the authenticated user may not have permission to delete that account.
Why? Validation checks whether data is acceptable. Authorization checks whether the current identity is allowed to perform the operation.
Common Developer Mistakes
❌ Trusting frontend validation.
❌ Validating only the request body while ignoring params and query values.
❌ Returning 200 for validation failures.
❌ Forgetting to return after sending an error response.
❌ Treating optional fields as completely unvalidated fields.
❌ Assuming query-string values are already numbers or booleans.
❌ Mixing validation rules throughout every controller.
❌ Treating sanitization as a complete security solution.
Quick Recap
  • Validate all client-controlled input on the server.
  • Validate body, query, and route parameters separately.
  • Use schemas for clear, reusable rules.
  • Required and optional fields both need type/value rules.
  • Nested data requires nested validation.
  • Sanitization and validation solve different problems.
  • Use validation middleware before controllers.
  • Return consistent validation error responses.
Interview-Ready Points
Strong interview line: “I treat API input as untrusted data. I validate body, params, and query values at the API boundary, use schema-based validation where appropriate, normalize data deliberately, and return a consistent 400 validation response before business logic runs.”
  • Explain validation vs sanitization.
  • Know body vs params vs query.
  • Know why server-side validation is mandatory.
  • Explain Joi, Zod, and express-validator at a high level.
  • Understand nested and custom validation.
  • Know how validation middleware protects controllers.
  • Know how to design useful field-level validation errors.
  • Understand that validation is not the same as authentication or authorization.
