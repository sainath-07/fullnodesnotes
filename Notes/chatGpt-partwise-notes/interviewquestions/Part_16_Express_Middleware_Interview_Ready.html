Node.js + Express.js Interview Preparation

Part 16 — Express Middleware ⭐⭐⭐

Simple explanations, execution-flow diagrams, tricky code questions, answers, WHY explanations, and interview-ready points.

1. What is Middleware?

Middleware is a function that runs between the incoming request and the final response. It can inspect or change the request, change the response, perform a task, stop the request, or pass control to the next function.

Layman example: Think of airport security. Before you reach the boarding gate, security checks your ticket and baggage. Middleware performs similar checks before the final route handler runs.
Client Request→Middleware 1→Middleware 2→Route Handler→Response
Why use middleware?
  • Authentication and authorization
  • Logging
  • Validation
  • Request parsing
  • Error handling
  • Adding common data to req or res
2. Basic Middleware and next()
function logger(req, res, next) {
  console.log(req.method, req.url);
  next();
}

app.use(logger);

app.get("/", (req, res) => {
  res.send("Home");
});
How it works: The middleware receives req, res, and next. Calling next() tells Express to continue to the next matching middleware or route handler.
Important: A middleware must normally either finish the response or call next(). If it does neither, the request can remain pending.

4. Application vs Router Middleware
// Application middleware
app.use((req, res, next) => {
  console.log("App middleware");
  next();
});

// Router middleware
const router = express.Router();

router.use((req, res, next) => {
  console.log("Router middleware");
  next();
});

router.get("/profile", (req, res) => {
  res.send("Profile");
});

app.use("/users", router);
Request→app.use()→/users router→router.use()→route

When to use: Application middleware is useful for logic shared across the application. Router middleware is useful for logic shared only by a group of routes.

5. Built-in, Third-party, and Custom Middleware
Built-in
app.use(express.json());

Parses JSON request bodies and makes the parsed data available through req.body.

Third-party
const cors = require("cors");
app.use(cors());

Third-party middleware is installed separately and provides reusable functionality.

Custom
function addRequestId(req, res, next) {
  req.requestId = Date.now();
  next();
}

app.use(addRequestId);
Interview point: Middleware is not limited to authentication. Parsing, logging, validation, security, metrics, and error handling are also common uses.
6. Authentication vs Authorization Middleware
function authenticate(req, res, next) {
  const token = req.headers.authorization;

  if (!token) {
    return res.status(401).json({ message: "Login required" });
  }

  req.user = { id: 10, role: "admin" };
  next();
}

function authorizeAdmin(req, res, next) {
  if (req.user.role !== "admin") {
    return res.status(403).json({ message: "Forbidden" });
  }

  next();
}

app.get("/admin",
  authenticate,
  authorizeAdmin,
  (req, res) => {
    res.json({ message: "Welcome admin" });
  }
);
Simple difference: Authentication asks, "Who are you?" Authorization asks, "Are you allowed to do this?"
Request→Authenticate→Authorize→Controller
7. Request and Response Modification
function userContext(req, res, next) {
  req.user = {
    id: 101,
    name: "Sam"
  };

  res.locals.requestTime = Date.now();

  next();
}

app.get("/profile", userContext, (req, res) => {
  res.json({
    user: req.user,
    time: res.locals.requestTime
  });
});
Why? Middleware can attach information that later handlers need. This avoids repeating the same work in every route.
Best practice: Keep request properties clearly named and avoid overwriting built-in Express request properties.
8. Middleware Order
app.use((req, res, next) => {
  console.log("A");
  next();
});

app.use((req, res, next) => {
  console.log("B");
  next();
});

app.get("/", (req, res) => {
  console.log("C");
  res.send("Done");
});
A→B→C→Response

Express generally executes matching middleware and handlers in registration order.

Important: Middleware order is part of application behavior. For example, body parsing must happen before code that expects parsed req.body.
9. Route-Specific Middleware and Multiple Middleware
function validateUser(req, res, next) {
  if (!req.body.name) {
    return res.status(400).json({
      message: "Name is required"
    });
  }
  next();
}

function audit(req, res, next) {
  console.log("Audit");
  next();
}

app.post("/users", validateUser, audit, (req, res) => {
  res.status(201).json({ message: "Created" });
});
When to use: Route-specific middleware is useful when a rule applies only to certain endpoints instead of the whole application.
10. Error Middleware and Error Propagation
app.get("/users", async (req, res, next) => {
  try {
    throw new Error("Database failed");
  } catch (err) {
    next(err);
  }
});

app.use((err, req, res, next) => {
  console.error(err);

  res.status(500).json({
    message: "Internal server error"
  });
});
Key rule: Error-handling middleware has four parameters: err, req, res, next. The four-argument signature tells Express this is error middleware.
Error→next(err)→Error Middleware→Error Response
11. Async Middleware
app.get("/profile", async (req, res, next) => {
  try {
    const user = await findUser();
    res.json(user);
  } catch (err) {
    next(err);
  }
});

Async middleware can perform asynchronous work. Errors must be propagated correctly to the error-handling layer.

Interview point: Do not assume every Express version and configuration handles rejected async handlers in exactly the same way. A portable pattern is to catch the error and call next(err), or use a tested async-wrapper strategy.
12. MAANG / FANG / MNC Code-Based Questions
Q1. What is the output order?
app.use((req, res, next) => {
  console.log("A");
  next();
});

app.use((req, res, next) => {
  console.log("B");
  next();
});

app.get("/", (req, res) => {
  console.log("C");
  res.send("OK");
});
Answer: A → B → C.
Why: Express runs matching middleware in registration order. Each middleware calls next(), so execution continues.
Q2. What happens if next() is removed?
app.use((req, res, next) => {
  console.log("Auth");
});

app.get("/", (req, res) => {
  res.send("Home");
});
Answer: The route handler does not execute and the request can remain pending.
Why: The middleware neither sends a response nor passes control with next().
Q3. What is the bug here?
app.use((req, res, next) => {
  if (!req.headers.authorization) {
    res.status(401).json({ message: "Unauthorized" });
  }
  next();
});
Answer: After sending the 401 response, the code still calls next(). This can allow later handlers to run and may lead to multiple-response errors.
Why: When middleware terminates the request with a response, it should normally return so execution does not continue.
Q4. Fix the authentication middleware.
function auth(req, res, next) {
  if (!req.headers.authorization) {
    res.status(401).json({ message: "Login required" });
  }
  next();
}
function auth(req, res, next) {
  if (!req.headers.authorization) {
    return res.status(401).json({
      message: "Login required"
    });
  }

  next();
}
Why: return stops the current middleware after the response is sent. Only authenticated requests reach next().
Q5. What does the error handler print?
app.get("/test", (req, res, next) => {
  next(new Error("Failed"));
});

app.use((err, req, res, next) => {
  console.log(err.message);
  res.status(500).send("Error");
});
Answer: Failed.
Why: Passing an error to next(err) switches Express into error-handling flow, so the four-argument error middleware is selected.
Q6. Will the normal middleware run after next(err)?
app.get("/x",
  (req, res, next) => {
    next(new Error("boom"));
  },
  (req, res, next) => {
    console.log("Normal");
    next();
  }
);

app.use((err, req, res, next) => {
  console.log("Error");
  res.status(500).end();
});
Answer: Only Error is printed. Normal is skipped.
Why: next(err) signals an error and skips regular handlers until Express finds error-handling middleware.
Q7. Which middleware handles GET /admin/users?
app.use("/admin", (req, res, next) => {
  console.log("Admin middleware");
  next();
});

app.get("/admin/users", (req, res) => {
  res.send("Users");
});
Answer: The /admin middleware runs first, followed by the /admin/users route.
Why: Path-mounted middleware matches requests whose path begins with its mount path and calls next() to continue.
Q8. What is the purpose of express.json()?
app.use(express.json());

app.post("/users", (req, res) => {
  console.log(req.body);
  res.json(req.body);
});
Answer: It parses incoming JSON request bodies so the parsed value can be accessed through req.body.
Why: HTTP request bodies arrive as data. The JSON parser converts a JSON payload into a JavaScript value for application code.
Q9. What is the difference between authentication and authorization middleware?
Answer: Authentication verifies identity. Authorization checks whether the authenticated identity has permission to perform the requested operation.
Why: A user can be successfully logged in but still lack permission to access an admin-only resource.
Q10. What is wrong with this error middleware?
app.use((err, req, res) => {
  console.log(err.message);
  res.status(500).send("Error");
});
Answer: The conventional Express error-handling signature has four parameters: err, req, res, next. The missing fourth parameter can prevent Express from recognizing the function as error-handling middleware.
Why: Express identifies error middleware by the four-argument function signature.
Q11. Where should a centralized 404 middleware usually be placed?
app.get("/users", usersHandler);

// 404 middleware
app.use((req, res) => {
  res.status(404).json({ message: "Not found" });
});


Answer: After all valid routes.



Why: Express moves through the registered stack in order. The fallback should run only after no valid route has handled the request.
Q12. Design a middleware chain for a protected API.

Requirements: log the request, authenticate the user, validate input, then execute the controller.

app.post(
  "/orders",
  logger,
  authenticate,
  validateOrder,
  createOrder
);
Why: Each middleware has one focused responsibility. Order matters: logging can happen first, identity must be known before permission-sensitive validation, and the controller runs only after checks pass.
Q13. What happens if middleware sends a response and then calls next()?
app.use((req, res, next) => {
  res.send("Done");
  next();
});


Answer: The response has already been completed, but later middleware may still execute. If later code tries to send another response, a headers-already-sent error can occur.



Why: Sending the response does not automatically make it safe to continue the application flow. When middleware terminates the request, stop execution with return.
Q14. What does router-level middleware mean?
const router = express.Router();

router.use(auth);

router.get("/profile", profileHandler);
router.get("/settings", settingsHandler);

app.use("/users", router);
Answer: auth applies to routes handled by this router, such as /users/profile and /users/settings.
Why: router.use() attaches middleware to a router instead of the entire application.
13. Common Developer Mistakes
1. Forgetting next(): The request can remain pending.
2. Calling next() after sending a response: Later code may try to send another response.
3. Wrong middleware order: A route may execute before required parsing, authentication, or validation.
4. Incorrect error signature: Error middleware should use (err, req, res, next).
5. Mixing authentication and authorization: Login success does not automatically mean permission is granted.
6. Doing too much in one middleware: Keep logging, authentication, validation, and business logic separate.
7. Leaking internal errors: Do not blindly send database stack traces or secrets to clients in production.
14. Quick Recap
  • Middleware runs between a request and a final response.
  • next() passes control forward.
  • Middleware can inspect or modify req and res.
  • Application middleware uses app.use().
  • Router middleware uses router.use().
  • express.json() is built-in middleware for JSON bodies.
  • Authentication verifies identity; authorization checks permissions.
  • Middleware order matters.
  • next(err) moves execution into error-handling flow.
  • Error middleware uses (err, req, res, next).
Golden interview answer: "Express middleware is a function in the request-response pipeline. It can perform common work such as logging, authentication, validation, or parsing, then either finish the response or call next() to continue the pipeline."
15. Interview-Ready Points
MAANG/MNC focus: Be ready to trace middleware execution from top to bottom and identify exactly where next() changes control flow.
Debugging question: If an API hangs, check whether a middleware forgot both to send a response and call next().
Senior-level question: Explain how centralized authentication, validation, logging, and error middleware reduce duplicated code and improve maintainability.
Code question strategy: Mark every middleware, identify whether it calls next(), sends a response, or calls next(err), then trace the execution path.
