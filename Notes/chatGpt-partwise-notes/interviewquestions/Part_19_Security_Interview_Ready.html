Node.js + Express.js Interview Preparation

Part 19 — Security ⭐⭐⭐

Understand the most important security risks and practical protections used in Node.js and Express.js applications.

Interview goal: Security is not one package or one middleware. A secure API uses several layers: safe input handling, authentication, authorization, secure headers, rate limits, safe secrets, HTTPS, secure cookies, and careful error handling.

1. What is Application Security?

What: Application security means protecting your application, users, data, APIs, and server from unauthorized access and malicious input.

Why: A working API can still be unsafe. For example, an API may correctly return data but expose itself to XSS, injection, brute-force attacks, or stolen secrets.

Layman example: A house needs more than a front door. It also needs locks, windows, an alarm, limits on who enters, and protection for important rooms. Web security works in a similar way.

2. CORS

What: CORS, or Cross-Origin Resource Sharing, is a browser security mechanism that controls which origins are allowed to access resources from another origin.

Why: A frontend at one origin may need to call an API at another origin. The server must explicitly allow the required origin.

const cors = require("cors");

app.use(cors({
  origin: "https://myfrontend.com",
  credentials: true
}));
Common mistake: Using origin: "*" together with credentialed browser requests is not a valid replacement for a carefully configured trusted origin.
Interview answer: CORS does not make the API itself private. It mainly controls whether browsers permit cross-origin frontend JavaScript to read responses. Non-browser clients are not controlled by browser CORS rules.
Why? The browser enforces the same-origin policy. CORS provides a controlled way for a server to declare which cross-origin browser requests are permitted.

3. CSRF

What: Cross-Site Request Forgery tricks a user's browser into sending an unwanted authenticated request to a site where the user is already logged in.

When important: CSRF is especially relevant when authentication is automatically attached by the browser, such as cookies.

Common protections: SameSite cookies, CSRF tokens where appropriate, checking request origin/referer where suitable, and avoiding unsafe state changes through GET requests.

4. XSS — Cross-Site Scripting

What: XSS happens when attacker-controlled content is treated as executable HTML or JavaScript in another user's browser.

Example risk: Rendering untrusted HTML directly into a page.

// Dangerous when userInput is not trusted:
element.innerHTML = userInput;
// Safer for plain text:
element.textContent = userInput;
Protection: Validate input, encode output for its context, avoid unsafe HTML injection, use a strong Content Security Policy where appropriate, and use framework protections correctly.

5. SQL Injection and NoSQL Injection

SQL Injection

Attacker-controlled input changes the meaning of a SQL query.

Use parameterized queries or prepared statements instead of building SQL by string concatenation.
NoSQL Injection

Unexpected objects or operators can change the meaning of a database query when application input is passed directly into a query.

Validate the expected type and shape of input. Do not blindly pass request objects into database filters.
// Good idea: validate the expected type first
const email = String(req.body.email || "").trim();

// Then use a controlled query shape.
// Example with a MongoDB/Mongoose model:
const user = await User.findOne({ email });

6. HTTP Security Headers and Helmet

What: HTTP security headers give browsers instructions that can reduce common web attack risks.

Helmet: Helmet is a popular Express middleware package that sets several security-related HTTP headers.

const helmet = require("helmet");

app.use(helmet());
Interview point: Helmet does not magically secure every part of an application. It is one security layer. You still need input validation, authentication, authorization, HTTPS, safe cookies, rate limiting, and other controls.

7. Rate Limiting and Brute-Force Protection

What: Rate limiting restricts how many requests a client can make in a period.

Why: It can reduce abuse, credential guessing, scraping, and accidental traffic spikes.

const rateLimit = require("express-rate-limit");

const loginLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  limit: 10,
  message: "Too many login attempts. Try again later."
});

app.post("/login", loginLimiter, loginHandler);
Production note: In a multi-server deployment, rate-limit state often needs a shared store such as Redis rather than only in-memory state.

8. Input Validation vs Input Sanitization

ConceptSimple meaningExample
ValidationChecks whether input is allowed and has the expected shape.Email must be a valid email; age must be a number.
SanitizationTransforms or cleans input according to the application's rules.Trim unwanted surrounding whitespace.
 
const email = String(req.body.email || "").trim();

if (!email.includes("@")) {
  return res.status(400).json({ message: "Invalid email" });
}
Common mistake: Sanitization is not a universal replacement for output encoding or validation. Security depends on the context in which data is used.

9. Password Security

  • Never store plain-text passwords.
  • Use a password hashing algorithm designed for passwords, such as bcrypt or Argon2.
  • Use a suitable cost/work factor.
  • Do not log passwords.
  • Do not put passwords in JWT payloads.
  • Use strong authentication policies appropriate to the application.
  • Consider MFA for sensitive accounts.
const hash = await bcrypt.hash(password, 12);

// During login:
const valid = await bcrypt.compare(password, hash);

10. JWT Security

JWTs are useful, but a signed JWT is not automatically encrypted or safe from theft.

Do:
  • Use strong secrets or appropriate keys.
  • Verify signature.
  • Validate expiration.
  • Use short-lived access tokens where appropriate.
  • Keep sensitive data out of payloads.
Do not:
  • Hard-code secrets.
  • Trust decoded payloads before verification.
  • Use unlimited token lifetime.
  • Put passwords in payloads.
  • Assume signing hides payload contents.

11. Secrets, .env and dotenv

What: Secrets include database passwords, JWT secrets, API keys, and private credentials.

Purpose: Keep environment-specific secrets outside source code and manage them securely.

// .env
JWT_SECRET=replace-with-a-strong-secret
DATABASE_URL=replace-with-a-secure-value
require("dotenv").config();

const secret = process.env.JWT_SECRET;
Important: Never commit a real .env file containing secrets to Git. Use secret management facilities in production deployments.

12. Secure Cookies

res.cookie("refreshToken", token, {
  httpOnly: true,
  secure: true,
  sameSite: "strict",
  maxAge: 7 * 24 * 60 * 60 * 1000
});
AttributePurpose
HttpOnlyJavaScript cannot read the cookie through document.cookie.
SecureCookie is sent over HTTPS connections.
SameSiteControls cross-site cookie sending and can help reduce CSRF risk.

13. HTTPS and Request Size Limits

HTTPS: Encrypts data in transit between the client and server and helps protect confidentiality and integrity.

app.use(express.json({
  limit: "100kb"
}));
Why request limits? A huge request body can consume server resources. Set limits based on what each endpoint actually needs.

14. Code-Based Interview Questions

Q1. What is wrong with this code?
const query = `SELECT * FROM users WHERE email = '${req.body.email}'`;
db.query(query);
The code directly inserts user input into a SQL query. It is vulnerable to SQL injection. Use parameterized queries or prepared statements.
An attacker can provide input that changes the SQL expression instead of being treated only as data.
Q2. What is the security problem?
app.get("/search", (req, res) => {
  res.send(`
${req.query.q}
`);
});
Untrusted input is being inserted into HTML without appropriate output handling. This can create an XSS vulnerability.
If the browser interprets attacker-controlled content as markup or script, the attacker's code may execute in the user's browser.
Q3. What is the purpose of this middleware?
app.use(helmet());
Helmet sets several security-related HTTP headers for Express applications.
Security headers give browsers additional instructions that can reduce some common web security risks.
Q4. What does this configuration protect against?
const limiter = rateLimit({
  windowMs: 60 * 1000,
  limit: 5
});

app.post("/login", limiter, login);
It limits the number of login requests from a client during the configured time window, helping reduce brute-force and abusive traffic.
Without limits, an attacker can send many password guesses quickly. Rate limiting makes repeated attempts harder and gives the application a chance to reject abusive traffic.
Q5. Is this JWT payload secret?
jwt.sign(
  { userId: 10, role: "admin" },
  process.env.JWT_SECRET
);
No. A normal signed JWT payload should be treated as readable. The signature protects integrity, not confidentiality.
JWT encoding is not the same as encryption. Anyone possessing the token can generally decode its payload.
Q6. Which cookie is safer for a refresh token?
res.cookie("refresh", token);

res.cookie("refresh", token, {
  httpOnly: true,
  secure: true,
  sameSite: "strict"
});
The second version has important security attributes enabled.
HttpOnly reduces JavaScript access, Secure requires HTTPS, and SameSite controls cross-site cookie behavior. Exact settings should match the application's architecture.
Q7. What is the problem?
const JWT_SECRET = "mysecret123";
The secret is hard-coded in source code. It should be supplied through a secure environment or secret-management system.
Source code can be copied, logged, committed to Git, or exposed to other developers and systems. Secrets should be managed separately.
Q8. What happens if an Express JSON body limit is too large?
app.use(express.json({ limit: "50mb" }));
The server accepts much larger JSON request bodies, which can increase memory and processing pressure if clients send unnecessarily large payloads.
Request parsing consumes resources. A limit helps prevent oversized requests from consuming excessive server capacity.

16. Common Developer Mistakes

  • Thinking CORS protects an API from every attacker.
  • Using origin: "*" without understanding credentials.
  • Building SQL queries with string concatenation.
  • Passing uncontrolled objects directly into NoSQL queries.
  • Rendering untrusted HTML.
  • Storing passwords in plain text.
  • Hard-coding JWT secrets or API keys.
  • Putting sensitive data in JWT payloads.
  • Not limiting login attempts.
  • Using cookies without understanding CSRF and SameSite.
  • Accepting very large request bodies unnecessarily.
  • Assuming one security package can secure the entire application.

17. Quick Recap

  • CORS: controls browser cross-origin access.
  • CSRF: unwanted authenticated requests, especially relevant to cookie-based auth.
  • XSS: attacker-controlled content executes in a user's browser.
  • SQL injection: attacker changes SQL query meaning.
  • NoSQL injection: unexpected query operators or shapes change database behavior.
  • Helmet: helps configure security-related headers.
  • Rate limiting: reduces repeated or abusive requests.
  • Validation: checks whether input matches expected rules.
  • Sanitization: cleans/transforms input according to rules.
  • HTTPS: protects data in transit.
  • Secure cookies: use appropriate HttpOnly, Secure and SameSite settings.
  • Request limits: reduce resource abuse from oversized bodies.

18. Interview-Ready Points

Be ready to explain
CORS vs CSRF, XSS, SQL vs NoSQL injection, JWT security, cookies, rate limiting, and input validation.

I also monitor and handle security failures safely.”
