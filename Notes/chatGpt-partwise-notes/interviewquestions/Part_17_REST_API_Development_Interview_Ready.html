Node.js + Express.js Interview Preparation

Part 17 — REST API Development

Interview-ready concepts, code questions, answers and “Why?” explanations.

Target: MAANG, FANG and strong MNC interviews • Simple English • Output/code focused

Interview goal: Do not only memorize HTTP methods. Be able to design a clean API, choose the correct method and status code, validate input, handle errors, and explain pagination, filtering, sorting and searching.
1. REST — What, Why and How?

What? REST (Representational State Transfer) is a set of design principles for building web APIs around resources.

Why? It gives clients and servers a simple, predictable way to communicate over HTTP.

Layman example: Think of a library. A book is a resource. You can list books, get one book, add a book, update it or remove it.

Client → HTTP Request → REST API → Business Logic → Database
Database → REST API → HTTP Response → Client

Good resource naming: /users, /users/42, /users/42/orders

Mistake: Avoid action-heavy URLs such as /getUsers or /deleteUser/42. Prefer the resource name and let the HTTP method describe the action.
2. HTTP Methods + CRUD
MethodTypical purposeExampleCommon success
GETRead resource(s)GET /users/42200
POSTCreate a resource / trigger a non-idempotent operationPOST /users201
PUTReplace a resource representationPUT /users/42200 / 204
PATCHPartially update a resourcePATCH /users/42200 / 204
DELETERemove a resourceDELETE /users/42204 / 200
Interview point: PUT is normally used as a replacement operation and is idempotent. PATCH is intended for partial changes and may or may not be idempotent depending on the operation design.
3. HTTP Status Codes You Must Know
  • 200 OK — successful request with a response body.
  • 201 Created — a new resource was created.
  • 204 No Content — successful request with no response body.
  • 400 Bad Request — invalid request data or malformed input.
  • 401 Unauthorized — authentication is missing or invalid.
  • 403 Forbidden — identity is known, but access is not allowed.
  • 404 Not Found — requested resource does not exist.
  • 409 Conflict — request conflicts with current resource state, such as a duplicate unique value.
  • 422 Unprocessable Content — syntactically valid request but validation/business rules fail.
  • 429 Too Many Requests — rate limit exceeded.
  • 500 Internal Server Error — unexpected server-side failure.
Common mistake: Do not return 200 for every failure and put “error” in the JSON. HTTP status codes are part of the API contract.
4. Request Headers, Body and JSON

Headers carry metadata such as authentication, content type and client information.

Authorization: Bearer <token>
Content-Type: application/json

Request body carries data sent to the server, commonly with POST, PUT and PATCH.

{
  "name": "Sam",
  "email": "sam@example.com"
}

Response body contains the result sent back to the client.

{
  "id": 42,
  "name": "Sam"
}
Security tip: Never trust client input. Authentication, authorization and validation must happen on the server.
5. REST Naming Rules
Good
/users
/users/42
/users/42/orders
/products?category=books
Avoid
/getUsers
/createUser
/deleteUser/42
/userData when the resource is users

Rule: Use nouns for resources; use HTTP methods for actions. Keep naming consistent and predictable.

6. CRUD API Example in Express
const express = require("express");
const app = express();

app.use(express.json());

app.get("/users", (req, res) => {
  res.status(200).json([{ id: 1, name: "Sam" }]);
});

app.post("/users", (req, res) => {
  const user = { id: 2, ...req.body };
  res.status(201).json(user);
});

app.patch("/users/:id", (req, res) => {
  res.status(200).json({ id: req.params.id, ...req.body });
});

app.delete("/users/:id", (req, res) => {
  res.status(204).end();
});

app.listen(3000);
Flow: Client → Route matching → Validation → Controller/service → Database → Response
7. Validation and API Errors

Validation checks whether incoming data follows the API rules before business logic or database work continues.

app.post("/users", (req, res) => {
  const { name, email } = req.body;

  if (!name || !email) {
    return res.status(400).json({
      error: "name and email are required"
    });
  }

  res.status(201).json({ name, email });
});

Why return after sending the error? It stops the handler from continuing and potentially sending another response.

Mistake: Validation is not only a frontend job. A user can call your API directly without using your UI.
8. Pagination, Filtering, Sorting and Searching

These are usually implemented with query parameters.

GET /products?page=2&limit=20
GET /products?category=phone
GET /products?sort=price
GET /products?search=iphone

Pagination: return a manageable portion instead of thousands of records.

const page = Math.max(Number(req.query.page) || 1, 1);
const limit = Math.min(Number(req.query.limit) || 20, 100);
const skip = (page - 1) * limit;
Interview tip: Always discuss a maximum page size. Otherwise a client could request an extremely large result set and hurt performance.
9. Code-Based Interview Questions
1 What status code should this endpoint normally return after creating a user? 
app.post("/users", (req, res) => {
  const user = createUser(req.body);
  res.json(user);
});
Answer: 201 Created is the normal choice. For example: res.status(201).json(user).
The request created a new resource. The status code communicates that fact clearly to the client.
2 What is wrong with this validation code? 
app.post("/users", (req, res) => {
  if (!req.body.email) {
    res.status(400).json({ error: "Email required" });
  }
  saveUser(req.body);
});
Answer: The handler continues after sending the error response. Use return res.status(400)... so saveUser() does not run.
Sending an HTTP response does not automatically stop your JavaScript function. Explicitly return from the handler.
3 What does this route represent? 
app.get("/users/:id", (req, res) => {
  console.log(req.params.id);
});
Answer: It is a dynamic route for one user. In /users/42, req.params.id is "42".
The :id part is a route parameter. It identifies a specific resource.
4 What will be returned for this request? 
GET /products?page=3&limit=10
Answer: The server can interpret it as page 3 with 10 records per page. The usual offset is (3 - 1) * 10 = 20.
The first two pages contain 20 records, so page 3 starts after those 20 records.
5 Is this a good REST URL? Why? 
POST /createUser
Answer: It works technically, but it is not a clean REST-style name. Prefer POST /users.
REST uses resource nouns in URLs and HTTP methods to describe the operation. POST already means create/submit in this design.
6 What is the difference between PUT and PATCH in an API? 
PUT   /users/10
PATCH /users/10
Answer: PUT normally represents replacement of the resource. PATCH represents a partial update.
The distinction helps clients communicate whether they are replacing the representation or changing only selected fields.
7 Which status should usually be returned here when the user does not exist? 
app.get("/users/:id", async (req, res) => {
  const user = await findUser(req.params.id);

  if (!user) {
    // ???
  }
});
Answer: 404 Not Found.
The endpoint was valid, but the requested resource could not be found.
8 Find the bug in this pagination code. 
const page = Number(req.query.page);
const limit = Number(req.query.limit);
const skip = page * limit;
Answer: For 1-based pages, skip should normally be (page - 1) * limit. Also validate and cap the inputs.
With page 1 and limit 10, the current code skips 10 records and incorrectly starts at page 2.
9 What is the difference between authentication and authorization in an API? 
Authorization: Bearer eyJ...
Answer: Authentication asks “Who are you?” Authorization asks “Are you allowed to do this?”
A valid token can identify a user, but that does not automatically give the user permission to access every resource.
10 What is the main problem with returning every database record from this endpoint? 
app.get("/products", async (req, res) => {
  const products = await Product.find();
  res.json(products);
});
Answer: It can return a huge amount of data, increasing database work, memory use, response time and network traffic. Add pagination and allow controlled filtering.
Large result sets do not scale well. APIs should control result size and avoid unnecessary data transfer.
11 Which URL is better for filtering products by category? 
A) GET /products/category/phones
B) GET /products?category=phones
Answer: For a filter, B is usually cleaner: /products?category=phones.
The resource remains products; the query parameter changes which products are returned.
12 What should happen when a client sends invalid JSON or invalid input? 
POST /users
Content-Type: application/json

{ "email": "" }
Answer: Validate the request and return a suitable 4xx response, commonly 400 or 422 depending on the API contract.
The client sent data that cannot be accepted. A 4xx response tells the client the problem is with the request rather than an unexpected server failure.
10. Common Developer Mistakes
  • Using verbs in every REST URL instead of resource nouns.
  • Returning 200 for validation, authentication or not-found errors.
  • Trusting client input without server-side validation.
  • Returning all database rows without pagination.
  • Allowing unlimited limit values.
  • Confusing 401 with 403.
  • Using PUT when only a few fields need to be changed without understanding replacement semantics.
  • Putting sensitive information into URLs because URLs may appear in logs and browser history.
  • Not defining a consistent error response format.
11. Interview-Ready Quick Recap
REST: Design APIs around resources and standard HTTP behavior.
  • GET = read
  • POST = create/submit
  • PUT = replace
  • PATCH = partial update
  • DELETE = remove
  • Use correct HTTP status codes.
  • Headers carry metadata; body carries request/response data.
  • Use query parameters for filtering, sorting, searching and pagination.
  • Validate all client input on the server.
  • Keep API errors consistent and useful.
Golden interview answer: “A good REST API models resources with predictable URLs, uses HTTP methods according to their meaning, returns correct status codes, validates input, handles errors consistently, and supports scalable access patterns such as pagination, filtering, sorting and searching.”
