NODE.JS + EXPRESS INTERVIEW PREPARATION

Part 28 — Testing Node.js + Express

Interview-ready notes, diagrams, and code/output questions for MAANG, product companies, and MNC interviews.

1. What is Testing?

What: Testing checks whether application code behaves as expected.

Why: Tests catch bugs early, protect existing behavior, and make refactoring safer.

Layman example: Before selling a car, you check the brakes, lights, engine, and steering. Software tests do similar checks for code.

Code → Test → Expected result = Pass
Code → Test → Unexpected result = Fail
Interview line: Good tests should be repeatable, isolated, focused, and clear about the behavior they verify.
2. Unit vs Integration vs API Testing
TypeWhat it testsExample
UnitOne small unit in isolationPassword validation function
IntegrationSeveral parts working togetherService + repository + test DB
APIHTTP behavior of an endpointPOST /users returns 201
Interview tip: Unit tests are usually fast and isolated. Integration tests verify collaboration. API tests verify behavior through the HTTP boundary.
3. Jest, Node Test Runner, and Supertest

Jest: Popular JavaScript testing framework with assertions, mocking, spies, setup/teardown, and coverage support.

Node test runner: Node provides a built-in runner through node:test.

Supertest: Commonly used to test HTTP servers and Express applications.

import request from "supertest"; import app from "./app.js"; const response = await request(app).get("/users"); console.log(response.status);
Important: Keep the Express app separate from the file that calls listen(). Tests can then import the app without starting a production server.
4. Test Structure and Lifecycle
Arrange → Act → Assert
  • Arrange: Prepare input, mocks, fixtures, and state.
  • Act: Call the function or API.
  • Assert: Check the result.
beforeAll → beforeEach → test → afterEach → afterAll

Why: Lifecycle hooks prepare and clean state so tests do not depend on execution order.

5. Mocking and Spies

Mock: Replaces a dependency with controlled behavior.

Spy: Observes whether a function was called and can be configured depending on the framework.

const emailService = { send: () => Promise.resolve(true) }; // Unit test can replace or spy on send() // so no real email is sent.
Interview point: Mock external dependencies when the unit test should focus on the unit rather than a database, email server, payment service, or network.
6. Test Fixtures and Test Database

Fixture: Known test data used to make a test predictable.

Test database: Separate database environment for tests.

Test starts → Create isolated data → Run test → Verify → Clean data
Never: Point automated tests at a production database.
7. Authentication and Error Testing

Test both successful and unsuccessful access.

GET /profile + valid token → 200 OK GET /profile + missing token → 401 Unauthorized GET /admin + valid user token → 403 Forbidden

Error testing: Verify status code, safe response format, and important failure behavior. Production responses should not expose stack traces or secrets.

8. Middleware, Controller, and Service Testing
Request → Middleware → Controller → Service → Repository / DB → Response
  • Middleware test: Authentication, validation, logging, and next() behavior.
  • Controller test: HTTP input, service call, and response.
  • Service test: Business rules without requiring HTTP.
Best practice: Keep business logic in services rather than putting large amounts of logic inside route handlers.
9. Async Testing
test("returns user", async () => { const user = await getUser(10); expect(user.id).toBe(10); });
Common mistake: Forgetting to await or return a Promise can make a test finish before the assertion runs.
10. Code / Output Interview Questions
Q1. What type of test is this?
function add(a, b) { return a + b; } test("adds numbers", () => { expect(add(2, 3)).toBe(5); });
Answer: A unit test.
Why: It tests one small function directly without HTTP, a database, or another external dependency.
Q2. What status code should this successful create API normally return?
const response = await request(app) .post("/users") .send({ name: "Sam" }); console.log(response.status);
Answer: Commonly 201 Created when a new resource is successfully created.
Why: HTTP 201 communicates that the request successfully created a resource. The API contract should define the exact response.
Q3. What is the problem with this async test?
test("loads user", () => { getUser().then(user => { expect(user.name).toBe("Sam"); }); });
Answer: The test does not return or await the Promise.
Why: The test can finish before the Promise callback runs. Use async/await or return the Promise.
Q4. What should the test verify for this protected route?
const response = await request(app).get("/profile"); console.log(response.status);
Answer: A request without valid authentication should normally be rejected with 401 Unauthorized.
Why: A protected endpoint should not allow an unauthenticated caller to access protected resources.
Q5. What is the difference between mocking and integration testing here?
service.createUser = jest.fn() .mockResolvedValue({ id: 1, name: "Sam" });
Answer: This replaces a dependency with controlled behavior, typical of an isolated unit test.
Why: The test does not need the real dependency. Integration testing verifies real component interaction.
Q6. What is the likely test isolation problem?
let user; test("creates user", async () => { user = await createUser("Sam"); }); test("updates user", async () => { await updateUser(user.id); });
Answer: The second test depends on state created by the first test.
Why: Tests should be independently runnable. If the first test fails, the second can fail for the wrong reason.
Q7. What should you test when an Express controller calls a service that rejects?
try { const user = await userService.findById(req.params.id); res.json(user); } catch (err) { next(err); }
Answer: Test that the error reaches the error handler and the API returns the expected safe HTTP error response.
Why: Error paths are part of application behavior. Testing only success cases leaves important failures unverified.
Q8. What does this test mainly verify?
const response = await request(app) .get("/users?page=2&limit=10"); expect(response.status).toBe(200); expect(response.body.items).toHaveLength(10);
Answer: API/integration-style testing of HTTP behavior and pagination output.
Why: The test enters through the HTTP boundary and checks status and response body.
Q9. What is the purpose of a test fixture?
const userFixture = { name: "Test User", email: "test@example.com" };
Answer: It provides predictable test data.
Why: Known input makes tests repeatable and easier to understand.
Q10. What does test coverage tell you?
Statements: 90% Branches: 80% Functions: 95% Lines: 91%
Answer: Coverage measures which instrumented code areas were executed by the test suite.
Why: High coverage can reveal untested areas, but coverage percentage alone does not prove tests are meaningful or correct.
11. Common Developer Mistakes
Mistake 1: Testing only success cases.
Correct: Test validation, authentication, authorization, database failures, and unexpected errors.
Mistake 2: Forgetting await in async tests.
Correct: Make the test wait for the Promise.
Mistake 3: Sharing mutable state between tests.
Correct: Create and clean test data per test or use controlled fixtures.
Mistake 4: Using a production database.
Correct: Use an isolated test database/environment.
Mistake 5: Mocking everything.
Correct: Mock for isolation, but keep integration/API tests to verify real component interaction.
Mistake 6: Chasing coverage percentage only.
Correct: Test important behavior, edge cases, and failure paths.
12. Interview Testing Strategy
Unit tests → Fast feedback
Integration tests → Component collaboration
API tests → HTTP contract
End-to-end tests → Full user flow
  • Keep unit tests focused.
  • Mock external systems when isolation is the goal.
  • Use a separate test database for database integration tests.
  • Test success and failure paths.
  • Keep tests independent.
  • Test asynchronous behavior correctly.
  • Use coverage to find gaps, not as the only quality metric.
13. Quick Recap — Interview Ready
  • Unit: one unit in isolation.
  • Integration: multiple components working together.
  • API testing: verify HTTP request/response behavior.
  • Jest: popular testing framework.
  • node:test: Node.js built-in test runner.
  • Supertest: useful for Express HTTP/API testing.
  • Mock: replaces a dependency with controlled behavior.
  • Spy: observes calls and can be configured.
  • Fixture: predictable test data.
  • Isolation: one test should not depend on another test's state.
  • Async tests: await or return Promises.
  • Coverage: shows executed code areas; it does not guarantee quality.
30-second interview answer: “In Node.js and Express, I separate unit, integration, and API tests. Unit tests isolate functions and mock external dependencies. Integration tests verify multiple components together, while Supertest can verify Express HTTP behavior. I keep tests isolated with controlled fixtures and a separate test database, test success and error paths, correctly await asynchronous operations, and use coverage to identify gaps rather than treating coverage percentage as proof of quality.”
