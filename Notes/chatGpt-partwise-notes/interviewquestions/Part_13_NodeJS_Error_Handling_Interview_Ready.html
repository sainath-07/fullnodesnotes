Part 13 — Error Handling in Node.js ⭐⭐⭐

Learn how to detect, handle, propagate, log and safely recover from errors in Node.js applications.

1. What is Error Handling?

What: Error handling is the process of detecting a problem, deciding what to do about it, and preventing one failure from unnecessarily crashing or corrupting the application.

Why: Real applications can fail because of invalid input, missing files, unavailable databases, network problems, programming mistakes and many other reasons.

Layman example: If a delivery driver cannot reach an address, a good system does not simply disappear. It reports the problem, chooses a safe next step and records what happened.

Q1 — What is the main purpose of error handling?

Answer: To detect failures, handle expected problems safely, give useful information, and keep the application in a known safe state.

Q2 — Does error handling mean every error must be ignored?

Answer: No. Some errors should be handled and recovered from. Some programmer errors indicate a broken program and should be fixed. Some serious process-level failures may require a controlled shutdown.
2. try, catch and finally
try { const result = JSON.parse('{"name":"Sam"}'); console.log(result.name); } catch (error) { console.error("Invalid JSON:", error.message); } finally { console.log("Cleanup completed"); }

try: Contains code that may throw.

catch: Receives an error thrown inside the matching try block.

finally: Runs after try/catch whether an exception occurred or not, unless control leaves the process in an unusual way such as termination.

Q3 — What happens if JSON.parse() throws?

Answer: Control moves from the throwing statement to the catch block. After that, the finally block runs.

Q4 — Is finally useful even when there is no error?

Answer: Yes. It is commonly used for cleanup, such as closing a resource, resetting a state, or hiding a loading indicator.
3. throw and the Error Object
function withdraw(balance, amount) { if (amount > balance) { throw new Error("Insufficient balance"); } return balance - amount; } try { console.log(withdraw(100, 150)); } catch (error) { console.log(error.message); }

throw: Immediately signals an exception. The thrown value should normally be an Error object or an appropriate Error subclass.

Q5 — What is the difference between throw and return?

Answer: return normally sends a value back to the caller. throw interrupts normal control flow and searches for a matching error handler.

Q6 — Why prefer new Error("message") instead of throwing a string?

Answer: Error objects provide standard information such as name, message and usually a stack, which makes debugging and logging more useful.

Q7 — Predict the error type

const user = null; console.log(user.name);
Answer: TypeError, because the code attempts to access a property on null.

Q8 — Predict the error type

console.log(totalAmount);
Answer: Usually ReferenceError if totalAmount has not been declared in the accessible scope.
5. Custom Errors
class ValidationError extends Error { constructor(message, field) { super(message); this.name = "ValidationError"; this.field = field; } } function createUser(email) { if (!email.includes("@")) { throw new ValidationError("Invalid email", "email"); } return { email }; } try { createUser("hello"); } catch (error) { console.log(error.name); console.log(error.field); }

Q9 — Why create a custom error class?

Answer: It lets the application distinguish different business or application error categories and attach useful structured information.

Q10 — What should a custom Error class preserve?

Answer: It should normally extend Error, call super(message), and may add properties such as an error code, field, HTTP status or operational flag.
6. Error-First Callbacks
const fs = require("node:fs"); fs.readFile("data.txt", "utf8", (err, data) => { if (err) { console.error(err); return; } console.log(data); });

Q11 — Why is err checked before data?

Answer: In Node.js error-first callbacks, the first argument represents an error. If it exists, the operation failed and the success result should not be used as if it were valid.

Q12 — What common mistake can cause duplicate work?

fs.readFile("data.txt", (err, data) => { if (err) { console.log(err); } save(data); // dangerous });
Answer: After handling the error, execution continues unless you return or otherwise stop it. save(data) could therefore receive invalid or missing data. A common pattern is if (err) return callback(err).
7. Promise Errors
Promise.reject(new Error("Database failed")) .then(() => { console.log("success"); }) .catch(error => { console.log("caught:", error.message); });

Q13 — Where does a rejected Promise go if there is no handler on the same step?

Answer: Rejection propagates through the Promise chain until a rejection handler such as catch() handles it.

Q14 — What is wrong with this pattern?

doSomething() .then(result => { throw new Error("failed"); }) .then(() => { console.log("success"); });
Answer: The thrown error rejects the Promise returned by the first then(). Because there is no rejection handler shown, the rejection can become unhandled. Add a suitable catch() at the end or at an appropriate boundary.
8. async/await Errors ⭐⭐⭐
async function loadUser() { try { const user = await getUser(); return user; } catch (error) { console.error("Unable to load user:", error); throw error; } }

Q15 — Why rethrow an error after logging it?

Answer: If the current layer cannot fully handle the failure, rethrowing preserves error propagation so a higher layer can decide what response or recovery is appropriate.

Q16 — What happens when an async function throws?

Answer: The async function returns a rejected Promise. The caller can handle it with await ... try/catch or .catch().
9. Unhandled Promise Rejection
async function start() { throw new Error("Startup failed"); } start();

Q17 — Why is this dangerous?

Answer: The returned rejected Promise is not handled. Depending on Node.js behavior and application setup, this can produce an unhandled rejection and may terminate the process. Production code should handle expected async failures explicitly.

Q18 — Better version

start().catch(error => { console.error("Startup failed:", error); });
Answer: The rejection is explicitly handled at the call site.
10. uncaughtException ⭐⭐⭐⭐⭐
process.on("uncaughtException", (error) => { console.error("Uncaught:", error); });

Q19 — Should uncaughtException be used as normal application error handling?

Answer: No. It is a last-resort process-level mechanism. An uncaught exception means the application reached an unexpected state. The safer production strategy is usually to log enough information, stop accepting new work, perform limited cleanup, and restart the process using a process manager/container platform.

Q20 — Why is continuing after an uncaught exception risky?

Answer: The program's state may be corrupted or inconsistent. Continuing can cause incorrect data, repeated failures or security problems. The process should generally be treated as unhealthy.

Q21 — Should every function catch every error?

Answer: No. Catch an error where you can meaningfully handle or transform it. Otherwise, propagate it to a layer that knows how to handle it.

Q22 — What is a common error-propagation mistake?

Answer: Catching an error, logging it, and then silently returning a fake success value. This hides the failure from higher layers and can produce incorrect application behavior.
12. Operational Errors vs Programmer Errors ⭐⭐⭐
TypeMeaningExamplesTypical response
Operational errorExpected failure that can happen during normal operation.Database unavailable, file missing, invalid user input, request timeout.Handle, report useful status, retry when appropriate, or degrade safely.
Programmer errorBug in application logic or invalid assumptions.Accessing a property on an unexpected null, broken invariant, coding mistake.Fix the code; serious unexpected failures may justify restarting the process.

Q23 — Is "database unavailable" always a programmer error?

Answer: Usually it is treated as an operational failure because external systems can temporarily be unavailable. The application should handle it deliberately, possibly with timeout/retry/fallback behavior where appropriate.

Q24 — Why should the distinction matter?

Answer: It helps decide whether recovery is sensible or whether the process is in an unsafe state and should be restarted.
13. Centralized Error Handling in Express
app.get("/users/:id", async (req, res, next) => { try { const user = await getUser(req.params.id); res.json(user); } catch (error) { next(error); } }); // Error-handling middleware: 4 parameters app.use((err, req, res, next) => { console.error(err); res.status(err.statusCode || 500).json({ message: err.isOperational ? err.message : "Internal server error" }); });

Q25 — Why is centralized error handling useful?

Answer: It gives the application one consistent place to log errors and format HTTP error responses instead of duplicating the same response logic in every route.

Q26 — How do you identify Express error-handling middleware?

Answer: It has four parameters: (err, req, res, next). The four-argument signature tells Express that this middleware handles errors.
14. Graceful Shutdown ⭐⭐⭐⭐⭐
const server = app.listen(3000); function shutdown(signal) { console.log(`${signal} received`); server.close(() => { console.log("HTTP server closed"); process.exit(0); }); } process.on("SIGTERM", () => shutdown("SIGTERM")); process.on("SIGINT", () => shutdown("SIGINT"));

Q27 — What is graceful shutdown?

Answer: It is a controlled shutdown in which the application stops accepting new work and gives existing work and resources a chance to finish or close cleanly.

Q28 — Why is graceful shutdown important in production?

Answer: It reduces dropped requests, unfinished work and resource leaks during deployments, container termination or process restarts.
15. Output-Based Interview Question ⭐⭐⭐⭐⭐

Q29 — What happens?

async function test() { try { await Promise.reject(new Error("A")); console.log("B"); } catch (error) { console.log(error.message); } finally { console.log("C"); } } test(); console.log("D");
Answer: Output order is D → A → C.

Why: Calling test() starts synchronously, but the rejected Promise resumes the async function later. The outer synchronous console.log("D") runs first. Then catch prints A and finally prints C. B is skipped because the await rejected.

Q30 — Find the bug

async function saveUser(user) { try { await database.save(user); } catch (error) { console.error(error); } return { success: true }; }
Answer: The function reports success even when the database operation fails. If the function cannot recover, it should rethrow/reject or return an explicit failure result instead of hiding the error.
16. Common Developer Mistakes
  • Using try/catch around asynchronous code without actually awaiting or otherwise handling the asynchronous failure.
  • Forgetting return after handling an error in an error-first callback.
  • Creating a Promise rejection without attaching a handler.
  • Catching an error and silently ignoring it.
  • Logging an error and incorrectly returning a successful result.
  • Sending more than one HTTP response after an error.
  • Exposing internal stack traces or database details to API clients in production.
  • Using uncaughtException as the normal application error handler.
  • Retrying every error blindly, including programmer errors or non-retryable validation errors.
  • Shutting down immediately without closing servers and important resources.

Golden interview answer: “In Node.js, I separate expected operational failures from programmer bugs. I handle synchronous exceptions with try/catch, Promise failures with catch or async/await try/catch, and use centralized error handling at the application boundary. I avoid hiding errors and avoid using uncaughtException as normal control flow. For serious unexpected process failures, I log the problem, perform limited cleanup and use graceful shutdown so the process can be restarted safely.”
18. Interview Tips
  • Be ready to explain the difference between operational and programmer errors.
  • Know why uncaughtException is a last-resort mechanism.
  • Explain how a rejected Promise moves through a Promise chain.
  • Know why try/catch works with await.
  • Know the error-first callback convention.
  • Explain why centralized Express error handling is useful.
  • Know what graceful shutdown means and why deployments need it.
  • In output questions, identify synchronous code first, then asynchronous continuation.
