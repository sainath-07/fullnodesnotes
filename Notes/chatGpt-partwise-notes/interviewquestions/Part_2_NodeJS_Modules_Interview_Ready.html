Part 2 — Node.js Modules ⭐⭐⭐

Learn how Node loads, executes, caches and shares code.

1. What is a Module?

What: A module is a separate unit of code that can contain variables, functions, classes or other logic.

Why / purpose: Modules keep large applications organized. They make code easier to test, reuse and maintain.

Layman example: Think of a toolbox. Each tool has a separate purpose. You take only the tool you need.

main.js → loads module → module executes → exported value is received → main.js uses it
Interview point: Modules provide boundaries between pieces of code and let one file expose selected functionality to another.

Q1 — Identify the module type

const fs = require("fs"); const math = require("./math"); const express = require("express");
Answer: fs is built-in, ./math is local, and express is third-party.
Why? Built-in modules come with Node, paths beginning with ./ or ../ point to local modules, and package names normally resolve through installed dependencies.
3. CommonJS — require() and module.exports

CommonJS is Node's traditional module system. It commonly uses require() to load a module and module.exports to expose a value.

// math.js function add(a,b){ return a+b; } module.exports = add; // app.js const add = require("./math"); console.log(add(2,3));

Q2 — What is printed?

5
Why? module.exports exposes the add function. require() receives that exported function.

Q3 — What does require() conceptually do?

Answer: It resolves the module, loads it if needed, executes it, gets its exports and returns the exported value. Loaded CommonJS modules are cached.
4. module.exports vs exports

exports starts as a reference to module.exports. Adding properties through exports.x works, but assigning a new value to exports does not replace what the module exports.

Q4 — Tricky output

// test.js exports.a = 10; exports = { b: 20 }; // app.js const value = require("./test"); console.log(value);
{ a: 10 }
Why? Reassigning exports only changes the local variable. It does not replace module.exports.

Q5 — Fix the mistake

exports = function greet(){ return "hello"; };
module.exports = function greet(){ return "hello"; };
Why? Reassign module.exports when exporting a complete function, class or other single value.
5. Module Loading, Execution and Caching

A CommonJS module normally executes when it is first loaded. Node then stores its exports in the module cache. Later require() calls can reuse the cached module.

require("./counter") → resolve → load → execute once → cache exports → reuse cached exports

Q6 — Predict the output

// counter.js console.log("counter module executed"); module.exports = { value: 1 }; // app.js const a = require("./counter"); const b = require("./counter"); console.log(a === b);
counter module executed true
Why? The first require() executes and caches the module. The second gets the cached export. Both variables refer to the same exported object.
6. require.cache

require.cache contains cached CommonJS modules for the current process. It can be inspected and, carefully, manipulated.

Q7 — What does this do?

const path = require.resolve("./counter"); delete require.cache[path]; const again = require("./counter");
Answer: It removes the resolved module from the CommonJS cache, so the next require() loads and executes it again.
Why? Without the cache entry, Node does not reuse the previous cached module instance.
Interview warning: Do not use cache deletion as a normal application design. It can create confusing state and side effects.
7. Circular Dependencies

A circular dependency happens when module A loads B while B directly or indirectly loads A.

A → require(B) → B → require(A) → A again

CommonJS can expose partially initialized exports during a cycle. This can produce surprising undefined values.

Q8 — Why can this be surprising?

// a.js exports.name = "A"; const b = require("./b"); console.log("A sees:", b.name); // b.js const a = require("./a"); exports.name = a.name;
Answer: The exact result depends on initialization order. During a cycle, one module can receive an incomplete export object.
Why? CommonJS may return the currently available cached module exports before that module has finished executing.
Best practice: Break large circular dependencies by extracting shared logic into a third module.
8. ES Modules — import and export

ES Modules (ESM) are JavaScript's standard module system. Node supports ESM with .mjs or with "type":"module" in package.json.

// math.js export function add(a,b){ return a+b; } export const version = 1; // app.js import { add, version } from "./math.js"; console.log(add(2,3), version);

Q9 — Output

5 1
Why? The named exports add and version are imported by their names.
9. Named Export vs Default Export
// named export const add = (a,b) => a+b; // default export default function multiply(a,b){ return a*b; }

Named import: import { add } from "./math.js"

Default import: import multiply from "./math.js"

Q10 — Is this valid?

export default function test(){} export default function another(){}
Answer: No. A module can have only one default export.
Why? The default export represents the module's single default value. It can have many named exports.
10. .mjs and "type": "module"

Node can identify ESM using the .mjs extension. A package can also use "type":"module" so its .js files are treated as ESM.

Q11 — Which statement is correct?

  • file.mjs → ESM
  • package.json with "type":"module" → .js files in that package scope are ESM
  • CommonJS commonly uses .cjs when an explicit CommonJS extension is useful in a module package
Interview answer: .mjs explicitly marks an ES module; "type":"module" changes the interpretation of .js files within the package scope.

Q12 — Spot the module-system issue

// package.json { "type": "module" } // app.js const fs = require("fs");
Answer: In a normal ESM file, require is not available as the CommonJS loader.
Why? "type":"module" makes app.js an ES module. Use import fs from "node:fs" / appropriate ESM syntax, or intentionally use a CommonJS file such as .cjs.
12. Interoperability

Interoperability means CommonJS and ESM code can work together, but the rules are not identical in both directions.

CommonJS ↔ ESM
Supported paths exist, but module format, package type, exports and import rules matter.

Q13 — Conceptual interview question

Can you always replace require() with import by changing one word?

Answer: No.
Why? Module format, file extension, package configuration, export shape, resolution rules and whether the dependency is CommonJS or ESM can affect the result.

Q14 — Dynamic import

async function load(){ const mod = await import("./math.js"); console.log(mod.add(2,3)); } load();
5
Why? import() returns a Promise for the module namespace object. The named export is accessed as mod.add.
13. Interview-Level Code Questions

Q15 — Same object or different object?

// user.js module.exports = { count: 0 }; // app.js const a = require("./user"); const b = require("./user"); a.count++; console.log(b.count);
1
Why? Both require() calls receive the same cached exported object for that module instance.

Q16 — Export reassignment

// test.js exports.name = "Sainath"; module.exports = { name: "Node" }; // app.js const x = require("./test"); console.log(x.name);
Node
Why? The final value assigned to module.exports is what require() returns. The earlier property added through exports is no longer the exported object.

Q17 — What does this export?

// test.js module.exports.a = 10; module.exports.b = 20; // app.js const { a, b } = require("./test"); console.log(a + b);
30
Why? The module exports an object with properties a and b, which are destructured in app.js.

Q18 — Module executes how many times?

// logger.js console.log("loaded"); module.exports = {}; // app.js require("./logger"); require("./logger"); require("./logger");
loaded
Why? CommonJS caches the module after its first load, so later require() calls reuse the cached module.
14. Common Developer Mistakes
  • Confusing exports with module.exports after reassigning one of them.
  • Assuming every require() executes the module again.
  • Forgetting CommonJS caching when a module contains mutable state.
  • Creating circular dependencies without understanding initialization order.
  • Mixing ESM and CommonJS syntax without checking package configuration.
  • Assuming "type":"module" affects only one file instead of the package scope.
  • Assuming named and default exports are interchangeable.
  • Thinking dynamic import() returns the module synchronously.

16. Quick Recap — Interview Ready
  • Module: A reusable unit of code with a clear boundary.
  • Built-in: Comes with Node.js.
  • Local: Your own module.
  • Third-party: Installed dependency such as Express.
  • CommonJS: require() + module.exports.
  • exports: Initially points to module.exports; reassigning it does not replace the exported value.
  • Cache: CommonJS modules are cached after loading.
  • Circular dependency: A module dependency cycle that can expose partially initialized exports.
  • ESM: import + export.
  • ESM activation: .mjs or "type":"module".
  • Named export: Many are allowed and imported by name.
  • Default export: One default value per module.
  • Dynamic import: import() returns a Promise and loads a module asynchronously.
  • Interoperability: CJS and ESM can interact, but resolution and export rules must be respected.
Top interview tip: If asked “What happens when require() is called?”, explain the sequence: resolve → load → wrap/execute → cache → return exports. Then mention that a later require normally uses the cache.
Golden interview line: “CommonJS uses require and module.exports, and Node caches a module after its first execution. ES Modules use import/export and follow standard JavaScript module semantics. Mixing the two requires understanding Node's module-resolution and interoperability rules.”
