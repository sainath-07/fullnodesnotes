Part 23 — Database Integration

MongoDB, Mongoose, SQL, connection lifecycle, async database work, errors, transactions and connection pooling.

Interview goal: Do not only memorize database methods. Be ready to explain how a request reaches the database, how connections are managed, how errors are handled, and when transactions or pooling are needed.
1. What is Database Integration?

What: Database integration means connecting a Node.js/Express application to a database so the application can store, read, update and delete data.

Why: Application memory is temporary. A database provides persistent storage.

Layman example: Express is the waiter, your business logic is the kitchen, and the database is the storage room containing customer and product information.

Client → Express Route → Controller/Service → DB Driver / Mongoose → Database → Response
Interview line: “A database integration layer manages database connections and translates application operations into database queries while handling asynchronous results and errors.”
2. MongoDB + Mongoose
MongoDB

MongoDB is a document database. Data is commonly stored as BSON documents inside collections.

Mongoose

Mongoose is an ODM (Object Data Modeling) library for MongoDB. It provides schemas, models, validation, middleware and convenient query APIs.

MongoDB
Database → Collections → Documents
Mongoose
Schema → Model → Query → MongoDB
Connection
const mongoose = require("mongoose");

async function connectDB() {
  await mongoose.connect(process.env.MONGO_URI);
  console.log("MongoDB connected");
}

Important: In production, keep the connection string in an environment variable and do not hard-code secrets.

3. Schema, Model, CRUD, Validation & Middleware
const userSchema = new mongoose.Schema({
  name: { type: String, required: true, trim: true },
  email: { type: String, required: true, unique: true }
}, { timestamps: true });

const User = mongoose.model("User", userSchema);

// Create
const user = await User.create({ name: "Sam", email: "sam@example.com" });

// Read
const users = await User.find({});

// Update
await User.findByIdAndUpdate(id, { name: "Alex" }, { new: true });

// Delete
await User.findByIdAndDelete(id);

Schema: Describes the expected document shape and rules.

Model: The object used to interact with a MongoDB collection.

Validation: Checks whether data satisfies defined rules.

Middleware: Code that runs before or after certain Mongoose operations, depending on the hook.

Common trap: unique: true is not a normal validation rule. It is commonly used to create a unique index; duplicate writes can still result in a database error.
4. References & Population

MongoDB can store references between documents. Mongoose populate() can replace referenced IDs with related documents.

const orderSchema = new mongoose.Schema({
  user: {
    type: mongoose.Schema.Types.ObjectId,
    ref: "User"
  }
});

const orders = await Order.find().populate("user");

Think: An order stores the user's ID. populate() asks Mongoose to fetch the related user document.

Interview point: Population is convenient, but fetching large related datasets can be expensive. Select only the fields you need and consider query design and indexes.
5. SQL: MySQL / PostgreSQL

SQL databases store structured data in tables and provide strong relational features such as joins and transactions.

const mysql = require("mysql2/promise");

const pool = mysql.createPool({
  host: process.env.DB_HOST,
  user: process.env.DB_USER,
  password: process.env.DB_PASSWORD,
  database: process.env.DB_NAME,
  connectionLimit: 10
});

const [rows] = await pool.execute(
  "SELECT * FROM users WHERE email = ?",
  [email]
);
Security rule: Never build SQL using user input through string concatenation. Use parameterized queries or prepared statements.
6. Connection Lifecycle
Application starts → Create DB connection/pool → Handle requests → Reuse connections → Graceful shutdown

Recommended idea: Create a shared database connection or connection pool rather than opening a brand-new database connection for every HTTP request.

On shutdown, stop accepting new work and close the database resources cleanly.

7. Connection Pooling

A connection pool keeps a controlled number of database connections available for reuse.

Request ARequest BRequest C
↓ ↓ ↓
Connection Pool → Database

Why: Creating a database connection has a cost. Reusing connections improves performance and prevents the application from opening unlimited connections.

Interview line: “A connection pool maintains reusable database connections and limits concurrency so many application requests can share a controlled set of connections.”
8. Transactions

A transaction groups multiple database operations into one logical unit. The goal is usually: either all required changes succeed, or the changes are rolled back.

const connection = await pool.getConnection();

try {
  await connection.beginTransaction();

  await connection.execute(
    "UPDATE accounts SET balance = balance - ? WHERE id = ?",
    [100, fromId]
  );

  await connection.execute(
    "UPDATE accounts SET balance = balance + ? WHERE id = ?",
    [100, toId]
  );

  await connection.commit();
} catch (err) {
  await connection.rollback();
  throw err;
} finally {
  connection.release();
}

Layman example: Moving money from account A to B requires two changes. You do not want A debited while B is not credited.

9. Async DB Operations & DB Errors

Database operations are I/O operations, so Node.js applications normally use asynchronous APIs.

app.get("/users/:id", async (req, res, next) => {
  try {
    const user = await User.findById(req.params.id);

    if (!user) {
      return res.status(404).json({ message: "User not found" });
    }

    res.json(user);
  } catch (err) {
    next(err);
  }
});

Why next(err)? It passes the error to Express error-handling middleware instead of leaving the request hanging.

Common mistake: Sending a success response before the database promise finishes, or catching an error and doing nothing.
10. Interview Questions — Code Based
Q1. What is printed, and why?
console.log("A");

User.find({}).then(() => {
  console.log("B");
});

console.log("C");
Answer: A C B.
The database operation is asynchronous. The synchronous logs run first. The promise callback runs after the database operation settles.
Q2. Find the security problem and fix it.
const sql =
  "SELECT * FROM users WHERE email = '" + req.body.email + "'";
const [rows] = await pool.execute(
  "SELECT * FROM users WHERE email = ?",
  [req.body.email]
);
String concatenation allows user input to become part of the SQL command. Parameterized queries keep the value separate from the SQL structure.
Q3. What is wrong with this design?
app.get("/users", async (req, res) => {
  const db = await mongoose.createConnection(process.env.MONGO_URI);
  const users = await db.collection("users").find({}).toArray();
  res.json(users);
});
The application creates a new database connection for every request. Use a shared connection initialized when the application starts.
Connection creation has overhead and too many connections can exhaust database resources. A shared connection or pool is designed for reuse.
Q4. Why can this code cause an Express request to fail silently?
app.get("/users", async (req, res) => {
  const users = await User.find({});
  res.json(users);
});
The exact behavior depends on the Express version and error-handling setup. The safe pattern is to ensure rejected promises reach centralized error handling, for example with try/catch and next(err), or a reliable async-error wrapper.
A database rejection must become an HTTP error response. If the rejection is not forwarded to error middleware, the client may not receive the intended response.
Q5. What is the purpose of finally here?
const connection = await pool.getConnection();

try {
  await connection.beginTransaction();
  // database work
  await connection.commit();
} catch (err) {
  await connection.rollback();
  throw err;
} finally {
  connection.release();
}
It releases the connection whether the transaction succeeds or fails.
Without releasing the connection, connections can remain occupied and eventually exhaust the pool.
Q6. What does populate() solve?
const orders = await Order.find().populate("user");
It tells Mongoose to resolve the referenced user document instead of leaving only the referenced ObjectId.
It is useful when an application needs related data, but it should be used carefully because fetching many related documents can increase database work.
Q7. What is the problem?
try {
  await User.create(data);
  res.json({ message: "Saved" });
} catch (err) {
  console.log(err);
}
The error is logged, but no response is sent and the error is not forwarded. Use next(err) or send a suitable error response.
The request can remain unresolved. Centralized error handling gives the API a consistent response format and status code.
Q8. Which design is better for high traffic?
// Option A
app.get("/products", async (req, res) => {
  const connection = await createConnection();
  // query
});

// Option B
const pool = createPool();

app.get("/products", async (req, res) => {
  // get/reuse a connection from pool
});
Option B.
Pooling reuses a controlled number of connections and avoids repeatedly paying connection setup costs.

12. Common Developer Mistakes
  • Opening a new database connection for every request.
  • Hard-coding database credentials.
  • Ignoring rejected database promises.
  • Returning success before an async database operation finishes.
  • Building SQL using string concatenation.
  • Using too many database queries when one well-designed query is enough.
  • Fetching huge documents or related data unnecessarily.
  • Forgetting to release pooled connections.
  • Using transactions for every simple read operation.
  • Returning raw database errors and sensitive details to clients.
13. Quick Recap
  • MongoDB: document database.
  • Mongoose: ODM that adds schemas, models, validation and middleware.
  • SQL: relational database model using tables and queries.
  • Connection lifecycle: connect once or use a pool, reuse resources, close gracefully.
  • Async DB operations: use promises/async-await and handle errors.
  • Transactions: use when multiple changes must behave as one logical unit.
  • Connection pooling: reuse a limited set of connections.
  • Parameterized queries: protect SQL from injection caused by unsafe string construction.
