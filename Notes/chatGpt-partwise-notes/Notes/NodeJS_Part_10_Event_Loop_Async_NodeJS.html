Node.js Interview Preparation • Part 10

🟢 Event Loop & Async Node.js ⭐⭐⭐

Understand how Node.js handles asynchronous work without blocking the main JavaScript execution thread.

1. What is the Event Loop?

The event loop is the mechanism that allows Node.js to keep running JavaScript while asynchronous operations are waiting for I/O or other work to finish.

Layman example

Imagine one restaurant waiter. The waiter takes your order, gives it to the kitchen, and while the kitchen prepares the food, the waiter serves other customers. The waiter does not stand in the kitchen waiting.

JavaScript code ↓ Call Stack ↓ Async operation starts ↓ Node.js / OS handles waiting work ↓ JavaScript continues ↓ Callback becomes ready ↓ Event Loop schedules callback ↓ Call Stack runs callback
Interview-ready: “The event loop enables Node.js to handle asynchronous operations while JavaScript execution remains single-threaded. It checks when the call stack is free and processes ready callbacks according to the event-loop scheduling rules.”
2. Call Stack

The call stack keeps track of JavaScript function calls currently being executed.

function one() {
  two();
}

function two() {
  console.log("Hello");
}

one();
one() ↓ two() ↓ console.log() ↓ stack becomes empty

JavaScript executes the current stack of synchronous work before moving on to other scheduled callbacks.

Important: A long-running synchronous function blocks the call stack and therefore prevents other JavaScript callbacks from running.
3. Node.js Architecture — High-Level View
Node.js Process │ ┌─────────┴─────────┐ ↓ ↓ JavaScript Runtime Call Stack facilities │ │ │ ┌─────┴─────┐ │ ↓ ↓ │ Event Loop libuv │ │ │ OS / thread pool │ │ └───────────────┬─────────┘ ↓ Async callbacks

At interview level, remember that Node.js uses a JavaScript execution thread together with an event loop and runtime mechanisms such as libuv. Some asynchronous work can be handled by the operating system, while other operations may use libuv's thread pool.

Do not say: “Node.js has only one thread for everything.” JavaScript execution is single-threaded by default, but Node.js can use the OS and worker threads/thread pool for certain work.
4. Event Loop Phases

Node's event loop has several phases. For interviews, understand what each phase is responsible for rather than memorizing implementation details.

Timers
Runs callbacks for timers such as setTimeout() and setInterval() when their timing conditions are satisfied.
Pending callbacks
Handles certain callbacks deferred from previous operations.
Poll
Processes I/O-related callbacks and may wait for new I/O events when appropriate.
Check
Runs setImmediate() callbacks.
Close callbacks
Runs callbacks for close events, such as some socket close handlers.
Timers ↓ Pending callbacks ↓ Poll ↓ Check ↓ Close callbacks ↺ Event loop continues
Interview line: “Node's event loop moves through phases such as timers, pending callbacks, poll, check, and close callbacks. The exact callback that runs next also depends on microtask processing and the state of the event loop.”
5. setTimeout()
console.log("A");

setTimeout(() => {
  console.log("B");
}, 0);

console.log("C");

Output:

A
C
B

setTimeout(fn, 0) does not mean “run immediately.” It means the timer is eligible after the minimum delay, and the callback must still wait for the current synchronous work and event-loop scheduling.

Interview trap: Never say that setTimeout(..., 0) guarantees execution exactly after zero milliseconds.
6. setImmediate()

setImmediate() schedules a callback for the event loop's check phase.

const fs = require("node:fs");

fs.readFile(__filename, () => {
  setTimeout(() => console.log("timeout"), 0);
  setImmediate(() => console.log("immediate"));
});

When scheduled inside an I/O callback such as this file-read callback, setImmediate() commonly runs before the zero-delay timer.

I/O callback │ ├── setTimeout(...) │ └── setImmediate(...) ↓ Check phase
Interview-ready: “setImmediate() runs in the check phase. Its ordering relative to setTimeout(0) depends on where they are scheduled; inside an I/O callback, setImmediate() commonly runs first.”
7. process.nextTick()

process.nextTick() schedules a callback to run after the current operation completes, before the event loop continues to its next phase.

console.log("A");

process.nextTick(() => {
  console.log("B");
});

console.log("C");
A
C
B

It is not an ordinary event-loop phase. Node processes the next-tick queue at high priority between JavaScript operations.

Common mistake: Recursively scheduling huge numbers of process.nextTick() callbacks can starve the event loop and prevent I/O from getting a chance to run.
8. Microtasks — Promises and queueMicrotask()

Promise callbacks such as .then() and callbacks scheduled with queueMicrotask() are microtasks.

console.log("A");

Promise.resolve().then(() => {
  console.log("B");
});

queueMicrotask(() => {
  console.log("C");
});

console.log("D");
A
D
B
C

The current synchronous code finishes first. Then the microtask queue is processed. The microtasks keep their scheduling order.

Remember: Promise callbacks do not jump into the middle of currently executing synchronous JavaScript. They wait until the current stack has completed.
9. process.nextTick() vs Promise Microtasks
console.log("A");

process.nextTick(() => console.log("nextTick"));

Promise.resolve().then(() => console.log("promise"));

queueMicrotask(() => console.log("microtask"));

console.log("B");

In standard Node.js behavior, the output is:

A
B
nextTick
promise
microtask

Node drains the next-tick queue before proceeding to the regular microtask queue.

Interview tip: Do not casually describe process.nextTick() as simply “a microtask.” It has special Node.js scheduling behavior and a higher priority than the regular microtask queue.
10. Event Loop Ordering
console.log("1");

setTimeout(() => console.log("2"), 0);

Promise.resolve().then(() => console.log("3"));

process.nextTick(() => console.log("4"));

console.log("5");

Output:

1
5
4
3
2
Synchronous: 1 → 5 ↓ nextTick queue: 4 ↓ Promise microtask: 3 ↓ Timer callback: 2
Why? Synchronous JavaScript runs first. Then Node processes the next-tick queue, then regular microtasks, and later the timer callback when its timer phase is reached.
11. Async File System
const fs = require("node:fs");

console.log("Start");

fs.readFile(__filename, "utf8", (err, data) => {
  if (err) throw err;
  console.log("File read complete");
});

console.log("End");
Start
End
File read complete

The asynchronous file operation starts, and JavaScript can continue. When the file operation completes, its callback is scheduled for execution.

readFile() ↓ async I/O starts ↓ JavaScript continues ↓ "End" ↓ file operation completes ↓ callback becomes ready ↓ "File read complete"
12. Async HTTP

HTTP servers are event-driven. Incoming requests are handled through callbacks/events, so the server can continue accepting and processing other work rather than waiting synchronously for every request.

const http = require("node:http");

const server = http.createServer((req, res) => {
  console.log("Request received");

  setTimeout(() => {
    res.end("Done");
  }, 1000);
});

server.listen(3000);
Important: The timer itself is asynchronous, but a CPU-heavy synchronous function inside the request handler would still block JavaScript and delay other requests.
13. Blocking vs Non-Blocking Code ⭐⭐⭐
Blocking
const fs = require("node:fs");

const data = fs.readFileSync("large.txt", "utf8");

console.log("Done");

The JavaScript execution thread waits for the synchronous file operation to finish.

Non-blocking
const fs = require("node:fs");

fs.readFile("large.txt", "utf8", (err, data) => {
  if (err) throw err;
  console.log("Done");
});

console.log("Continue");

The asynchronous version lets JavaScript continue while the file operation is handled asynchronously.

Blocking: JS → wait for file → continue Non-blocking: JS → start file I/O → continue ↓ callback later
Interview-ready: “Blocking code prevents the JavaScript thread from progressing. Non-blocking APIs start asynchronous work and allow JavaScript to continue until the result is ready.”
14. Event Loop Starvation ⭐⭐⭐

Event loop starvation happens when one kind of work keeps the event loop busy for too long, preventing other callbacks such as I/O from getting a chance to run.

function block() {
  const start = Date.now();

  while (Date.now() - start < 5000) {
    // CPU-heavy synchronous work
  }
}

block();
console.log("Finished");

During those five seconds, the JavaScript thread cannot process other JavaScript callbacks.

Long synchronous work ↓ Call stack stays busy ↓ Event loop cannot run other callbacks ↓ I/O / timers are delayed ↓ Poor responsiveness
How to reduce it: Break up CPU-heavy work, move suitable work to worker threads/processes, use streaming/chunking where appropriate, and avoid unnecessary synchronous APIs in request paths.
15. Timers Do Not Guarantee Exact Execution Time
setTimeout(() => {
  console.log("Timer");
}, 100);

for (let i = 0; i < 1000000000; i++) {
  // long synchronous work
}

The timer becomes eligible after its delay, but if the call stack is busy, the callback cannot run until JavaScript is able to process it.

Interview line: “The delay passed to setTimeout is a minimum delay, not an exact execution time.”
16. A Practical Event Loop Flow
┌──────────────────┐ │ JavaScript Code │ └────────┬─────────┘ ↓ ┌───────────┐ │ Call Stack│ └─────┬─────┘ │ async work │ ↓ ┌────────────────────┐ │ Node.js / OS / │ │ libuv mechanisms │ └─────────┬──────────┘ ↓ callback ready ↓ ┌────────────────────┐ │ Event Loop Phases │ │ timers │ │ pending callbacks │ │ poll │ │ check │ │ close │ └─────────┬──────────┘ ↓ callback runs ↓ Call Stack
17. Common Developer Mistakes
  • Thinking Node.js is completely single-threaded for every kind of work.
  • Thinking setTimeout(fn, 0) means “run immediately.”
  • Thinking setImmediate() always runs before setTimeout().
  • Calling process.nextTick() a normal event-loop phase.
  • Forgetting that Promise callbacks are microtasks.
  • Running large CPU-heavy loops inside HTTP request handlers.
  • Using synchronous filesystem APIs in latency-sensitive server paths.
  • Creating recursive process.nextTick() work that starves I/O.
  • Assuming asynchronous means “runs on another JavaScript thread.”
  • Assuming timers execute at an exact time.
18. Interview Questions — Click to Show / Hide Answer + Why ⭐⭐⭐
Q1. What is the Node.js event loop?
Answer: The event loop is the scheduling mechanism that allows Node.js to process asynchronous callbacks while JavaScript execution remains single-threaded.

Why? It is the foundation of Node.js's event-driven, non-blocking programming model.
Q2. Is Node.js single-threaded?
Answer: JavaScript execution in the main Node.js thread is single-threaded, but Node.js itself can use the operating system, libuv's thread pool, and worker threads for other work.

Why? Saying simply “Node.js is single-threaded” is incomplete and can lead to wrong conclusions about I/O and CPU work.
Q3. Explain the main event-loop phases.
Answer: Important phases include timers, pending callbacks, poll, check, and close callbacks.

Why? Different types of callbacks are scheduled in different parts of the event loop. Understanding this explains timer and I/O ordering.
Q4. What is the difference between setTimeout() and setImmediate()?
Answer: setTimeout() schedules a timer callback, while setImmediate() schedules a callback for the check phase. Their ordering depends on where they are scheduled.

Why? Interviewers commonly test the incorrect belief that one always wins.
Q5. What happens here?
console.log("A");

setTimeout(() => console.log("B"), 0);

Promise.resolve().then(() => console.log("C"));

process.nextTick(() => console.log("D"));

console.log("E");
Output: 
A
E
D
C
B
Why? Synchronous code runs first. Node then processes process.nextTick(), followed by Promise microtasks, and the timer callback is handled later by the timer phase.
Q6. Does setTimeout(fn, 0) run immediately?
Answer: No. Zero is the minimum timer delay. The callback still waits for the current JavaScript work and event-loop scheduling.

Why? A busy call stack can delay the timer well beyond zero milliseconds.
Q7. What is process.nextTick()?
Answer: It schedules a callback to run after the current operation, with special high-priority Node.js scheduling before the event loop continues normally.

Why? It is useful in some Node internals/API situations but can starve the event loop when abused.
Q8. What is a microtask?
Answer: A microtask is a small callback that is processed after the current synchronous JavaScript completes and before normal later event-loop work proceeds. Promise callbacks and queueMicrotask() use the regular microtask queue.

Why? Microtask ordering is critical for understanding Promise output questions.
Q9. Why is this code dangerous?
function loop() {
  process.nextTick(loop);
}

loop();
Answer: It continuously adds next-tick callbacks and can prevent the event loop from reaching other work.

Why? This can cause event loop starvation and prevent timers and I/O callbacks from getting enough execution time.
Q10. Why can a CPU-heavy function make an asynchronous Node.js server slow?
Answer: CPU-heavy synchronous JavaScript occupies the main call stack, so the event loop cannot process other callbacks while that code is running.

Why? Non-blocking I/O does not make CPU-heavy JavaScript automatically non-blocking.
Q11. What is the difference between blocking and non-blocking code?
Answer: Blocking code keeps the JavaScript execution thread busy until the operation finishes. Non-blocking APIs start asynchronous work and allow JavaScript to continue.

Why? Non-blocking behavior is a major reason Node.js works well for I/O-heavy applications.
Q12. What is event loop starvation?
Answer: Event loop starvation occurs when callbacks or synchronous work continuously occupy execution time and prevent other queued work from being processed.

Why? Starvation causes delayed requests, timers, and I/O callbacks even though the process is technically still running.
Q13. What happens in this code?
const fs = require("node:fs");

fs.readFile(__filename, () => {
  console.log("I/O");

  setTimeout(() => console.log("timeout"), 0);
  setImmediate(() => console.log("immediate"));
});
Expected ordering in this I/O callback: 
I/O
immediate
timeout
Why? The callback is already executing as an I/O callback. setImmediate() targets the check phase, which follows the poll phase in this situation, while the timer is handled in a timer phase.
Q14. Why does async filesystem code not necessarily run on the JavaScript call stack immediately?
Answer: The asynchronous filesystem operation is handed to Node.js runtime mechanisms. When the operation completes, its callback is scheduled so JavaScript can process it later.

Why? This separation lets JavaScript continue instead of synchronously waiting for the file operation.
Q15. What is the difference between concurrency and parallelism in Node.js?
Answer: Concurrency means multiple tasks can make progress during overlapping periods. Parallelism means tasks actually execute at the same time on different execution resources.

Why? Node.js can handle many I/O operations concurrently without running all JavaScript code in parallel on multiple main JavaScript threads.
Q16. Why should you avoid long synchronous loops in an HTTP handler?
Answer: A long synchronous loop blocks the JavaScript thread and prevents the event loop from processing other requests and callbacks.

Why? One slow request can therefore delay unrelated requests handled by the same process.
