Node.js + Express Interview Mastery

🏆 Part 32 — Node.js + Express System Design

Intermediate and experienced interview preparation: design real backend systems, explain trade-offs, and scale Express applications.

How to Approach Any System Design Question
  1. Clarify requirements: users, features, read/write traffic, latency, consistency, security.
  2. Estimate scale: requests per second, storage growth, file sizes, peak traffic.
  3. Design the API: endpoints, request/response shape, authentication, idempotency.
  4. Draw the architecture: load balancer, Express, cache, DB, queue, workers, external providers.
  5. Find bottlenecks: database, CPU, network, external APIs, memory.
  6. Add reliability: retries, timeouts, rate limits, health checks, graceful shutdown.
  7. Explain trade-offs: do not add Redis, Kafka, workers, or microservices without a reason.
Interview mindset: A good design is not the design with the most technologies. It is the simplest design that meets the stated requirements and can grow safely.
Common Scalable Express Architecture
Clients ↓ CDN / Reverse Proxy / Load Balancer ↓ ┌─────────────── Express API instances ───────────────┐ │ Auth → Validation → Controller → Service → Repository│ └──────────────────────┬───────────────────────────────┘ ↓ Redis / Cache / Rate Limit ↓ Database + Indexes │ └────→ Queue → Workers → Email / Files / Jobs ↓ Logs + Metrics + Health Checks
Key principle: Keep HTTP handlers fast. Push slow, retryable, or CPU-heavy work to suitable background workers.
Design 1: 1. URL Shortener

What: Create a short URL for a long URL and redirect users to the original address.

Why / purpose: Choose a collision-safe ID strategy, indexed lookup, cache hot URLs, and define expiration/ownership rules.

How it works
  • API: POST /urls, GET /:code
  • Store code → long URL in a database
  • Use a unique short-code generator and an index
  • Add cache for hot redirects
  • Track clicks asynchronously
Visual flow
Client → Express → URL Service → Cache → DB ↓ Event / Analytics
Interview tip: Start with a simple architecture, then explain what you would change when traffic, reliability, or data volume grows.
Design 2: 2. Authentication System

What: Build registration, login, token handling, protected routes, roles, and logout.

Why / purpose: Separate authentication from authorization. Never store plain-text passwords or expose secrets in responses.

How it works
  • Hash passwords with bcrypt/Argon2
  • Use short-lived access tokens
  • Use refresh tokens carefully
  • Store sensitive tokens in HttpOnly, Secure cookies when cookie auth is chosen
  • Add rate limits to login and reset endpoints
Visual flow
Client → Auth Middleware → Controller → Auth Service → User DB ↓ Access Token

Design 5: 5. Rate Limiter

What: Protect APIs from abuse and sudden traffic spikes.

Why / purpose: In a multi-instance app, local memory counters are not enough because each instance has different state.

How it works

  • Use Redis for distributed counters
  • Use a window/token-bucket style algorithm
  • Return HTTP 429 when limited
  • Set different limits by endpoint

Layman Examples
  • URL shortener: Like giving a long address a small ticket number.
  • Cache: Like keeping frequently used items on your desk instead of walking to the storeroom every time.
  • Queue: Like a restaurant order line: the customer does not wait for the kitchen to finish every step.
  • Rate limiter: Like a security guard allowing only a certain number of people through a door per minute.
  • Load balancer: Like a receptionist distributing customers across several available counters.
  • Worker: Like sending a heavy task to another employee so the front desk stays available.
Common System Design Mistakes
  1. Starting with technology names instead of requirements.
  2. Designing everything as microservices when a modular monolith is enough.
  3. Ignoring database indexes and connection pooling.
  4. Keeping CPU-heavy work inside the Express request handler.
  5. Using in-memory cache/state when multiple API instances need shared state.
  6. Retrying every failure forever and creating retry storms.
  7. Ignoring idempotency for payments, jobs, and retried requests.
  8. Trusting client-provided prices, roles, file types, or security-sensitive data.
  9. Returning huge result sets instead of paginating.
  10. Ignoring observability: logs, metrics, request IDs, health checks.
  11. Forgetting graceful shutdown during deployment.
Quick Recap
  • Express: keep routing and HTTP concerns separate from business logic.
  • Redis: useful for shared caching, distributed rate limiting, and short-lived state.
  • Database: indexes and connection pooling are fundamental for scale.
  • Queue: separates slow/background work from user-facing requests.
  • Workers: process jobs without holding the HTTP request open.
  • Load balancer: distributes traffic across stateless API instances.
  • Idempotency: makes retries safe for operations that must not happen twice.
  • Observability: logs + metrics + tracing help find production bottlenecks.
  • Security: authentication, authorization, validation, rate limiting, HTTPS, and secret management belong in the design.
Interview-Ready Framework
Use this answer structure:
1. Requirements → 2. Scale assumptions → 3. API design → 4. High-level architecture → 5. Data model → 6. Main request flow → 7. Bottlenecks → 8. Caching/queues → 9. Reliability → 10. Security → 11. Monitoring → 12. Trade-offs.
Strong interview lines
  • “I would keep the API stateless so it can scale horizontally behind a load balancer.”
  • “I would use a shared cache rather than process-local memory when multiple instances need the same cached state.”
  • “I would make retryable operations idempotent before adding retries.”
  • “I would move slow work to a queue so request latency is not tied to the external provider.”
  • “I would measure the bottleneck before choosing a scaling strategy.”
  • “For high traffic, I would consider database indexes, connection pooling, caching, pagination, and horizontal scaling before adding unnecessary complexity.”
