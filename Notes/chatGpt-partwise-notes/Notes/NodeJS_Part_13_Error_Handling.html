Node.js Interview Preparation • Part 13

🟢 Error Handling in Node.js ⭐⭐⭐

Learn how Node.js detects, throws, catches, propagates, logs, and safely handles errors.

1. What is Error Handling?

Error handling means detecting a problem, deciding what to do about it, and preventing the application from failing in an uncontrolled way.

Layman example

Imagine a delivery driver cannot find a house. A good system does not simply stop. It reports the problem, checks another option, contacts the customer, or safely ends the delivery.

Application ↓ Something goes wrong ↓ Detect error ↓ Classify / log error ↓ Handle or propagate ↓ Recover OR safely shut down
Interview-ready: “Good Node.js error handling separates expected operational failures from programmer bugs and makes sure errors are observed, handled, and propagated correctly.”
2. try / catch / finally

try contains code that may throw. catch handles a thrown error. finally runs whether an error occurred or not.

try {
  const result = JSON.parse('{"name":"Sam"}');
  console.log(result.name);
} catch (error) {
  console.error("Invalid JSON:", error.message);
} finally {
  console.log("Finished");
}
try ↓ success ─────────→ finally ↓ error → catch → finally
When to use?

Use try/catch around operations where you can meaningfully handle the failure, especially synchronous code that can throw and await expressions inside async functions.

Common mistake: A try/catch does not automatically catch errors from every asynchronous callback scheduled later.
3. throw

throw creates an exception and immediately stops normal execution at that point until a matching handler catches it.

function withdraw(balance, amount) {
  if (amount > balance) {
    throw new Error("Insufficient balance");
  }

  return balance - amount;
}

try {
  console.log(withdraw(100, 200));
} catch (error) {
  console.error(error.message);
}

In application code, prefer throwing Error objects rather than strings.

// Good
throw new Error("User not found");

// Avoid
throw "User not found";
4. Error Object

An Error object carries information about a failure.

const error = new Error("Database failed");

console.log(error.name);    // Error
console.log(error.message); // Database failed
console.log(error.stack);   // stack trace
  • name — type/name of the error.
  • message — human-readable explanation.
  • stack — useful debugging information showing where the error was created.
Interview tip: Never depend on exact stack text for application logic. Use structured error properties or custom error classes when the application needs to distinguish error types.
5. Common JavaScript Error Types
Error

General error object.

throw new Error("Failed");
TypeError

Operation uses a value of an unsuitable type.

const x = null;
x.name;
ReferenceError

Code refers to an identifier that cannot be found.

console.log(notDefined);
SyntaxError

JavaScript syntax is invalid.

const = 10;
Important: Syntax errors can prevent a file from running at all, so normal runtime try/catch cannot be used to recover from a syntax error in that same invalid source file.
6. Custom Errors

Custom errors let an application attach meaningful names or properties to domain-specific failures.

class ValidationError extends Error {
  constructor(message, field) {
    super(message);
    this.name = "ValidationError";
    this.field = field;
  }
}

throw new ValidationError("Email is required", "email");

A centralized handler can then check error instanceof ValidationError and choose an appropriate response.

Why? Custom errors make error handling clearer because different failures can carry different meanings and metadata.
7. Error-First Callbacks

Traditional Node.js callback APIs commonly use the first argument for the error.

const fs = require("node:fs");

fs.readFile("data.txt", "utf8", (err, data) => {
  if (err) {
    console.error("Read failed:", err);
    return;
  }

  console.log(data);
});
(err, data) ↓ err exists? ── yes → handle error → return │ no ↓ use data
Common mistake: Forgetting to return after handling an error can cause the success code to continue running.
8. Promise Errors

A rejected Promise represents an asynchronous failure.

getUser()
  .then(user => getOrders(user.id))
  .then(orders => console.log(orders))
  .catch(error => {
    console.error("Request failed:", error);
  });

A rejection can travel through the Promise chain until a rejection handler catches it.

Promise rejected ↓ next .then() skipped ↓ nearest matching .catch() ↓ handle error
Interview line: “Promise errors propagate through the chain until they are handled by a rejection handler such as catch, or they remain unhandled.”
9. Async/Await Errors

When an awaited Promise rejects, await throws the rejection reason inside the async function.

async function loadUser() {
  try {
    const user = await getUser();
    return user;
  } catch (error) {
    console.error("Could not load user:", error);
    throw error;
  }
}

You can handle errors at the level where you have enough information to recover. If you cannot recover, rethrow so a higher-level handler can decide what to do.

Common mistake: Catching an error and doing nothing can hide a real failure.
10. Unhandled Promise Rejection
Promise.reject(new Error("Database unavailable"));

This creates a rejected Promise with no rejection handler attached. Node.js reports unhandled Promise rejections, and behavior can be serious for an application depending on runtime/version and configuration.

Promise rejects ↓ No catch / handler ↓ Unhandled rejection reported ↓ Application monitoring should detect it ↓ Fix the original error path
Best practice: Do not use a global unhandled-rejection handler as a substitute for handling expected failures at the correct application layer.
11. uncaughtException

process.on("uncaughtException", ...) can observe an exception that reached the process without being caught.

process.on("uncaughtException", (error) => {
  console.error("Uncaught exception:", error);
});
Very important: Do not treat this as normal application recovery. An uncaught exception can leave the process in an unsafe or inconsistent state. A common production strategy is to log the error, stop accepting new work, clean up what is safe to clean up, and exit so a process manager can restart the service.
Interview-ready: “uncaughtException is a last-resort process-level safety mechanism, not a normal error-handling strategy.”
12. Error Propagation
function validateUser(user) {
  if (!user.email) {
    throw new Error("Email is required");
  }
}

function createUser(user) {
  validateUser(user);
  return "User created";
}

try {
  createUser({});
} catch (error) {
  console.error(error.message);
}
validateUser() ↓ throw createUser() ↓ propagates caller try/catch ↓ handle error

Error propagation means an error moves upward through the call chain until some layer handles it.

13. Operational Errors vs Programmer Errors
Operational error

A failure that can happen during normal operation.

  • Database temporarily unavailable
  • Network timeout
  • File does not exist
  • Invalid user input
  • External API unavailable

Typical response: handle, retry when appropriate, return a useful response, or safely degrade.

Programmer error

A bug in the application code.

  • Using an undefined variable
  • Wrong assumption about a value
  • Calling a method on null
  • Broken application logic

Typical response: fix the bug. Do not hide it with a generic catch.

Interview tip: “Operational errors are expected failures of the environment or input; programmer errors are defects in code. The handling strategy should be different.”
14. Centralized Error Handling

Instead of handling every application error in a different style, larger applications often use a central error-handling layer.

Request ↓ Route / Controller ↓ Service ↓ Database / External API ↓ Error occurs ↓ Propagate ↓ Central error handler ↓ Log + classify + response

In an Express application, this is commonly implemented with error-handling middleware.

app.use((err, req, res, next) => {
  console.error(err);

  res.status(500).json({
    message: "Internal server error"
  });
});
Security tip: Log useful technical details internally, but do not expose stack traces, database details, passwords, tokens, or secrets to clients.
15. Graceful Shutdown

Graceful shutdown means stopping the application in an orderly way instead of suddenly killing it.

const server = require("node:http").createServer((req, res) => {
  res.end("OK");
});

server.listen(3000);

process.on("SIGTERM", () => {
  console.log("Shutdown requested");

  server.close(() => {
    console.log("Server stopped accepting new requests");
    process.exit(0);
  });
});
SIGTERM ↓ Stop accepting new work ↓ Finish safe in-flight work ↓ Close server / DB / resources ↓ Log completion ↓ Exit process

Graceful shutdown is especially important in containers, cloud deployments, and systems managed by process supervisors.

Common mistake: Calling process.exit() immediately can terminate the process before pending cleanup finishes.
16. Common Developer Mistakes
  • Using try/catch as a replacement for fixing programmer bugs.
  • Throwing strings instead of Error objects.
  • Ignoring callback errors.
  • Forgetting return after handling an error-first callback.
  • Creating a Promise rejection without a handler.
  • Swallowing errors inside catch blocks.
  • Logging sensitive information such as passwords or access tokens.
  • Sending internal stack traces to users.
  • Using uncaughtException as normal recovery.
  • Calling process.exit() before cleanup is complete.
  • Retrying every error blindly, including validation errors.
  • Returning HTTP 500 for every type of client/input error.
17. Interview Questions — Click to Show / Hide Answer + Why ⭐⭐⭐
Q1. What is the difference between try/catch and Promise catch?
Answer: try/catch handles synchronous throws and, inside an async function, rejections produced by awaited Promises. .catch() handles rejected Promises in a Promise chain.

Why? Knowing which asynchronous model you are using prevents errors from being missed.
Q2. Will this catch the error?
try {
  setTimeout(() => {
    throw new Error("Boom");
  }, 0);
} catch (error) {
  console.log("Caught");
}
Answer: No. The callback runs later, after the try block has already finished.

Why? The try/catch surrounds the scheduling call, not the later callback execution.
Q3. What is an error-first callback?
Answer: A callback convention where the first argument is the error and later arguments contain successful results.

Why? It gives Node.js callback APIs a consistent error-handling pattern.
Q4. What happens when an async function throws an error?
async function test() {
  throw new Error("Failed");
}

const result = test();
Answer: test() returns a rejected Promise.

Why? An async function converts thrown errors into Promise rejections.
Q5. What is error propagation?
Answer: It is the movement of an error upward through the call stack or Promise chain until a handler deals with it.

Why? It lets lower-level functions report failures without needing to know how the final caller will respond.
Q6. What is the difference between operational and programmer errors?
Answer: Operational errors are expected failures such as network problems or invalid input. Programmer errors are defects in application code.

Why? Operational errors can often be handled or retried; programmer errors usually need a code fix.
Q7. What is uncaughtException?
Answer: It is a process-level event emitted when an exception reaches the Node.js process without being caught.

Why? It is a last-resort safety mechanism, not a replacement for local error handling.
Q8. Should an application continue normally after uncaughtException?
Answer: Generally, you should not assume the process is safe to continue. Log what happened, perform safe cleanup, stop accepting work, and exit so a supervisor can restart it when appropriate.

Why? An uncaught exception can leave application state inconsistent.
Q9. What is an unhandled Promise rejection?
Answer: It occurs when a Promise rejects and no rejection handler is attached in time.

Why? Unhandled rejections can hide failures and create unstable application behavior.
Q10. Why should you throw new Error() instead of a string?
Answer: Error objects provide standard information such as name, message, and stack, and work naturally with error handling and custom error classes.

Why? Structured errors are easier to debug, classify, and log.
Q11. What is the difference between Error and TypeError?
Answer: Error is the general base error type. TypeError indicates an operation was attempted with an unsuitable value type.

Why? Specific error types give more information about the nature of a failure.
Q12. Why is finally useful?
Answer: It runs after success or failure and is useful for cleanup.

Why? Cleanup should often happen regardless of whether the main operation succeeded.
Q13. What is centralized error handling?
Answer: It is a common error-handling layer where propagated errors are classified, logged, and converted into consistent application responses.

Why? It avoids duplicated error-response logic across many routes and services.
Q14. What should you do during graceful shutdown?
Answer: Stop accepting new work, allow safe in-flight work to finish where possible, close servers and resources, then exit.

Why? It prevents dropped requests, corrupted work, and incomplete cleanup.
Q15. Predict the result.
async function test() {
  try {
    await Promise.reject("X");
    console.log("A");
  } catch (error) {
    console.log("B", error);
  }
  console.log("C");
}

test();
Output: 
B X
C
Why? The rejected Promise causes await to throw. The catch handles it, and execution then continues with C.
Q16. What happens here?
async function test() {
  try {
    throw new Error("A");
  } catch (error) {
    console.log("B");
    throw error;
  }
}

test().catch(() => console.log("C"));
Output: 
B
C
Why? The error is caught locally, logged as B, then rethrown. The async function returns a rejected Promise, which the outer catch handles as C.
Q17. Is this a good production strategy?
process.on("uncaughtException", () => {
  console.log("Ignore it and continue");
});
Answer: No. Treating uncaught exceptions as harmless is unsafe.

Why? The process may be in an unknown state. A safer strategy is to log, perform controlled cleanup, stop accepting work, and exit when appropriate.
Q18. Why should sensitive error details not be returned to API clients?
Answer: Stack traces and internal error details can reveal database structure, file paths, libraries, credentials, or other implementation information.

Why? Clients usually need a safe, useful error message, while detailed diagnostics belong in protected server logs.
Q19. What is the danger of swallowing an error?
try {
  await saveData();
} catch (error) {
  console.log(error);
}

return "Success";
Answer: The function may report success even though saveData failed.

Why? Catching an error changes control flow. If the operation did not succeed, the caller should usually receive a failure signal or an intentional fallback result.
Q20. Why is process.exit() risky during shutdown?
Answer: It can terminate the process before pending cleanup or important output completes.

Why? Graceful shutdown should first close servers and resources safely, then exit.

Strong interview summary:
“Node.js applications should handle expected operational failures at the appropriate layer, propagate errors when a lower layer cannot recover, and keep programmer bugs visible. Promises use rejection handling, async/await commonly uses try/catch, and process-level events such as uncaughtException are last-resort safety mechanisms. Production applications should log safely, avoid exposing sensitive details, and use graceful shutdown when the process must stop.”
