Node.js Interview Preparation • Part 1

🟢 Node.js Fundamentals

Simple, practical, interview-ready notes for Node.js fundamentals.

1. What Is Node.js?
What?

Node.js is a JavaScript runtime environment that allows JavaScript to run outside the browser.

Why / purpose?

It gives JavaScript access to server-side capabilities such as files, networking, processes, and servers.

Layman example

JavaScript is the language. A browser is one place where it can run. Node.js is another place where it can run.

JavaScript code ↓ Node.js runtime ↓ V8 engine ↓ Execution outside the browser
When to use?
  • REST APIs
  • Real-time applications
  • CLI tools
  • Automation scripts
  • Microservices
  • Streaming applications
Interview-ready: “Node.js is an open-source, cross-platform JavaScript runtime built around the V8 engine. It lets JavaScript run outside the browser and provides APIs for I/O, networking, files, and processes.”
2. Node.js Runtime Environment
What is a runtime?

A runtime environment provides the things needed to execute a program. Node.js combines V8 with Node-specific APIs and an event-driven I/O system.

Your JavaScript ↓ Node.js APIs ┌────┼───────────┐ ↓ ↓ ↓ fs http process └────┼───────────┘ ↓ Operating System ↓ Files / Network / Processes
Remember: Node.js is not a programming language. JavaScript is the language; Node.js is a runtime.

Common mistake: JavaScript language features and runtime APIs are different things. A browser API is not automatically a Node.js API.
4. V8 Engine
What?

V8 is Google's open-source JavaScript engine. Node.js uses V8 to execute JavaScript.

Node.js ├── V8 → executes JavaScript ├── Node APIs → files, network, process └── Event-driven I/O → coordinates async work
Interview point: V8 alone is not Node.js. V8 executes JavaScript; Node.js adds runtime APIs and other components around it.
5. Node.js Architecture
Node.js Application │ ↓ JavaScript code │ ↓ V8 │ ┌───────────┴───────────┐ ↓ ↓ Node.js APIs Event Loop │ │ ↓ ↓ OS / I/O Ready callbacks │ │ └───────────┬───────────┘ ↓ JavaScript runs
  • V8 executes JavaScript.
  • Node APIs provide file, network, process and other runtime capabilities.
  • The event-driven model coordinates asynchronous work.
Common mistake: “Node.js is single-threaded, so it can do only one thing.” JavaScript execution uses a main thread, but Node.js and the operating system can use other mechanisms for asynchronous work.
6. Event-Driven Architecture
What?

Work is coordinated around events and handlers. Something happens, an event is produced, and relevant code reacts.

Layman example

A doorbell rings → that is the event. You hear it → that is the reaction.

Event occurs ↓ Runtime receives/completes operation ↓ Callback becomes ready ↓ Event loop schedules it ↓ JavaScript callback executes
Interview-ready: “Node.js uses an event-driven programming model where callbacks, promises, and event handlers respond to completed or triggered operations.”
7. Non-Blocking I/O
What?

I/O means input/output, such as reading files or waiting for network responses. Non-blocking I/O lets JavaScript continue instead of synchronously waiting for supported I/O work.

const fs = require("fs");

fs.readFile("data.txt", "utf8", (err, data) => {
  if (err) return console.error(err);
  console.log(data);
});

console.log("This can run before the callback.");
Start readFile ↓ Request I/O ↓ JavaScript continues ↓ File operation completes ↓ Callback becomes ready ↓ Callback executes when the event loop can run it
Important: Non-blocking does not mean “instant.” It means JavaScript is not forced to synchronously wait for supported asynchronous I/O.
8. Single-Threaded JavaScript Execution

JavaScript execution in a Node.js process normally uses one main JavaScript thread. That thread executes one piece of JavaScript at a time.

JavaScript Call Stack │ ↓ One task at a time │ ↓ Event loop chooses ready work │ ↓ Next callback executes
CPU-heavy work

A long CPU-heavy operation can block the main JavaScript thread. Node.js provides mechanisms such as worker threads and child processes for other workloads.

Common mistake: “Node.js has only one thread” is too broad. Say: “JavaScript execution uses a main thread, while Node.js can use other mechanisms for asynchronous and parallel work.”
9. Node.js Process
What?

A process is a running instance of a program. When you run a Node.js file, the OS starts a Node.js process.

node app.js
Operating System ↓ Start: node app.js ↓ Node.js Process ├── JavaScript execution ├── process object ├── event loop └── active resources
10. process

process is a Node.js global object containing information about and controls for the current process.

console.log(process.pid);
console.log(process.platform);
console.log(process.cwd());
  • process.argv — command-line arguments
  • process.env — environment variables
  • process.exit() — terminate the process
  • process.cwd() — current working directory
Interview line: “The process object gives a Node.js application information about and control over its current process.”
11. process.argv

process.argv is an array containing command-line arguments.

// app.js
console.log(process.argv);
node app.js Sam 25

The array contains the Node executable path, script path, then custom arguments.

process.argv[2] // "Sam"
process.argv[3] // "25"
Common mistake: Forgetting that your first custom argument is normally at index 2.
12. process.env

process.env exposes environment variables available to the process.

console.log(process.env.NODE_ENV);
console.log(process.env.PORT);
Environment PORT=5000 NODE_ENV=production ↓ process.env ↓ Your Node.js program
Why?

Configuration can change between environments without hard-coding every value.

Security mistake: Do not commit real secrets to source control. Also remember that environment variable values are strings.
13. process.exit()
console.log("Before");

process.exit(1);

console.log("After");

Output: Before

process.exit() terminates the process. Exit code 0 generally means success; a non-zero code generally indicates an error or abnormal termination.

Common mistake: Do not use process.exit() casually in server code because abrupt termination can prevent pending work from completing. Prefer graceful shutdown where appropriate.
14. process.cwd()

process.cwd() returns the current working directory of the Node.js process.

console.log(process.cwd());

Think of it as “the folder from which this process is currently working.”

Important: It is not necessarily the folder containing the current JavaScript file.
15. __dirname

In Node.js CommonJS modules, __dirname is the absolute path of the directory containing the current module file.

console.log(__dirname);
project/ └── src/ └── app.js Inside app.js: __dirname ↓ project/src
Important: __dirname is a CommonJS convenience variable. Native ES modules commonly use import.meta.url for module-relative paths.
16. __filename

In Node.js CommonJS modules, __filename is the absolute path of the current module file.

console.log(__filename);
ValueMeaning
__dirnameDirectory of current CommonJS module
__filenameFull path of current CommonJS module file
process.cwd()Current working directory of the process
Very common interview question: They can differ because module location and process working directory are different concepts.
17. global

global is Node.js's global object.

global.myValue = 100;
console.log(global.myValue);

Top-level variables in a CommonJS module do not automatically become properties of global.

Common mistake: Node.js modules have their own module scope. Do not treat every module variable as a global variable.
18. globalThis

globalThis is the standard JavaScript way to access the global object across JavaScript environments.

console.log(globalThis === global);

In Node.js, globalThis refers to the Node global object. In browsers it refers to the browser global object.

Interview point: globalThis is the portable standard name; global is Node-specific and window is associated with browsers.
19. console

console provides methods for messages and diagnostics.

console.log("Normal");
console.error("Error");
console.warn("Warning");
console.table([{name:"Sam", age:25}]);

It is useful for development and debugging.

Production mistake: Do not rely on scattered console statements as a complete production logging system. Structured logging is usually better for production applications.
20. Node.js REPL
REPL = Read, Eval, Print, Loop
Read ↓ Read your input ↓ Eval ↓ Evaluate it ↓ Print ↓ Show result ↓ Loop ↓ Wait for next command
Start it
node
Try it

> name

Useful for: quick experiments, testing JavaScript expressions, checking Node APIs, and learning.

Exit: use .exit or press Ctrl + C twice.
21. Output-Based Interview Questions
Q1 — cwd vs __dirname
console.log(process.cwd());
console.log(__dirname);

Are they guaranteed to be the same? No.

Why? cwd() depends on where the process was started; __dirname depends on the current CommonJS module's location.

Q2 — process.argv
// app.js
console.log(process.argv[2]);
node app.js hello

Output: hello. The first custom argument is at index 2.

Q3 — process.env
console.log(typeof process.env.PORT);

If PORT=5000, the output is "string" because environment variables are exposed as strings.

Q4 — process.exit
console.log("A");
process.exit(0);
console.log("B");

Output: A. The process terminates before the final statement runs.

Q5 — global vs module scope
const name = "Sam";
console.log(global.name);

The local variable does not automatically become global.name.

22. Common Developer Mistakes
  • Calling Node.js a programming language.
  • Assuming browser APIs and Node APIs are identical.
  • Thinking “single-threaded” means Node can never use other execution mechanisms.
  • Thinking non-blocking means an operation finishes instantly.
  • Blocking the JavaScript thread with large CPU-heavy synchronous work.
  • Confusing process.cwd() with __dirname.
  • Forgetting that __dirname and __filename are CommonJS conveniences.
  • Assuming process.env.PORT is a number automatically.
  • Using process.exit() for normal application flow.
  • Committing secrets to source control.
  • Thinking V8 is the entire Node.js runtime.
  • Using too many console.log() statements instead of proper logging.
