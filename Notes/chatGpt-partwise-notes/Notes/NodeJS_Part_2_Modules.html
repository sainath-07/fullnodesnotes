Node.js Interview Preparation • Part 2

🟢 Node.js Modules

Learn how Node.js splits code into reusable files and how CommonJS and ES Modules work.

1. What Is a Module?
What?

A module is a separate piece of code that can be used by another part of an application.

Why / purpose?

Modules help us divide a large application into small, focused files. This makes code easier to read, test, reuse, and maintain.

Layman example

Think about a kitchen. Instead of keeping every tool in one box, you keep knives, plates, and cooking tools in separate places. Each module has a clear responsibility.

Large Application ↓ ┌────┼────────────┐ ↓ ↓ ↓ User Product Payment Module Module Module ↓ ↓ ↓ Reusable and easier to maintain
When to use?
  • When a file becomes too large.
  • When code needs to be reused.
  • When different features have different responsibilities.
  • When you want clear project structure.
Interview-ready: “A module is a self-contained unit of code that helps organize, reuse, and maintain an application.”

3. Built-in Modules

Built-in modules are already included with Node.js. You normally do not install them with npm.

const fs = require("fs");
const path = require("path");
const http = require("http");
Common examples
  • fs — file system operations
  • path — work with file and directory paths
  • http — create HTTP servers
  • events — work with events
  • os — operating system information
  • crypto — cryptographic functionality
Remember: Built-in means Node provides it. You do not need to download it from npm.
4. Local Modules

A local module is code written inside your own project.

// math.js
function add(a, b) {
  return a + b;
}

module.exports = { add };
// app.js
const math = require("./math");

console.log(math.add(10, 20));
app.js ↓ require("./math") math.js ↓ exports.add app.js receives the exported value ↓ 30
Common mistake: For local files, use the path such as ./math. Do not confuse a local module with an npm package name.
5. Third-Party Modules

Third-party modules are packages created by other developers and distributed through npm or another package registry.

npm install express
const express = require("express");
Examples
  • Express — web applications and APIs
  • Axios — HTTP requests
  • Mongoose — MongoDB object modeling
Interview point: Third-party packages are dependencies of your application and are usually recorded in package.json.
6. CommonJS

CommonJS (CJS) is a Node.js module system traditionally used with require() and module.exports.

// math.js
const multiply = (a, b) => a * b;

module.exports = { multiply };
// app.js
const { multiply } = require("./math");

console.log(multiply(4, 5));
math.js │ │ module.exports ↓ Exported object │ │ require("./math") ↓ app.js
Interview-ready: “CommonJS is a module system that uses require() to import values and module.exports to export values.”
7. require()
What?

require() loads a CommonJS module and returns the value that the module exports.

// greet.js
module.exports = function greet(name) {
  return `Hello ${name}`;
};

// app.js
const greet = require("./greet");

console.log(greet("Sam"));

Output: Hello Sam

How it works conceptually
require("./greet") ↓ Resolve module ↓ Check module cache ↓ If not cached → load file ↓ Execute module ↓ Read module.exports ↓ Return exported value
Common mistake: require() does not simply “copy the source code into your file.” Node resolves, loads, executes, caches, and returns the module's exported value.
8. module.exports

module.exports is the actual value that a CommonJS module exports.

// user.js
module.exports = {
  name: "Sam",
  age: 25
};
// app.js
const user = require("./user");

console.log(user.name);
console.log(user.age);
Key idea: require() receives the final exported value from module.exports.
9. exports vs module.exports

At the beginning of a CommonJS module, exports is a reference to module.exports.

exports.add = (a, b) => a + b;

This works because you are adding a property to the same exported object.

module.exports.add = (a, b) => a + b;

This also works.

Important difference
exports = function() {
  console.log("Hello");
};

This does not replace module.exports. You changed the local exports variable to point somewhere else.

To replace the complete exported value, use:

module.exports = function() {
  console.log("Hello");
};
Initially: exports ──────────┐ ↓ module.exports ↓ exported object exports = newValue ↓ Only local exports changes module.exports = newValue ↓ Actual exported value changes
Very common interview question: “Why does exports = something fail while module.exports = something works?” Because reassigning exports breaks its reference to module.exports.
10. Module Loading

When CommonJS loads a module, Node.js performs several conceptual steps.

require("./math") ↓ 1. Resolve module path ↓ 2. Check require.cache ↓ 3. Create module object ↓ 4. Execute module code ↓ 5. Store exported value ↓ 6. Cache module ↓ 7. Return module.exports
Interview tip: Remember the words resolve → cache → execute → export → return.
11. Module Execution

A CommonJS module is executed when it is first loaded. Its top-level code runs during that module load.

// test.js
console.log("test.js executed");

module.exports = { value: 10 };
// app.js
const a = require("./test");
const b = require("./test");

With normal CommonJS caching, "test.js executed" is printed once because the second require() uses the cached module.

12. Module Caching

CommonJS modules are cached after they are loaded. Later require() calls for the same resolved module normally receive the cached exports.

// counter.js
let count = 0;

count++;

module.exports = { count };
const a = require("./counter");
const b = require("./counter");

console.log(a.count); // 1
console.log(b.count); // 1
First require ↓ Load + execute ↓ Cache result ↓ Second require ↓ Use cached module ↓ No second normal execution
Why?

It avoids repeatedly loading and executing the same module.

13. require.cache

require.cache contains cached CommonJS modules for the current process.

console.log(require.cache);

You can inspect whether a module is cached:

const path = require.resolve("./counter");

console.log(require.cache[path] !== undefined);

You can remove a specific cached module:

delete require.cache[require.resolve("./counter")];
Common mistake: Clearing the cache does not magically make an application safe to hot-reload. Modules may have side effects, references, timers, or other state that need careful handling.
14. Circular Dependencies

A circular dependency happens when modules depend on each other directly or indirectly.

a.js ↓ requires b.js ↓ requires a.js ↑ └──────── circular dependency
// a.js
const b = require("./b");

// b.js
const a = require("./a");

CommonJS can return partially initialized exports during a circular dependency. This can create surprising undefined values or incomplete objects.

Common developer mistake: Creating unnecessary circular dependencies. Prefer a third shared module when two modules need common functionality.
Interview-ready: “A circular dependency occurs when module A depends on B and B depends on A. In CommonJS, one module can receive partially initialized exports because loading is still in progress.”
15. ES Modules

ES Modules (ESM) are the standard JavaScript module system. They use import and export.

// math.js
export function add(a, b) {
  return a + b;
}
// app.js
import { add } from "./math.js";

console.log(add(2, 3));
math.js │ │ export ↓ ES module binding │ │ import ↓ app.js
Key idea: ESM is standardized JavaScript syntax and is widely used in modern Node.js projects and frontend applications.
16. import

import brings exported bindings into an ES module.

import { add } from "./math.js";
import { add, subtract } from "./math.js";

Default import:

import UserService from "./UserService.js";

Namespace import:

import * as math from "./math.js";

console.log(math.add(2, 3));
Common mistake: Import syntax must match the export style. Named exports and default exports are different concepts.
17. export

export makes declarations available to other ES modules.

export const name = "Sam";

export function greet() {
  return "Hello";
}

You can also export later:

const age = 25;

export { age };
Interview point: ESM exports are bindings, not simply copies of values. The imported binding is connected to the exported binding.
18. .mjs

A .mjs file is explicitly treated as an ES module by Node.js.

// math.mjs
export const add = (a, b) => a + b;
// app.mjs
import { add } from "./math.mjs";
Simple rule: .mjs clearly tells Node.js: “Treat this file as an ES module.”
19. "type": "module"

You can configure a package so that .js files are treated as ES modules.

{
  "type": "module"
}

Then:

// math.js
export const add = (a, b) => a + b;

// app.js
import { add } from "./math.js";
package.json │ └── "type": "module" ↓ .js files ↓ ES Module mode
Common mistake: Mixing CommonJS and ESM syntax without understanding which module system Node is treating the file as.

21. Interoperability
What?

Interoperability means CommonJS and ES Modules can work together, but the rules are not identical in both directions.

CommonJS ↕ Interoperability rules ↕ ES Modules
Important practical idea

ES modules can use dynamic import() to load modules. CommonJS can also use dynamic import(). Directly treating require() and import as interchangeable is not correct.

// CommonJS can dynamically import an ES module
async function load() {
  const math = await import("./math.mjs");
  console.log(math.add(2, 3));
}
Common mistake: Expecting every CommonJS package to have exactly the same import shape in ESM. Package export style and Node's interoperability rules matter.
For interviews: Explain the difference at a high level rather than memorizing every edge case. If a real project mixes systems, check the package's module format and Node.js documentation.
22. Output-Based Interview Questions
Question 1 — exports reference
// a.js
exports.name = "Sam";
console.log(module.exports.name);

Answer: Sam

Why? Initially, exports refers to the same export object as module.exports. Adding a property changes that shared object.

Question 2 — exports reassignment
// a.js
exports = { name: "Sam" };
console.log(module.exports.name);

Answer: undefined

Why? Reassigning exports changes only the local variable. It does not replace module.exports.

Question 3 — module caching
// counter.js
console.log("Executed");
module.exports = Math.random();
const a = require("./counter");
const b = require("./counter");

console.log(a === b);

Answer: Executed prints once, then true.

Why? The first require executes and caches the module. The second require gets the cached export.

Question 4 — complete export replacement
// math.js
module.exports = function add(a, b) {
  return a + b;
};
const add = require("./math");
console.log(add(2, 5));

Answer: 7

Why? module.exports was replaced with a function, so require() returns that function directly.

Question 5 — cache removal
const path = require.resolve("./counter");

const a = require("./counter");
delete require.cache[path];
const b = require("./counter");

What can happen? The module can be loaded and executed again because its cache entry was removed.

Why? The next require no longer finds that module in the CommonJS cache.

Question 6 — ESM syntax
// math.js
export const x = 10;
import { x } from "./math.js";

console.log(x);

Answer: 10, assuming the file is correctly configured as an ES module.

Why? x is a named export and is imported using the matching named import syntax.

Question 7 — default vs named export
export default function greet() {}
export const age = 25;

Correct imports:

import greet, { age } from "./user.js";

Why? The default export is imported without braces; the named export uses braces.

23. Common Developer Mistakes
  • Confusing a module with a package.
  • Forgetting ./ when requiring a local CommonJS file.
  • Using exports = value when you intended to replace module.exports.
  • Assuming every require() executes the module again.
  • Forgetting that CommonJS modules are cached.
  • Creating unnecessary circular dependencies.
  • Mixing require and import without knowing the module type.
  • Forgetting that .mjs is ESM.
  • Forgetting that "type": "module" changes how .js files are interpreted within that package scope.
  • Confusing default and named exports.
  • Assuming CommonJS and ESM interoperability works exactly the same in every direction.
  • Thinking require.cache is a normal application state store.
