🟢 Part 29 — Logging & Monitoring ⭐⭐⭐

Learn how production Node.js applications record events, detect problems and understand system health.

1. What is Logging?

What: Logging means recording useful information about what an application is doing.

Why: When a user reports a problem, logs help developers understand what happened without guessing.

Layman example: A shop keeps a register of sales, returns and important events. Application logs are a similar activity record.

Interview line: Logging records application events; monitoring observes system health and behavior over time.
2. console

Node.js provides console methods for simple output.

console.log("Server started"); console.info("User logged in"); console.warn("Cache is nearly full"); console.error("Database connection failed");

When to use: console is useful for local development and simple scripts. Production applications commonly use a logging library for levels, structured output, transports and consistent formatting.

Common mistake: Leaving large amounts of random console.log() output in production makes debugging harder and can expose sensitive information.
3. Logging Levels

Logging levels tell us how important a message is.

LevelSimple meaningExample
traceVery detailed debugging informationInternal execution detail
debugDeveloper troubleshooting informationQuery parameters used by a service
infoNormal important eventsServer started
warnSomething unusual but not necessarily a failureRetrying a request
errorAn operation failedDatabase query failed
fatalVery serious failureApplication cannot start
Interview point: Production logging should be intentional. Do not log everything at the highest severity.
4. Winston

Winston is a popular Node.js logging library. It supports logging levels, formats and different destinations called transports.

const winston = require("winston"); const logger = winston.createLogger({ level: "info", format: winston.format.json(), transports: [ new winston.transports.Console() ] }); logger.info("Server started");

When to use: Use Winston when your application needs flexible logging configuration and multiple output destinations.

5. Pino

Pino is a fast Node.js logger designed around structured logging and low overhead.

const pino = require("pino"); const logger = pino(); logger.info({ userId: 42 }, "User logged in");
Interview point: Winston and Pino are both Node.js logging libraries. Pino is especially known for high performance and structured JSON logging.
6. Structured Logs ⭐⭐⭐

What: Structured logs store information as fields, usually JSON, instead of only a free-form sentence.

{ "level": "info", "message": "User logged in", "userId": 42, "requestId": "req-8f21", "service": "auth" }

Why: Log systems can search and filter fields such as userId, requestId, service and level.

Layman example: A handwritten note says “Sam bought a phone.” A structured record stores customer=Sam, product=phone and event=purchase separately, making it easier to search.
7. Request Logging

Request logging records useful HTTP information such as method, route, status code, duration and request ID.

{ "level": "info", "method": "GET", "route": "/api/users", "statusCode": 200, "durationMs": 34, "requestId": "req-123" }

8. Error Logging

Error logs should contain enough context to diagnose a failure.

logger.error({ message: err.message, stack: err.stack, requestId, route: req.originalUrl });

Useful fields can include error type, message, stack trace, request ID, route and safe contextual data.

Security rule: Never blindly log passwords, access tokens, session secrets, API keys or other sensitive data.

11. Metrics

Metrics are numerical measurements collected over time.

  • Request rate: requests per second/minute.
  • Error rate: percentage or count of failed requests.
  • Latency: how long requests take.
  • CPU usage: processor usage.
  • Memory usage: RAM usage.
  • Database metrics: query time, connections and failures.
Interview point: A common production view is request rate + error rate + latency, combined with resource and dependency health.
12. Health Checks

Health endpoints give infrastructure a simple way to check whether an application is functioning.

app.get("/health", (req, res) => { res.status(200).json({ status: "ok" }); });

When to use: Load balancers, orchestrators and monitoring systems can call health endpoints.

16. Production Debugging

Production debugging means investigating real problems while minimizing risk to users.

A simple process
  1. Check alerts and dashboards.
  2. Find the affected endpoint or service.
  3. Search logs using the request/correlation ID.
  4. Check error rate and latency.
  5. Check dependencies such as database or external APIs.
  6. Compare the timing with recent deployments or configuration changes.
  7. Fix safely, verify the result and document the root cause.
Common mistake: Debugging production by adding random logs and restarting services repeatedly can hide the original problem. Prefer controlled investigation using existing observability data.

18. Common Developer Mistakes
  1. Logging sensitive information such as passwords or tokens.
  2. Using only console.log() for a production system.
  3. Writing unstructured messages that are difficult to search.
  4. Using the wrong log level for important errors.
  5. Not including request/correlation IDs.
  6. Logging errors without useful context.
  7. Creating health checks that are too expensive.
  8. Confusing “process is alive” with “application is ready for traffic.”
  9. Collecting metrics without alerts or useful dashboards.
  10. Ignoring latency and focusing only on error count.
  11. Exposing internal error details to API clients.
  12. Keeping unlimited logs without a retention strategy.
