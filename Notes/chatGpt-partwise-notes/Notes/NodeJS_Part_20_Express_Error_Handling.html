🟢 Part 20 — Express Error Handling ⭐⭐⭐

Learn how to catch, classify, propagate, log, and safely return errors from Express APIs.

Simple English • Practical code • Interview questions • Production thinking

1. What is Error Handling?

Error handling means deciding what your application should do when something goes wrong.

Layman example: Imagine a restaurant. If the kitchen cannot prepare a dish, the waiter should not disappear. The problem should be reported, the customer should receive a clear response, and the restaurant should record what happened.
Client request ↓ Route / Middleware ↓ Something fails ↓ next(error) ↓ Global Error Handler ↓ Log technical details ↓ Safe HTTP response ↓ Client
Interview line: “Centralized error handling keeps route handlers simple and gives the API a consistent error response.”
2. Error Middleware

Express error middleware is middleware specifically used to handle errors.

The important difference is that it has four parameters:

app.use((err, req, res, next) => {
  // handle error
});
Interview trap: Express identifies error-handling middleware by its four-argument signature: (err, req, res, next).
3. Four-Argument Middleware
app.use((err, req, res, next) => {
  console.error(err);

  res.status(500).json({
    message: "Something went wrong"
  });
});

The first argument is the error. The other arguments are the normal Express request, response, and next function.

Why? Express uses the four-argument signature to recognize that this middleware is an error handler.
4. next(error)

Calling next(error) tells Express: “There is an error. Skip normal middleware and move to error handling.”

app.get("/users", (req, res, next) => {
  try {
    throw new Error("Database failed");
  } catch (err) {
    next(err);
  }
});
Route ↓ next(error) ↓ Express error pipeline ↓ Error middleware ↓ Response
5. Synchronous Errors

Errors thrown synchronously inside an Express handler are automatically caught by Express and passed toward error handling.

app.get("/test", (req, res) => {
  throw new Error("Something failed");
});
Important: You should still design a centralized error handler. Do not send stack traces or sensitive details to production users.
6. Async Errors

Async errors need careful handling. In modern Express, rejected promises from route handlers are handled differently depending on the Express version and setup. A common pattern is still to use a wrapper so your code is explicit and consistent.

const asyncHandler = (fn) =>
  (req, res, next) =>
    Promise.resolve(fn(req, res, next))
      .catch(next);

app.get("/users", asyncHandler(async (req, res) => {
  const users = await getUsers();
  res.json(users);
}));
Common mistake: Assuming every async error will automatically reach your error middleware regardless of your Express version or wrapper setup.
7. Promise Rejection

A Promise can reject. If that rejection is not properly forwarded to Express, the request may not receive the expected error response.

app.get("/users", async (req, res, next) => {
  try {
    const users = await getUsers();
    res.json(users);
  } catch (err) {
    next(err);
  }
});
Interview line: “Async failures must enter the Express error pipeline; otherwise the client may not receive a proper API response.”
8. Custom Error Classes

Custom errors allow you to attach useful information such as HTTP status codes and error types.

class AppError extends Error {
  constructor(message, statusCode, code) {
    super(message);
    this.statusCode = statusCode;
    this.code = code;
  }
}

throw new AppError(
  "User not found",
  404,
  "USER_NOT_FOUND"
);
AppError ├── message ├── statusCode └── code ↓ Global error handler ↓ Consistent API response
9. HTTP Error Responses

Invalid request data400 Bad Request
Not authenticated401 Unauthorized

Do not overuse 500. A missing user is normally a 404, while invalid credentials are commonly 401. Choose a status code that describes the client-visible problem.
10. 404 Handling

A 404 handler is commonly placed after all valid routes.

app.use((req, res) => {
  res.status(404).json({
    message: "Route not found"
  });
});
Request ↓ Route 1? No ↓ Route 2? No ↓ All routes finished ↓ 404 handler ↓ 404 response
11. Validation Errors
if (!req.body.email) {
  return next(new AppError(
    "Email is required",
    400,
    "VALIDATION_ERROR"
  ));
}

Validation errors should return a useful but safe message. Avoid exposing internal database or server details.

12. Authentication vs Authorization Errors
401 — Authentication
The server cannot treat the request as authenticated. Example: missing or invalid access token.
403 — Authorization
The user is authenticated but does not have permission to perform the action.
if (!user) {
  return next(new AppError(
    "Authentication required",
    401,
    "AUTH_REQUIRED"
  ));
}

if (user.role !== "admin") {
  return next(new AppError(
    "Access denied",
    403,
    "FORBIDDEN"
  ));
}
13. Database Errors

Database failures should be converted into safe API errors. Do not expose raw database messages, SQL statements, connection strings, or stack traces.

try {
  const user = await User.findById(req.params.id);
  res.json(user);
} catch (err) {
  next(new AppError(
    "Database operation failed",
    500,
    "DATABASE_ERROR"
  ));
}
Security rule: Log the detailed technical error internally, but send only the necessary safe message to the client.
14. Global Error Handler
app.use((err, req, res, next) => {
  const statusCode = err.statusCode || 500;

  console.error({
    message: err.message,
    stack: err.stack,
    path: req.path,
    method: req.method
  });

  res.status(statusCode).json({
    success: false,
    error: {
      code: err.code || "INTERNAL_ERROR",
      message: statusCode >= 500
        ? "Internal server error"
        : err.message
    }
  });
});
Why centralized handling? Every route does not need to repeat the same response and logging logic.
15. Error Response Format

A consistent error format makes frontend development easier.

{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Email is required"
  }
}

For validation errors, you may also include structured field errors:

{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Please fix the input",
    "fields": {
      "email": "Email is required",
      "age": "Age must be a number"
    }
  }
}
16. Production vs Development Error Messages
Development
Detailed stack traces and technical information can help debugging.
Production
Return safe, generic messages for unexpected internal failures.
const isProduction = process.env.NODE_ENV === "production";

res.status(500).json({
  success: false,
  message: isProduction
    ? "Internal server error"
    : err.message,
  ...(isProduction ? {} : { stack: err.stack })
});
Common mistake: Returning err.stack to real users in production.
17. Logging Errors

Good logs help developers find the real problem.

Useful information can include:

  • Error message and stack.
  • HTTP method and route.
  • Request ID or correlation ID.
  • Timestamp.
  • Relevant safe identifiers.
  • Environment and service information.
Never log secrets such as passwords, access tokens, refresh tokens, API keys, or sensitive credentials.
18. Error Propagation
Database / Service error ↓ Repository / Service ↓ Controller ↓ next(error) ↓ Global error handler ↓ Log ↓ Safe HTTP response

Propagation means allowing the error to move through the application until the correct layer handles it.

Do not catch an error only to silently ignore it. Either handle it correctly or propagate it.
19. Graceful API Failure

A good API should fail in a controlled way instead of crashing, hanging, or returning random responses.

Request ↓ Validate ↓ Execute business logic ↓ Failure? ├─ No → Success response └─ Yes ↓ next(error) ↓ Central handler ↓ Log safely ↓ Correct HTTP status ↓ Safe JSON response
20. Complete Express Error Handling Example
const express = require("express");

const app = express();
app.use(express.json());

class AppError extends Error {
  constructor(message, statusCode, code) {
    super(message);
    this.statusCode = statusCode;
    this.code = code;
  }
}

const asyncHandler = (fn) =>
  (req, res, next) =>
    Promise.resolve(fn(req, res, next)).catch(next);

app.get("/users/:id", asyncHandler(async (req, res) => {
  if (!req.params.id) {
    throw new AppError(
      "User ID is required",
      400,
      "VALIDATION_ERROR"
    );
  }

  // Imagine this comes from a database.
  const user = null;

  if (!user) {
    throw new AppError(
      "User not found",
      404,
      "USER_NOT_FOUND"
    );
  }

  res.json({
    success: true,
    data: user
  });
}));

// 404 handler — after valid routes
app.use((req, res) => {
  res.status(404).json({
    success: false,
    error: {
      code: "ROUTE_NOT_FOUND",
      message: "Route not found"
    }
  });
});

// Global error handler — last
app.use((err, req, res, next) => {
  console.error(err);

  const statusCode = err.statusCode || 500;
  const production = process.env.NODE_ENV === "production";

  res.status(statusCode).json({
    success: false,
    error: {
      code: err.code || "INTERNAL_ERROR",
      message: statusCode >= 500 && production
        ? "Internal server error"
        : err.message
    }
  });
});

app.listen(3000);
21. Common Developer Mistakes
  1. Forgetting the four arguments in error middleware.
  2. Putting the error handler before routes.
  3. Not forwarding async errors.
  4. Sending two responses for the same request.
  5. Using 500 for every kind of error.
  6. Returning stack traces in production.
  7. Logging passwords and tokens.
  8. Swallowing errors inside a catch block.
  9. Returning database error details to clients.
  10. Creating a different error response format in every route.
  11. Forgetting a final 404 route handler.
  12. Mixing authentication failures and authorization failures.
  13. Letting failed requests hang without a response.
  14. Using broad try/catch blocks that hide the actual source of a bug.
22. Quick Recap
  • next(error) sends an error into Express's error pipeline.
  • Error middleware uses (err, req, res, next).
  • Put the global error handler after routes and the 404 handler.
  • Async Promise failures must reach the Express error handler.
  • Custom errors can carry status codes and error codes.
  • Use appropriate HTTP status codes.
  • Return safe messages in production.
  • Log detailed technical information internally.
  • Never log secrets.
  • Keep API error responses consistent.
  • Handle 404 separately from unexpected server errors.

24. Interview Questions — Show / Hide Answers
Q1. Why does Express error middleware have four parameters?
Answer: Express recognizes (err, req, res, next) as error-handling middleware.
Why? The first parameter identifies the error and tells Express that this middleware belongs to the error pipeline.
Q2. What does next(error) do?
Answer: It forwards the error to Express error handling.
Why? It prevents each route from having to manually create the complete error response.
Q3. Where should the global error handler be placed?
Answer: Normally after the application routes and the final 404 handler.
Why? It needs to be available after errors are generated by the earlier middleware and route handlers.
Q4. Find the problem. 
app.use((err, req, res) => {
  res.status(500).json({ message: err.message });
});
Answer: The standard error-handler signature is incomplete because it should have four parameters: (err, req, res, next).
Why? Express uses the four-argument signature to identify error-handling middleware.
Q5. What is the difference between a 401 and 403?
Answer: 401 means the request is not successfully authenticated. 403 means the requester is authenticated but is not allowed to perform the action.
Why? Authentication asks “Who are you?” Authorization asks “Are you allowed?”
Q6. What status code would you normally return when a user does not exist?
Answer: Usually 404 Not Found.
Why? The requested resource could not be found.
Q7. What is wrong with this production error response? 
res.status(500).json({
  message: err.message,
  stack: err.stack
});
Answer: Returning stack traces and raw internal messages can expose implementation details.
Why? Attackers may learn paths, libraries, database details, or internal logic. Log the details internally and return a safe production message.
Q8. Why use a custom error class?
Answer: It can carry application-specific information such as status code and error code.
Why? The global handler can convert many different failures into a consistent HTTP response.
Q9. What is error propagation?
Answer: Error propagation means passing an error from the layer where it occurs to the layer responsible for handling it.
Why? A database or service layer can report the failure while a centralized API layer controls the final HTTP response.
Q10. Find the async error-handling problem. 
app.get("/users", async (req, res) => {
  const users = await getUsers();
  res.json(users);
});
Answer: The code does not explicitly show how a rejected Promise reaches the Express error handler.
Fix: Use a supported Express async-error mechanism or a wrapper such as Promise.resolve(fn(...)).catch(next).
Why? Async failures must reach the error pipeline.
Q11. What happens when next(error) is called?
Answer: Express skips normal middleware and searches for error-handling middleware.
Why? Passing an argument to next tells Express that the current flow contains an error.
Q12. Why should you avoid swallowing errors?
Answer: A swallowed error disappears without being handled or logged.
Why? The request may fail silently, debugging becomes harder, and the client may receive an incorrect success response.
Q13. Where should the 404 handler be placed?
Answer: After all valid routes.
Why? If it comes earlier, it can catch requests before the correct route has a chance to handle them.
Q14. Why should the API return a consistent error format?
Answer: A consistent format makes frontend and client-side error handling predictable.
Why? The frontend can always look for the same fields such as success, code, and message.
Q15. Design the error flow for a database failure.
Answer:
Database fails ↓ Catch / reject ↓ next(error) ↓ Global error handler ↓ Log detailed error ↓ 500 response ↓ Safe client message
Why? The client does not need internal database details, while developers still need the technical information in logs.
Q16. Should every error return HTTP 500?
Answer: No.
Why? 500 means an unexpected server-side failure. Client errors such as invalid input or missing resources should use suitable status codes such as 400 or 404.
Q17. What is graceful API failure?
Answer: It means the API handles failures predictably by returning an appropriate status and safe response instead of hanging, exposing internals, or crashing unnecessarily.
Why? Clients can recover or show a useful message, and the service remains easier to operate.
Q18. Why should errors be logged centrally?
Answer: Centralized logging gives developers one place to capture important error information.
Why? It reduces duplicated logging code and makes production debugging easier.
Q19. What is the danger in this catch block? 
try {
  await saveUser();
} catch (err) {
  console.log("failed");
}
Answer: The error is caught but not propagated or converted into a response.
Why? The request may continue in an incorrect state or fail to return the expected error response. Use next(err) or handle the failure completely.
Q20. Why is centralized error handling important in a large Express application?
Answer: It provides one consistent place for status mapping, logging, response formatting, and production-safe messages.
Why? Without it, every route may implement errors differently, causing duplicated code and inconsistent API behavior.
