🟢 Part 24 — API Architecture ⭐⭐⭐

Learn how to organize an Express application so that routes, controllers, services, models and infrastructure stay easy to understand, test and scale.

1. What is API Architecture?

What: API architecture is the way we organize an API's code, responsibilities and flow.

Why: A small Express application can work with a few files. A large application needs clear boundaries so one file does not contain routes, business rules, database queries, validation and error handling all together.

Layman example: Think of a restaurant. The waiter takes your order, the kitchen prepares it, the store provides ingredients, and the manager handles rules. Each person has a different job.

Interview line: Good API architecture separates responsibilities so each layer has a clear job and can change with minimal impact on other layers.
2. Separation of Concerns

Meaning: Each part of the application should focus on a specific responsibility.

LayerMain responsibility
RoutesMap HTTP methods and URLs to handlers.
MiddlewareRun reusable request/response processing such as auth, logging and validation.
ControllerHandle HTTP input/output and coordinate the use case.
ServiceContain business rules and application logic.
RepositoryHandle database access when this abstraction is useful.
ModelRepresent database data and model-level behavior.
Common mistake: Do not create layers only because a diagram says so. The goal is clear responsibility. Very small applications may need fewer layers.
3. MVC — Model, View, Controller

In an API, MVC is commonly adapted because there is usually no server-rendered HTML view. The important pieces are the model and controller, with services often added for business logic.

Controller: receives HTTP input, calls application logic and sends the HTTP response.

Model: represents the data layer or database model.

View: in a REST API, the response is often JSON rather than a traditional HTML view.

4. Routes

Routes define which HTTP method and URL should execute which handler.

router.get("/users/:id", userController.getUser); router.post("/users", userController.createUser); router.patch("/users/:id", userController.updateUser); router.delete("/users/:id", userController.deleteUser);

When to use: Keep routes focused on HTTP mapping rather than business logic.

Good route: router.post("/users", userController.createUser)
Avoid: Putting 50 lines of database and business logic directly inside the route callback.
5. Controllers

The controller is the HTTP-facing layer.

async function getUser(req, res, next) { try { const user = await userService.getUserById(req.params.id); res.status(200).json({ success: true, data: user }); } catch (error) { next(error); } }

Controller responsibility: read request data, call the appropriate service, choose an HTTP status and format the response.

Interview tip: A controller should coordinate the request, not become the place where all business rules live.
6. Services

A service contains business or application logic that should not be tied closely to Express's req and res objects.

async function getUserById(userId) { const user = await userRepository.findById(userId); if (!user) { throw new Error("User not found"); } return user; }

Why: Services are easier to reuse and test when they are independent of HTTP details.

7. Repository Pattern

A repository is an abstraction around data access.

const userRepository = { findById(id) { return User.findById(id); }, create(data) { return User.create(data); } };

When useful: Large applications, complex data access or projects where you want business logic separated from database-specific code.

Important: A repository layer is not mandatory for every Express application.

9. Middleware

Middleware runs during the request pipeline and can inspect or modify the request/response, end the request, or pass control with next().

function requireAuth(req, res, next) { const token = req.headers.authorization; if (!token) { return res.status(401).json({ message: "Authentication required" }); } next(); }

Common middleware: authentication, authorization, validation, logging, rate limiting and error handling.

10. Dependency Injection

What: Dependency injection means giving a component the dependencies it needs instead of having it create those dependencies internally.

function createUserService(userRepository) { return { async createUser(data) { return userRepository.create(data); } }; } const userService = createUserService(userRepository);

Why: It makes components easier to test because you can provide a fake repository instead of a real database repository.

Layman example: Instead of a chef buying and building a stove every time, give the chef a ready-to-use stove. The chef can focus on cooking.
11. Configuration Management

Configuration includes database URLs, ports, API keys, feature flags and environment-specific settings.

PORT=5000 MONGO_URI=mongodb://localhost:27017/myapp NODE_ENV=development
require("dotenv").config(); const config = { port: Number(process.env.PORT) || 5000, mongoUri: process.env.MONGO_URI, nodeEnv: process.env.NODE_ENV || "development" }; module.exports = config;
Security: Never commit real passwords, private keys or production secrets to source control.

13. Recommended Folder Structure
src/ ├── app.js ├── server.js ├── config/ │ └── config.js ├── routes/ │ ├── user.routes.js │ └── order.routes.js ├── controllers/ │ ├── user.controller.js │ └── order.controller.js ├── services/ │ ├── user.service.js │ └── order.service.js ├── repositories/ │ ├── user.repository.js │ └── order.repository.js ├── models/ │ ├── user.model.js │ └── order.model.js ├── middleware/ │ ├── auth.middleware.js │ ├── validation.middleware.js │ └── error.middleware.js ├── validators/ ├── utils/ └── logs/
Note: There is no single correct folder structure. Organize around the team's needs, application size and maintainability.
14. Reusable Utilities

Utilities contain small reusable helpers that do not belong to a particular business layer.

// utils/asyncHandler.js const asyncHandler = (handler) => { return (req, res, next) => { Promise.resolve(handler(req, res, next)) .catch(next); }; }; module.exports = asyncHandler;

Other examples can include date formatting, ID generation or safe parsing helpers.

Common mistake: Do not create one giant utils.js file containing unrelated business logic.

class AppError extends Error { constructor(message, statusCode) { super(message); this.statusCode = statusCode; } } app.use((err, req, res, next) => { console.error(err); const status = err.statusCode || 500; res.status(status).json({ success: false, message: status === 500 ? "Internal server error" : err.message }); });

Why: Centralized error handling avoids repeating the same response and logging logic in every controller.

16. API Response Architecture

A consistent response shape makes frontend integration easier.

{ "success": true, "data": { "id": "123", "name": "Sam" } }
{ "success": false, "message": "User not found", "errorCode": "USER_NOT_FOUND" }
Good practice: Decide on a consistent API response style, document it and use it across the project.

Good logs: request ID, method, route, status code, duration and useful error context.

Avoid: passwords, access tokens, private keys and sensitive personal information.

18. Large Application Structure

As the application grows, grouping files by feature can become easier to maintain than keeping every controller, service and route in huge global folders.

src/ ├── modules/ │ ├── users/ │ │ ├── user.routes.js │ │ ├── user.controller.js │ │ ├── user.service.js │ │ ├── user.repository.js │ │ ├── user.model.js │ │ └── user.validation.js │ └── orders/ │ ├── order.routes.js │ ├── order.controller.js │ ├── order.service.js │ ├── order.repository.js │ ├── order.model.js │ └── order.validation.js ├── config/ ├── middleware/ └── utils/

Benefit: Code related to one business feature stays together.

20. Common Developer Mistakes
  1. Putting database queries directly in route files.
  2. Putting business rules inside controllers.
  3. Making controllers extremely large.
  4. Creating unnecessary layers in a tiny project.
  5. Sharing global mutable state between unrelated requests.
  6. Scattering configuration and secrets throughout the application.
  7. Returning different response shapes for similar endpoints without a reason.
  8. Logging passwords, tokens or sensitive data.
  9. Duplicating error handling in every route.
  10. Creating a repository layer without a real need for the abstraction.
  11. Making services depend directly on Express req and res.
  12. Using dependency injection as a pattern without understanding why it helps testing or flexibility.
21. Quick Recap
  • Routes map HTTP requests to handlers.
  • Controllers handle HTTP input and output.
  • Services contain business/application rules.
  • Repositories can isolate database access.
  • Models represent database data and model behavior.
  • Middleware handles reusable request pipeline behavior.
  • Dependency injection makes dependencies explicit and can improve testability.
  • Configuration should be centralized and environment-aware.
  • Error handling should be consistent and centralized.
  • Logging should help debugging without exposing secrets.
  • For large systems, organize code by feature when it improves maintainability.
22. Interview-Ready Points ⭐⭐⭐
  • Separation of concerns: each layer has a focused responsibility.
  • Controller vs service: controller handles HTTP; service handles application/business logic.
  • Service vs repository: service decides what should happen; repository handles data access.
  • Why centralize errors? consistent responses, logging and less duplicated code.
  • Why dependency injection? explicit dependencies and easier testing/replacement.
  • Why configuration management? separate environment-specific values from application logic.
  • Why connection/config modules? prevent infrastructure details from spreading throughout the codebase.
  • Scalable architecture: organize around clear boundaries, not merely around the number of folders.
