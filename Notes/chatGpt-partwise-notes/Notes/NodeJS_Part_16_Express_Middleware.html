🟢 Part 16 — Express Middleware ⭐⭐⭐

A practical, interview-ready guide to understanding how middleware works in Express.js.

Simple English • Examples • Visual flow • Common mistakes • Interview questions

1. What is Middleware?

Middleware is a function that runs between the incoming request and the final response.

It can inspect the request, change the request, change the response, perform some work, stop the request, or pass control to the next function.

Client → Request → Middleware 1 → Middleware 2 → Route Handler → Response
Layman example: Think of a security gate at an office. Before you reach the room, the guard checks your ID. Middleware works like that gate.
Basic shape
app.use((req, res, next) => {
  console.log("Middleware ran");
  next();
});

next() tells Express: “I am done. Continue to the next middleware or route handler.”

2. Why / Purpose of Middleware
  • Authentication: check whether a user is logged in.
  • Authorization: check whether the user has permission.
  • Logging: record request information.
  • Validation: check incoming data.
  • Request modification: attach useful data to req.
  • Error handling: handle errors in one place.
  • Common setup: JSON parsing, cookies, CORS, etc.
Interview line: “Express middleware provides reusable request-processing logic and controls whether execution continues through the middleware chain.”
3. How Middleware Works
app.use((req, res, next) => {
  console.log("Step 1");
  next();
});

app.use((req, res, next) => {
  console.log("Step 2");
  next();
});

app.get("/users", (req, res) => {
  res.send("Users");
});
Request → Step 1 → next() → Step 2 → next() → /users handler → Response
Important: If middleware neither sends a response nor calls next(), the request can remain stuck.

5. Application Middleware

Application middleware is attached to the Express application using app.use().

const express = require("express");
const app = express();

app.use((req, res, next) => {
  console.log(req.method, req.url);
  next();
});

app.get("/", (req, res) => {
  res.send("Home");
});

It can run for many routes, depending on where it is registered.

6. Router Middleware

Router middleware is attached to an express.Router(). It helps keep large applications organized.

const express = require("express");
const router = express.Router();

router.use((req, res, next) => {
  console.log("User router middleware");
  next();
});

router.get("/profile", (req, res) => {
  res.json({ name: "Sam" });
});

app.use("/users", router);
GET /users/profile → /users router → router middleware → /profile handler
7. Built-in, Third-party and Custom Middleware
Built-in
app.use(express.json());

This parses JSON request bodies and makes the data available through req.body.

Third-party
const cors = require("cors");
app.use(cors());

Third-party middleware is installed separately and adds functionality.

Custom
function logger(req, res, next) {
  console.log(`${req.method} ${req.url}`);
  next();
}

app.use(logger);
8. Middleware Order ⭐⭐⭐

Middleware normally executes in the order in which it is registered.

app.use((req, res, next) => {
  console.log("A");
  next();
});

app.use((req, res, next) => {
  console.log("B");
  next();
});

app.get("/", (req, res) => {
  console.log("C");
  res.send("Done");
});

Output:

A
B
C
Interview point: A middleware registered after a route will not normally run for a request if that route already sends the response.
9. Multiple Middleware Functions
function first(req, res, next) {
  console.log("first");
  next();
}

function second(req, res, next) {
  console.log("second");
  next();
}

app.get("/data", first, second, (req, res) => {
  res.json({ message: "success" });
});
Request → first → next() → second → next() → route handler → Response
10. Request Modification

Middleware can attach information to the request object.

function userMiddleware(req, res, next) {
  req.user = {
    id: 101,
    role: "admin"
  };
  next();
}

app.get("/dashboard", userMiddleware, (req, res) => {
  res.json({
    message: "Welcome",
    user: req.user
  });
});
Common pattern: authentication middleware verifies a token and attaches the decoded user to req.user.
11. Response Modification

Middleware can modify response-related properties before the final response is sent.

app.use((req, res, next) => {
  res.setHeader("X-App-Version", "1.0");
  next();
});

Be careful not to send a response too early if another handler still needs to run.

12. Authentication vs Authorization Middleware
Authentication = Who are you?
function authenticate(req, res, next) {
  const token = req.headers.authorization;

  if (!token) {
    return res.status(401).json({ message: "Login required" });
  }

  req.user = { id: 10, role: "admin" };
  next();
}
Authorization = Are you allowed?
function requireAdmin(req, res, next) {
  if (req.user?.role !== "admin") {
    return res.status(403).json({ message: "Forbidden" });
  }
  next();
}

app.get("/admin", authenticate, requireAdmin, (req, res) => {
  res.send("Admin area");
});
Request → Authentication → Authorization → Controller
Remember: 401 usually means authentication is missing/invalid. 403 means the identity is known but access is not allowed.
13. Logging Middleware
function logger(req, res, next) {
  const start = Date.now();

  res.on("finish", () => {
    const time = Date.now() - start;
    console.log(req.method, req.originalUrl, res.statusCode, `${time}ms`);
  });

  next();
}

app.use(logger);

This records useful information about requests and responses.

14. Validation Middleware
function validateUser(req, res, next) {
  const { name, email } = req.body;

  if (!name || !email) {
    return res.status(400).json({
      message: "name and email are required"
    });
  }

  next();
}

app.post("/users", validateUser, (req, res) => {
  res.status(201).json(req.body);
});

Validation middleware keeps validation logic outside the route handler.

15. next() — The Most Important Function

next() passes control to the next matching middleware.

app.use((req, res, next) => {
  console.log("Before");
  next();
  console.log("After");
});

app.get("/", (req, res) => {
  console.log("Route");
  res.send("OK");
});

The code after next() does not execute immediately after the next middleware. The current function continues after next() returns.

Possible output:

Before
Route
After
Best practice: If middleware sends a response, use return when needed so execution does not continue accidentally.
16. Error Middleware ⭐⭐⭐

Error middleware has four parameters:

(err, req, res, next)
app.get("/test", (req, res, next) => {
  const error = new Error("Something failed");
  next(error);
});

app.use((err, req, res, next) => {
  console.error(err.message);

  res.status(500).json({
    message: "Internal server error"
  });
});
Route → next(error) → Error middleware → Error response
Important: Error middleware must be registered after the normal routes/middleware that can pass errors to it.
17. Async Middleware

Modern Express applications often use asynchronous operations such as database calls.

async function loadUser(req, res, next) {
  try {
    const user = await getUserFromDatabase(req.params.id);

    if (!user) {
      return res.status(404).json({ message: "User not found" });
    }

    req.user = user;
    next();
  } catch (error) {
    next(error);
  }
}
Interview point: The important idea is not to let an asynchronous failure disappear. Pass the error to the error-handling flow.

19. Common Middleware Mistakes
  1. Forgetting next() when the middleware should continue.
  2. Calling next() after already sending a response.
  3. Registering middleware in the wrong order.
  4. Putting error middleware before the routes.
  5. Forgetting return after an early response.
  6. Doing expensive blocking work inside middleware.
  7. Trusting user input without validation.
  8. Confusing authentication with authorization.
  9. Not passing asynchronous errors to the error handler.
  10. Putting global middleware where route-specific middleware is enough.
20. Interview Quick Recap
  • Middleware runs between request and response.
  • next() moves execution forward.
  • Middleware order matters.
  • Middleware can modify req and response-related data.
  • Authentication checks identity; authorization checks permission.
  • Error middleware uses (err, req, res, next).
  • Application middleware uses app.use().
  • Router middleware uses router.use().
  • Built-in middleware includes express.json().
  • Middleware can be global, router-specific, or route-specific.
21. Interview-Ready Questions
Q1. What is Express middleware?
Answer: Middleware is a function that can access req, res, and next during request processing.
Why? It lets us reuse common logic such as logging, authentication, validation, and error handling.
Q2. What happens if middleware does not call next() and does not send a response?
Answer: The request can remain pending because Express has not been told to continue and no response was sent.
Why? Express is waiting for the current middleware to finish its job.
Q3. Predict the output. 
app.use((req,res,next) => {
  console.log("A");
  next();
});

app.get("/", (req,res) => {
  console.log("B");
  res.send("OK");
});
Answer:
A
B
Why? The application middleware matches the request first, calls next(), and then the route handler runs.
Q4. Why is middleware order important?
Answer: Express processes matching middleware in registration order.
Why? If authentication is registered after a route that already sends a response, that route may be reached without the authentication check.
Q5. What is the difference between app.use() and router.use()?
Answer: app.use() attaches middleware to the application. router.use() attaches middleware to a particular Express router.
Why? Router middleware helps isolate logic for a group of related routes.
Q6. What is next(error) used for?
Answer: It passes the error into Express's error-handling flow.
Why? It allows centralized error middleware to create a consistent response.
Q7. What makes error middleware different?
Answer: Error middleware has four parameters: (err, req, res, next).
Why? Express identifies it as error-handling middleware by its four-argument signature.
Q8. Find the bug. 
app.get("/admin", (req,res) => {
  if (!req.user) {
    res.status(401).json({message:"Login required"});
  }
  next();
});
Answer: next() may execute after a response has already been sent.
Fix:
if (!req.user) {
  return res.status(401).json({ message: "Login required" });
}
next();
Why? return stops the current function after sending the response.
Q9. Authentication or authorization: which one checks the user's role?
Answer: Authorization.
Why? Authentication answers “Who are you?” Authorization answers “What are you allowed to do?”
Q10. Write route-specific middleware that allows only admins.
function adminOnly(req, res, next) {
  if (req.user?.role !== "admin") {
    return res.status(403).json({ message: "Forbidden" });
  }
  next();
}

app.get("/admin", adminOnly, handler);
Why? The route is protected without applying the admin check to every route.
Q11. Predict the output. 
app.use((req,res,next) => {
  console.log("Before");
  next();
  console.log("After");
});

app.get("/", (req,res) => {
  console.log("Route");
  res.send("Done");
});
Answer:
Before
Route
After
Why? Calling next() transfers control forward, but the current JavaScript function continues after next() returns.
Q12. Can middleware modify req?
Answer: Yes.
Why? Middleware commonly attaches values such as req.user, validated data, or request IDs for later handlers.
Q13. Where should centralized error middleware usually be registered?
Answer: Usually after the routes and normal middleware that may pass errors to it.
Why? It needs to be part of the downstream error-handling chain.
Q14. What is the difference between global and route-specific middleware?
Answer: Global middleware can affect many routes, while route-specific middleware is attached only to selected routes.
Why? Route-specific middleware reduces unnecessary work and makes permissions easier to reason about.
Q15. Why should heavy blocking work be avoided inside middleware?
Answer: Blocking work can delay other requests handled by the Node.js process.
Why? JavaScript execution is event-loop based, so long synchronous work can reduce responsiveness.
Q16. What should async middleware do when an awaited operation fails?
Answer: It should pass the error into the error-handling path, commonly with next(error) when using a try/catch pattern.
Why? The application needs a controlled place to handle the failure and send a safe response.
Q17. What is the difference between res.send() and next() in middleware?
Answer: res.send() sends the response and normally ends request processing. next() passes control to another matching middleware or route handler.
Why? One finishes the request; the other continues the middleware chain.
Q18. Can one route have multiple middleware functions?
Answer: Yes.
app.get("/profile", auth, validate, handler);
Why? It lets each middleware perform one focused responsibility before the final handler.
Q19. What is a common security mistake with authentication middleware?
Answer: Treating the presence of a token as proof that the token is valid and trusted.
Why? Authentication middleware must properly verify credentials/tokens before trusting user information.
Q20. Explain middleware execution in one interview answer.
Answer: “Express processes matching middleware in order. Each middleware can end the response or call next() to continue. If an error is passed with next(error), Express moves into error-handling middleware.”
Why? This shows you understand both normal and error execution flow.
22. Final Interview Checklist
You should be able to explain these without notes:
  • What middleware is and why it exists.
  • How next() works.
  • Why middleware order matters.
  • Application vs router vs route-specific middleware.
  • Authentication vs authorization.
  • How to create logging and validation middleware.
  • How middleware modifies req.
  • How error middleware works.
  • How async errors reach error middleware.
  • Why forgetting next() can hang a request.
