🟢 Part 19 — Security ⭐⭐⭐

Learn the most important security ideas for Node.js and Express applications.

Simple English • Attack prevention • Secure configuration • Authentication security • API protection

1. What is Web Security?

Web security means protecting an application, its users, data, and APIs from unauthorized access, malicious input, and unsafe behavior.

Layman example: Think of your application as a house. Authentication checks who is entering, authorization checks which rooms they can enter, and security controls are the locks, alarms, gates, and visitor rules.
Browser / Client ↓ HTTPS ↓ Security headers ↓ CORS / CSRF controls ↓ Rate limiting ↓ Input validation ↓ Authentication ↓ Authorization ↓ Application ↓ Database
Interview line: “Security is a layered process. No single library or header can secure an entire application.”
2. CORS — Cross-Origin Resource Sharing

CORS is a browser security mechanism that controls whether a web page from one origin can make certain requests to another origin.

An origin is based on the combination of scheme + host + port.

const cors = require("cors");

app.use(cors({
  origin: "https://myfrontend.example.com"
}));
Frontend https://frontend.example ↓ API request ↓ https://api.example ↓ Browser checks CORS rules ↓ Allowed / Blocked
Common mistake: Using origin: "*" everywhere without understanding the application's authentication and credential requirements. CORS is a browser policy; it is not a replacement for API authentication.
3. CSRF — Cross-Site Request Forgery

CSRF tricks a user's browser into sending an unwanted request to a site where the user is already authenticated.

Layman example: You are logged into your bank. A malicious page tries to make your browser send a money-transfer request. If the server accepts the browser's automatic credentials without enough protection, the unwanted action may succeed.

Common defenses include:

  • CSRF tokens for state-changing requests.
  • Appropriate SameSite cookie settings.
  • Checking request origin/referer where appropriate.
  • Using a secure application architecture.
Important: CSRF protection depends strongly on how authentication credentials are transported. Do not blindly copy one defense to every architecture.
4. XSS — Cross-Site Scripting

XSS happens when attacker-controlled content is treated as executable HTML/JavaScript in another user's browser.

// Dangerous pattern when userInput is untrusted:
element.innerHTML = userInput;

Safer approaches include:

  • Prefer textContent when inserting plain text.
  • Escape output for its specific context.
  • Sanitize HTML only when HTML is genuinely required.
  • Use a suitable Content Security Policy where possible.
  • Avoid unsafe HTML insertion APIs with untrusted data.
Untrusted input ↓ Validation / output encoding / sanitization ↓ Safe rendering ↓ Browser
5. SQL Injection

SQL injection occurs when untrusted input changes the meaning of an SQL query.

Dangerous idea: Building SQL statements by directly concatenating user input.
// Bad idea
const sql = "SELECT * FROM users WHERE email = '" + email + "'";

Use parameterized queries or prepared statements:

// Example shape
const result = await db.query(
  "SELECT * FROM users WHERE email = ?",
  [email]
);
Interview line: “Parameterized queries keep user data separate from SQL instructions.”
6. NoSQL Injection

NoSQL injection can happen when an application accepts attacker-controlled objects/operators where it expected simple values.

// Risky idea
User.findOne(req.body);

If the API expects an email string, explicitly validate that it is a string and construct the allowed query fields yourself.

const { email } = req.body;

if (typeof email !== "string") {
  return res.status(400).json({
    message: "Invalid email"
  });
}

const user = await User.findOne({ email });
Common mistake: Treating the entire request body as a database query object.
7. HTTP Security Headers

Security headers tell browsers how they should handle certain parts of an application.

HeaderSimple purpose
Content-Security-PolicyControls which content/resources the browser may load and execute.
Strict-Transport-SecurityTells browsers to use HTTPS for the site for a specified period.
X-Content-Type-OptionsHelps prevent MIME-type sniffing.
Referrer-PolicyControls referrer information sent with requests.
Permissions-PolicyControls access to selected browser features.
Exact headers and policies should match the application's needs. Security headers can improve defense, but they do not fix server-side authorization or injection bugs.
8. Helmet

Helmet is a Node.js/Express middleware package that helps set several HTTP security headers.

const helmet = require("helmet");

app.use(helmet());
Express request ↓ helmet() ↓ Security response headers ↓ Browser
Important: Installing Helmet does not make an application automatically secure. You still need validation, authentication, authorization, safe database queries, secure cookies, rate limits, and other controls.
9. Rate Limiting

Rate limiting restricts how many requests a client can make within a time period.

Client ↓ 100 requests / minute allowed ↓ Request #101 ↓ Rate limit reached ↓ 429 Too Many Requests
const rateLimit = require("express-rate-limit");

const apiLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  limit: 100
});

app.use("/api", apiLimiter);

Use stricter limits for sensitive endpoints such as login, password reset, OTP, and account recovery.

10. Brute-Force Protection

A brute-force attack repeatedly tries passwords or codes until one works.

Useful defenses include:

  • Rate-limit login attempts.
  • Use strong password hashing such as bcrypt.
  • Use sensible account/identity-based controls, not only IP-based controls.
  • Add additional verification for suspicious activity.
  • Protect password-reset and OTP endpoints too.
Interview point: “Rate limiting reduces the number of guesses an attacker can make, but the design should also consider distributed attacks and account recovery flows.”
11. Input Validation

Validation checks whether input follows the rules your application expects.

const { email, age } = req.body;

if (typeof email !== "string" || !email.includes("@")) {
  return res.status(400).json({ message: "Invalid email" });
}

if (!Number.isInteger(age) || age < 18) {
  return res.status(400).json({ message: "Invalid age" });
}
Why? Validation prevents invalid data from reaching application logic and reduces the attack surface.
12. Input Sanitization

Sanitization transforms or removes unsafe parts of input according to the context and expected data.

Validation asks: “Is this allowed?”

Sanitization asks: “How should this input be cleaned or normalized?”

Do not blindly sanitize everything. The correct defense depends on the output context: HTML, SQL, shell commands, URLs, JSON, and other contexts have different rules.
13. Password Security
  • Never store plain-text passwords.
  • Use a dedicated password hashing algorithm such as bcrypt, scrypt, or Argon2.
  • Never log passwords.
  • Use strong password policies without making recovery impossible.
  • Protect password reset tokens.
  • Do not return password hashes in API responses.
  • Consider multi-factor authentication for sensitive applications.
Password ↓ Password hashing algorithm ↓ Salted password hash ↓ Database Login password ↓ Compare with stored hash ↓ Match / Reject
14. JWT Security
  • Use strong signing keys and keep them secret.
  • Verify signatures on the server.
  • Validate expiration and other required claims.
  • Keep payloads minimal.
  • Do not store passwords or secrets in the payload.
  • Use short-lived access tokens where appropriate.
  • Protect refresh tokens carefully.
  • Plan token revocation/rotation for the application's risk level.
const claims = jwt.verify(
  token,
  process.env.JWT_SECRET
);

// Do not simply trust:
const decoded = jwt.decode(token);
Interview trap: decode() is not a security check. Verification is required before trusting signed-token claims.
15. Secrets, .env and dotenv

Secrets include database passwords, API keys, JWT signing keys, and private credentials.

# .env
PORT=5000
JWT_SECRET=use-a-strong-secret
DATABASE_URL=...
require("dotenv").config();

console.log(process.env.PORT);
Never commit real secrets to Git. Add .env to .gitignore and use your deployment platform's secret/environment-variable system in production.
If a real secret is accidentally committed, removing the file from the latest commit is not enough. Treat the secret as exposed and rotate it.
16. Secure Cookies
res.cookie("refreshToken", token, {
  httpOnly: true,
  secure: true,
  sameSite: "lax",
  maxAge: 7 * 24 * 60 * 60 * 1000
});
OptionMeaning
HttpOnlyJavaScript cannot read the cookie through normal document.cookie APIs.
SecureCookie is sent only over HTTPS.
SameSiteControls cross-site cookie sending behavior.
17. HTTPS

HTTPS is HTTP protected by TLS. It helps provide confidentiality and integrity for data in transit and authenticates the server through certificates.

Client ↓ TLS handshake ↓ Encrypted connection ↓ HTTPS request/response ↓ Server
Common mistake: Thinking HTTPS protects a vulnerable server from SQL injection or broken authorization. HTTPS protects the connection; application security still matters.
18. Request Size Limits

Attackers can send extremely large request bodies to consume memory, CPU, or network resources.

app.use(express.json({
  limit: "100kb"
}));

Choose limits based on the actual API. File uploads should usually use dedicated upload handling and limits rather than allowing unlimited JSON bodies.

19. Security Best Practices
Input
Validate types, ranges, lengths, and allowed values.
Database
Use parameterized SQL and safe NoSQL query construction.
Authentication
Hash passwords and protect tokens.
Authorization
Check permissions on the server.
Transport
Use HTTPS and secure cookies.
Abuse
Use rate limits and brute-force protection.
Secrets
Keep credentials out of source control.
Dependencies
Keep packages updated and review security advisories.
20. Common Developer Mistakes
  1. Using CORS as if it were authentication.
  2. Using Access-Control-Allow-Origin: * without understanding the application's needs.
  3. Storing plain-text passwords.
  4. Putting secrets inside JWT payloads.
  5. Using jwt.decode() and treating the result as trusted.
  6. Putting real secrets directly in source code.
  7. Committing .env to Git.
  8. Using weak JWT secrets.
  9. Not rate-limiting login and password-reset endpoints.
  10. Trusting the entire request body as a database query.
  11. Building SQL queries with string concatenation.
  12. Using innerHTML with untrusted content.
  13. Relying only on frontend authorization.
  14. Not limiting request body size.
  15. Assuming Helmet alone secures an application.
  16. Sending authentication cookies without appropriate security attributes.
  17. Logging passwords, tokens, API keys, or sensitive personal data.
21. Quick Recap
  • CORS: browser cross-origin access control.
  • CSRF: unwanted authenticated actions caused through a user's browser.
  • XSS: attacker-controlled content executes in a user's browser.
  • SQL injection: untrusted input changes SQL meaning.
  • NoSQL injection: untrusted query objects/operators change database behavior.
  • Helmet: helps configure security-related HTTP headers.
  • Rate limiting: limits request frequency.
  • Validation: checks whether input is allowed.
  • Sanitization: cleans/transforms input for a specific context.
  • HTTPS: protects data in transit using TLS.
  • Secure cookies: use appropriate HttpOnly, Secure, and SameSite settings.
  • Secrets: keep them outside source code and rotate exposed credentials.

23. Interview Questions — Show / Hide Answers
Q1. What is CORS? Is CORS an authentication mechanism?
Answer: CORS controls which browser origins are allowed to access resources across origins. It is not authentication.
Why? An API must still authenticate and authorize users even when CORS is configured.
Q2. What is the difference between CORS and CSRF?
Answer: CORS controls browser cross-origin access. CSRF is an attack where a victim's browser is tricked into making an unwanted authenticated request.
Why? They solve different security problems.
Q3. How does XSS happen?
Answer: XSS can happen when untrusted input is inserted into a page in a way that allows it to be interpreted as executable HTML/JavaScript.
Why? The browser may execute attacker-controlled code in the application's security context.
Q4. Find the security problem. 
element.innerHTML = req.body.comment;
Answer: Untrusted input is being inserted as HTML.
Fix: Use textContent for plain text, or use a carefully designed sanitization/encoding strategy when HTML is required.
Why? Unsafe HTML insertion can create an XSS vulnerability.
Q5. Why are parameterized SQL queries safer?
Answer: They keep user data separate from SQL instructions.
Why? User input is treated as data instead of changing the structure of the SQL statement.
Q6. Find the SQL injection problem. 
const sql = "SELECT * FROM users WHERE name = '" + req.query.name + "'";
Answer: User input is directly concatenated into SQL.
Fix: Use the database driver's parameterized query/prepared statement mechanism.
Why? Direct concatenation allows input to affect SQL syntax.
Q7. What is NoSQL injection?
Answer: It occurs when attacker-controlled values are interpreted as database operators or query objects instead of the simple data the API expected.
Why? A query can behave differently from the developer's intended filter.
Q8. Find the risky NoSQL pattern. 
const user = await User.findOne(req.body);
Answer: The entire request body becomes the query object.
Fix: Validate the expected fields and construct the query explicitly.
Why? Attackers may supply unexpected operators or fields.
Q9. What does Helmet do?
Answer: Helmet helps an Express application set several security-related HTTP response headers.
Why? These headers can enable browser-side protections and safer defaults, but they do not replace application-level security.
Q10. What is rate limiting and why is it important for login APIs?
Answer: Rate limiting restricts how many requests a client can make in a period. Login endpoints benefit because it slows repeated password guesses.
Why? It reduces the number of brute-force attempts an attacker can make.
Q11. What is the difference between validation and sanitization?
Answer: Validation checks whether input meets expected rules. Sanitization transforms or removes unsafe content according to a specific context.
Why? They address different parts of safe input handling.
Q12. Why should passwords be hashed?
Answer: Passwords should be stored using a dedicated password hashing algorithm such as bcrypt, scrypt, or Argon2 rather than plain text.
Why? If the database is exposed, attackers should not immediately receive users' original passwords.
Q13. Is this JWT handling safe? 
const payload = jwt.decode(token);
if (payload.role === "admin") {
  deleteUser();
}
Answer: No. The code decodes the token without verifying its signature.
Fix: Verify the JWT first, then use trusted claims from the verified result.
Why? Decoding does not prove the token was issued by the trusted server.
Q14. Why should JWT payloads not contain passwords?
Answer: A normal JWT payload is readable by anyone holding the token.
Why? JWT encoding is not the same as encryption.
Q15. Why should .env not be committed to Git?
Answer: It may contain passwords, API keys, database credentials, or signing secrets.
Why? Source repositories can be copied, logged, or accessed by people who should not receive those credentials.
Q16. What should you do if a secret is committed to Git?
Answer: Treat it as exposed and rotate/revoke it immediately, then clean up repository history as appropriate.
Why? Removing the visible line later does not guarantee that old copies, forks, caches, or clones no longer contain the secret.
Q17. What do HttpOnly, Secure, and SameSite mean?
Answer: HttpOnly limits JavaScript access, Secure restricts sending to HTTPS, and SameSite controls cross-site cookie sending behavior.
Why? These attributes provide important protections for authentication cookies.
Q18. Why is HTTPS not enough to secure an API?
Answer: HTTPS protects data in transit, but it does not prevent SQL injection, broken authorization, weak passwords, XSS, or insecure business logic.
Why? Transport security and application security solve different problems.
Q19. What problem does this configuration help prevent? 
app.use(express.json({ limit: "100kb" }));
Answer: It limits the size of JSON request bodies accepted by that parser.
Why? Reasonable request limits reduce resource-abuse risk from unexpectedly large payloads.
Q20. Design a secure login endpoint. What protections would you add?
Answer:
HTTPS ↓ Request size limit ↓ Input validation ↓ Rate limiting ↓ Find user ↓ bcrypt password comparison ↓ Create short-lived access token ↓ Secure refresh-token handling ↓ Log safely — never passwords/tokens
Why? Security is defense in depth. Multiple controls reduce the chance that one mistake becomes a complete account compromise.
24. Final Interview Lines
  • CORS: “CORS is a browser cross-origin access control mechanism, not authentication.”
  • CSRF: “CSRF tricks an authenticated browser into making an unwanted state-changing request.”
  • XSS: “XSS occurs when untrusted content is executed as script in a user's browser.”
  • SQL injection: “Use parameterized queries so user input remains data, not SQL syntax.”
  • NoSQL injection: “Validate expected types and construct database queries explicitly.”
  • Helmet: “Helmet helps set security-related HTTP headers in Express.”
  • Rate limiting: “Rate limits reduce abuse and brute-force attempts.”
  • JWT: “Verify JWTs before trusting their claims; decoding alone is not authentication.”
  • Secrets: “Keep secrets outside source code and rotate them if exposed.”
  • HTTPS: “HTTPS protects data in transit, but it does not fix application vulnerabilities.”
  • Defense in depth: “Use multiple independent security layers instead of depending on one control.”
