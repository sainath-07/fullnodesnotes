Node.js Interview Preparation • Part 11

🟢 Node.js Timers ⭐⭐

Learn how Node.js schedules delayed, repeated, and immediate callbacks — and how timers interact with the event loop.

1. What are Node.js Timers?

Node.js timers let you schedule a function to run later. The main timer APIs are setTimeout(), setInterval(), and setImmediate().

Layman example

Think of setting reminders. “Call me after 5 seconds” is like setTimeout(). “Remind me every 5 seconds” is like setInterval(). “Do this as soon as the current I/O cycle allows” is similar to setImmediate().

JavaScript ↓ Schedule timer ↓ Current code continues ↓ Timer becomes eligible ↓ Event loop reaches the right point ↓ Callback runs
Interview-ready: Timers schedule callbacks; they do not create a guarantee that the callback will execute at an exact clock time.
2. setTimeout()

setTimeout(callback, delay) schedules a callback after a minimum delay.

console.log("Start");

setTimeout(() => {
  console.log("Timer");
}, 2000);

console.log("End");
Start
End
Timer

The synchronous code runs first. The timer callback runs later when it becomes eligible and the event loop can process it.

Important: “2000 ms” means the callback should not be expected before that delay under normal timer rules, but it may run later.
3. Timer Delay and Minimum Delay
setTimeout(() => {
  console.log("Timer");
}, 0);

console.log("Done");
Done
Timer

A delay of 0 does not mean “run immediately.” The callback is scheduled and must wait for the current JavaScript work and event-loop scheduling.

setTimeout(fn, 0) ↓ timer is scheduled ↓ current synchronous code runs ↓ timer becomes eligible ↓ event loop can run callback ↓ fn()
Common mistake: Saying “setTimeout 0 runs after exactly 0 ms” is incorrect. Timer delays are minimum scheduling delays, not exact execution times.
4. setInterval()

setInterval(callback, delay) schedules a callback repeatedly.

let count = 0;

const id = setInterval(() => {
  count++;
  console.log(count);

  if (count === 3) {
    clearInterval(id);
  }
}, 1000);
1
2
3

setInterval() returns a timer handle. Use clearInterval() when the repeated work should stop.

Best practice: Always have a clear stopping condition for intervals that should not live forever.
5. clearTimeout(), clearInterval(), clearImmediate()
const timeoutId = setTimeout(() => {
  console.log("Won't run");
}, 3000);

clearTimeout(timeoutId);

Cancellation APIs stop scheduled work when it has not already run.

6. setImmediate()

setImmediate() schedules a callback for the event loop's check phase.

const fs = require("node:fs");

fs.readFile(__filename, () => {
  setImmediate(() => {
    console.log("Immediate");
  });
});
I/O callback ↓ setImmediate(...) ↓ check phase ↓ callback runs
Interview-ready: setImmediate is especially useful when you want work to run after the current poll/I/O phase has completed.

9. Timer Callbacks

The function passed to a timer is called a timer callback.

function greet() {
  console.log("Hello");
}

setTimeout(greet, 1000);

Node stores the timer information. When the timer becomes eligible, the callback can be executed by the event loop.

Key point: Scheduling a callback and executing a callback are two different steps.
10. Timers + Closures

A closure allows a timer callback to remember variables from the scope where the callback was created.

function createTimer(name) {
  setTimeout(() => {
    console.log("Hello " + name);
  }, 1000);
}

createTimer("Sainath");
createTimer("Sainath") ↓ name = "Sainath" ↓ callback closes over name ↓ timer becomes ready ↓ callback reads name ↓ Hello Sainath

The callback still has access to name even though createTimer() has already returned.

11. Timers + this
const user = {
  name: "Sam",

  greet() {
    setTimeout(function () {
      console.log(this.name);
    }, 1000);
  }
};

user.greet();

In this normal function callback, this is not automatically the user object.

Using an arrow function preserves the surrounding lexical this:

const user = {
  name: "Sam",

  greet() {
    setTimeout(() => {
      console.log(this.name);
    }, 1000);
  }
};

user.greet();
Sam
Interview tip: Timers are a common way interviewers test this and arrow-function behavior.
12. Timers + Event Loop
setTimeout(fn, 100) ↓ Timer is registered ↓ Current JavaScript continues ↓ 100 ms minimum delay passes ↓ Timer becomes eligible ↓ Event loop reaches timer processing ↓ fn() enters the call stack ↓ Callback executes

A timer callback cannot interrupt currently running JavaScript.

setTimeout(() => console.log("Timer"), 0);

console.log("Start");

for (let i = 0; i < 100000000; i++) {}

console.log("End");

The timer must wait until the long synchronous loop releases the call stack.

13. Recursive Timers

A recursive timer schedules the next timer from inside the current callback.

let count = 0;

function run() {
  count++;
  console.log(count);

  if (count < 3) {
    setTimeout(run, 1000);
  }
}

run();
run() ↓ setTimeout(run) ↓ wait ↓ run() ↓ setTimeout(run) ↓ wait ↓ run() ↓ stop
Why use recursive setTimeout instead of setInterval?

It gives you more control. The next timer is not scheduled until the current callback decides to schedule it.

Useful for: polling APIs, retry logic, or repeated work where each cycle may take a different amount of time.
14. setInterval() vs Recursive setTimeout()
// setInterval
setInterval(() => {
  doWork();
}, 1000);
// recursive setTimeout
function run() {
  doWork();
  setTimeout(run, 1000);

15. Common Developer Mistakes
  • Thinking setTimeout(fn, 0) means immediate execution.
  • Thinking timer delay is an exact execution time.
  • Assuming setImmediate() always beats setTimeout().
  • Forgetting to clear an interval.
  • Creating an infinite recursive timer without a stopping condition.
  • Using a normal function in a timer and expecting lexical this.
  • Using setInterval() for work that can take longer than the interval without considering overlapping/queued work.
  • Running CPU-heavy synchronous work and expecting timers to run on time.
  • Using process.nextTick() recursively and starving the event loop.
  • Keeping unnecessary timer callbacks alive and holding references longer than needed.
16. Interview Questions — Click to Show / Hide Answer + Why ⭐⭐⭐
Q1. What is setTimeout()?
Answer: setTimeout schedules a callback to run after a minimum delay.

Why? The callback still waits for the call stack and event-loop scheduling, so the delay is not an exact execution time.
Q2. Does setTimeout(fn, 0) run immediately?
Answer: No. It schedules the callback and makes it eligible after the minimum delay; it still waits for the current JavaScript work and event-loop processing.

Why? The call stack cannot be interrupted by a timer callback.
Q3. What is the difference between setTimeout() and setImmediate()?
Answer: setTimeout schedules timer work, while setImmediate schedules work for the check phase. Their ordering depends on where they are scheduled.

Why? In an I/O callback, setImmediate commonly runs before a zero-delay timer.
Q4. Predict the output.
console.log("A");

setTimeout(() => console.log("B"), 0);

console.log("C");
Output:

B
Why? Synchronous statements finish before the timer callback can run.
Q5. Predict the output.
console.log("A");

process.nextTick(() => console.log("B"));

setTimeout(() => console.log("C"), 0);

console.log("D");
Output: 
A
D
B
C
Why? Synchronous code runs first, then Node processes nextTick before the timer callback.
Q6. What does setInterval() return?
Answer: It returns a timer handle that can be passed to clearInterval() to stop the interval.

Why? Keeping the handle lets your program control the lifetime of the repeated timer.
Q7. How do you stop a setTimeout()?
Answer: Store the returned handle and call clearTimeout(handle) before the callback executes.

Why? This is useful when the scheduled action is no longer needed.
Q8. Why can a timer execute later than its delay?
Answer: The callback can be delayed by currently running JavaScript, other scheduled work, and event-loop scheduling.

Why? Timers do not interrupt synchronous code.
Q9. What is the output?
const user = {
  name: "Sam",
  greet() {
    setTimeout(function () {
      console.log(this.name);
    }, 0);
  }
};

user.greet();
Answer: It does not print Sam. In a CommonJS Node.js callback, the normal function's this is not the surrounding user object.

Why? A normal function gets its own this based on how it is called. An arrow function would capture the surrounding this.
Q10. Fix the previous code so it prints Sam.
const user = {
  name: "Sam",
  greet() {
    setTimeout(function () {
      console.log(this.name);
    }, 0);
  }
};
Answer: 
const user = {
  name: "Sam",
  greet() {
    setTimeout(() => {
      console.log(this.name);
    }, 0);
  }
};
Why? The arrow function does not create its own this; it uses the surrounding method's this.
Q11. What is recursive setTimeout()?
Answer: It schedules another timeout from inside the current timer callback.

Why? It gives you control over when the next cycle is scheduled and is useful for polling and retry patterns.
Q12. Why might recursive setTimeout() be preferred over setInterval()?
Answer: Recursive setTimeout lets the current operation finish before deciding when to schedule the next one.

Why? This can prevent repeated scheduling from getting ahead of slow work.
Q13. What is event-loop starvation with timers?
Answer: It occurs when synchronous work or continuously prioritized callbacks prevent timer callbacks and other event-loop work from getting a chance to run.

Why? Starvation causes timers to execute much later than expected.
Q14. Predict the output in an I/O callback.
const fs = require("node:fs");

fs.readFile(__filename, () => {
  setTimeout(() => console.log("timeout"), 0);
  setImmediate(() => console.log("immediate"));
});
Typical output: 
immediate
timeout
Why? The code schedules both from an I/O callback; setImmediate targets the check phase and commonly runs before the timer in this situation.
Q15. What is the difference between setInterval() and recursive setTimeout()?
Answer: setInterval automatically schedules repeated callbacks, while recursive setTimeout explicitly schedules each next callback.

Why? Recursive scheduling provides more control over delays and the completion of each cycle.
Q16. Can setTimeout() interrupt a running loop?
setTimeout(() => console.log("Timer"), 0);

while (true) {
  // long-running synchronous code
}
Answer: No. The timer callback cannot execute while the JavaScript call stack is continuously blocked by the synchronous loop.

Why? The event loop needs the JavaScript execution stack to become available.
Q17. What is clearImmediate() used for?
Answer: It cancels a scheduled setImmediate() callback before it executes.

Why? It provides explicit cancellation for immediate callbacks when the work is no longer required.
Q18. Why should you be careful with setInterval() for slow API calls?
Answer: If the work takes a long time, repeated scheduling can cause multiple operations to be active or queued before earlier work has completed.

Why? Recursive setTimeout can be easier to control when each cycle must finish before the next cycle starts.

Strong interview answer:

For repeated asynchronous work, recursive setTimeout can provide more control than setInterval.”
