Node.js Interview Preparation • Part 12

🟢 Asynchronous Programming ⭐⭐⭐

Learn callbacks, Promises, async/await, parallel work, sequential work, error propagation, and async loops in simple words.

1. What is Asynchronous Programming?

Asynchronous programming means starting work that may take time without making JavaScript wait unnecessarily for that work to finish.

Layman example

Imagine ordering food at a restaurant. You place the order and then sit down. You do not stand in the kitchen until the food is ready. You can do other things while the order is being prepared.

Start async work ↓ Do not wait synchronously ↓ Continue other JavaScript ↓ Async work completes ↓ Handle result / error
Interview-ready: “Asynchronous programming allows a program to start time-consuming I/O work and continue other work instead of blocking the JavaScript execution thread while waiting.”
2. Callbacks

A callback is a function passed to another function so it can be called later.

function getUser(callback) {
  setTimeout(() => {
    callback({ name: "Sam" });
  }, 1000);
}

getUser((user) => {
  console.log(user.name);
});
getUser() ↓ async work starts ↓ 1 second passes ↓ callback(user) ↓ console.log()
When to use?

Callbacks are still common in Node.js APIs, event handlers, and older codebases.

3. Error-First Callbacks

Node.js traditionally uses the error-first callback pattern: the first callback argument is the error, and the next argument contains the result.

const fs = require("node:fs");

fs.readFile("data.txt", "utf8", (err, data) => {
  if (err) {
    console.error(err);
    return;
  }

  console.log(data);
});
(err, data) │ ├── err exists → handle error │ └── err is null → use data
Interview line: “In Node-style callbacks, the first argument is normally the error and the following arguments contain successful results.”
4. Callback Hell

Callback hell happens when many dependent asynchronous operations are nested inside one another, making code hard to read and maintain.

getUser((err, user) => {
  if (err) return handle(err);

  getOrders(user.id, (err, orders) => {
    if (err) return handle(err);

    getPayment(orders[0].id, (err, payment) => {
      if (err) return handle(err);

      sendReceipt(payment, (err) => {
        if (err) return handle(err);

        console.log("Done");
      });
    });
  });
});

Promises and async/await can make this kind of flow easier to read.

Important: Callback nesting itself is not automatically wrong. The problem is excessive nesting, repeated error handling, and difficult control flow.
5. Promises

A Promise represents the eventual result of an asynchronous operation.

const promise = new Promise((resolve, reject) => {
  setTimeout(() => {
    resolve("Success");
  }, 1000);
});

promise.then((value) => {
  console.log(value);
});
Promise created ↓ pending ↓ ┌────┴────┐ ↓ ↓ fulfilled rejected ↓ ↓ .then() .catch()

A Promise does not mean “the result is already available.” It represents a result that may become available later.

6. Promise States
Pending

The operation has not finished yet.

Fulfilled

The operation completed successfully.

Rejected

The operation failed.

A settled Promise is either fulfilled or rejected. It does not go back to pending.

Interview tip: Promise state changes only once: pending → fulfilled or pending → rejected.
7. .then(), .catch(), and .finally()
fetchData()
  .then((data) => {
    return processData(data);
  })
  .then((result) => {
    console.log(result);
  })
  .catch((error) => {
    console.error(error);
  })
  .finally(() => {
    console.log("Finished");
  });
  • .then() handles fulfillment and can transform the result.
  • .catch() handles rejection/errors in the chain.
  • .finally() runs after the Promise settles, whether fulfilled or rejected.
Common use for finally: hide a loading spinner, release a resource, or perform cleanup.
8. Promise Chaining
getUser()
  .then((user) => {
    return getOrders(user.id);
  })
  .then((orders) => {
    return getPayment(orders[0].id);
  })
  .then((payment) => {
    console.log(payment);
  })
  .catch((err) => {
    console.error(err);
  });
getUser() ↓ user ↓ getOrders(user.id) ↓ orders ↓ getPayment(...) ↓ payment

Returning a Promise from a .then() lets the next .then() wait for it.

Common mistake: Forgetting return inside a .then() can break the intended chain.
9. async and await

An async function always returns a Promise. await pauses that async function until the awaited Promise settles; it does not block the entire Node.js JavaScript process in the same way as a synchronous blocking operation.

async function getData() {
  const user = await getUser();
  const orders = await getOrders(user.id);

  return orders;
}

getData()
  .then((orders) => console.log(orders))
  .catch((err) => console.error(err));
async function ↓ await getUser() ↓ function suspends here ↓ other JS can run ↓ Promise settles ↓ function continues ↓ await getOrders() ↓ return result
Interview-ready: “async/await is syntax built on top of Promises. It makes asynchronous control flow look more like sequential code while preserving asynchronous behavior.”
10. Async Function Return Values
async function getName() {
  return "Sam";
}

const result = getName();

console.log(result);

result is a Promise, not the string directly.

getName().then(name => {
  console.log(name);
});

Even when an async function returns a normal value, JavaScript wraps it in a fulfilled Promise.

Remember: async function always returns a Promise.
11. Error Propagation
async function run() {
  try {
    const data = await getData();
    return data;
  } catch (error) {
    console.error("Failed:", error);
    throw error;
  }
}

Errors can move upward through Promise chains until a handler catches them.

async operation ↓ Promise rejected ↓ await throws ↓ catch handles error ↓ throw again? ── yes → caller receives rejection
Important: Catching an error and not rethrowing it means the caller may see the operation as successfully completed unless another rejected Promise is returned/thrown.
12. Promise.all()

Promise.all() waits for all input Promises to fulfill. If one rejects, the returned Promise rejects.

const [users, products] = await Promise.all([
  getUsers(),
  getProducts()
]);
getUsers() ───────┐ ├──→ Promise.all() → both results getProducts() ────┘
When to use?

Use it when operations are independent and you need all successful results.

Key point: Promise.all runs independent Promise operations concurrently from the JavaScript caller's perspective; it does not make CPU-bound JavaScript execute in parallel automatically.
13. Promise.allSettled()

Promise.allSettled() waits for every input Promise to settle, whether fulfilled or rejected.

const results = await Promise.allSettled([
  getUsers(),
  getProducts(),
  getOrders()
]);

console.log(results);

Each result tells you its status and either its value or reason.

P1 ── fulfilled ─┐ P2 ── rejected ──┼→ allSettled() → all outcomes P3 ── fulfilled ─┘
Use when: You want a complete report of successes and failures instead of failing the whole operation when one Promise rejects.
14. Promise.race()

Promise.race() settles as soon as the first input Promise settles — whether fulfilled or rejected.

const result = await Promise.race([
  fetchFromServer(),
  timeoutPromise()
]);
P1 ───────────┐ P2 ──────┐ │ P3 ──────┴────┼→ first settled → race result │ └→ other Promises continue unless separately cancelled
Important: Promise.race does not automatically cancel the losing operations.
15. Promise.any()

Promise.any() fulfills when the first input Promise fulfills. It rejects only when all input Promises reject.

const result = await Promise.any([
  getFromServerA(),
  getFromServerB(),
  getFromServerC()
]);
A ── rejected ───┐ B ── fulfilled ──┼→ first fulfillment → result C ── pending ────┘

If every Promise rejects, Promise.any() rejects with an AggregateError.

16. Promise Combinators — Quick Comparison
MethodSettles whenRejects whenBest use
Promise.all()All fulfill.Any rejects.Need every result.
Promise.allSettled()All settle.Does not reject because one input rejects.Need every outcome.
Promise.race()First input settles.First settled input rejects.First completion wins.
Promise.any()First input fulfills.All inputs reject.Any successful source is enough.
17. Sequential Operations

Sequential operations run one after another because the next operation depends on the previous result.

const user = await getUser();
const orders = await getOrders(user.id);
const invoice = await getInvoice(orders[0].id);
getUser() ↓ waits getOrders() ↓ waits getInvoice() ↓ result

Use sequential execution when there is a real dependency between operations.

Performance mistake: Do not make independent operations sequential just because await is easy to write.
18. Parallel / Concurrent Operations

If operations are independent, start them together.

const [users, products] = await Promise.all([
  getUsers(),
  getProducts()
]);
getUsers() ───────────┐ ├→ Promise.all() → results getProducts() ────────┘

This can reduce total waiting time compared with waiting for each independent operation one by one.

// Sequential: roughly userTime + productTime
const users = await getUsers();
const products = await getProducts();

// Concurrent: roughly max(userTime, productTime)
const [users, products] = await Promise.all([
  getUsers(),
  getProducts()
]);
19. Async Loops
Sequential async loop
for (const id of ids) {
  const user = await getUser(id);
  console.log(user);
}

This waits for each operation before starting the next.

Concurrent async operations
const users = await Promise.all(
  ids.map(id => getUser(id))
);

This starts the independent operations together.

Interview tip: for...of with await is sequential. map() creates an array of Promises; use Promise.all() when you want them handled concurrently.
20. Common Developer Mistakes
  • Forgetting to await a Promise when the resolved value is required.
  • Forgetting that an async function always returns a Promise.
  • Using sequential await for independent operations.
  • Using Promise.all() when partial success is required without handling its fail-fast behavior.
  • Thinking Promise.race() cancels the losing Promises.
  • Confusing Promise.any() with Promise.race().
  • Forgetting to return a Promise inside a .then() chain.
  • Swallowing errors inside catch blocks without deciding what the caller should receive.
  • Using forEach(async () => ...) and expecting forEach to await the callbacks.
  • Creating too many concurrent operations and overwhelming an API or database.
  • Assuming “async” means the CPU-heavy JavaScript automatically runs on another thread.
21. Interview Questions — Click to Show / Hide Answer + Why ⭐⭐⭐
Q1. What is asynchronous programming?
Answer: It allows a program to start work that may take time and continue other work instead of synchronously waiting for completion.

Why? This is important for efficient I/O-heavy Node.js applications.
Q2. What is a callback?
Answer: A callback is a function passed to another function so it can be called later.

Why? Node.js historically used callbacks heavily for asynchronous APIs.
Q3. What is an error-first callback?
Answer: It follows the Node.js convention where the first callback argument represents an error and later arguments contain successful results.

Why? It provides a consistent pattern for handling success and failure.
Q4. What is callback hell?
Answer: Excessive nested callbacks that make asynchronous control flow difficult to read, test, and maintain.

Why? Promises and async/await can flatten this control flow.
Q5. What are the states of a Promise?
Answer: Pending, fulfilled, and rejected.

Why? A Promise starts pending and settles once into fulfilled or rejected.
Q6. What does an async function return?
async function test() {
  return 10;
}

console.log(test());
Answer: A Promise that fulfills with 10.

Why? Every async function automatically wraps its returned value in a Promise.
Q7. What is the difference between .then() and await?
Answer: Both work with Promises. .then() uses callback-style Promise chaining, while await lets code inside an async function be written in a more sequential style.

Why? They are different syntax styles built around the same Promise-based asynchronous model.
Q8. What happens if an awaited Promise rejects?
Answer: The await expression throws the rejection reason, which can be handled with try/catch.

Why? This gives async/await a familiar synchronous-looking error-handling style.
Q9. Predict the output.
async function test() {
  console.log("A");
  await Promise.resolve();
  console.log("B");
}

console.log("C");
test();
console.log("D");
Output: 
C
A
D
B
Why? test() starts synchronously and prints A. The await pauses the async function until its Promise continuation is scheduled, so the outer synchronous code prints D first.
Q10. What is Promise.all()?
Answer: It returns a Promise that fulfills when all input Promises fulfill and rejects when any input Promise rejects.

Why? It is useful when multiple independent results are all required.
Q11. Promise.all() vs Promise.allSettled()?
Answer: Promise.all fails when one input rejects. Promise.allSettled waits for every input and returns each outcome.

Why? Choose all when every result is required; choose allSettled when you need a complete success/failure report.
Q12. Promise.race() vs Promise.any()?
Answer: race settles on the first settled Promise, whether fulfilled or rejected. any fulfills on the first fulfilled Promise and rejects only if all reject.

Why? This distinction is a common interview trap.
Q13. Does Promise.race() cancel the other Promises?
Answer: No. Promise.race only settles its returned Promise based on the first settled input. The other operations may continue unless you explicitly support cancellation.

Why? Promise coordination and operation cancellation are separate concepts.
Q14. Which is faster?
const a = await getA();
const b = await getB();
const [a, b] = await Promise.all([
  getA(),
  getB()
]);
Answer: If getA and getB are independent, the second version can complete sooner because both operations can be started without waiting for the first result.

Why? Sequential code waits for A before starting B; Promise.all coordinates both operations together.
Q15. What is wrong with this?
ids.forEach(async (id) => {
  await getUser(id);
});

console.log("Done");
Answer: forEach() does not await the Promises returned by its async callback. “Done” can print before the async operations finish.

Why? Use for...of for sequential async work or map() + Promise.all() for concurrent work.
Q16. How do you run async operations sequentially?
Answer: Use await one operation at a time, commonly inside an async function and a for...of loop.

Why? Sequential execution is useful when one operation depends on the result of the previous operation.
Q17. How do you run independent operations concurrently?
Answer: Start the Promises and coordinate them with Promise.all() when all results are required.

Why? This avoids unnecessary waiting between independent operations.
Q18. What happens when an error is thrown inside an async function?
Answer: The async function's returned Promise becomes rejected with that error.

Why? Callers can handle it with await try/catch or Promise .catch().
Q19. What does finally() do?
Answer: It runs after the Promise settles, regardless of fulfillment or rejection.

Why? It is ideal for cleanup tasks such as hiding loading indicators or releasing resources.
Q20. What is the difference between concurrency and parallelism in async Node.js?
Answer: Concurrency means multiple operations can be in progress during overlapping periods. Parallelism means actual simultaneous execution on separate execution resources.

Why? Promise.all can coordinate concurrent I/O operations without making CPU-bound JavaScript automatically run in parallel.
