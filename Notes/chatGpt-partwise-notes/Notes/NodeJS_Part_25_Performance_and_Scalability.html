🟢 Part 25 — Performance & Scalability ⭐⭐⭐

Learn how to make Node.js applications faster, safer under load and easier to scale.

1. What is Performance?

What: Performance is how efficiently an application uses time, CPU, memory, network and database resources.

Why: A fast application gives users quicker responses and can serve more requests with the same infrastructure.

Layman example: A restaurant that serves 100 customers using the same kitchen more efficiently has better performance.

Interview line: Performance optimization should start with measurement. Do not optimize code blindly; identify the actual bottleneck first.
2. Blocking Operations & Event Loop Blocking ⭐⭐⭐

Node.js runs JavaScript on an event loop. If JavaScript performs a long CPU-heavy or synchronous operation, the event loop cannot handle other JavaScript callbacks during that time.

const fs = require("node:fs"); // Blocking operation: const data = fs.readFileSync("large-file.txt", "utf8"); console.log(data);
Request A
→
Long blocking task
→
Request B waits
Common mistake: Thinking "Node.js is non-blocking" means every Node.js operation is automatically non-blocking. Synchronous APIs and CPU-heavy JavaScript can still block the event loop.
3. CPU-Heavy Tasks

Examples include large calculations, image processing, compression of large data, encryption work and complex loops.

function expensiveWork() { let result = 0; for (let i = 0; i < 1e9; i++) { result += i; } return result; }

When to use: CPU-heavy work should be kept away from the main JavaScript execution path when it can significantly delay other requests.

4. Worker Threads

What: Worker threads allow JavaScript CPU-heavy work to run in separate threads instead of occupying the main JavaScript thread.

const { Worker } = require("node:worker_threads"); const worker = new Worker("./worker.js"); worker.on("message", (result) => { console.log("Result:", result); });
Main thread
→

Interview point: Worker threads are mainly useful for CPU-intensive JavaScript work. They are not a replacement for normal asynchronous I/O APIs.

8. Redis

Redis is an in-memory data store commonly used for caching, counters, sessions and other fast-access data structures.

Request ↓ Redis cache ↓ cache hit → return data ↓ cache miss Database ↓ store result in Redis
Common mistake: Treating cached data as permanently correct. Cache invalidation, expiration and consistency must be designed deliberately.
9. HTTP Caching

Browsers and intermediary caches can reuse responses based on HTTP caching headers.

res.setHeader("Cache-Control", "public, max-age=3600"); res.json(data);

Purpose: Reduce repeated network requests and server work for cacheable resources.

Interview point: Application caching such as Redis and HTTP caching solve related but different problems. HTTP caching operates through HTTP cache semantics; Redis is an application-side data store.
10. Compression

Compression reduces response size before sending data over the network. This can improve transfer time, especially for large text responses.

const compression = require("compression"); app.use(compression());

Trade-off: Compression uses CPU. Measure whether the CPU cost is worth the network savings for your workload.

11. Streaming

Streaming sends or processes data in smaller pieces instead of loading the entire content into memory first.

const fs = require("node:fs"); app.get("/download", (req, res) => { const stream = fs.createReadStream("large-video.mp4"); stream.pipe(res); });

12. Pagination ⭐⭐⭐

Pagination prevents an API from returning thousands or millions of records in one response.

Why: Smaller responses reduce database work, memory use, network transfer and frontend rendering cost.

Common mistake: Allowing the client to request an unlimited page size such as limit=1000000.

17. Memory Leaks

A memory leak happens when objects that are no longer needed remain reachable and therefore cannot be garbage-collected.

const listeners = []; function addUser(user) { listeners.push(user); // grows forever if never removed }

Common causes: global collections that grow forever, forgotten event listeners, timers, caches without limits and references that should have been released.

Interview point: A memory leak is not simply "using a lot of memory." It is unwanted retention of memory that should have become reclaimable.
18. Performance Profiling

Profiling means measuring where CPU time, memory or latency is actually being spent.

Useful Node.js tools and techniques include the Node.js inspector, CPU profiles, heap snapshots, application metrics and load testing.

Golden rule: Measure before and after optimization. An optimization that sounds good can make another part of the system worse.

20. Common Developer Mistakes
  1. Using synchronous APIs in high-throughput request handlers without a good reason.
  2. Running huge CPU loops on the main JavaScript thread.
  3. Adding caching without an invalidation or expiration strategy.
  4. Adding too many database indexes without measuring their write/storage cost.
  5. Returning huge datasets without pagination.
  6. Creating a new database connection for every request.
  7. Using only in-memory rate limiting when the API has multiple instances.
  8. Keeping unlimited in-memory caches.
  9. Assuming compression is always beneficial without considering CPU cost.
  10. Profiling only after production incidents instead of monitoring important metrics.
  11. Keeping application state in one process when requests can be routed to other instances.
  12. Scaling horizontally without thinking about sessions, caches, jobs and shared state.
21. Quick Recap
  • Do not block the Node.js event loop with long synchronous or CPU-heavy work.
  • Use worker threads for suitable CPU-intensive JavaScript tasks.
  • Cluster uses multiple Node.js processes; worker threads use threads.
  • Vertical scaling means a stronger machine; horizontal scaling means more instances.
  • Caching can avoid repeated expensive work.
  • Redis is commonly used as a fast shared cache.
  • HTTP caching can reduce repeated network and server work.
  • Compression reduces response size but uses CPU.
  • Streaming is useful for large data without loading everything into memory.
  • Pagination protects APIs from huge responses.
  • Database indexes can speed suitable queries but have storage/write costs.
  • Connection pools reuse database connections.
  • Rate limiting protects APIs from excessive traffic.
  • Load balancers distribute traffic across instances.
  • Profile first; optimize based on measured bottlenecks.
22. Interview-Ready Points ⭐⭐⭐
  • Why can Node.js be blocked? JavaScript execution is concentrated on the event loop thread; long synchronous/CPU work prevents other callbacks from running.
  • Worker threads vs cluster: worker threads use threads for CPU work; cluster runs separate processes.
  • Horizontal vs vertical scaling: more instances vs a stronger machine.
  • Why caching? Reduce repeated expensive computation, database work or network calls.
  • Why Redis? Fast shared in-memory storage, commonly used for cache and distributed counters/state.
  • Why pagination? Prevent huge queries and responses.
  • Why indexes? Speed suitable query patterns at the cost of storage and write overhead.
  • Why connection pooling? Efficiently reuse a controlled number of DB connections.
  • Why rate limiting? Protect resources and reduce abuse.
  • How do you optimize? Measure → identify bottleneck → change → benchmark/profile again.
