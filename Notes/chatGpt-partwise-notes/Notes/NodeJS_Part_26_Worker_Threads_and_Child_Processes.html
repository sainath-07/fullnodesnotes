🟢 Part 26 — Worker Threads & Child Processes ⭐⭐⭐

Understand how Node.js can run CPU-heavy work outside the main JavaScript thread and how it can start separate processes.

1. Why Do We Need Workers and Child Processes?

What: Node.js normally executes JavaScript on a main thread. Worker threads and child processes let an application move certain work away from that main execution path.

Why: Long CPU-heavy JavaScript can delay other callbacks and increase request latency.

Layman example: Imagine one cashier serving every customer. If the cashier spends 10 minutes doing one complex task, everyone else waits. A worker is like giving that task to another employee.

Main Node.js thread
→
CPU-heavy task
→
Other requests wait
Interview line: Node.js is very good at asynchronous I/O, but CPU-heavy JavaScript can still block the main event-loop thread.
2. Worker Threads

What: The worker_threads module allows JavaScript to run in separate threads.

Purpose: Use workers mainly for CPU-intensive JavaScript work that would otherwise block the main thread.

Main thread
→
Worker
→
CPU-heavy work

When to use: Large calculations, CPU-heavy parsing, some image/data processing and other expensive JavaScript computations.

When not to use: Do not create workers for every normal database or file operation just because it is asynchronous. Node.js already provides asynchronous I/O APIs for many such tasks.

3. Creating a Worker

The main thread creates a Worker and can communicate with it using messages.

const { Worker } = require("node:worker_threads"); const worker = new Worker("./worker.js"); worker.on("message", (result) => { console.log("Worker result:", result); }); worker.on("error", (err) => { console.error("Worker error:", err); }); worker.on("exit", (code) => { console.log("Worker exited:", code); });
Important: A worker has its own JavaScript execution context. It is not simply another callback inside the same main JavaScript execution flow.
4. postMessage() and parentPort

The main thread can send data to a worker using worker.postMessage(). Inside the worker, parentPort is used to communicate with the parent.

// main.js const { Worker } = require("node:worker_threads"); const worker = new Worker("./worker.js"); worker.postMessage({ number: 10 }); worker.on("message", (result) => { console.log("Result:", result); }); // worker.js const { parentPort } = require("node:worker_threads"); parentPort.on("message", ({ number }) => { parentPort.postMessage(number * number); });

Common mistake: Forgetting that communication between the main thread and worker has a cost. A worker is not automatically faster for small tasks.

Useful worker events include message, error and exit.

worker.on("message", handler); worker.on("error", handler); worker.on("exit", handler); // Request an early stop when appropriate: worker.terminate();

Why lifecycle matters: A production application should handle worker errors, completion and cleanup instead of creating workers and ignoring their state.

6. Child Processes

What: The child_process module lets Node.js start separate operating-system processes.

A child process has its own process boundary and can run another command, executable or Node.js process.

Node.js parent
→
Operating-system child process
→
Command / program
Key idea: A child process is a separate OS process. This gives stronger process isolation than a worker thread, but process creation and communication can have more overhead.
7. exec()

exec() runs a command in a shell and collects its output. It is convenient when you want the complete output of a command.

const { exec } = require("node:child_process"); exec("node --version", (error, stdout, stderr) => { if (error) { console.error(error); return; } console.log(stdout); });
Security warning: Never directly place untrusted user input into a shell command. Shell injection can become a serious security problem.
8. execFile()

execFile() runs a specific executable file without using a shell by default.

const { execFile } = require("node:child_process"); execFile(process.execPath, ["--version"], (error, stdout, stderr) => { if (error) { console.error(error); return; } console.log(stdout); });

When to use: Useful when you know the executable and want to pass arguments directly rather than constructing a shell command.

9. spawn()

spawn() starts a process and gives you streams for its standard output and error. It is useful for commands that produce a lot of output or run for a longer time.

const { spawn } = require("node:child_process"); const child = spawn(process.execPath, ["worker-task.js"]); child.stdout.on("data", (data) => { console.log("stdout:", data.toString()); }); child.stderr.on("data", (data) => { console.error("stderr:", data.toString()); }); child.on("close", (code) => { console.log("Process closed:", code); });
Think: exec() is convenient for collected command output; spawn() is better suited to streaming output from longer-running commands.
10. fork()

fork() is designed to start another Node.js process and provides a built-in messaging channel between the parent and child.

// parent.js const { fork } = require("node:child_process"); const child = fork("./child.js"); child.send({ number: 5 }); child.on("message", (message) => { console.log("Child replied:", message); }); // child.js process.on("message", ({ number }) => { process.send({ result: number * number }); });

Interview point: fork() is specifically for starting another Node.js process with an IPC channel. It is not the same thing as git fork or a normal function call.

11. IPC — Inter-Process Communication

IPC means communication between separate processes.

Parent process
↔
IPC channel
↔
Child process

With a forked Node.js child process, child.send() and process.send() can be used for messaging.

Worker threads also communicate by messages, but they are threads rather than separate OS processes.

13. When Should You Use Workers?
  • Large CPU calculations.
  • CPU-heavy data transformation.
  • Some expensive parsing or processing tasks.
  • Work that would noticeably block request handling.

14. When Should You NOT Use Workers?
  • For every small function call.
  • For simple asynchronous database queries.
  • For ordinary asynchronous file operations.
  • When worker startup and message-transfer costs are greater than the task itself.
Common mistake: "Worker threads make every Node.js application faster." False. Workers are useful for the right workload, especially CPU-heavy work.
15. Common Developer Mistakes
  1. Creating a worker for tiny tasks where the overhead is larger than the benefit.
  2. Using workers as a replacement for normal async I/O.
  3. Ignoring worker error and exit events.
  4. Sending huge amounts of data between threads without considering transfer/copy costs.
  5. Using exec() with untrusted user input.
  6. Confusing a worker thread with a child process.
  7. Forgetting to clean up workers that are no longer needed.
  8. Assuming fork() is the same as a worker thread.
  9. Ignoring backpressure or output volume when using child-process streams.
  10. Using child processes when a normal Node.js asynchronous API already solves the problem.
16. Quick Recap
  • Worker threads: separate JavaScript threads inside the Node.js process.
  • worker_threads: Node.js module for workers.
  • postMessage(): sends messages to a worker.
  • parentPort: worker-side communication channel with the parent.
  • Child process: separate operating-system process.
  • child_process: Node.js module for creating child processes.
  • exec(): runs a shell command and collects output.
  • execFile(): runs a specific executable.
  • spawn(): starts a process and exposes streams.
  • fork(): starts another Node.js process with Node.js IPC support.
  • IPC: communication between processes.
  • Use workers mainly for CPU-heavy JavaScript; use child processes for separate programs/process isolation.
