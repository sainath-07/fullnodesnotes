🟢 Part 17 — REST API Development ⭐⭐⭐

Build clean, predictable APIs using REST principles and practical Node.js/Express patterns.

Simple English • CRUD • HTTP methods • validation • errors • pagination • filtering • sorting • searching

1. What is REST?

REST means Representational State Transfer. It is a set of principles for designing web APIs around resources.

In simple words, instead of creating a different URL for every action, we identify a resource and use HTTP methods to describe what we want to do.

Layman example: Think of a library. /books is the book collection. GET can read books, POST can add a book, PUT/PATCH can update a book, and DELETE can remove one.
Client ↓ HTTP Request ↓ REST API ↓ Resource / Controller / Database ↓ JSON Response ↓ Client
Interview line: “REST is an architectural style where APIs expose resources through URLs and use standard HTTP methods and status codes to represent operations and results.”
2. Resources

A resource is a thing your API manages, such as users, products, orders, or books.

ResourceCollection URLSingle resource URL
Users/users/users/101
Products/products/products/501
Orders/orders/orders/9001

Good REST naming: use nouns such as /users, not action words such as /getUsers.

3. HTTP Methods and CRUD
MethodCommon meaningCRUDExample
GETRead resource(s)ReadGET /users
POSTCreate a new resourceCreatePOST /users

PATCHPartially update a resourceUpdatePATCH /users/101

Interview point: PUT is commonly described as replacement/update of the target representation, while PATCH is intended for partial modification. Exact application semantics should be documented by the API.
4. CRUD API Example with Express
const express = require("express");
const app = express();

app.use(express.json());

app.get("/users", (req, res) => {
  res.json([{ id: 1, name: "Sam" }]);
});

app.post("/users", (req, res) => {
  const user = req.body;
  res.status(201).json(user);
});

app.put("/users/:id", (req, res) => {
  res.json({ message: "User replaced", id: req.params.id });
});

app.patch("/users/:id", (req, res) => {
  res.json({ message: "User partially updated", id: req.params.id });
});

app.delete("/users/:id", (req, res) => {
  res.status(204).end();
});
POST /users → Create GET /users → Read collection GET /users/1 → Read one PUT/PATCH /users/1 → Update DELETE /users/1 → Delete
5. Request Headers

Headers carry extra information about an HTTP request.

GET /users HTTP/1.1
Host: example.com
Accept: application/json
Authorization: Bearer TOKEN123

In Express:

app.get("/users", (req, res) => {
  console.log(req.headers);
  console.log(req.get("Authorization"));
  res.json([]);
});

Common headers include Content-Type, Accept, Authorization, and caching-related headers.

6. Request Body

The request body usually carries data sent to the server, especially for POST, PUT, and PATCH.

POST /users
Content-Type: application/json

{
  "name": "Sam",
  "email": "sam@example.com"
}
app.use(express.json());

app.post("/users", (req, res) => {
  console.log(req.body);
  res.status(201).json(req.body);
});
Common mistake: Forgetting express.json() can cause JSON request bodies not to be parsed into req.body.
7. Response Body and JSON

REST APIs commonly return JSON because it is easy for frontend applications and other services to consume.

res.status(200).json({
  success: true,
  data: {
    id: 101,
    name: "Sam"
  }
});

A useful response structure should be consistent across the API.

9. REST API Naming Rules
AvoidPrefer
GET /getUsersGET /users
POST /createUserPOST /users
POST /deleteUser/10DELETE /users/10
GET /user for a collectionGET /users
GET /users/getActiveGET /users?status=active

Use resource-oriented names and let the HTTP method describe the main operation.

10. API Validation

Validation checks whether incoming data is acceptable before processing or saving it.

function validateUser(req, res, next) {
  const { name, email } = req.body;

  if (!name || !email) {
    return res.status(400).json({
      message: "name and email are required"
    });
  }

  if (!email.includes("@")) {
    return res.status(400).json({
      message: "Invalid email"
    });
  }

  next();
}

app.post("/users", validateUser, createUser);
Request → Parse body → Validate → Business logic → Database → Response
Security rule: Never assume data is valid just because it came from your own frontend. A client can call your API directly.
11. API Errors

A good API returns a useful status code and a safe, consistent error response.

app.get("/users/:id", async (req, res, next) => {
  try {
    const user = await findUser(req.params.id);

    if (!user) {
      return res.status(404).json({
        success: false,
        error: {
          code: "USER_NOT_FOUND",
          message: "User not found"
        }
      });
    }

    res.json({ success: true, data: user });
  } catch (error) {
    next(error);
  }
});
Do not expose sensitive internal details such as database stack traces, passwords, tokens, or secret configuration values in production responses.
12. Pagination ⭐⭐⭐

Pagination prevents the server from returning thousands or millions of records in one response.

Example:

GET /products?page=2&limit=10

Concept:

page 1 → records 1–10
page 2 → records 11–20
page 3 → records 21–30

Example response:

{
  "data": [ ... ],
  "pagination": {
    "page": 2,
    "limit": 10,
    "totalItems": 57,
    "totalPages": 6
  }
}
Interview point: Always define limits. Do not allow a client to request an unlimited number of records.
13. Filtering

Filtering selects resources that match conditions.

GET /products?category=mobile
GET /products?status=active
GET /products?category=mobile&status=active

In Express:

app.get("/products", (req, res) => {
  const { category, status } = req.query;

  // Build database filters from validated values.
  res.json({ category, status });
});
14. Sorting

Sorting controls the order of returned resources.

GET /products?sort=price
GET /products?sort=-price
GET /products?sort=name

A common convention is using - to mean descending order, but your API should document its exact syntax.

Security/performance: Allow sorting only on known fields instead of blindly accepting any field from the client.
15. Searching

Searching looks for resources matching a text or search condition.

GET /products?search=iphone

Do not confuse searching with exact filtering:

filter: category=mobile
search: search=iphone

The database query should be designed carefully so search remains fast as data grows.

16. Combining Pagination + Filtering + Sorting + Searching
GET /products
  ?page=2
  &limit=20
  &category=mobile
  &search=iphone
  &sort=-price
Client ↓ Parse query parameters ↓ Validate allowed values ↓ Build filter ↓ Apply search ↓ Apply sort ↓ Apply pagination ↓ Database ↓ JSON response

For larger applications, separating routing, validation, business logic, and data access makes the code easier to maintain.

18. Common REST API Mistakes
  1. Using action-heavy URLs such as /getUsers everywhere.
  2. Returning 200 for every success and error.
  3. Using the wrong HTTP method.
  4. Not validating request body and query parameters.
  5. Returning huge collections without pagination.
  6. Allowing arbitrary sort fields without validation.
  7. Exposing database errors or stack traces to clients.
  8. Using inconsistent response shapes.
  9. Ignoring authentication and authorization where required.
  10. Allowing clients to request unlimited page sizes.
  11. Confusing filtering, searching, sorting, and pagination.
  12. Trusting frontend validation as the only validation layer.
19. Quick Recap
  • REST APIs are resource-oriented.
  • URLs identify resources; HTTP methods describe operations.
  • GET reads, POST creates, PUT/PATCH updates, DELETE removes.
  • Headers carry metadata about requests and responses.
  • Request bodies commonly carry JSON for create/update operations.
  • Status codes communicate the result.
  • Validation protects API correctness and security.
  • Pagination controls response size.
  • Filtering narrows results by conditions.
  • Sorting controls result order.
  • Searching finds matching text/conditions.

21. Interview Questions — Show / Hide Answers
Q1. What is REST?
Answer: REST is an architectural style for designing network APIs around resources, HTTP methods, representations, and stateless communication.
Why? It gives APIs a predictable structure that clients can understand and use.
Q2. Why is /users usually better than /getUsers?
Answer: /users represents the resource while GET already communicates the read operation.
Why? The URL stays focused on the resource and the HTTP method expresses the operation.
Q3. What is the difference between PUT and PATCH?
Answer: PUT is commonly used for replacing/updating a full representation, while PATCH is for partial modification.
Why? PATCH is useful when only a few fields need to change.
Q4. Which status code should commonly be returned after creating a resource?
Answer: 201 Created.
Why? It explicitly tells the client that a new resource was successfully created.
Q5. Find the API design problem. 
GET /getAllProducts
POST /createProduct
POST /updateProduct/10
POST /deleteProduct/10
Answer: The URLs use action names and POST for operations that have standard HTTP methods.
Better:
GET    /products
POST   /products
PATCH  /products/10
DELETE /products/10
Why? The resource is represented by the URL and the method communicates the operation.
Q6. Why is API validation required when the frontend already validates data?
Answer: The frontend cannot be trusted because clients can bypass it and call the API directly.
Why? The server is the final authority for validating incoming data.
Q7. What is the purpose of pagination?
Answer: Pagination divides a large collection into smaller pages.
Why? It reduces response size, database work, memory usage, and frontend rendering work.
Q8. What is the difference between filtering and searching?
Answer: Filtering usually applies structured conditions such as status=active or category=mobile. Searching usually looks for a text/query match such as search=iphone.
Why? They solve different query needs even though both narrow results.
Q9. What is the difference between request headers and request body?
Answer: Headers carry metadata such as authorization and content type. The body carries the main data being submitted.
Why? Keeping metadata and content separate follows HTTP's message structure.
Q10. What status code would you use if a requested user does not exist?
Answer: 404 Not Found.
Why? The requested resource could not be found.
Q11. What status code is commonly used when the user is authenticated but not allowed to access a resource?
Answer: 403 Forbidden.
Why? The server understands who the caller is but refuses access.
Q12. Design an endpoint to get active products.
Answer:
GET /products?status=active
Why? Status is a filter on the products collection, so a query parameter is appropriate.
Q13. Design an endpoint for page 3 with 20 products per page.
Answer:
GET /products?page=3&limit=20
Why? Pagination controls belong naturally in query parameters.
Q14. How would you add sorting by price descending?
Answer:
GET /products?sort=-price
Why? Query parameters are suitable for optional result-ordering instructions. The exact syntax should be documented and validated.
Q15. What is wrong with allowing limit=1000000?
Answer: It can create excessive database work, memory use, network traffic, and response time.
Fix: Validate the limit and enforce a reasonable maximum.
Q16. What should an API do when a request body is invalid?
Answer: Reject it with an appropriate 4xx status and a clear, safe error response.
Why? The client needs to know that its request was invalid and what it needs to correct.
Q17. Why should API errors have consistent structure?
Answer: Consistent errors make frontend handling, logging, testing, and debugging easier.
Why? Clients can rely on predictable fields such as code and message.
Q18. Predict the response status. 
app.post("/users", (req, res) => {
  // user successfully saved
  res.status(201).json({ id: 10 });
});
Answer: 201 Created.
Why? The endpoint successfully created a new user.
Q19. Why should a REST API use status codes instead of always returning 200?
Answer: Status codes communicate the class and outcome of the HTTP operation.
Why? Clients, monitoring tools, proxies, and developers can understand success, client errors, and server errors without parsing only the response body.
Q20. Design a single request that filters, searches, sorts, and paginates products.
Answer:
GET /products?page=2&limit=20&category=mobile&search=iphone&sort=-price
Why? These are optional query controls applied to the same products collection.
22. Final Interview Lines
  • REST: “Resources are identified by URLs, and HTTP methods represent operations on those resources.”
  • CRUD: “GET reads, POST creates, PUT/PATCH update, DELETE removes.”
  • Validation: “Server-side validation is mandatory because clients cannot be trusted.”
  • Pagination: “Pagination limits the amount of data returned in one request.”
  • Filtering: “Filtering narrows resources using structured conditions.”
  • Sorting: “Sorting controls the order of returned resources.”
  • Searching: “Searching finds resources matching a search query.”
  • Error handling: “A good API uses meaningful status codes and consistent, safe error bodies.”
