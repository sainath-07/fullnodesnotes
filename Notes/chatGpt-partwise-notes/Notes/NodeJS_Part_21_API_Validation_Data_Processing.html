🟢 Part 21 — API Validation & Data Processing ⭐⭐⭐

Learn how to check API input before it reaches your business logic or database.

Simple English • Practical Express examples • Validation libraries • Interview preparation

1. What is Input Validation?

Validation means checking whether incoming data follows the rules your API expects.

Layman example: A form asks for your age. If someone enters abc, the form should reject it instead of sending invalid data to the database.
Client ↓ HTTP request ↓ Validation ↓ Valid? ── No ──→ 400 response ↓ Yes Sanitize / normalize ↓ Business logic ↓ Database ↓ Response
Interview line: “Validation protects the API by checking input shape, type, required fields, and business rules before processing the request.”
2. Why is Validation Important?
  • Prevents invalid data from reaching the database.
  • Gives clients clear error messages.
  • Reduces unexpected runtime errors.
  • Keeps API behavior predictable.
  • Helps protect application boundaries.
  • Makes business logic easier to write.
  • Can reject oversized or unexpected input early.
Important: Validation is not a replacement for authentication, authorization, or security controls. It is one layer of defense.

4. Request Body Validation

Request body validation checks data sent inside the request.

const body = req.body;

if (typeof body.name !== "string" || body.name.trim() === "") {
  return res.status(400).json({
    success: false,
    error: {
      code: "VALIDATION_ERROR",
      message: "Name is required"
    }
  });
}
Why? A route should not assume that the client sent the correct shape.
5. Query Validation

Query parameters often arrive as strings, even when they represent numbers.

// GET /products?page=2&limit=20

const page = Number(req.query.page);
const limit = Number(req.query.limit);

if (!Number.isInteger(page) || page < 1) {
  return res.status(400).json({
    message: "page must be a positive integer"
  });
}

if (!Number.isInteger(limit) || limit < 1 || limit > 100) {
  return res.status(400).json({
    message: "limit must be between 1 and 100"
  });
}
Common mistake: Treating req.query.page as a number without converting and checking it.
6. Params Validation

Route parameters are values inside the URL path.

app.get("/users/:id", (req, res) => {
  const { id } = req.params;

  if (!/^[0-9]+$/.test(id)) {
    return res.status(400).json({
      message: "User id must be numeric"
    });
  }

  res.json({ id: Number(id) });
});
If your application uses MongoDB ObjectIds, validate the expected ObjectId format before querying the database.
7. Schema Validation

Schema validation means defining the expected structure and rules in one place.

User schema

name    → string → required → min 2
email   → string → required → valid email
age     → number → optional → >= 18
roles   → array  → optional
address → object → optional
Input ↓ Schema ↓ Every rule checked ↓ Valid → continue Invalid → validation errors
8. Required vs Optional Fields
{
  name: "Sainath",       // required
  email: "user@test.com",// required
  phone: "9999999999"    // optional
}

Required means the field must exist and satisfy its rules.

Optional means the field may be absent, but if it is supplied, its value must still be valid.

Optional does not mean “accept anything.” An optional email field should still be a valid email when provided.
9. Type Checking
if (typeof req.body.name !== "string") {
  return res.status(400).json({
    message: "name must be a string"
  });
}

if (!Number.isInteger(req.body.age)) {
  return res.status(400).json({
    message: "age must be an integer"
  });
}
Interview point: JavaScript is dynamically typed, so API boundaries are a useful place to enforce expected types.
10. Nested Validation

Real APIs often receive nested objects.

{
  "name": "Sam",
  "address": {
    "city": "Hyderabad",
    "pincode": "500001"
  }
}

You should validate both the parent object and its nested fields.

if (
  !req.body.address ||
  typeof req.body.address !== "object" ||
  typeof req.body.address.city !== "string"
) {
  return res.status(400).json({
    message: "A valid address.city is required"
  });
}
11. Custom Validation

Sometimes a simple type check is not enough. You may have a business rule.

function isStrongPassword(password) {
  return typeof password === "string"
    && password.length >= 8
    && /[A-Z]/.test(password)
    && /[0-9]/.test(password);
}

if (!isStrongPassword(req.body.password)) {
  return res.status(400).json({
    message: "Password does not meet the required rules"
  });
}
Security note: Never store passwords in plain text. Validation only checks the input; password hashing is a separate security step.
12. Validation Middleware

Validation middleware keeps validation logic separate from the controller.

function validateCreateUser(req, res, next) {
  const { name, email } = req.body;

  if (typeof name !== "string" || !name.trim()) {
    return res.status(400).json({
      message: "name is required"
    });
  }

  if (typeof email !== "string" || !email.includes("@")) {
    return res.status(400).json({
      message: "valid email is required"
    });
  }

  next();
}

app.post("/users", validateCreateUser, createUser);
POST /users ↓ validateCreateUser ↓ valid createUser ↓ Database
Why? It keeps route handlers focused on business logic and makes validation reusable.
13. Joi — Schema Validation

Joi is a popular schema validation library.

const Joi = require("joi");

const userSchema = Joi.object({
  name: Joi.string().min(2).required(),
  email: Joi.string().email().required(),
  age: Joi.number().integer().min(18).optional()
});

const { error, value } = userSchema.validate(req.body);

if (error) {
  return res.status(400).json({
    success: false,
    error: {
      code: "VALIDATION_ERROR",
      message: error.details[0].message
    }
  });
}

req.body = value;
next();
Joi lets you describe rules as a schema instead of writing many manual if statements.
14. Zod — Schema Validation

Zod is another schema validation library. It is especially popular in TypeScript projects because schemas can also provide strong type information.

const { z } = require("zod");

const userSchema = z.object({
  name: z.string().min(2),
  email: z.string().email(),
  age: z.number().int().min(18).optional()
});

const result = userSchema.safeParse(req.body);

if (!result.success) {
  return res.status(400).json({
    success: false,
    error: {
      code: "VALIDATION_ERROR",
      message: "Invalid request data"
    }
  });
}

const userData = result.data;
next();
Interview point: Joi and Zod are both schema-validation tools. Zod is particularly attractive when a project already uses TypeScript.
15. express-validator

express-validator provides validation and sanitization helpers designed around Express request data.

const {
  body,
  validationResult
} = require("express-validator");

app.post(
  "/users",
  body("email").isEmail(),
  body("name").isString().trim().isLength({ min: 2 }),
  (req, res) => {
    const errors = validationResult(req);

    if (!errors.isEmpty()) {
      return res.status(400).json({
        success: false,
        errors: errors.array()
      });
    }

    res.json({ success: true });
  }
);
It is convenient when you want validation rules directly in Express middleware chains.

JoiSchema-first validationNode.js APIs needing mature schema rules
ZodSchema + strong TypeScript supportTypeScript applications

The best choice depends on the project's stack, team preference, and existing architecture. The important interview skill is understanding validation concepts, not memorizing one library.
17. Sanitization

Sanitization means cleaning or normalizing input into a safer or more useful form.

const email = req.body.email
  .trim()
  .toLowerCase();

For example, these inputs may represent the same email:

"  USER@EXAMPLE.COM  "
        ↓
" user@example.com "
Important: Sanitization is not the same as escaping every value or making an application secure. Use context-specific protections for HTML, SQL, NoSQL, shell commands, and other sinks.
18. Validation vs Sanitization

Asks: “Is this acceptable?”Asks: “Can this be normalized or cleaned?”

Example: email must be validExample: trim surrounding spaces
Raw input ↓ Sanitize / normalize ↓ Validate ↓ Business rules ↓ Store / process
19. Validation Error Response

Return a predictable structure so frontend code can handle errors easily.

{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Please fix the input",
    "fields": {
      "email": "Email is invalid",
      "age": "Age must be at least 18"
    }
  }
}
Interview line: “A good validation response identifies the error clearly without exposing internal implementation details.”
20. Validation Order
Request arrives ↓ Parse body ↓ Basic type / shape checks ↓ Normalize / sanitize where appropriate ↓ Schema validation ↓ Business validation ↓ Authentication / authorization as required ↓ Database / external service ↓ Response

The exact order depends on the API, but the main idea is to reject bad input early.

21. Complete Validation Middleware Example
const express = require("express");
const Joi = require("joi");

const app = express();
app.use(express.json());

const createUserSchema = Joi.object({
  name: Joi.string().trim().min(2).required(),
  email: Joi.string().trim().lowercase().email().required(),
  age: Joi.number().integer().min(18).optional()
});

function validate(schema) {
  return (req, res, next) => {
    const { error, value } = schema.validate(req.body, {
      abortEarly: false,
      stripUnknown: true
    });

    if (error) {
      const fields = {};

      for (const detail of error.details) {
        const field = detail.path.join(".");
        fields[field] = detail.message;
      }

      return res.status(400).json({
        success: false,
        error: {
          code: "VALIDATION_ERROR",
          message: "Please fix the input",
          fields
        }
      });
    }

    req.body = value;
    next();
  };
}

app.post(
  "/users",
  validate(createUserSchema),
  (req, res) => {
    // Business logic receives validated data.
    res.status(201).json({
      success: true,
      data: req.body
    });
  }
);

app.listen(3000);
Architecture benefit: The controller receives data that has already passed the declared validation rules.
22. Common Developer Mistakes
  1. Trusting req.body without validation.
  2. Checking only whether a field exists, but not its type.
  3. Forgetting that query and route parameters commonly arrive as strings.
  4. Validating the body but forgetting req.params and req.query.
  5. Using sanitization as a replacement for validation.
  6. Returning different validation formats from different routes.
  7. Sending database queries before validating IDs and other input.
  8. Accepting unknown fields without a deliberate reason.
  9. Putting all validation code directly inside huge controllers.
  10. Revealing internal validation or database details unnecessarily.
  11. Confusing client input validation with authorization.
  12. Assuming a schema library automatically makes every security problem disappear.
23. Quick Recap
  • Validation checks whether input follows expected rules.
  • Validate body, query parameters, and route parameters.
  • Schema validation keeps rules organized.
  • Required fields must be present and valid.
  • Optional fields may be absent, but must be valid when supplied.
  • Nested objects need nested validation.
  • Custom validation handles business-specific rules.
  • Validation middleware keeps controllers clean.
  • Joi, Zod, and express-validator are common tools.
  • Sanitization and validation solve different problems.
  • Use consistent validation error responses.
  • Reject bad input early and never blindly trust client data.

25. Interview Questions — Show / Hide Answers
Q1. Why should an Express API validate req.body?
Answer: Because client input cannot be trusted to match the expected structure or types.
Why? Validation prevents invalid data from reaching business logic and the database.
Q2. What is the difference between body, query, and params?
Answer: Body contains request payload data, query contains URL query values, and params contain dynamic route values.
Example: /users/42?page=2 has id in params and page in query.
Q3. Why can this validation fail? 
if (req.query.page > 10) {
  ...
}
Answer: It does not check whether page is a valid number, integer, or positive value.
Why? Query input comes from the client and should be explicitly parsed and validated.
Q4. What is schema validation?
Answer: It defines the expected shape and rules of data in a schema and checks input against that schema.
Why? It centralizes rules and reduces repeated manual checks.
Q5. What is the difference between validation and sanitization?
Answer: Validation decides whether input is acceptable; sanitization transforms or normalizes input.
Example: Checking that an email is valid is validation. Trimming spaces around it is normalization/sanitization.
Q6. Why is type checking important in JavaScript APIs?
Answer: JavaScript is dynamically typed, so client input can have an unexpected type.
Why? A value expected to be an array, number, or object should be checked before code uses it.
Q7. What does “optional field” mean?
Answer: The field may be absent. If it is provided, its value still needs to satisfy the validation rules.
Why? Optional means “not required,” not “unrestricted.”
Q8. How would you validate a nested object? 
{
  "address": {
    "city": "Hyderabad"
  }
}
Answer: Validate that address exists and has the expected object type, then validate its nested fields such as city.
Why? Checking only the parent object does not guarantee that its children are valid.
Q9. Why use validation middleware?
Answer: It separates input checking from business logic.
Why? Controllers become smaller, rules can be reused, and invalid requests can stop before reaching the controller.
Q10. What is the purpose of Joi or Zod?
Answer: They provide schema-based validation for structured data.
Why? They make complex validation rules easier to define and maintain.
Q11. Why is Zod popular in TypeScript projects?
Answer: Zod schemas can be used with TypeScript type inference.
Why? The same schema can help describe runtime data rules while also supporting compile-time types.
Q12. What is wrong with this code? 
app.post("/users", async (req, res) => {
  const user = await User.create(req.body);
  res.json(user);
});
Answer: The code sends client input directly to the database without showing validation.
Why? Invalid, unexpected, or unsafe data could reach the persistence layer. Validate the expected fields before saving.
Q13. What validation should be applied to a user ID in /users/:id?
Answer: Validate the ID according to the database and application format, such as a positive integer or valid MongoDB ObjectId.
Why? It avoids unnecessary database queries and gives clients a clear input error.
Q14. What is a good validation error response?
Answer: Use a consistent structure containing an error code, readable message, and optionally field-level errors.
Why? Frontend applications can reliably display the correct field errors.
Q15. Should optional fields be ignored completely?
Answer: No. If an optional field is supplied, validate it.
Why? “Optional” only means the field may be absent.
Q16. Why validate before a database query?
Answer: It rejects bad input early and avoids unnecessary database work.
Why? This improves reliability and can reduce unnecessary load on the database.
Q17. What is custom validation?
Answer: Custom validation checks a business-specific rule that may not be covered by basic type or format checks.
Example: A booking date must be after today.
Q18. Is validation enough to prevent SQL or NoSQL injection?
Answer: No.
Why? Validation is one layer. Use parameterized queries, safe database APIs, appropriate query construction, authorization, and other security controls for the specific database.
Q19. Find the validation bug. 
if (!req.body.age) {
  return res.status(400).send("Age required");
}
Answer: This checks truthiness rather than type and business rules.
Why? Values such as 0, "", or other unexpected values may be treated as missing. Use explicit checks such as Number.isInteger(age) and range validation.
Q20. Explain the ideal API validation flow in an interview.
Answer:
Request ↓ Parse input ↓ Validate body / query / params ↓ Normalize where appropriate ↓ Reject invalid data ↓ Authenticate / authorize ↓ Business logic ↓ Database / service ↓ Response
Why? It keeps invalid data away from the core application and creates a predictable API boundary.
