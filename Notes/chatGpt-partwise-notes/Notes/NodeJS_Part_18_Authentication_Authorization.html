🟢 Part 18 — Authentication & Authorization ⭐⭐⭐

Learn how Node.js applications identify users and control what they are allowed to do.

Simple English • Passwords • bcrypt • JWT • Access/Refresh Tokens • Cookies • Roles • Permissions

1. Authentication vs Authorization
ConceptSimple meaningExample
Authentication“Who are you?”Login with email and password
Authorization“What are you allowed to do?”Only admins can delete users
Layman example: A security guard first checks your ID. That is authentication. Then the guard checks whether your ID allows you into the server room. That is authorization.
User ↓ Login credentials ↓ Authentication → Identity confirmed ↓ Authorization → Check role/permission ↓ Protected resource
Interview line: “Authentication verifies identity; authorization decides whether that authenticated identity can perform an action.”
2. Registration

Registration creates a new account. The important security rule is: never store the user's plain password.

const bcrypt = require("bcrypt");

app.post("/register", async (req, res) => {
  const { email, password } = req.body;

  const passwordHash = await bcrypt.hash(password, 12);

  // Save email + passwordHash, NOT the plain password.
  // await User.create({ email, passwordHash });

  res.status(201).json({ message: "Registered" });
});

The number 12 is the bcrypt cost factor used in this example. Choose a cost appropriate for your application's performance and security requirements.

Common mistake: Saving password directly in MongoDB/MySQL. Password hashing must happen before storage.
3. Password Hashing with bcrypt

Hashing converts a password into a one-way value. bcrypt is designed for password hashing and includes a salt as part of its process.

Plain password ↓ bcrypt.hash() ↓ Password hash ↓ Database

During login:

Entered password ↓ bcrypt.compare() ↓ Matches stored hash? ↙ ↘ YES NO ↓ ↓ Login Reject
const isValid = await bcrypt.compare(
  password,
  user.passwordHash
);

if (!isValid) {
  return res.status(401).json({
    message: "Invalid credentials"
  });
}
Important: You do not “decrypt” a bcrypt password hash. You compare the entered password with the stored hash.
4. Login Flow
app.post("/login", async (req, res) => {
  const { email, password } = req.body;

  const user = await findUserByEmail(email);

  if (!user) {
    return res.status(401).json({
      message: "Invalid credentials"
    });
  }

  const valid = await bcrypt.compare(
    password,
    user.passwordHash
  );

  if (!valid) {
    return res.status(401).json({
      message: "Invalid credentials"
    });
  }

  // Create access/refresh tokens here.

  res.json({ message: "Login successful" });
});
Security tip: Many systems use the same generic message such as “Invalid credentials” for unknown users and wrong passwords, reducing unnecessary account-enumeration information.
5. JWT — JSON Web Token

A JWT is a signed token often used to carry claims between a client and server.

A JWT normally has three dot-separated parts:

HEADER.PAYLOAD.SIGNATURE
PartPurpose
HeaderDescribes token metadata such as the signing algorithm.
PayloadContains claims such as user ID, role, and expiration.
SignatureAllows the server to verify that the token was signed with the expected secret/key.
Important: A normal JWT payload is encoded, not encrypted. Do not put passwords, secrets, or sensitive private data in it.
6. JWT Payload and Expiration
const jwt = require("jsonwebtoken");

const token = jwt.sign(
  {
    sub: user.id,
    role: user.role
  },
  process.env.JWT_SECRET,
  {
    expiresIn: "15m"
  }
);

Typical useful claims include sub for the subject/user identity and exp for expiration, depending on the JWT library and configuration.

Do not put sensitive information in the payload. Anyone holding a normal JWT can decode its header and payload even though they cannot create a valid signature without the required signing key.
7. Access Token vs Refresh Token ⭐⭐⭐
Access tokenRefresh token
Used to access protected APIsUsed to obtain a new access token
Usually short-livedUsually longer-lived
Sent frequently to APIsUsed less frequently
Limits exposure if stolenNeeds stronger protection because it can create new access tokens
Login ↓ Access token + Refresh token ↓ Access token → API requests ↓ Access token expires ↓ Refresh token → Token endpoint ↓ New access token
Interview line: “A short-lived access token limits the lifetime of API access, while a refresh token can be used to obtain a new access token without asking the user to log in again.”
8. JWT Signature

The signature helps the server detect whether the signed token was altered.

Header + Payload ↓ Signing key ↓ Signature Received JWT ↓ Verify signature ↙ ↘ Valid Invalid ↓ ↓ Continue Reject
const decoded = jwt.verify(
  token,
  process.env.JWT_SECRET
);
Never trust a decoded JWT by itself. Decoding reads claims. Verification checks the signature and relevant token validity.
9. Protected Routes
function authenticate(req, res, next) {
  const header = req.get("Authorization");

  if (!header || !header.startsWith("Bearer ")) {
    return res.status(401).json({
      message: "Authentication required"
    });
  }

  const token = header.slice(7);

  try {
    req.user = jwt.verify(
      token,
      process.env.JWT_SECRET
    );
    next();
  } catch {
    return res.status(401).json({
      message: "Invalid or expired token"
    });
  }
}

app.get("/profile", authenticate, (req, res) => {
  res.json({ user: req.user });
});
Request ↓ authenticate middleware ↓ Token present? ↓ Verify token ↓ Attach user to req ↓ next() ↓ Controller
10. Authorization Middleware
function requireRole(...allowedRoles) {
  return (req, res, next) => {
    if (!allowedRoles.includes(req.user.role)) {
      return res.status(403).json({
        message: "Forbidden"
      });
    }

    next();
  };
}

app.delete(
  "/users/:id",
  authenticate,
  requireRole("admin"),
  deleteUser
);

Notice the difference:

authenticate → Who is the user? ↓ requireRole → Is this role allowed? ↓ deleteUser → Perform the action
11. Role-Based Authorization

Role-based access control, or RBAC, assigns permissions through roles.

RoleExample permissions
userRead own profile, create own orders
editorCreate/update content
adminManage users and system resources
Do not rely only on the frontend. Hiding an “Admin” button does not protect an API. The server must enforce authorization.
12. Permissions

Permissions can be more precise than roles.

const permissions = {
  admin: ["users:read", "users:delete", "posts:write"],
  editor: ["posts:read", "posts:write"],
  user: ["posts:read"]
};

A permission check can answer questions such as: “Can this user delete users?” instead of only asking “Is this user an admin?”

13. Cookies

Cookies are small pieces of data that a browser can store and send with matching requests.

res.cookie("refreshToken", refreshToken, {
  httpOnly: true,
  secure: true,
  sameSite: "lax",
  maxAge: 7 * 24 * 60 * 60 * 1000
});

Cookies are especially useful when the browser should automatically send authentication/session information to the appropriate origin.

14. HttpOnly, Secure, SameSite
AttributeMeaningWhy it matters
HttpOnlyJavaScript cannot read the cookie through document.cookie.Helps reduce token theft through some XSS scenarios.
SecureCookie is sent only over HTTPS.Protects cookie transmission over insecure HTTP.
SameSiteControls when cookies are sent in cross-site contexts.Helps reduce CSRF risk and controls cross-site cookie behavior.
Important: Cookie security depends on the whole application design. These flags are protections, not a complete authentication system.
15. Authentication + Authorization Full Flow
REGISTER ↓ Hash password with bcrypt ↓ Store password hash ↓ LOGIN ↓ Find user ↓ bcrypt.compare() ↓ Create access + refresh tokens ↓ Client stores/sends credentials safely ↓ Protected API request ↓ Authentication middleware ↓ Verify token ↓ Identify user ↓ Authorization middleware ↓ Check role / permission ↓ Controller ↓ Response
16. Common Developer Mistakes
  1. Storing plain-text passwords.
  2. Trying to decrypt bcrypt hashes.
  3. Putting passwords or secrets in JWT payloads.
  4. Decoding a JWT and treating it as verified.
  5. Using a weak or exposed JWT signing secret.
  6. Making access tokens unnecessarily long-lived.
  7. Not protecting refresh tokens carefully.
  8. Checking authorization only in React/frontend code.
  9. Returning 401 and 403 interchangeably.
  10. Forgetting token expiration and revocation strategy.
  11. Using cookies without understanding HttpOnly, Secure, and SameSite.
  12. Logging passwords, access tokens, or refresh tokens.
  13. Returning detailed authentication errors that help attackers enumerate accounts.
  14. Not validating request data before authentication-related operations.
17. Quick Recap
  • Authentication: verifies identity.
  • Authorization: checks permission.
  • bcrypt: hashes passwords and compares entered passwords with stored hashes.
  • JWT: commonly carries signed claims.
  • Payload: readable claims; never treat it as secret storage.
  • Signature: lets the server verify token integrity.
  • Expiration: limits how long a token is valid.
  • Access token: short-lived API credential in many designs.
  • Refresh token: used to obtain new access tokens.
  • Authentication middleware: identifies the caller.
  • Authorization middleware: checks roles/permissions.
  • HttpOnly: blocks JavaScript access to a cookie.
  • Secure: sends a cookie only over HTTPS.
  • SameSite: controls cross-site cookie sending.

19. Interview Questions — Show / Hide Answers
Q1. What is the difference between authentication and authorization?
Answer: Authentication verifies who the user is. Authorization checks what that user is allowed to do.
Why? A valid identity does not automatically mean the user has permission for every operation.
Q2. Why should passwords be hashed instead of encrypted?
Answer: Password storage normally needs a one-way password hash, not reversible encryption.
Why? The server only needs to verify a password, not recover the original password. bcrypt is designed for this purpose.
Q3. Can you decrypt a bcrypt password hash?
Answer: No. You use bcrypt.compare() to test an entered password against the stored hash.
Why? bcrypt is a one-way password hashing scheme.
Q4. What are the three parts of a JWT?
Answer: Header, payload, and signature.
Why? The header describes token metadata, the payload carries claims, and the signature provides integrity verification.
Q5. Is a JWT payload encrypted?
Answer: A normal signed JWT is not encrypted; its payload is encoded and readable.
Why? Anyone holding the token can decode the payload. The signature prevents undetected modification when properly verified.
Q6. What is the difference between decoding and verifying a JWT?
Answer: Decoding reads the token contents. Verification checks the signature and token validity according to the verification rules.
Why? Reading a token does not prove that it was issued by your trusted server.
Q7. Why are access tokens often short-lived?
Answer: A short lifetime limits the period in which a stolen access token can be used.
Why? It reduces the impact window of token exposure.
Q8. What is the purpose of a refresh token?
Answer: It can be used to obtain a new access token after the access token expires, depending on the authentication design.
Why? Users can remain signed in without sending their password again.
Q9. Find the security problem. 
const token = jwt.sign({
  userId: user.id,
  password: user.password,
  creditCard: user.card
}, secret);
Answer: Sensitive data is being placed in the JWT payload.
Fix: Keep claims minimal, for example a subject/user ID and required non-sensitive authorization claims.
Why? Normal JWT payloads can be decoded by anyone holding the token.
Q10. What is the purpose of Authorization: Bearer token?
Answer: It is a common HTTP header format for sending a bearer access token to an API.
Why? The server can extract and verify the token before allowing protected operations.
Q11. What should happen here? 
app.delete("/users/:id",
  authenticate,
  requireRole("admin"),
  deleteUser
);
Answer: Authentication runs first, then authorization checks the admin role, and only then does deleteUser run.
Why? The server must identify the caller before checking whether the caller is allowed to perform the operation.
Q12. What is the difference between HTTP 401 and 403?
Answer: 401 means the request lacks valid authentication credentials or requires authentication. 403 means the server understood the caller but refuses access to the resource/action.
Why? They communicate different security states.
Q13. Why is frontend-only authorization insecure?
Answer: Users can bypass frontend code and directly call the backend API.
Why? The backend is the trusted enforcement point for authorization.
Q14. What does HttpOnly do?
Answer: It prevents normal client-side JavaScript from reading that cookie through document.cookie.
Why? This can reduce the ability of injected JavaScript to directly steal a cookie value.
Q15. What does Secure do on a cookie?
Answer: It tells the browser to send the cookie only over a secure HTTPS connection.
Why? It helps protect cookie transmission from being sent over plain HTTP.
Q16. What does SameSite control?
Answer: It controls when a browser includes the cookie in cross-site request contexts.
Why? It is an important part of controlling cross-site cookie behavior and reducing CSRF risk.
Q17. Predict the result. 
const passwordHash = await bcrypt.hash("hello123", 12);
const ok = await bcrypt.compare("hello123", passwordHash);
console.log(ok);
Answer: true.
Why? The original password matches the generated bcrypt hash.
Q18. Predict the result. 
const passwordHash = await bcrypt.hash("hello123", 12);
const ok = await bcrypt.compare("hello124", passwordHash);
console.log(ok);
Answer: false.
Why? The entered password is different from the password used to create the stored hash.
Q19. Where should authorization be checked in a Node.js API?
Answer: On the server, before the protected operation is executed.
Why? Client-side checks can be bypassed. Middleware or service-level authorization provides a trusted enforcement point.
Q20. Design the secure flow for an admin-only delete API.
Answer:
DELETE /users/10 ↓ Authenticate token ↓ Verify signature + expiration ↓ Identify user ↓ Check admin role/permission ↓ Delete user ↓ Return response
Why? Authentication answers “who?”, authorization answers “allowed to delete?”, and only then should the destructive operation execute.
20. Final Interview Lines
  • Authentication: “Authentication verifies identity.”
  • Authorization: “Authorization checks permissions after identity is established.”
  • bcrypt: “Passwords are hashed and later checked with bcrypt.compare(); they are not decrypted.”
  • JWT: “A signed JWT contains a header, payload, and signature.”
  • JWT security: “A normal JWT payload is readable, so sensitive secrets should never be stored there.”
  • Access token: “Usually short-lived and used for API access.”
  • Refresh token: “Used to obtain a new access token in designs that support refresh tokens.”
  • 401 vs 403: “401 is an authentication problem; 403 is an authorization refusal.”
  • Cookies: “HttpOnly limits JavaScript access, Secure requires HTTPS, and SameSite controls cross-site sending behavior.”
