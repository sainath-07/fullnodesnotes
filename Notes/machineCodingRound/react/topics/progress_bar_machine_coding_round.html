WHATUI COMPONENT

What is a Progress Bar?

A progress bar is a visual UI component that communicates how much of a task is completed compared with the total work. It normally represents progress as a percentage from 0% to 100%.

Simple example

65% completed

Typical use cases

  • File uploads and downloads
  • Multi-step forms and onboarding
  • Long-running API or processing jobs
  • Installations, imports and data migrations
  • Video/audio loading or buffering
WHY

What problem does it solve?

A progress bar solves the communication problem of uncertainty during a waiting operation.

Without progress
User sees a spinner and may not know whether the task is moving, stuck, or nearly complete.
With progress
User gets a clear estimate of completion and can understand the current state.

Interview answer

“The main problem is feedback. When an operation takes time, users need to know that work is progressing. A progress bar gives a measurable visual indication instead of leaving the user with an indefinite wait.”
HOW

How to implement a Progress Bar

  1. Keep a numeric progress value, normally between 0 and 100.
  2. Render an outer track representing the total possible progress.
  3. Render an inner fill element whose width represents the current percentage.
  4. When progress changes, update the state/value.
  5. Clamp the value so it never goes below 0 or above 100.
  6. Update accessible information such as aria-valuenow.
const progress = 65;

// Visual representation
fill.style.width = `${progress}%`;

// Accessible representation
bar.setAttribute("aria-valuenow", progress);

1 MINUTE

How to explain it to the interviewer in 1 minute

“I implemented a reusable progress bar that visually represents completion from 0 to 100 percent. The component has a track and a fill area. I keep the current percentage as the source of truth and update the fill width whenever the value changes. I also clamp the value between 0 and 100 so invalid input cannot break the UI. For accessibility, I expose the current value with ARIA attributes. The component can be driven by a timer, API progress, upload events, or any other source that produces a percentage.”

1-minute structure

  1. What: Visual indicator of task completion.
  2. How: State/value → fill width.
  3. Safety: Clamp 0–100.
  4. Accessibility: ARIA progress semantics.
  5. Extensibility: Can connect to API/upload/timer events.
5 MINUTES

How to explain it to the interviewer in 5 minutes

Opening: “I’ll first explain the component contract, then the state flow, rendering, edge cases, accessibility and how I would make it production-ready.”

1. Requirement

Accept a progress value and visually display completion from 0–100%. The component should remain predictable when the input is invalid.

2. Data flow

The external source owns the real progress. The component receives or stores the current value, validates it, and converts it into a visual width.

3. Rendering

The outer element is the track. The inner element uses width: progress%. CSS transition can make changes easier to perceive.

4. Edge cases

  • Negative values → treat as 0.
  • Values above 100 → treat as 100.
  • Missing/invalid values → choose a defined fallback.
  • Unknown duration → use an indeterminate progress indicator instead of pretending to know a percentage.

5. Accessibility

Use role="progressbar", aria-valuemin="0", aria-valuemax="100", and aria-valuenow.

6. Production improvements

Make the component reusable, support custom labels, expose completion callbacks if needed, test boundaries, and separate progress calculation from presentation.

FULL CODE

Standalone implementation

This is intentionally framework-free so the interviewer can focus on the core logic. The same pattern maps directly to React/Vue/Angular.

<div
  class="progress"
  role="progressbar"
  aria-valuemin="0"
  aria-valuemax="100"
  aria-valuenow="65"
  aria-label="Upload progress"
>
  <div class="progress__fill" style="width: 65%"></div>
</div>

<script>
function clampProgress(value) {
  const numericValue = Number(value);

  if (!Number.isFinite(numericValue)) {
    return 0;
  }

  return Math.min(100, Math.max(0, numericValue));
}

function setProgress(progressElement, value) {
  const progress = clampProgress(value);
  const fill = progressElement.querySelector(".progress__fill");

  fill.style.width = `${progress}%`;
  progressElement.setAttribute("aria-valuenow", progress);
}

// Example:
// setProgress(document.querySelector(".progress"), 75);
</script>

React version — core idea

function ProgressBar({ value }) {
  const progress = Math.min(100, Math.max(0, Number(value) || 0));

  return (
    <div
      role="progressbar"
      aria-valuemin={0}
      aria-valuemax={100}
      aria-valuenow={progress}
    >
      <div style={{ width: `${progress}%` }} />
    </div>
  );
}
COMMON MISTAKES

Common developer mistakes

1. Not clamping the value
Allowing -20% or 150% can produce incorrect UI. Normalize to 0–100.
2. Mixing calculation and presentation
Putting API/timer logic directly inside rendering makes the component harder to test and reuse.
3. Forgetting accessibility
A visual bar alone does not communicate its state to screen readers. Use progressbar semantics and ARIA values.
4. Treating unknown progress as 0%
If the system genuinely cannot calculate progress, an indeterminate indicator is more honest.
5. No completion handling
Consider what should happen at 100%: show “Complete”, trigger a callback, or transition to the next state.
6. Overengineering
For a basic machine-coding task, don't introduce unnecessary state managers, libraries or abstractions.
7. Ignoring boundary cases
Test 0, 1, 50, 99, 100, negative, greater-than-100, NaN and missing values.
8. Poor visual feedback
A progress update that jumps too aggressively or has no transition can feel broken. Use a small, appropriate CSS transition.
FOLLOW-UP QUESTIONS

Likely interviewer follow-ups

What if you don't know the percentage?

Use an indeterminate progress bar. It communicates that work is happening without making up a percentage.

How would you make it reusable?

Expose props such as value, max, label, showPercentage, and styling variants while keeping progress calculation outside.

How would an upload drive it?

Use upload progress events from the networking layer, convert bytes sent / total bytes into a percentage, then pass that value to the component.

How would you test it?

  • 0% renders an empty fill.
  • 50% renders half the track.
  • 100% renders full width.
  • Negative and >100 values are clamped.
  • ARIA values match the rendered state.
  • Indeterminate mode renders correctly when total work is unknown.
