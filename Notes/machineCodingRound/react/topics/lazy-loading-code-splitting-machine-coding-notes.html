Lazy Loading + Code Splitting

Interview-ready notes with React.lazy(), Suspense, dynamic import(), visual flow, full code and common mistakes.

LEFT — What is Lazy Loading?

Lazy loading means delaying the loading of code or content until it is actually needed.

Simple idea: “Don't download everything at the beginning. Download a feature when the user needs it.”
const Dashboard = React.lazy(() => import("./Dashboard"));

The Dashboard code can be loaded when React needs to render that component.

LEFT — Why is Lazy Loading Important?
  • Reduces JavaScript needed for the initial page.
  • Can improve initial load performance for large applications.
  • Users do not download features they never visit.
  • Works well for large routes such as Admin, Reports and Analytics.
  • Can help slower networks and devices.
Important: Lazy loading does not remove code. It changes when the code is downloaded.
LEFT — What is Code Splitting?

Code splitting divides a large JavaScript bundle into smaller chunks that can be downloaded separately.

Think of a large book:
Without code splitting → download the whole book.
With code splitting → download only the chapter you need.

Dynamic import() commonly creates a split point that build tools can turn into a separate chunk.

LEFT — How does it work?
  1. Application starts.
  2. Critical code loads first.
  3. A lazy component points to a dynamic import.
  4. User navigates to or triggers that feature.
  5. Browser requests its JavaScript chunk.
  6. Chunk downloads.
  7. React renders the component.
Relationship: import() provides the dynamic loading boundary; React.lazy() lets React render a component from that Promise; Suspense provides fallback UI while waiting.
LEFT — When should I use it?
  • Large route-based applications
  • Admin dashboards
  • Analytics/reporting pages
  • Heavy editors or charts
  • Rarely used dialogs/tools
  • Features triggered only after a user action
Don't lazy-load everything. Tiny, always-used components may not benefit from another chunk and loading state.

LEFT — Common Developer Mistakes
  1. Lazy-loading every tiny component.
  2. Forgetting Suspense around lazy content.
  3. Providing a poor or confusing loading UI.
  4. Using import paths that cannot be handled as intended by the build setup.
  5. Ignoring lazy chunk failures.
  6. Defining React.lazy() inside render unnecessarily.
  7. Assuming lazy loading fixes every performance problem.
  8. Not measuring whether the split actually helps.
LEFT — How I would explain it to the interviewer
“I would use route-level lazy loading for large or less frequently visited parts of the application. Instead of importing every page into the initial bundle, I use a dynamic import with React.lazy(). This creates a code-splitting boundary so the page's JavaScript can be downloaded when the route is needed. I wrap the lazy component with Suspense to show fallback UI while the chunk is loading. For production, I would also handle chunk-loading failures with an Error Boundary and avoid lazy-loading very small components where the extra request is not worthwhile.”
Interview tip: “Lazy loading controls when code is loaded; code splitting controls how code is divided into separately loadable chunks.”

RIGHT — Basic Syntax
import React, { Suspense } from "react";

const Dashboard = React.lazy(
  () => import("./Dashboard")
);

function App() {
  return (
    <Suspense fallback={<p>Loading Dashboard...</p>}>
      <Dashboard />
    </Suspense>
  );
}
Important: The dynamically imported module should resolve to a module whose default export is the component when using the standard React.lazy(() => import(...)) pattern.

Step 7: When the Promise resolves, React renders the component.
RIGHT — Full Machine Coding Example

This example demonstrates route-like lazy loading without requiring a routing library.

import React, { Suspense, useState } from "react";

// Define lazy component types at module scope.
const Home = React.lazy(() => import("./pages/Home"));
const Dashboard = React.lazy(() => import("./pages/Dashboard"));
const Reports = React.lazy(() => import("./pages/Reports"));

function App() {
  const [page, setPage] = useState("home");

  return (
    <div>
      <nav>
        <button onClick={() => setPage("home")}>Home</button>
        <button onClick={() => setPage("dashboard")}>Dashboard</button>
        <button onClick={() => setPage("reports")}>Reports</button>
      </nav>

      <main>
        <Suspense fallback={<Loading />}>
          {page === "home" && <Home />}
          {page === "dashboard" && <Dashboard />}
          {page === "reports" && <Reports />}
        </Suspense>
      </main>
    </div>
  );
}

function Loading() {
  return <p>Loading page...</p>;
}

export default App;
Machine-coding explanation: Each large page is a separate lazy boundary. Home can be used first, while Dashboard and Reports are loaded when selected.

RIGHT — Why Suspense?

When a lazy component is not available yet, React needs a fallback UI for the waiting period.

<Suspense fallback={<Loading />}>
  <Dashboard />
</Suspense>
Fallback is missing/poor

The transition can feel abrupt or confusing.

Useful fallback

The user immediately gets feedback that the requested feature is loading.

RIGHT — Common Developer Mistakes Explained
1. Forgetting Suspense
Render lazy content under an appropriate Suspense boundary.
2. Lazy-loading everything
Too many tiny chunks can add requests and loading states without meaningful benefit.
3. Defining lazy components inside render
Keep lazy component definitions at module scope so the component type is stable.
4. No error handling
A lazy chunk can fail to load. Use an Error Boundary for production recovery UI.
5. Wrong export
The standard lazy-import pattern expects the resolved module's default export to be the component.
6. Expecting instant performance everywhere
The first visit to a lazy route may require an additional network request.
7. Not measuring
Use real performance data to decide whether a split is beneficial.
RIGHT — Interview Follow-Up Questions
  1. Does React.lazy() perform code splitting by itself?
    It consumes a dynamic import. The build tool typically uses that dynamic import as a split point and produces separately loadable code.
  2. Why do we need Suspense?
    It provides fallback UI while the lazy component is waiting to load.
  3. What happens if the chunk fails?
    The lazy import rejects. An Error Boundary can provide recovery UI.
  4. Should every component be lazy-loaded?
    No. Prefer meaningful boundaries such as large routes or expensive/rare features.
  5. What is the trade-off?
    You reduce initial JavaScript, but a later feature may require another request before it can render.
