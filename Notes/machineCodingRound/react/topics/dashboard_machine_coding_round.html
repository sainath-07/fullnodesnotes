Questions / Topics
WHAT

What is a Dashboard?

A Dashboard is a UI that brings important information, metrics and actions into one place so a user can understand the current state of a system quickly and take action. In a machine coding round, a dashboard usually combines a layout, reusable widgets/cards, navigation, filters, tables or charts, loading states and responsive behavior.

Simple interview definition: “A dashboard is a data-driven UI that organizes key metrics and visualizations into reusable sections, with a clear information hierarchy so users can monitor and act on important information quickly.”

WHY

What problem does a Dashboard solve?

A dashboard solves the problem of presenting a large amount of operational or business information without forcing the user to inspect multiple screens individually.

Problems it demonstrates in a machine coding round

  • Information hierarchy: Important KPIs should be visible before secondary details.
  • Componentization: Cards, charts, tables, filters and navigation should be reusable.
  • Responsive design: The layout should adapt from desktop to smaller screens.
  • State management: Filters, selected navigation, loading and errors affect what is displayed.
  • Data handling: API results should be transformed into UI-friendly structures.
  • UI states: Empty, loading, error and success states should be considered.
  • Performance: Expensive charts and large tables should not cause unnecessary rendering.
Key interview point: Don't describe a dashboard as “just cards and charts.” The interesting part is the architecture: reusable components, data flow, state, responsive layout and clear handling of loading/error/empty states.
HOW

How to implement a Dashboard

  1. Clarify requirements: Identify required widgets, navigation, filters and interactions.
  2. Design the layout: Create sidebar/header/content regions using CSS Grid or Flexbox.
  3. Break into components: Sidebar, Header, KPI Card, Chart Card, Table, Filter Bar and Dashboard Page.
  4. Define the data model: Keep API/data structures separate from presentation where possible.
  5. Manage state: Track selected navigation, filters and UI states in the appropriate component.
  6. Render reusable widgets: Use arrays and mapping instead of duplicating markup.
  7. Handle async states: Show loading, error, empty and successful data states.
  8. Make responsive: Collapse or stack sidebar/widgets based on available width.
  9. Optimize: Memoize expensive derived data only when needed and avoid unnecessary API calls.

Interaction flow: filter example

  1. User changes a date/filter.
  2. Filter state updates.
  3. Dashboard decides whether data can be filtered locally or a new API request is needed.
  4. Loading state can be shown for remote data.
  5. New data is transformed and passed to widgets.
  6. Only the affected UI should update where practical.
Important: Keep data fetching and business logic separate from presentation components. It makes the dashboard easier to test and maintain.
1 MINUTE

How to explain Dashboard to the interviewer in 1 minute

“I built the dashboard as a responsive layout with reusable components. I separated the shell into sidebar, header and main content, and then composed the main content from reusable KPI cards, charts and a table. The dashboard data is kept separately from the presentation so the widgets can render from configuration or API responses. I also considered loading, error and empty states. For interactions like filters and navigation, I keep the selected values in state and derive the displayed data from that state. The main focus is componentization, predictable data flow, responsive layout and avoiding a large monolithic dashboard component.”

  • Data-driven rendering
  • Responsive CSS Grid / Flexbox

  • Separation of concerns
  • Performance
5 MINUTES

How to explain Dashboard in 5 minutes

1. Clarify the requirement

“I first identify the widgets and interactions. For example, KPI cards, a trend chart, recent activity, a table, sidebar navigation and a date filter. I also clarify whether the data is static or API-driven.”

2. Design the page structure

“I use a two-dimensional layout: a fixed or collapsible sidebar, a header and a responsive main content area. CSS Grid is useful for the widget layout because cards can resize and wrap naturally.”

3. Componentize

“I don't create one huge Dashboard component. I split it into DashboardLayout, Sidebar, Header, FilterBar, KpiCard, ChartCard and DataTable. Repeated widgets receive data through props.”

4. Define data flow

“API data is loaded at the page/container level and passed to presentation components. If a filter changes, I either derive the filtered result locally or refetch from the server depending on the requirement.”

5. Handle UI states

  • Initial loading → skeleton/spinner.
  • Success → dashboard widgets.
  • Empty → meaningful empty-state message.
  • Error → retry/error message.
  • Partial widget failure → ideally isolate failure to that widget.

6. Make it responsive

“On smaller screens, the sidebar can collapse and the KPI/chart grids can move from multiple columns to one column. Tables can scroll horizontally instead of breaking the layout.”

7. Performance

“For large datasets, I avoid rendering unnecessary rows, use pagination or virtualization for tables, and avoid recalculating expensive chart transformations on every render.”

Strong closing line: “My approach is to build the dashboard as a data-driven composition of small reusable components, with clear state boundaries and explicit loading/error/empty states. That keeps the UI scalable as more widgets are added.”
MY IMPLEMENTATION

How I implemented it — explanation to interviewer

Explain your implementation in this order:

1. Layout first

“I first created the dashboard shell with a sidebar, header and responsive content area. This gives every widget a predictable place.”

2. Reusable widgets

“I created a generic KPI card and used data mapping to render multiple metrics instead of copying markup.”

3. Data model

“I kept widget data in structured objects so the presentation component doesn't contain business-specific hard-coded values.”

4. State

“Navigation selection and filters are state. The rendered dashboard content is derived from that state.”

5. Async states

“If data comes from an API, I explicitly model loading, success, error and empty states instead of assuming the request always succeeds.”

6. Responsive behavior

“I used CSS Grid/Flexbox and breakpoints so cards stack naturally on smaller screens and the layout remains usable.”

How to narrate while coding

“First I will create the page shell. Then I will define the data structure for repeated widgets. Next I will build one reusable card and render the rest from data. After that I will add interactions such as filters/navigation, then handle loading/error/empty states, and finally check responsiveness and performance.”
Interview-friendly summary: “I separated layout, reusable presentation components, state and data transformation. This lets me change the data source or add another widget without rewriting the whole dashboard.”

COMMON MISTAKES

Common developer mistakes

1. Building one huge Dashboard component

Putting sidebar, API calls, cards, charts, tables and filters into one component becomes difficult to maintain.

Better: Split by responsibility and reuse repeated widgets.

2. Duplicating KPI/card markup

Copy-pasting five nearly identical cards makes future changes error-prone.

Better: Store widget data in arrays and map it into a reusable component.

3. Mixing API logic with presentation

A card that directly fetches and transforms its own unrelated data becomes hard to test and coordinate.

Better: Define clear data boundaries and pass data into presentation components.

4. Ignoring loading, error and empty states

A dashboard that only handles successful API responses is incomplete.

Better: Design all important UI states explicitly.

5. Poor responsive layout

Desktop-only fixed widths cause horizontal scrolling and broken charts/tables on smaller screens.

Better: Use responsive Grid/Flexbox, breakpoints and horizontal table scrolling where appropriate.

6. Fetching data on every render

Incorrect effect dependencies can trigger repeated API calls.

Better: Understand effect dependencies and separate fetch triggers from render logic.

7. Overusing global state

Putting every local UI state into a global store adds unnecessary complexity.

Better: Keep state close to the components that own it unless multiple areas truly need it.

8. No stable keys for lists

Using array indexes as keys for dynamic/reorderable lists can produce incorrect UI reconciliation.

Better: Use stable IDs from the data.

9. Ignoring large datasets

Rendering thousands of table rows or expensive charts directly can make the dashboard slow.

Better: Use pagination, virtualization, aggregation or lazy loading where appropriate.

10. Premature optimization

Adding memoization everywhere makes the code harder to understand without necessarily improving performance.

Better: First make the architecture correct, then optimize measured bottlenecks.

11. Poor accessibility

Icon-only controls, low contrast and charts with no meaningful alternative can make the dashboard difficult to use.

Better: Use semantic elements, labels, keyboard support and accessible data summaries.

12. No clear information hierarchy

Showing every metric with equal visual weight makes it hard to identify what matters.

Better: Prioritize the most important KPIs and actions.

Machine coding round tip: Don't spend the entire time perfecting chart visuals. Prioritize layout, reusable components, data flow, interactions, responsive behavior and correct UI states.
FOLLOW-UPS

Likely interviewer follow-up questions

How would you make the dashboard responsive?

Use CSS Grid/Flexbox, responsive breakpoints, collapsible navigation and horizontally scrollable tables where needed.

How would you handle API loading and errors?

Model request state explicitly and render loading, success, empty and error UI. For independent widgets, consider isolating failures.

How would you add filters?

Keep filter values in state and either derive filtered data locally or request new data from the server based on the filter.

How would you optimize a dashboard with many charts?

Lazy-load noncritical widgets, avoid unnecessary calculations, memoize only expensive work, and consider chart virtualization/aggregation.

How would you handle a large table?

Use pagination or virtualization, stable keys, server-side filtering/sorting when appropriate, and avoid rendering all rows at once.

Why use reusable KPI cards?

They enforce consistent structure and styling and let new metrics be added through data rather than copied markup.

Where should API calls live?

Usually at a container/page or data-fetching layer, keeping presentation components focused on rendering and user interaction.

How would you test the dashboard?

Test widget rendering, navigation/filter interactions, loading/error/empty states, and important data transformations separately.

How would you make charts accessible?

Provide meaningful labels, summaries or tabular alternatives and ensure keyboard users can access relevant controls.

What if different widgets use different APIs?

Give each widget an isolated loading/error boundary where appropriate, or aggregate requests in a data layer while keeping the UI independent.
