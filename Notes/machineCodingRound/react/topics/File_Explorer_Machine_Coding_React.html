1. What is a File Explorer?

A File Explorer is a UI that displays files and folders in a hierarchical tree structure. Folders can contain files and other folders.

Simple definition: A File Explorer is a nested tree UI that lets users navigate folders and files by expanding and collapsing folders.

Typical features

  • Show folders and files.
  • Expand a folder to see its children.
  • Collapse a folder to hide its children.
  • Support unlimited nesting.
  • Use different icons for folders and files.
  • Keep expanded/collapsed state independently for each folder.
Interview keyword: When you hear “File Explorer”, think tree data + recursion + expand/collapse state.

2. What problem does it solve?

A normal list works well when every item is at the same level. But files are naturally hierarchical: a folder can contain another folder, which can contain another folder.

Without hierarchy

Everything becomes one long flat list and relationships are difficult to understand.

With tree structure

Users can understand parent-child relationships immediately.

With expand/collapse

Users see only the level they currently need.

This pattern is used in IDE sidebars, cloud storage, operating-system file managers, documentation navigation, category trees, and organization charts.

3. What are the requirements?

Minimum machine-coding requirements

  1. Render folders and files.
  2. Display nested children.
  3. Click a folder to expand/collapse it.
  4. Allow multiple folders to remain open.
  5. Support nested folders recursively.
  6. Use a unique ID for every node.

Good follow-up features

  • Add file/folder.
  • Delete file/folder.
  • Rename.
  • Search.
  • Context menu.
  • Keyboard navigation.
  • Drag and drop.
  • Lazy-load children from an API.
Machine coding tip: First finish the core tree + expand/collapse behavior. Then add optional features only if time remains.

5. Why do we use recursion?

The data itself is recursive: a folder can contain a folder, and that folder can contain another folder. Therefore a recursive component is a natural solution.

📁 src
  ├── 📁 components
  │    └── 📄 Button.jsx
  └── 📄 App.jsx
📄 package.json

Recursive idea

function TreeNode({ node }) {
  // Render current node

  // If it is a folder and is open:
  // render children by calling TreeNode again

  return (
    <div>
      ...
      {node.children?.map(child => (
        <TreeNode key={child.id} node={child} />
      ))}
    </div>
  );
}
Easy way to remember: “Render myself, then render my children using the same component.”

6. How should state work?

We need to remember which folders are currently expanded. A Set of folder IDs is a clean approach. 

const [expanded, setExpanded] = useState(new Set());

Toggle logic

const toggleFolder = (id) => {
  setExpanded(prev => {
    const next = new Set(prev);

    if (next.has(id)) {
      next.delete(id);
    } else {
      next.add(id);
    }

    return next;
  });
};

Why create a new Set?

React state should be updated immutably. We create a new Set instead of directly mutating the previous one.

Bad: prev.add(id); return prev;
This mutates the existing Set and returns the same reference.
Good: const next = new Set(prev); next.add(id); return next;

Implementation rules

  1. If node is a file, show the file and stop.
  2. If node is a folder, show a clickable folder row.
  3. When clicked, toggle its ID in expanded.
  4. If expanded, map over children.
  5. For each child, render TreeNode again.
Core condition:
node.type === "folder" && expanded.has(node.id) determines whether children should be visible.

function TreeNode({ node, expanded, toggleFolder }) {
  const isFolder = node.type === "folder";
  const isOpen = expanded.has(node.id);

  const handleClick = () => {
    if (isFolder) {
      toggleFolder(node.id);
    }
  };

  return (
    <div className="tree-node">
      <div
        className={`tree-row ${isFolder ? "folder-row" : "file-row"}`}
        onClick={handleClick}
        role={isFolder ? "button" : undefined}
        tabIndex={isFolder ? 0 : undefined}
        onKeyDown={(e) => {
          if (isFolder && (e.key === "Enter" || e.key === " ")) {
            e.preventDefault();
            toggleFolder(node.id);
          }
        }}
      >
        <span className="icon">
          {isFolder ? (isOpen ? "📂" : "📁") : "📄"}
        </span>

        <span>{node.name}</span>
      </div>

      {isFolder && isOpen && node.children?.length > 0 && (
        <div className="children">
          {node.children.map((child) => (
            <TreeNode
              key={child.id}
              node={child}
              expanded={expanded}
              toggleFolder={toggleFolder}
            />
          ))}
        </div>
      )}
    </div>
  );
}

export default function FileExplorer() {
  const [expanded, setExpanded] = useState(new Set());

  const toggleFolder = (id) => {
    setExpanded((prev) => {
      const next = new Set(prev);

      if (next.has(id)) {
        next.delete(id);
      } else {
        next.add(id);
      }

      return next;
    });
  };

  return (
    <div className="file-explorer">
      <h2>File Explorer</h2>

      {fileData.map((node) => (
        <TreeNode
          key={node.id}
          node={node}
          expanded={expanded}
          toggleFolder={toggleFolder}
        />
      ))}
    </div>
  );
}

11. How to explain it to interviewer in 1 minute

“I implemented the File Explorer using a recursive tree structure. Each node contains an ID, name, type, and optional children. I maintain a Set of expanded folder IDs in React state. When a folder is clicked, I add or remove its ID from that Set, which controls whether its children are displayed. For rendering, I created a reusable TreeNode component. It renders the current node and, if the node is an open folder, recursively renders its children using the same component. This approach naturally supports any nesting depth and keeps each folder's expand/collapse state independent.”

Keywords to say: nested data, recursive component, Set, immutable state update, expand/collapse, independent state, reusable component.

Minute 2 — Data structure

13. How I have implemented this — interviewer explanation

While coding, explain in this order

  1. “I will start with the data.”
    Create a nested array containing folder and file nodes.
  2. “Now I need expanded state.”
    Use a Set because I only need to know whether a folder ID is open.
  3. “Now I will create the recursive TreeNode.”
    It receives the current node and state/update function.
  4. “A file has no expandable behavior.”
    Render the file row only.
  5. “A folder is clickable.”
    Toggle its ID in the Set.
  6. “If it is open, I recursively render children.”
    Map the children and render TreeNode again.
  7. “Finally I will add edge-case handling and accessibility.”
Best interview habit: Don't immediately type the complete solution silently. Explain the data structure, state design, and recursion first, then code each part.

14. Common developer mistakes

1. Using one boolean for all folders
const [isOpen, setIsOpen] = useState(false) cannot independently track every folder.
Fix: Store expanded folder IDs in a Set.
2. Forgetting recursion
Rendering only the first level fails when folders contain folders.
Fix: Render children with the same TreeNode component.
3. Mutating the Set directly
expanded.add(id) changes the existing state object.
Fix: Create new Set(prev) first.
4. Using name as the React key
Two folders can have the same name.
Fix: Give every node a stable unique ID.
5. Assuming every node has children
Files normally do not have a children array.
Fix: Check type and/or use optional chaining.
6. Clicking files changes folder state
Files should not trigger expand/collapse.
Fix: Toggle only when node.type === "folder".
7. Forgetting keyboard accessibility
A clickable folder implemented as a plain div may not be keyboard friendly.
Fix: Add appropriate keyboard behavior or use an accessible button.
8. Overengineering too early
Starting with drag/drop, API calls, context menus, and virtualization can waste machine-round time.
Fix: Finish the core tree first, then enhance it.

15. Edge cases / test cases

Test case Expected behavior
Folder has no children Show folder without crashing.
File is clicked No expand/collapse action.
Two folders have same name They still work independently because IDs are unique.
Open parent and child Both can remain open.
Close parent Its visible subtree disappears.
Deep nesting Recursive component continues rendering.
Empty data array Explorer should render an empty state rather than crash.
Keyboard Enter/Space on folder Folder toggles open/closed.

16. Interviewer follow-up questions

Q1. How would you add a new file?

I would update the tree immutably and insert the new node into the target folder's children array.

Q2. How would you implement delete?

I would recursively traverse the tree, remove the matching node, and return a new tree rather than mutating the existing one.

Q3. How would you implement rename?

Recursively find the node by ID and return a new node with the updated name.

Q4. How would you add search?

Filter or recursively traverse the tree and keep matching nodes. In a real UI, I would also keep ancestor folders visible so the matching file's location remains understandable.

Q5. What if there are thousands of files?

I would consider lazy loading, virtualization, memoization, and avoiding unnecessary re-renders. For remote data, children can be fetched only when a folder is opened.

Q6. Why not flatten the data?

A flat normalized structure can be better for large applications and frequent updates, but the nested structure is simpler for a machine-coding problem focused on recursive rendering.

Q7. What is the time complexity?

Initial rendering is proportional to the number of visible nodes, approximately O(V). Toggling a folder is effectively O(1) for the Set operation, excluding the React rendering work caused by the state update.
