What?

What is a Password Strength Indicator?

A Password Strength Indicator is a UI component that evaluates a user's password against predefined rules and gives immediate feedback such as Weak, Medium, or Strong.

Simple example: As the user types MyPassword123!, the UI checks length, uppercase letters, lowercase letters, numbers, and special characters, then updates the strength indicator.
Typical UI:
Strong
Why?

What problem does it solve?

1. Immediate feedback
The user knows whether the password satisfies the expected rules while typing.
2. Better UX
Users do not have to submit the form repeatedly just to discover password requirements.
3. Encourages stronger passwords
Visible rules make it easier for users to create passwords that meet the application's requirements.
Important
A strength indicator is a UX aid, not a complete security system. Server-side security controls are still required.
Machine Coding Requirement

What should I build?

  1. Password input field.
  2. Calculate strength whenever the password changes.
  3. Display a visual strength bar.
  4. Display a label such as Weak, Medium, or Strong.
  5. Show password requirements/checklist.
  6. Handle the empty-password state cleanly.
  7. Keep the logic reusable and easy to extend.
Machine-round goal: Demonstrate state management, derived state, event handling, conditional rendering, clean validation logic, and good UX.
Logic

Example Strength Rules

For an interview implementation, you can define five simple rules:

1At least 8 characters
2Contains a lowercase letter
3Contains an uppercase letter
4Contains a number
5Contains a special character
Example scoring:
0 rules → Empty/Weak
1–2 rules → Weak
3 rules → Medium
4–5 rules → Strong

The exact scoring model is a product decision. In an interview, clearly state your assumptions before coding.

How?

How does it work?

The password is stored in React state. Every time it changes, the component checks the rules and derives a strength score.

Implementation

How I have implemented it — interviewer explanation

1. State: “I keep the password in a controlled React state.”

2. Rules: “I define five requirements: length, lowercase, uppercase, number, and special character.”

3. Derived calculation: “I calculate the score from the current password rather than storing duplicated strength state.”

4. UI mapping: “The score is mapped to a label and progress percentage.”

5. Feedback: “I show the user which requirements are already satisfied.”

6. Extensibility: “Because the rules are isolated, I can add or remove requirements without rewriting the entire component.”

Full Code

React Password Strength Indicator

This implementation uses one password state and derives the rules and strength from it.

import { useMemo, useState } from "react";

function PasswordStrength() {
  const [password, setPassword] = useState("");

  const rules = useMemo(() => {
    return [
      {
        label: "At least 8 characters",
        valid: password.length >= 8
      },
      {
        label: "Contains lowercase letter",
        valid: /[a-z]/.test(password)
      },
      {
        label: "Contains uppercase letter",
        valid: /[A-Z]/.test(password)
      },
      {
        label: "Contains a number",
        valid: /\d/.test(password)
      },
      {
        label: "Contains special character",
        valid: /[^A-Za-z0-9]/.test(password)
      }
    ];
  }, [password]);

  const score = rules.filter((rule) => rule.valid).length;

  const getStrength = () => {
    if (!password) {
      return {
        label: "Enter a password",
        percentage: 0
      };
    }

    if (score <= 2) {
      return {
        label: "Weak",
        percentage: 40
      };
    }

    if (score === 3) {
      return {
        label: "Medium",
        percentage: 70
      };
    }

    return {
      label: "Strong",
      percentage: 100
    };
  };

  const strength = getStrength();

  return (
    <div className="password-container">
      <h2>Password Strength</h2>

      <label htmlFor="password">Password</label>

      <input
        id="password"
        type="password"
        value={password}
        onChange={(e) => setPassword(e.target.value)}
        placeholder="Enter password"
      />

      <div className="progress">
        <div
          className="progress-bar"
          style={{ width: `${strength.percentage}%` }}
        />
      </div>

      <p>
        Strength: <strong>{strength.label}</strong>
      </p>

      <ul>
        {rules.map((rule) => (
          <li key={rule.label}>
            {rule.valid ? "✓" : "○"} {rule.label}
          </li>
        ))}
      </ul>
    </div>
  );
}

export default PasswordStrength;
Core logic to remember: password → check rules → count valid rules → map score → render UI
Common Developer Mistakes

Mistakes to avoid in a machine coding round

1. Storing too much duplicated state
Avoid separate state such as isStrong, score, and label when they can be derived from the password.
2. Updating strength only on submit
A strength indicator should normally provide feedback while the user types.
3. Hard-coding many nested conditions
Keep rules separate so the logic is readable and easy to extend.
4. Treating length alone as password strength
Length is important, but the chosen requirements should reflect the application's security policy.
5. Calling the UI label a security guarantee
“Strong” in a simple indicator does not guarantee that a password is secure against every attack.
6. Weak accessibility
Always provide a proper label and make important status information understandable to assistive technologies.
7. Logging passwords
Never add console.log(password) in production code or expose passwords unnecessarily.
8. Ignoring server-side validation
Client-side checks can be bypassed. The server must enforce the actual security rules.
Interview

How to explain in 1 minute

“I implemented a password strength indicator as a controlled React component. I store the password in state and evaluate it against a set of rules such as minimum length, lowercase, uppercase, number, and special character. Every time the password changes, I calculate how many rules are satisfied and map that score to a strength level like Weak, Medium, or Strong. I then display the result using a progress bar and a checklist so the user can immediately understand what is missing. I keep the strength value derived from the password instead of storing duplicate state. In production, I would also keep the actual security validation on the backend and avoid treating the UI strength label as a security guarantee.”

Interview

How to explain in 5 minutes

  1. Requirement: “The component should give real-time feedback about password quality.”
  2. State: “I use one controlled password state.”
  3. Rules: “I define five independent checks for length, lowercase, uppercase, number, and special character.”
  4. Scoring: “I count the number of rules that return true.”
  5. Mapping: “I convert the score into a user-friendly label and progress percentage.”
  6. Rendering: “The UI renders the progress bar, strength label, and individual requirement status.”
  7. Maintainability: “Rules are isolated, so adding another requirement does not require rewriting the component.”
  8. Performance: “For a small form, direct calculation is enough; for more expensive validation, I can memoize derived calculations.”
  9. Security: “The frontend is only for feedback. The backend must still enforce password policy and security controls.”
Strong closing line: “The main design decision is to keep the password as the source of truth and derive the score, label, and UI state from it, avoiding inconsistent duplicate state.”
Edge Cases

What can the interviewer test?

  • Empty password.
  • Password containing only spaces.
  • Very short password such as aA1!.
  • Long password that satisfies all rules.
  • Password containing Unicode characters.
  • User deletes the password after reaching Strong.
  • Show/hide password toggle.
  • Confirm password field integration.
  • API submission after the password passes the client-side rules.
Advanced Follow-up

How can you improve it?

  • Add a show/hide password button.
  • Use a reusable getPasswordStrength(password) utility.
  • Use a strength meter with accessible status text.
  • Add confirmation-password validation.
  • Disable submit until required password rules are satisfied.
  • Integrate a server-side password policy.
  • For production security decisions, use established password-strength guidance and avoid relying on simplistic scoring alone.
