1. What is Optimistic UI?

Definition: Optimistic UI is a UI pattern where the application updates the screen immediately, assuming that the server request will succeed. The API request runs in the background.

Layman example: Imagine pressing a “Like” button. Instead of waiting for the server to say “Like successful,” the heart changes immediately. The application then sends the request to the server. If the server fails, the UI can roll the change back.

2. What Problem Does Optimistic UI Resolve?

Without Optimistic UI, the user may have to wait for a network request before seeing the result of an action.

User clicks Like → API request → wait → UI updatesUser clicks Like → UI updates → API request runs

Problem solved: It reduces the perceived waiting time for actions that are expected to succeed most of the time.
3. Why Do We Use Optimistic UI?
⚡ Faster Feeling

The interface responds immediately to the user's action.

😊 Better UX

The application feels more responsive on slower networks.

❤️ Likes

Like/unlike actions are common optimistic UI candidates.

🛒 Cart

A cart quantity can update immediately while the server is being updated.

Good use case: Actions where failure is relatively uncommon and the UI can safely undo or reconcile the temporary change.
4. How Does Optimistic UI Work?
  1. User performs an action.
  2. React immediately updates the local UI state.
  3. React sends the API request in the background.
  4. If the API succeeds, keep the optimistic state.
  5. If the API fails, restore the previous state or refetch the authoritative server state.
Core idea: The UI does not wait for the API before showing the expected result.

7. Full React Code
LikeButton.jsx
import { useState } from "react";

// Fake API for machine-coding demonstration
const likePostApi = () => {
  return new Promise((resolve, reject) => {
    setTimeout(() => {
      // Simulate 80% success and 20% failure
      if (Math.random() < 0.8) {
        resolve({ success: true });
      } else {
        reject(new Error("Server failed to update like"));
      }
    }, 1200);
  });
};

function LikeButton() {
  const [liked, setLiked] = useState(false);
  const [likeCount, setLikeCount] = useState(10);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState("");

  const handleLike = async () => {
    // Prevent duplicate requests while one is running
    if (loading) return;

    // Save previous state for rollback
    const previousLiked = liked;
    const previousLikeCount = likeCount;

    // Optimistic update
    const nextLiked = !liked;

    setLiked(nextLiked);
    setLikeCount((count) =>
      nextLiked ? count + 1 : count - 1
    );

    setLoading(true);
    setError("");

    try {
      await likePostApi();

      // API succeeded.
      // Keep the optimistic state.
    } catch (err) {
      // API failed: rollback to previous state
      setLiked(previousLiked);
      setLikeCount(previousLikeCount);
      setError("Could not update like. Please try again.");
    } finally {
      setLoading(false);
    }
  };

  return (
    <div>
      <button
        onClick={handleLike}
        disabled={loading}
        style={{
          fontSize: "32px",
          border: "none",
          background: "transparent",
          cursor: loading ? "not-allowed" : "pointer"
        }}
        aria-label={liked ? "Unlike post" : "Like post"}
      >
        {liked ? "♥" : "♡"}
      </button>

      <span> {likeCount} likes</span>

      {loading && (
        <p>Saving...</p>
      )}

      {error && (
        <p style={{ color: "red" }}>
          {error}
        </p>
      )}
    </div>
  );
}

export default LikeButton;
Important pieces: previous state optimistic update API request rollback loading error handling
8. API Failure & Rollback

Rollback is one of the most important parts of a basic Optimistic UI implementation.

Before click
liked = false
count = 10
Optimistic update
liked = true
count = 11
API fails
restore false / 10
Why rollback? The optimistic state was only an assumption. The server is the source of truth, so the UI must be corrected when the operation fails.
Two common recovery strategies
  • Rollback: restore the exact previous local state.
  • Refetch: request the latest server state and replace local state with the authoritative result.
Interview tip: Mention that refetching can be useful when several pieces of data may have changed and calculating a perfect rollback locally is difficult.
9. Common Developer Mistakes
1. Updating UI but not handling API failure
An optimistic update without rollback or reconciliation can leave the UI inconsistent with the server.
2. Not saving the previous state
If rollback is required, keep the previous values before applying the optimistic change.
3. Allowing duplicate clicks
Multiple requests can create race conditions or duplicate operations. Disable the action or otherwise manage concurrent requests when appropriate.
4. Assuming every operation should be optimistic
Actions with high consequences or complicated server-side rules may need confirmation before updating the UI.
5. Ignoring race conditions
When multiple requests can be in flight, an older response can arrive after a newer response. Design the state update strategy accordingly.
6. Treating frontend validation as security
The backend remains authoritative. Client-side behavior should not be trusted for authorization or data integrity.
7. Forgetting loading/error feedback
The UI should communicate that the server operation is still being synchronized or that the optimistic update was rolled back.
10. How I Would Explain My Implementation to the Interviewer
Interview explanation:

“I implemented Optimistic UI for a Like button. When the user clicks the button, I first capture the previous state. Then I immediately update the local React state so the UI responds without waiting for the network. At the same time, I send the API request. If the request succeeds, I keep the optimistic state. If it fails, I restore the previous state and show an error. I also prevent duplicate requests while the current request is running. This makes the interface feel faster while still keeping the UI consistent with the server.”

Explain the code in this order
  1. State: “I have liked, likeCount, loading and error state.”
  2. Previous state: “I save the old values because I may need to rollback.”
  3. Optimistic update: “I update the UI immediately.”
  4. API: “I send the request after updating the UI.”
  5. Success: “If the API succeeds, I keep the state.”
  6. Failure: “If it fails, I restore the previous state.”
  7. UX: “I disable duplicate clicks and show loading/error feedback.”
Strong interview line: “Optimistic UI is not simply updating the UI before the API. The important part is having a recovery strategy when the server rejects the optimistic assumption.”
