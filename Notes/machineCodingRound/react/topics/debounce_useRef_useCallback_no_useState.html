Debounce with useRef + useCallback

Machine Coding Round — React implementation without useState

Goal: Keep the input value and timeout in refs, use useCallback for stable functions, and avoid a React state update for every keystroke.

1. What are we building?

We want a debounced search/input handler:

User types:  r → re → rea → reac → react

Do NOT run:
API(r)
API(re)
API(rea)
API(reac)
API(react)

Instead:
wait until typing stops
        ↓
API(react)

The debounce algorithm remains the same: clear the previous timer → create a new timer → execute after the user pauses.

React-specific change: We will not use useState for the input value or timer. The DOM input is accessed with useRef.

2. Why only useRef + useCallback?

useRef — store values without re-rendering

const inputRef = useRef(null);
const timerRef = useRef(null);
  • inputRef points to the DOM input.
  • timerRef stores the active timeout ID.
  • Changing .current does not trigger a render.

useCallback — keep function reference stable

const debounceSearch = useCallback(
  () => { ... },
  []
);
  • Memoizes the function reference.
  • It does not create the debounce delay.
  • The delay still comes from setTimeout.
Remember: useRef = persistent mutable value. useCallback = memoized function. setTimeout = delay. Debounce = the behavior created by combining clearTimeout + setTimeout.

3. Why avoid useState here?

With useState 
const [query, setQuery] = useState("");

onChange:
setQuery(value);

→ state changes
→ component renders again
With useRef 
const inputRef = useRef(null);

onChange:
inputRef.current.value

→ no state update
→ no render caused by the input value
This is appropriate when the input value does not need to be used to render React UI. If the UI must react to the value, state may still be the correct choice.

Simple example: Think of an elevator door. Every time someone enters, the closing countdown starts again. Only after nobody enters for the waiting period does the door close. Debounce works similarly.

5. Implementation Step-by-Step — No useState

Step 1 — Create the refs

const inputRef = useRef(null);
const timerRef = useRef(null);

inputRef will point to the input element. timerRef will remember the current timeout.

Step 2 — Create the actual function

const searchAPI = useCallback(async (value) => {
  console.log("API call:", value);

  const response = await fetch(
    `/api/search?q=${encodeURIComponent(value)}`
  );

  const data = await response.json();

  console.log(data);
}, []);

Step 3 — Create debounce with useCallback + useRef

const debounceSearch = useCallback(() => {

  // Read latest value directly from DOM
  const value = inputRef.current.value;

  // Cancel previous timer
  clearTimeout(timerRef.current);

  // Schedule latest call
  timerRef.current = setTimeout(() => {
    searchAPI(value);
  }, 500);

}, [searchAPI]);

Step 4 — Connect ref to input

<input
  ref={inputRef}
  onChange={debounceSearch}
  placeholder="Search..."
/>

Step 5 — Cleanup

useEffect(() => {
  return () => {
    clearTimeout(timerRef.current);
  };
}, []);

Complete Example

import {
  useCallback,
  useEffect,
  useRef
} from "react";

function SearchBox() {
  const inputRef = useRef(null);
  const timerRef = useRef(null);

  const searchAPI = useCallback(async (value) => {
    if (!value.trim()) return;

    console.log("API call:", value);

    try {
      const response = await fetch(
        `/api/search?q=${encodeURIComponent(value)}`
      );

      if (!response.ok) {
        throw new Error("API request failed");
      }

      const data = await response.json();
      console.log("Result:", data);

    } catch (error) {
      console.error(error);
    }
  }, []);

  const debounceSearch = useCallback(() => {
    const value = inputRef.current.value;

    clearTimeout(timerRef.current);

    timerRef.current = setTimeout(() => {
      searchAPI(value);
    }, 500);

  }, [searchAPI]);

  useEffect(() => {
    return () => {
      clearTimeout(timerRef.current);
    };
  }, []);

  return (
    <input
      ref={inputRef}
      onChange={debounceSearch}
      placeholder="Search..."
    />
  );
}

export default SearchBox;
Notice: There is no useState in this implementation. The input value comes from inputRef.current.value, and the timer comes from timerRef.current.

6. Interview — Two-Side Explanation

LEFT SIDE — Question → Answer → How I Explain

Q1. How did you implement debounce?

Answer: I store the timer ID in a ref and create the debounce handler using useCallback. On every input event, I clear the previous timeout and start a new timeout.

How I explain: “The debounce algorithm is clear previous timer, create a new timer, and execute after the user stops typing. I use a ref because the timer must survive renders without causing a render.”

Q2. Why don't you use state for the input?

Answer: In this specific implementation, the input value is not required to drive React rendering.

How I explain: “I use an uncontrolled input and access its latest value through inputRef.current.value. This avoids a state update and React render for every keystroke.”

Q3. Why useCallback?

Answer: To memoize the callback and keep its reference stable when dependencies do not change.

How I explain: “useCallback is not debounce. setTimeout provides the waiting period. useCallback keeps the function reference stable.”

Q4. Why useRef for timerId?

Answer: The timer ID needs to persist but does not need to trigger UI updates.

How I explain: “I need the same timer reference on the next keystroke so I can call clearTimeout. useRef gives me that persistent mutable value without a re-render.”

Q5. What happens when the user types quickly?

Answer: Each new event cancels the previous timer and schedules another one.

How I explain: “If the user types react quickly, only the final timer survives long enough to execute. Therefore the API is called after the pause with the latest value.”

7. Common Developer Mistakes

1. Saying useCallback is debounce
Wrong. useCallback memoizes a function. setTimeout + clearTimeout create the debounce behavior.
2. Forgetting clearTimeout
If you don't cancel the previous timer, multiple delayed calls can execute.
3. Using useState for timerId
The timer ID is not UI state. useRef is a better fit for this mutable value.
4. Assuming useRef automatically means better performance
Do not blindly replace state with refs. If the value must update the UI, state is usually appropriate.
5. Reading the ref too late
Read the current input value when scheduling the debounce. Pass that value into the timeout callback.
6. Forgetting cleanup
Cancel the pending timer when the component unmounts.
7. Ignoring API race conditions
Debounce controls when a request starts. It does not guarantee that responses arrive in order. For real applications, consider AbortController or request/version checks.
8. Forgetting empty input
Avoid unnecessary API requests for empty or whitespace-only values.
9. Overusing useCallback
useCallback is not a performance magic switch. Use it when stable function identity is useful and explain the reason in the interview.

8. Important Trade-off

No useState means React does not know about input changes.

That is intentional here. This pattern is useful when the input is mainly an imperative source for an operation such as searching, logging, or triggering an API call.

But if you need to show something like:

then React needs to render based on the value, and useState may be the better choice.

Interview maturity: Don't say “useRef is always better because it avoids renders.” Say “I chose useRef here because this value does not need to participate in rendering.”

9. Final Interview Checklist

  • ☑ Explain debounce before explaining hooks.
  • ☑ Explain why the timer is stored in useRef.
  • ☑ Explain that useCallback does not create debounce.
  • ☑ Show clearTimeout before setTimeout.
  • ☑ Show cleanup on unmount.
  • ☑ Explain why no useState is used.
  • ☑ Mention that refs are not suitable when the value must drive UI rendering.
  • ☑ Be ready to discuss API cancellation and race conditions.
