What?

What is a Toast Notification?

A Toast Notification is a small temporary message displayed on the screen to give the user feedback about an action without interrupting the current page.

Examples include:

  • “Profile updated successfully.”
  • “Failed to upload file.”
  • “Item added to cart.”
  • “Your session will expire soon.”
Success
Profile updated successfully.
Error
Unable to save changes.
Interview definition: “A Toast Notification is a non-blocking feedback component that appears temporarily, informs the user about an action, and usually disappears automatically or can be dismissed manually.”
Why?

What problem does it solve?

Immediate feedback

Users immediately know whether an action succeeded or failed.

Non-blocking UX

Unlike alerts or modal dialogs, a toast does not stop the user's workflow.

Reusable notifications

One toast system can be used by forms, API calls, uploads, payments, and other features.

Consistent UI

All success, error, warning, and information messages can follow one design.

Requirements

What should I implement?

  1. Create a reusable toast component.
  2. Support toast types such as success, error, warning, and info.
  3. Allow any component to trigger a toast.
  4. Automatically remove a toast after a configurable duration.
  5. Allow manual dismissal.
  6. Support multiple toasts at the same time.
  7. Give every toast a unique ID.
  8. Position the toast container consistently.
  9. Clean up timers when a toast is removed or the component unmounts.
Machine coding strategy: First build one toast → add state array → add add/remove functions → add auto-dismiss → add types → expose a reusable useToast() API.
How?

How does it work?

The central idea is to keep a list of active toast objects in state.

const [toasts, setToasts] = useState([]);

Example:

[
  {
    id: 101,
    message: "Profile updated",
    type: "success",
    duration: 3000
  },
  {
    id: 102,
    message: "Network error",
    type: "error",
    duration: 5000
  }
]

When a component calls showToast():

  1. Create a unique ID.
  2. Create a toast object.
  3. Add it to the state array.
  4. React renders the new toast.
  5. Start a timer for automatic removal.
  6. Remove the toast when the timer expires or the user clicks close.

Full Code

React Toast Notification — Interview Version

This implementation uses Context so any component inside the provider can trigger notifications.

1. ToastContext.jsx
import {
  createContext,
  useCallback,
  useContext,
  useRef,
  useState
} from "react";

const ToastContext = createContext(null);

export function ToastProvider({ children }) {
  const [toasts, setToasts] = useState([]);
  const timers = useRef(new Map());

  const removeToast = useCallback((id) => {
    setToasts((prev) =>
      prev.filter((toast) => toast.id !== id)
    );

    const timer = timers.current.get(id);

    if (timer) {
      clearTimeout(timer);
      timers.current.delete(id);
    }
  }, []);

  const showToast = useCallback(
    ({
      message,
      type = "info",
      duration = 3000
    }) => {
      const id = Date.now() + Math.random();

      const newToast = {
        id,
        message,
        type
      };

      setToasts((prev) => [...prev, newToast]);

      if (duration > 0) {
        const timer = setTimeout(() => {
          removeToast(id);
        }, duration);

        timers.current.set(id, timer);
      }

      return id;
    },
    [removeToast]
  );

  // Cleanup all timers when provider unmounts.
  const clearAll = useCallback(() => {
    timers.current.forEach((timer) => {
      clearTimeout(timer);
    });

    timers.current.clear();
    setToasts([]);
  }, []);

  return (
    <ToastContext.Provider
      value={{
        toasts,
        showToast,
        removeToast,
        clearAll
      }}
    >
      {children}

      <ToastContainer
        toasts={toasts}
        onClose={removeToast}
      />
    </ToastContext.Provider>
  );
}

export function useToast() {
  const context = useContext(ToastContext);

  if (!context) {
    throw new Error(
      "useToast must be used inside ToastProvider"
    );
  }

  return context;
}

function ToastContainer({ toasts, onClose }) {
  return (
    <div
      className="toast-container"
      aria-live="polite"
      aria-atomic="true"
    >
      {toasts.map((toast) => (
        <Toast
          key={toast.id}
          toast={toast}
          onClose={onClose}
        />
      ))}
    </div>
  );
}

function Toast({ toast, onClose }) {
  const iconMap = {
    success: "✓",
    error: "✕",
    warning: "!",
    info: "i"
  };

  return (
    <div
      className={`toast toast-${toast.type}`}
      role="status"
    >
      <span className="toast-icon">
        {iconMap[toast.type]}
      </span>

      <span className="toast-message">
        {toast.message}
      </span>

      <button
        type="button"
        className="toast-close"
        aria-label="Close notification"
        onClick={() => onClose(toast.id)}
      >
        ×
      </button>
    </div>
  );
}

3. Any component can trigger a toast
import { useToast } from "./ToastContext";

function SaveButton() {
  const { showToast } = useToast();

  const handleSave = async () => {
    try {
      // await saveData();

      showToast({
        message: "Profile saved successfully!",
        type: "success",
        duration: 3000
      });
    } catch (error) {
      showToast({
        message: "Unable to save profile.",
        type: "error",
        duration: 5000
      });
    }
  };

  return (
    <button onClick={handleSave}>
      Save
    </button>
  );
}

export default SaveButton;

Interview Answer

How to explain in 1 minute

“I built a reusable Toast Notification system using React Context. The provider maintains an array of active toast objects, where each toast has a unique ID, message, type, and duration. Any child component can call showToast() through a custom useToast hook. When a toast is added, React renders it in a fixed toast container and a timer automatically removes it after the configured duration. I also provide a close button for manual dismissal. I keep timer references in a ref so I can clear individual timers and clean up all timers when the provider unmounts. Context makes the notification system available across the application without prop drilling.”
Interview Answer

How to explain in 5 minutes

  1. Requirement: “We need a non-blocking notification system that can display temporary messages.”
  2. State design: “I store all active notifications in an array because multiple toasts may be visible simultaneously.”
  3. Toast object: “Each toast has a unique ID, message, type, and optional duration.”
  4. Adding: “The showToast function creates a toast object and appends it to the array.”
  5. Rendering: “ToastContainer maps over the array and renders each toast using its ID as the React key.”
  6. Auto-dismiss: “After the duration, setTimeout calls removeToast(id).”
  7. Manual dismiss: “The close button also calls removeToast(id).”
  8. Timer management: “I store timeout IDs in a ref-based Map, allowing me to clear a specific timer when a toast is manually removed.”
  9. Global access: “I use Context because toast notifications may be triggered from many parts of the application.”
  10. Cleanup: “When the provider unmounts, I clear every timer so there are no stale callbacks.”
  11. Accessibility: “I use an appropriate live region and meaningful button labels so notification updates can be communicated to assistive technology.”
Strong closing line: “The key design decision is separating notification management from individual pages. The provider owns the toast state and lifecycle, while consuming components only call a simple showToast API.”
Debugging

Common Developer Mistakes

Mistake Why it is a problem Better approach
Using one boolean like showToast Cannot represent multiple active notifications. Use an array of toast objects.
No unique ID You cannot reliably remove one toast. Generate a unique ID for every toast.
Using array index as React key Removing/reordering toasts can cause incorrect reconciliation. Use the toast's stable unique ID.
Creating timers without cleanup Stale timers can fire after a toast is already removed or after unmount. Store timer IDs and call clearTimeout.
Calling setTimeout directly during render Every render can create another timer. Create side effects in appropriate lifecycle logic.
Not clearing manual-close timer A closed toast may still have a timer waiting to run. Clear the corresponding timer when removing manually.
Prop drilling showToast Notification API becomes difficult to use across deep components. Use Context for app-wide toast behavior.
Mixing API logic into Toast component The UI becomes tightly coupled to backend behavior. Let the caller decide when to show success/error messages.
No maximum/overflow strategy Hundreds of notifications can fill the screen. Consider a maximum visible count or queue.
Missing accessibility Screen-reader users may miss important feedback. Use live-region semantics and accessible close controls.
Toast disappears too quickly Users may not have time to read the message. Use a sensible default duration and allow configuration.
Long message breaks layout Toast may overflow on smaller screens. Use responsive width and text wrapping.
Most common interview bug: Creating a new timer every render or forgetting to clear timers. Explain that timers are side effects and need controlled lifecycle management.

Implementation Explanation

How I implemented it — interviewer flow

1. I started with toast state

“I used an array because multiple toast notifications can exist at the same time.”

2. I created showToast

“The function creates a unique ID and adds a toast object to state.”

3. I created removeToast

“I remove only the toast whose ID matches the requested ID.”

4. I added auto-dismiss

“Every toast gets its own timeout based on its duration.”

5. I added Context

“I exposed showToast through a custom hook so any descendant can trigger notifications.”

6. I handled cleanup

“I clear timers when a toast is manually removed and when the provider unmounts.”

If the interviewer asks: “Why use an array?”
“Because users can trigger several notifications close together. An array lets each toast have its own identity, message, type, and lifecycle.”
If the interviewer asks: “Why use Context?”
“Toast notifications are cross-cutting UI. Context gives unrelated components access to the same notification API without passing props through every intermediate component.”
If the interviewer asks: “Why use useRef for timers?”
“Timer IDs are mutable values that do not need to trigger a React render. A ref is a suitable place to retain them between renders so I can clear the correct timer.”
If the interviewer asks: “How would you improve it for production?”
“I would add a maximum visible count, queue management, pause-on-hover if required, animation, controlled placement, deduplication for repeated messages, better live-region behavior, and tests for timer lifecycle.”
