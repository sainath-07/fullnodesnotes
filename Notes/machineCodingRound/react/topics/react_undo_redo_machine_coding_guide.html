1. What is Undo / Redo?

Definition: Undo/Redo is a state-history pattern that lets a user move backward to a previous state and forward again to a state that was undone.

Layman example: Imagine writing on paper and keeping a copy of every version after each change. If you make a mistake, you can go back to the previous copy. If you change your mind, you can move forward again.

In React, we can implement this by keeping a history of states and maintaining a pointer to the current state.

2. What Problem Does Undo / Redo Resolve?

Users often make changes and then realize they want to reverse one or more of those changes.

Text Editor

Drawing App

Form Builder
Restore earlier field changes.
Todo App

Design Tools
Move through editing history.
Data Editor
Reverse accidental changes.
Problem solved: Users can safely experiment with changes because they have a way to return to earlier states.
3. Why Do We Need Undo / Redo?
  • Improves user control over editing.
  • Allows accidental changes to be reversed.
  • Lets users experiment without fear of permanently losing earlier work.
  • Provides a familiar editing experience.
  • Can be implemented with a reusable state-history pattern.
Machine-coding expectation: The interviewer is usually looking for correct state management, a clear history model, proper handling of new changes after undo, and disabled states for unavailable actions.
4. How Does Undo / Redo Work?

The simplest mental model is Past → Present → Future.

  1. Past: States before the current state.
  2. Present: The state currently displayed.
  3. Future: States available through Redo.
When a new change happens

Add the new state after the current state and discard the old future states.

When Undo happens

Move one position backward in history.

When Redo happens

Move one position forward in history.

Important rule: If the user performs Undo and then makes a brand-new change, the old Redo history should normally be removed because that future branch no longer represents the current editing path.

6. Core Concept — History + Current Index

A clean implementation can keep two important pieces of information:

history

An array containing every state in the current editing path.

currentIndex

The position of the state currently displayed.

Example
history = ["Hello", "Hello World", "Hello World!"]
currentIndex = 2

Here, "Hello World!" is the present state. Undo changes the index to 1, while Redo can move it back to 2.

History Stack
Index 0 → "Hello"
Index 1 → "Hello World"
Index 2 → "Hello World!" ← Current

8. Full React Code

This implementation creates a small text editor with Undo, Redo and Reset.

UndoRedoEditor.jsx
import { useState } from "react";

function UndoRedoEditor() {
  const [history, setHistory] = useState([""]);
  const [currentIndex, setCurrentIndex] = useState(0);

  const currentValue = history[currentIndex];

  const handleChange = (event) => {
    const newValue = event.target.value;

    // Remove the future states after the current position.
    const newHistory = history.slice(0, currentIndex + 1);

    // Add the new state.
    newHistory.push(newValue);

    setHistory(newHistory);
    setCurrentIndex(newHistory.length - 1);
  };

  const handleUndo = () => {
    if (currentIndex === 0) {
      return;
    }

    setCurrentIndex((index) => index - 1);
  };

  const handleRedo = () => {
    if (currentIndex === history.length - 1) {
      return;
    }

    setCurrentIndex((index) => index + 1);
  };

  const handleReset = () => {
    setHistory([""]);
    setCurrentIndex(0);
  };

  return (
    <div>
      <h2>Undo / Redo Editor</h2>

      <textarea
        value={currentValue}
        onChange={handleChange}
        rows={8}
        placeholder="Start typing..."
      />

      <div>
        <button
          onClick={handleUndo}
          disabled={currentIndex === 0}
        >
          Undo
        </button>

        <button
          onClick={handleRedo}
          disabled={currentIndex === history.length - 1}
        >
          Redo
        </button>

        <button onClick={handleReset}>
          Reset
        </button>
      </div>

      <p>
        History size: {history.length}
      </p>

      <p>
        Current index: {currentIndex}
      </p>
    </div>
  );
}

export default UndoRedoEditor;
Key line for the interview: history.slice(0, currentIndex + 1) removes the future branch before adding a new change.
Why does that line matter?

9. Important Edge Cases
Undo at first state
Do nothing. Keep index at 0.
Redo at latest state
Do nothing. Keep index at the last position.
Undo → New Change
Clear future/Redo states.
Reset
Replace history with the initial state.

10. Common Developer Mistakes
1. Not clearing Redo history after a new change
After Undo, if the user creates a new state, the old future branch should normally be discarded.
2. Allowing Undo below the first state
Always prevent the index from becoming negative.
3. Allowing Redo beyond the latest state
Check whether the current index is already at the last history item.
4. Mutating the history array directly
React state should be updated immutably. Use operations such as slice() and create a new array.
5. Storing only the previous value
One previous value is not enough for multiple Undo operations. You need a history of states or commands.
6. Saving every keystroke without considering memory
A large editor can create a very large history. Consider debouncing, batching or a command/patch strategy when appropriate.
7. Using stale state incorrectly
When the next state depends on the previous state, use React's functional state update form where appropriate.
11. How I Would Explain My Implementation to the Interviewer
Interview explanation:

“I implemented Undo and Redo using a history array and a current index. Every valid change creates a new state and moves the current index to that state. Undo moves the index one step backward, while Redo moves it one step forward. An important case is when the user performs Undo and then makes a new change. In that case, I remove the old future states before adding the new state, because the previous Redo branch is no longer valid. I also disable Undo and Redo when movement is not possible.”

Explain the implementation in this order
  1. State: “I maintain history and currentIndex.”
  2. Current value: “The displayed value comes from history[currentIndex].”
  3. New change: “I remove future states and append the new state.”
  4. Undo: “I decrement the index if possible.”
  5. Redo: “I increment the index if possible.”
  6. Reset: “I replace the history with the initial state.”
  7. Edge cases: “I prevent moving outside the history boundaries.”
  8. Complexity: “Undo and Redo are O(1), while storing snapshots uses O(n) space.”
Strong interview line: “The core of Undo/Redo is not two buttons; it is maintaining a correct state history and a pointer to the current state.”
