Password Strength Indicator

A React component that evaluates a password against predefined rules and visually communicates its strength.

Goal: provide immediate feedback while the user types without storing unnecessary derived state.

Left Side — Questions
1. What is a Password Strength Indicator?

Technical definition: A Password Strength Indicator is a UI component that evaluates a user's password against a set of password rules and gives immediate visual feedback such as Weak, Medium, Strong, or Very Strong.

Layman example: When you create an account and type a password, the website may show a bar saying "Weak", "Medium", or "Strong". It helps you understand whether your password meets the expected security rules.
Password strength Strong
✓ At least 8 characters   ✓ Uppercase   ✓ Number   ✓ Special character

Core React concepts Controlled Input → Validation Rules → Derived Calculation → Conditional Rendering → Visual Feedback

2. What Problem Does It Solve?

It gives users real-time feedback about password quality while they type, so they can correct weak passwords before submitting a form.

  • Improves user feedback during signup.
  • Shows which password requirements are satisfied.
  • Reduces form submission errors.
  • Encourages users to create stronger passwords.
  • Demonstrates client-side validation in an interactive way.
Important security point: A strength indicator is primarily a client-side UX feature. It does not replace server-side password validation, secure password hashing, rate limiting, or other authentication security controls.
3. Requirements + Clarification Questions
Basic requirements
  1. Create a password input.
  2. Evaluate the password while the user types.
  3. Check predefined password rules.
  4. Show which rules are satisfied.
  5. Calculate an overall strength.
  6. Display a strength label.
  7. Display a visual progress bar.
  8. Update the UI immediately when the password changes.
Good clarification questions

  • How many strength levels are required?
  • Should an empty password show a strength label?
  • Should each rule be displayed separately?
  • Should common weak passwords be detected?
  • Should password visibility toggle be included?
  • Is this only a UI indicator or part of actual form validation?
Interview tip: Do not start coding before defining what "weak" and "strong" mean. Ask for the rules or clearly state your assumptions.
4. Password Rules — How Do I Calculate Strength?

A simple machine-coding implementation can use independent rules. For example:

Rule 1: Length ≥ 8
Rule 2: Contains uppercase letter
Rule 3: Contains lowercase letter
Rule 4: Contains a number
Rule 5: Contains special character
Optional: Not a commonly weak password
Simple scoring approach

Each satisfied rule contributes one point.

ScoreExample Result
0–1Weak
2–3Medium
4Strong
5Very Strong
Important: The exact scoring system is a product requirement, not a universal security standard. In an interview, state the rules and scoring clearly before implementing them.
5. What State Do I Need?

For the basic implementation, I only need to store the actual password input:

const [password, setPassword] = useState("");

The strength score, label, and rule results can be derived from password instead of being stored as separate state.

One source of truth:
password → calculate rules → calculate score → calculate label → render UI
Why avoid separate state?

If I store password, score, strength, and every rule result separately, I can create inconsistent state. For example, the password may change while the score still contains the previous value.

Interview point: "I keep the user input in state and derive the rest because strength is a deterministic result of the current password."

7. How I Have Implemented It — Interview Explanation
Step 1 — Controlled input

I use a controlled password input where the input value is stored in React state.

Step 2 — Define independent rules

I check length, uppercase, lowercase, number, and special character using simple regular expressions.

Step 3 — Calculate score

I convert the boolean rule results into a score by counting how many rules are satisfied.

Step 4 — Derive strength

Based on the score, I derive a label such as Weak, Medium, Strong, or Very Strong.

Step 5 — Render feedback

I display the label, progress bar, and individual rule status so the user knows exactly what is missing.

One-line implementation summary: "I built it as a controlled input, separated validation rules from the UI, derived a score and strength from the current password, and rendered real-time visual feedback."
8. Full React Code — Password Strength Indicator
import { useMemo, useState } from "react";

function PasswordStrength() {
  const [password, setPassword] = useState("");

  const result = useMemo(() => {
    const rules = {
      minLength: password.length >= 8,
      uppercase: /[A-Z]/.test(password),
      lowercase: /[a-z]/.test(password),
      number: /[0-9]/.test(password),
      special: /[^A-Za-z0-9]/.test(password),
    };

    const score = Object.values(rules).filter(Boolean).length;

    let label = "Weak";

    if (!password) {
      label = "Enter password";
    } else if (score <= 2) {
      label = "Weak";
    } else if (score === 3) {
      label = "Medium";
    } else if (score === 4) {
      label = "Strong";
    } else {
      label = "Very Strong";
    }

    return { rules, score, label };
  }, [password]);

  return (
    <div>
      <label>Password</label>

      <input
        type="password"
        value={password}
        onChange={(event) => {
          setPassword(event.target.value);
        }}
        placeholder="Enter password"
      />

      <h3>{result.label}</h3>

      <div>
        Strength: {result.score} / 5
      </div>

      <ul>
        <li>
          {result.rules.minLength ? "✓" : "✗"}
          At least 8 characters
        </li>

        <li>
          {result.rules.uppercase ? "✓" : "✗"}
          Uppercase letter
        </li>

        <li>
          {result.rules.lowercase ? "✓" : "✗"}
          Lowercase letter
        </li>

        <li>
          {result.rules.number ? "✓" : "✗"}
          Number
        </li>

        <li>
          {result.rules.special ? "✓" : "✗"}
          Special character
        </li>
      </ul>
    </div>
  );
}

export default PasswordStrength;

Why useMemo? It is optional for this small component. The calculation is cheap enough to perform directly during render. In an interview, useMemo can demonstrate memoization, but don't claim it is required. Prefer simple code unless the calculation is expensive or the requirements justify memoization.
9. How to Explain Password Strength Indicator in 1 Minute

Interview-ready answer:

"I implemented a Password Strength Indicator as a controlled React input. I store only the current password in state. Whenever the user types, I evaluate the password against independent rules such as minimum length, uppercase, lowercase, number, and special character. I count the satisfied rules to calculate a score, then derive a strength label such as Weak, Medium, Strong, or Very Strong. I display the result with a strength bar and individual rule indicators so the user gets immediate feedback. I intentionally derive the score and strength from the password instead of storing them separately because they are derived values. This component is for client-side user experience; actual password security and validation must also be handled on the server."

  2. Rules: length + character categories
  3. Score: count passed rules
  4. Strength: derive label from score
  5. UI: bar + rule feedback
  6. Design: avoid unnecessary derived state
  7. Security: client-side indicator is not authentication security
10. How to Explain Password Strength Indicator in 5 Minutes
Minute 1 — Clarify requirements

I first ask what rules define password strength, how many levels are required, and whether the component is only a UI indicator or also part of form validation.

Minute 2 — Design the state

I keep only password in state. The rule results, score, label, and progress value are derived from that password.

Minute 3 — Implement validation

I create independent validation rules using string length and regular expressions. Each rule returns a boolean. Then I count the rules that passed to get the score.

Minute 4 — Build the UI

I show the current strength label, progress bar, and individual requirements. Because the input is controlled, every keystroke immediately recalculates the result and updates the UI.

Minute 5 — Discuss production considerations
  • Detect common passwords and compromised-password patterns when appropriate.
  • Do not treat client-side strength as a security boundary.
  • Validate on the server as well.
  • Use accessible labels and text, not only color, to communicate strength.
  • Consider password visibility toggle.
  • Use a well-designed password strength estimator if the product requires more sophisticated scoring.
  • Avoid storing plaintext passwords unnecessarily.
Strong closing line: "The important design decision is to keep the password as the source of truth and derive all strength information from it, which prevents inconsistent UI state."
11. Common Developer Mistakes
Mistake 1 — Storing score and strength as separate state 
// ❌ Unnecessary
const [password, setPassword] = useState("");
const [score, setScore] = useState(0);
const [strength, setStrength] = useState("Weak");

These values can become inconsistent. Derive them from the password instead.

Mistake 2 — Checking only password length

Length alone does not satisfy the complete set of rules defined for the component. Make each requirement explicit.

Mistake 3 — Writing one huge validation condition 
// Hard to maintain
if (
  password.length >= 8 &&
  /[A-Z]/.test(password) &&
  /[0-9]/.test(password) &&
  ...
) {}

Separate rules into named booleans so the UI can reuse them and the code is easier to understand.

Mistake 4 — Showing strength only after form submission

The purpose of this component is immediate feedback, so validation should react to password changes.

Mistake 5 — Using only colors

Do not communicate Weak/Strong only through red/green colors. Include text and rule descriptions for accessibility and clarity.

Mistake 6 — Treating the indicator as actual security

Client-side checks can be bypassed. Server-side validation and secure authentication practices are still required.

Mistake 7 — Overusing useMemo

The calculation is small. useMemo is optional here. Don't add memoization simply because it exists.

Mistake 8 — Exposing or logging the password

Never log passwords to the console or unnecessarily store them elsewhere.

12. Interview Questions You May Be Asked

The score, rules, label, and progress are all deterministic results of the current password. Storing only the source value avoids duplicated state and synchronization problems.

Regular expressions provide a concise way to check whether the password contains categories such as uppercase letters, numbers, and special characters.

The validation calculation is small and fast. Recalculating it during render is normally fine. useMemo can be used when there is a real performance reason or when the calculation becomes more expensive.

The indicator itself is not a security mechanism. For stronger password security, combine appropriate server-side policy enforcement, secure hashing, rate limiting, breached-password checks where appropriate, and other authentication controls.

Move the rules into a reusable validation function or configuration, and pass requirements, labels, strength levels, and styling as props when the product needs customization.

Test empty input, each individual rule, combinations of rules, boundary length such as 7 versus 8 characters, strength transitions, and UI updates as the user types.

The controlled input updates password state. React re-renders, the rules are recalculated from the new value, and the strength label and rule indicators update.

If there are a fixed number of regex checks and each check scans the password, the calculation is generally O(n) with respect to password length. With a fixed number of rules, the constant factor remains small.
