React Search / Filter

A common React machine-coding task for searching and filtering a list of data.

Goal: Let the user type a search term and show only matching items without modifying the original data.

Left Side — Questions
1. What is Search / Filter?

Technical definition: Search/filter is a UI feature that takes user input and displays only the items from a data collection that satisfy a condition.

Layman example: Imagine a list of 100 products in a shop. Instead of looking through all 100 products, you type "phone". The application shows products related to "phone".

Core React concepts Controlled Input → State → filter() → Derived Data → Conditional Rendering

Basic idea:
Original Data + Search Term → filter() → Matching Data → Display
2. What Problem Does Search / Filter Solve?

Search/filter helps users quickly find relevant information from a larger collection of data.

  • Reduces the amount of information shown at one time.
  • Helps users find a specific item quickly.
  • Improves usability when a list becomes large.
  • Demonstrates array filtering and conditional rendering.
  • Tests React state and controlled inputs.
Machine-coding point: The interviewer is checking whether you can connect user input to state, derive filtered results correctly, and keep the original data unchanged.
3. Requirements
Basic requirements
  1. Display a list of products/users/items.
  2. Provide a search input.
  3. Update the search value when the user types.
  4. Filter the original list based on the search value.
  5. Display only matching results.
  6. Show a "No results found" message when nothing matches.
  7. Searching should be case-insensitive.
Good clarification questions
  • Should the search match the beginning of the text or anywhere inside it?
  • Should the search be case-insensitive?
  • Should we search only the name or multiple fields?
  • Should filtering happen immediately while typing?
  • For a large dataset, should search happen locally or through an API?
  • Do we need debounce for the search input?
4. State Design — What State Do I Need?

For a basic client-side search, I usually need only the search term as state.

const [search, setSearch] = useState("");
What about filtered results?

For this basic version, I do not need another state variable for filtered results.

Why? The filtered list can be derived from the original data and the current search term. 
const filteredProducts = products.filter(product =>
  product.name
    .toLowerCase()
    .includes(search.toLowerCase())
);
Important interview concept: Avoid storing derived data in state when it can be calculated directly from existing state/props.

6. How I Have Implemented It — Interview Explanation
Step 1 — Start with the original data

I keep the original products/items list unchanged. It can come from props, an API, or component data.

Step 2 — Create search state

I use useState to store whatever the user enters into the search box.

Step 3 — Make the input controlled

The input's value comes from the search state, and onChange updates that state.

Step 4 — Derive filtered data

I use filter() against the original list. I convert both values to lowercase so the search is case-insensitive.

Step 5 — Render the result

I use map() to display the filtered items. If the result is empty, I show a "No results found" message.

One-line implementation summary: "I keep the original data unchanged, store only the search term in state, derive the matching items using filter(), and render the derived result."
7. Full React Code
import { useState } from "react";

function SearchFilter() {
  const [search, setSearch] = useState("");

  const products = [
    { id: 1, name: "Laptop" },
    { id: 2, name: "Mobile Phone" },
    { id: 3, name: "Smart Watch" },
    { id: 4, name: "Headphones" },
    { id: 5, name: "Phone Case" }
  ];

  const filteredProducts = products.filter(product =>
    product.name
      .toLowerCase()
      .includes(search.toLowerCase())
  );

  return (
    <div>
      <h2>Product Search</h2>

      <input
        type="text"
        value={search}
        onChange={(e) => setSearch(e.target.value)}
        placeholder="Search products..."
      />

      {filteredProducts.length === 0 ? (
        <p>No results found</p>
      ) : (
        <ul>
          {filteredProducts.map(product => (
            <li key={product.id}>
              {product.name}
            </li>
          ))}
        </ul>
      )}
    </div>
  );
}

export default SearchFilter;
Important search logic
const filteredProducts = products.filter(product =>
  product.name
    .toLowerCase()
    .includes(search.toLowerCase())
);

What this means:

  1. products.filter() checks every product.
  2. product.name gets the product name.
  3. toLowerCase() makes comparison case-insensitive.
  4. includes() checks whether the search text exists anywhere in the name.
  5. Only matching products are returned in the new array.
Important: filter() does not change the original array. It returns a new array containing the matching elements.
8. How to Explain Search / Filter in 1 Minute

Interview-ready answer:

"I implemented a client-side search feature in React. I keep the original data unchanged and use a controlled input to store the user's search term in state. Whenever the user types, the search state updates and the component re-renders. I then derive the filtered list by using JavaScript's filter method on the original data. I convert both the item value and search term to lowercase so the search is case-insensitive, and I use includes to support partial matches. Finally, I use map to render the filtered results and display a no-results message when the filtered array is empty. I don't store the filtered list separately because it is derived from the original data and search term."
1-minute structure
  1. Input: controlled search box
  2. State: search term
  3. Filter: filter() + includes()
  4. Case: toLowerCase()
  5. Display: map()
  6. Empty result: No results found
9. How to Explain Search / Filter in 5 Minutes
Minute 1 — Clarify the requirement

I first confirm what needs to be searched, whether the search is case-insensitive, whether partial matches are allowed, and whether the data is local or coming from an API.

Minute 2 — Decide the state

I only store the search term in state. I don't store filtered results because filtered results can be calculated from the original data and search term.

Minute 3 — Implement controlled input

The input value is controlled by React. onChange updates the search state on every keystroke.

Minute 4 — Implement filtering

I use filter() and compare normalized strings using toLowerCase() and includes(). The original array remains unchanged.

Minute 5 — Discuss scalability

For a small client-side list, filtering during rendering is simple and sufficient. For a very large dataset or server-side search, I would consider debouncing the input, pagination, API-based filtering, caching, or other performance techniques depending on the requirements.

Strong closing line: "For the basic machine-coding requirement, I prefer the simplest correct solution: keep source data unchanged, store the search term, derive filtered data, and render the result."
10. Common Developer Mistakes
Mistake 1 — Mutating the original data

Do not remove items from the source array just because they don't match. Keep the original data intact and derive a filtered array.

Mistake 2 — Case-sensitive search unintentionally 
// Can fail for different letter cases
product.name.includes(search)

// Better
product.name.toLowerCase()
  .includes(search.toLowerCase())
Mistake 3 — Using filter incorrectly

Remember that filter() expects a condition that returns true for items that should remain in the result.

Mistake 4 — Storing derived filtered data unnecessarily 
// Usually unnecessary
const [filteredProducts, setFilteredProducts] = useState([]);

If filtered data can be calculated directly from source data and search state, derive it instead of creating another state source.

Mistake 5 — Forgetting stable keys

When rendering results with map(), provide a stable unique key, normally the item's id.

Mistake 6 — No empty-state handling

When no item matches, show a clear message instead of leaving the user wondering whether the application is broken.

Mistake 7 — Adding debounce without a requirement

For a small local list, debounce may be unnecessary. Discuss it when the dataset is large or the search calls an API on each keystroke.

includes() supports partial matching. For example, searching "phone" can match "Mobile Phone" and "Phone Case".

It normalizes both strings so "Phone", "phone", and "PHONE" can be treated as the same search text.

Because it is derived data. Storing both the source and derived result can create two sources of truth and unnecessary synchronization work.

Debounce delays an operation until the user stops typing for a specified period. It is useful when each search triggers an expensive operation such as an API request.

For n items, filter() generally checks each item once, so the filtering operation is O(n). Rendering the matching results adds work proportional to the number of displayed items.

const filtered = users.filter(user =>
  user.name.toLowerCase().includes(search) ||
  user.email.toLowerCase().includes(search)
);

Depending on requirements, I could use debounced server-side search, pagination, virtualization, memoization, or a backend search mechanism rather than filtering a huge dataset entirely on every keystroke in the browser.
