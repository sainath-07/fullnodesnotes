Questions / Topics
WHAT

What is an Email Client?

An Email Client is a user interface that lets people view, organize, compose, send, reply to, forward, search and manage email messages. Examples include web-based clients and desktop/mobile mail applications.

Simple interview definition: “An email client is a data-driven application that manages a collection of messages and provides navigation, list/detail views, composition and message actions such as read, unread, archive and delete.”

WHY

What problem does an Email Client solve?

An email client provides a single interface for managing potentially thousands of messages. It hides the complexity of mail storage, folders, message state and server communication behind simple user actions.

Problems it demonstrates in a machine coding round

  • List/detail UI: Show a collection of messages and the selected message together.
  • State management: Track selected email, folder, search term and message status.
  • CRUD-like actions: Archive, delete, mark read/unread, star and compose.
  • Search/filtering: Derive the visible list from user input and current folder.
  • Data flow: Keep email data separate from the rendering components.
  • Async behavior: Real clients need loading, error, retry and optimistic update handling.
  • Scalability: Large inboxes require pagination, virtualization and server-side search where appropriate.
Interview point: The challenge is not drawing an inbox. The interviewer is evaluating how you model message state, interactions, data flow, reusable components and edge cases.
HOW

How to implement an Email Client

  1. Clarify scope: Decide whether the round requires inbox only or also compose, search, folders and actions.
  2. Define the email model: Use fields such as id, sender, recipients, subject, body, timestamp, read and folder.
  3. Build the layout: Sidebar/folders → email list → reader/detail pane.
  4. Componentize: EmailSidebar, Toolbar, EmailList, EmailListItem, EmailReader and ComposeModal.
  5. Manage state: Selected email, current folder, search text, compose visibility and message state.
  6. Derive visible messages: Filter by folder/search instead of maintaining duplicate lists unnecessarily.
  7. Implement actions: Mark read/unread, archive, delete, star, reply and compose.
  8. Handle async states: Loading, error, empty inbox and sending state.
  9. Make responsive: On mobile, switch from three panes to list → reader navigation.
  10. Optimize: Virtualize large lists and debounce server-side search when needed.

Example: opening an unread email

  1. User clicks an email row.
  2. Store its ID as selectedEmailId.
  3. Reader finds the message from the source collection.
  4. If it was unread, update its read state.
  5. Reader displays sender, subject, timestamp and body.
  6. The list updates the unread styling/count.

Example: search flow

  1. User enters search text.
  2. Update searchQuery.
  3. Filter by subject/sender/body for local data, or debounce and query the server for large datasets.
  4. Render matching messages.
  5. If there are no matches, show a useful empty state.
Real-world distinction: In a production client, sending, reading and moving mail are server operations. The UI should handle network latency and failures rather than assuming every action succeeds.
1 MINUTE

How to explain Email Client to the interviewer in 1 minute

“I built the email client as a three-part responsive layout: folders on the left, the email list in the middle, and the selected email on the right. I keep the emails as the source of truth and store UI state such as selected email, current folder and search query separately. The visible list is derived from the current folder and search state. Email actions like mark read, archive and delete update the message state, while real applications would synchronize those changes with an API. I also considered loading, error and empty states, responsive mobile behavior, keyboard accessibility and large inbox performance.”

5 MINUTES

How to explain Email Client in 5 minutes

1. Clarify the requirements

“I first clarify whether we need only an inbox or a complete client with compose, reply, folders, search, star, archive and delete. I also clarify whether the data is static or comes from an API.”

2. Choose the UI pattern

“I use a master-detail pattern. The sidebar controls the current folder, the list shows messages and the reader displays the selected message. On mobile, these can become separate navigable views.”

3. Define the state

“The source of truth is the message collection. UI state includes current folder, selected message ID, search query, compose state and request status. I avoid storing values that can be derived, such as the filtered list.”

4. Componentize

“I create small components such as Sidebar, EmailList, EmailListItem, EmailReader and ComposeModal. EmailListItem receives message data and callbacks rather than owning the entire application state.”

5. Implement interactions

  • Select email → update selected ID and show reader.
  • Mark read → update message state and synchronize with server.
  • Archive/delete → change folder/status and remove from the current derived list.
  • Search → filter locally or debounce a server query.
  • Compose → validate fields, show sending state, then add/sync the sent message.

6. Handle async states

“I explicitly handle initial loading, failed requests, empty folders and send failures. For an action such as archive, I can use an optimistic update and roll it back if the server rejects the operation.”

7. Performance and accessibility

“For a large inbox, I would paginate or virtualize rows and debounce remote search. I would use semantic buttons, keyboard navigation, visible focus states and accessible labels for icon actions.”

Strong closing line: “My main design decision is to keep messages as the source of truth and derive the current view from folder, search and selection state. That avoids inconsistent duplicate collections and makes the client easier to extend.”
MY IMPLEMENTATION

How I implemented it — explanation to interviewer

Explain your implementation in this order:

1. Created the shell

“I started with the three-pane layout: folders, message list and reader. I made the layout responsive so the reader can become a separate mobile view.”

2. Defined one email model

“Each message has an ID, sender, recipients, subject, body, timestamp, read/starred state and folder. This becomes the source of truth.”

3. Added UI state

“I track selected email ID, active folder, search query and compose visibility. These are UI concerns and remain separate from the email data.”

4. Derived the list

“The displayed messages are calculated from the source collection using folder and search filters. I don't maintain separate inbox and search arrays.”

5. Added actions

“Selecting opens a message. Mark read, archive and delete update the source collection and therefore automatically update the derived list.”

6. Added production considerations

“For real APIs, I would add loading/error states, optimistic updates where appropriate, retry handling, debounced search and pagination or virtualization.”

How to narrate while coding

“First I will build the three-pane layout. Then I'll define the email data model and render the list from data. Next I'll add selected-email state and the reader. After that I'll implement search and message actions. Finally I'll add async states, responsive behavior and accessibility.”

Implementation decisions worth explaining

  • Selected ID instead of selected object: avoids holding a stale copy after a message changes.
  • Derived filtered list: prevents duplicate state from becoming inconsistent.
  • Reusable EmailListItem: keeps repeated message markup consistent.
  • Server synchronization: UI state is not treated as the final source of truth in a real client.
Interview-ready summary: “I separated the message data model, UI state, derived views and presentation components. That makes actions predictable and lets me add features such as starred mail, labels or pagination without rewriting the entire client.”

React core implementation
import { useMemo, useState } from "react";

const initialEmails = [
  {
    id: "1",
    sender: "Priya",
    subject: "Interview preparation",
    body: "Let's review the machine coding round.",
    read: false,
    starred: true,
    folder: "Inbox"
  },
  {
    id: "2",
    sender: "Team",
    subject: "Weekly update",
    body: "Here is the weekly project update.",
    read: true,
    starred: false,
    folder: "Inbox"
  }
];

const folders = ["Inbox", "Starred", "Sent", "Archive", "Trash"];

function EmailClient() {
  const [emails, setEmails] = useState(initialEmails);
  const [folder, setFolder] = useState("Inbox");
  const [selectedId, setSelectedId] = useState(null);
  const [query, setQuery] = useState("");

  const visibleEmails = useMemo(() => {
    const q = query.trim().toLowerCase();

    return emails.filter(email => {
      const folderMatch =
        folder === "Starred"
          ? email.starred
          : email.folder === folder;

      const text =
        `${email.sender} ${email.subject} ${email.body}`
          .toLowerCase();

      return folderMatch && text.includes(q);
    });
  }, [emails, folder, query]);

  const selectedEmail =
    emails.find(email => email.id === selectedId) || null;

  function markRead() {
    if (!selectedId) return;

    setEmails(prev =>
      prev.map(email =>
        email.id === selectedId
          ? { ...email, read: true }
          : email
      )
    );
  }

  function archive() {
    if (!selectedId) return;

    setEmails(prev =>
      prev.map(email =>
        email.id === selectedId
          ? { ...email, folder: "Archive" }
          : email
      )
    );

    setSelectedId(null);
  }

  return (
    <div className="email-client">
      <aside>
        {folders.map(item => (
          <button
            key={item}
            onClick={() => setFolder(item)}
          >
            {item}
          </button>
        ))}
      </aside>

      <section>
        <input
          value={query}
          onChange={event => setQuery(event.target.value)}
          placeholder="Search emails"
        />

        {visibleEmails.map(email => (
          <button
            key={email.id}
            onClick={() => {
              setSelectedId(email.id);
              if (!email.read) markRead();
            }}
          >
            <strong>{email.sender}</strong>
            <span>{email.subject}</span>
          </button>
        ))}
      </section>

      <main>
        {selectedEmail ? (
          <>
            <h2>{selectedEmail.subject}</h2>
            <p>{selectedEmail.body}</p>
            <button onClick={markRead}>Mark read</button>
            <button onClick={archive}>Archive</button>
          </>
        ) : (
          <p>Select an email</p>
        )}
      </main>
    </div>
  );
}

export default EmailClient;

COMMON MISTAKES

Common Developer Mistakes

1. Maintaining duplicate email collections

Keeping separate inbox, search, archive and starred arrays can easily make the UI inconsistent.

Better: Keep one source of truth and derive views.

2. Storing the entire selected email as state

The selected object can become stale after mark-read/archive updates.

Better: Store selectedEmailId and derive the object.

3. Making EmailListItem responsible for everything

Individual rows should not own global search, folder or server synchronization logic.

Better: Pass focused props and callbacks.

4. Ignoring loading/error/empty states

Real email data is asynchronous and can fail.

Better: Explicitly model request states and useful empty messages.

5. Searching on every keystroke against the server

This can create unnecessary requests and race conditions.

Better: Debounce server search and handle stale responses.

6. Rendering thousands of emails

A huge DOM list can make scrolling and interaction slow.

Better: Use pagination or virtualization.

7. No optimistic update strategy

Waiting for every archive/read action before updating the UI can feel slow.

Better: Consider optimistic updates with rollback when the operation is safe and reversible.

8. No confirmation strategy for destructive actions

Delete or permanently remove actions can cause accidental data loss.

Better: Use undo, confirmation or soft-delete depending on the product.

9. Poor responsive behavior

A three-column desktop layout does not automatically work on phones.

Better: Switch to list/detail navigation or stacked views.

10. Weak accessibility

Icon-only buttons, unreadable labels and mouse-only interactions exclude keyboard and assistive-technology users.

Better: Use semantic buttons, labels, focus states and keyboard-friendly navigation.

11. Unsafe HTML rendering of email bodies

Real emails can contain HTML and untrusted content.

Better: Sanitize untrusted HTML before rendering it and use safe link handling.

12. Mixing UI and server synchronization

Putting API calls everywhere makes failure handling difficult.

Better: Centralize or clearly isolate data-access logic.

Machine coding tip: If time is limited, prioritize the list/detail interaction, state model, search, one or two message actions, responsive behavior and clear component boundaries before adding advanced email features.
FOLLOW-UPS

Likely Interviewer Follow-up Questions

How would you handle 100,000 emails?

Use server-side pagination/search, virtualization for visible rows and avoid loading the entire mailbox into the browser.

How would you implement search?

For small local data, filter derived state. For production-scale mail, debounce and send a server-side search request.

How would you prevent stale search responses?

Use request cancellation, request IDs or a data-fetching library that handles stale results.

How would you implement optimistic archive?

Update the UI immediately, send the request, and restore the previous state with an error message if the server rejects it.

How would you handle compose?

Use a controlled form, validate recipients/subject/body, track sending state, disable duplicate submission and handle server errors.

How would you render HTML email safely?

Sanitize untrusted HTML before inserting it into the DOM and apply safe policies to links and embedded content.

How would you implement unread counts?

Derive the count from the source email collection or use server-provided counts for large datasets.

Why store selectedId instead of selectedEmail?

The ID remains stable while the email object can change after actions. Deriving the object prevents stale state.

How would you make the email client accessible?

Use semantic controls, keyboard navigation, focus management, clear labels, sufficient contrast and meaningful announcements for state changes.

How would you test it?

Test folder switching, search, selection, read/unread state, archive/delete, empty/error states and important data transformations.
