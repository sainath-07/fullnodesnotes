WHATUI COMPONENT

What is Theme Toggle / Dark Mode?

A theme toggle lets the user switch the application's visual theme, commonly between Light Mode and Dark Mode. The theme controls shared UI properties such as background color, text color, borders, surfaces and sometimes shadows.

Typical use cases

  • Web applications and dashboards
  • Developer tools and code editors
  • Mobile/web products with user appearance preferences
  • Applications that support system theme preferences
WHY

What problem does it solve?

Light mode
Works well in bright environments and is familiar for many users.
Dark mode
Can be more comfortable in low-light environments and gives users a personalization option.

Interview answer

“The main problem is user preference and visual comfort. A theme toggle gives users control over the application's appearance. Instead of hardcoding colors in individual components, I centralize theme values so one state change can update the entire UI consistently.”

Important design goal

One source of truth: the current theme should be represented by one state or document-level attribute/class, not duplicated across every component.

HOW

How to implement Theme Toggle / Dark Mode

  1. Define theme tokens such as background, text, surface and border colors.
  2. Represent the current theme using state or a root attribute such as data-theme="dark".
  3. Use CSS variables so components consume the theme tokens instead of hardcoded colors.
  4. When the toggle changes, update the root theme.
  5. Persist the user's choice using localStorage if the preference should survive reloads.
  6. Optionally respect prefers-color-scheme when the user has not chosen a preference.
:root {
  --bg: #ffffff;
  --text: #111827;
}

[data-theme="dark"] {
  --bg: #111827;
  --text: #f9fafb;
}

document.documentElement.dataset.theme = "dark";

1 MINUTE

How to explain it to the interviewer in 1 minute

“I implemented a theme toggle using a single source of truth for the current theme. I keep the colors in CSS variables, and JavaScript only changes the active theme on the root element. When the user toggles, I switch between light and dark, which causes all components using those variables to update consistently. I can persist the selected theme in localStorage so it survives page reloads. I would also consider the user's system preference using prefers-color-scheme when no explicit preference has been saved.”

1-minute structure

  1. What: Switch between application themes.
  2. State: One current theme value.
  3. Styling: CSS variables provide theme tokens.
  4. Persistence: localStorage preserves user preference.
  5. System preference: Optional fallback to prefers-color-scheme.
5 MINUTES

How to explain it to the interviewer in 5 minutes

Opening: “I’ll explain the requirements, state design, theme application, persistence, accessibility and edge cases.”

1. Requirement

The user should be able to switch between light and dark themes, and the whole application should update consistently.

2. State design

I maintain one theme state such as "light" or "dark". The theme is a global UI concern, so I apply it at the document/root level.

3. Styling strategy

I prefer CSS custom properties. Components consume variables like --bg, --text and --surface. The component does not need to know the actual color value for each theme.

4. Persistence

On initial load, read a saved value from localStorage. On toggle, update both the root theme and the saved value.

5. System preference

If there is no saved preference, use window.matchMedia("(prefers-color-scheme: dark)") as a sensible default.

6. Accessibility

The toggle should be keyboard accessible and expose its current state. A native checkbox/button with an accessible label is preferable to a clickable non-semantic div.

7. Edge cases

  • Invalid localStorage value → fall back to a valid theme.
  • First visit → use saved preference or system preference.
  • Rapid toggling → state remains the single source of truth.
  • Missing theme variable → define sensible defaults.

FULL CODE

Standalone implementation

This version is framework-free and includes theme state, localStorage persistence, system preference fallback and accessible controls.

<button id="themeToggle"
  type="button"
  aria-label="Toggle dark mode"
  aria-pressed="false">
  Toggle theme
</button>

<script>
const STORAGE_KEY = "theme";
const root = document.documentElement;
const toggle = document.querySelector("#themeToggle");

function getInitialTheme() {
  const saved = localStorage.getItem(STORAGE_KEY);

  if (saved === "light" || saved === "dark") {
    return saved;
  }

  return window.matchMedia("(prefers-color-scheme: dark)").matches
    ? "dark"
    : "light";
}

function applyTheme(theme, persist = true) {
  const validTheme = theme === "dark" ? "dark" : "light";

  root.dataset.theme = validTheme;

  toggle.setAttribute(
    "aria-pressed",
    String(validTheme === "dark")
  );

  if (persist) {
    localStorage.setItem(STORAGE_KEY, validTheme);
  }
}

toggle.addEventListener("click", () => {
  const currentTheme = root.dataset.theme;
  applyTheme(currentTheme === "dark" ? "light" : "dark");
});

applyTheme(getInitialTheme(), false);
</script>

React version — core idea

function App() {
  const [theme, setTheme] = useState("light");

  useEffect(() => {
    document.documentElement.dataset.theme = theme;
  }, [theme]);

  return (
    <button
      onClick={() =>
        setTheme(t => t === "light" ? "dark" : "light")
      }
    >
      Toggle theme
    </button>
  );
}
COMMON MISTAKES

Common developer mistakes

1. Changing every component individually
This creates duplicated logic and makes the UI difficult to maintain. Prefer root-level theme state plus CSS variables.
2. Hardcoding colors everywhere
Use semantic tokens such as --background, --text and --surface.
3. Forgetting persistence
If the requirement expects the preference to survive reloads, save the explicit user choice.
4. Ignoring system preference
When there is no saved preference, prefers-color-scheme can provide a better first-load experience.
5. Using a non-accessible clickable div
Use a native button or checkbox and expose the current state to assistive technologies.
6. Flash of the wrong theme
Applying the saved theme only after the page renders can cause a visible light-to-dark flash. In production, initialize the theme as early as possible.
7. Storing arbitrary values
Validate localStorage values instead of trusting them blindly.
8. Overengineering
For a basic machine-coding round, avoid unnecessary state-management libraries when document-level state and CSS variables are sufficient.
FOLLOW-UP QUESTIONS

Likely interviewer follow-ups

How would you avoid a flash during page load?

Run a small initialization script before the main UI paints, or set the theme as early as possible based on saved preference/system preference.

Why use CSS variables?

They keep theme values centralized and let the same components automatically consume different values without duplicated styling logic.

How would you support more than two themes?

Use a theme identifier such as light, dark, high-contrast or blue, with a corresponding token set.

What if the user changes the OS theme?

If the user has not explicitly selected a theme, listen to the matchMedia change event and update the application. If the user has explicitly chosen a theme, keep their choice.

How would you test it?

  • Toggle light → dark → light.
  • Reload and verify the saved preference.
  • Test first load with system dark/light preference.
  • Test invalid localStorage values.
  • Verify keyboard accessibility and aria state.
  • Verify all major components use theme tokens.
