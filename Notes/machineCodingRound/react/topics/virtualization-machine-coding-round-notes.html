Virtualization

Interview-ready notes for rendering very large lists efficiently by keeping only the visible items in the DOM.

LEFT — What is Virtualization?

Virtualization is a performance technique where a UI renders only the items that are currently visible, plus a small buffer around them, instead of rendering every item in a huge list.

Simple idea: “If I have 100,000 rows, I don't need 100,000 DOM elements. I only need the rows the user can see.”

It is also called windowing because the UI creates a small “window” into a much larger dataset.

LEFT — Why is Virtualization Important?
  • Reduces the number of DOM nodes.
  • Reduces initial rendering work.
  • Reduces memory usage for very large lists.
  • Reduces the amount of React work needed when updating the visible list.
  • Makes large tables, feeds and dropdowns more usable.
  • Helps prevent the browser from struggling with thousands of mounted elements.
Important: Pagination reduces how much data you fetch. Virtualization reduces how many of those loaded items you render at once. They solve different problems and can be used together.

LEFT — How Does Virtualization Work?
  1. Know the total number of items.
  2. Know or estimate the height of each row.
  3. Track the scroll position.
  4. Calculate which indexes are visible.
  5. Render only those indexes.
  6. Create a large scrollable area so the scrollbar still represents the full list.
  7. Move the visible rows to their correct visual position.
  8. Repeat when the user scrolls.
Core formula for fixed-height rows:
startIndex = floor(scrollTop / itemHeight)
LEFT — When Should I Use Virtualization?
  • Thousands of table rows
  • Large product lists
  • Large chat/message histories
  • File managers
  • Activity feeds
  • Large dropdowns/autocomplete results
  • Data-heavy dashboards
Don't use it automatically. A list with 30 items usually does not need virtualization.

LEFT — Common Developer Mistakes
  1. Rendering the complete huge array and calling it virtualization.
  2. Not creating enough scrollable space, causing the scrollbar to represent only the rendered items.
  3. Calculating visible indexes incorrectly.
  4. Forgetting a buffer/overscan, causing blank gaps during fast scrolling.
  5. Using array indexes as keys when items have stable IDs.
  6. Assuming every row has the same height when the UI actually has variable heights.
  7. Doing expensive work on every scroll event without optimization.
  8. Using virtualization for small lists where the complexity is unnecessary.
  9. Confusing virtualization with lazy loading or pagination.
  10. Ignoring accessibility and keyboard navigation.
LEFT — How I Would Explain It to the Interviewer
“I would use virtualization when a list contains a very large number of items. Instead of mounting every item in the DOM, I calculate the visible range from the scroll position and row height and render only that range plus an overscan buffer. I keep a spacer with the total list height so the scrollbar behaves as if the whole list is rendered. As the user scrolls, I update the visible range. This reduces DOM nodes, memory usage and rendering work.”
Strong interview point: “Virtualization is about rendering fewer UI elements, not fetching less data.”

RIGHT — Step-by-Step Working
Step 1 — Full dataset: Suppose there are 10,000 items.
Step 2 — Fixed row height: Suppose each row is 50px.
Step 3 — Viewport: The container is 500px tall, so roughly 10 rows fit.
Step 4 — Scroll: If scrollTop = 1000, then 1000 / 50 = 20, so the visible area starts around item 20.
Step 5 — Overscan: Render a few rows before and after the visible range.
Step 6 — Position: Use a spacer/transform so those few rows appear at the correct position in the large virtual list.
Step 7 — Repeat: On scroll, calculate a new range and render the new window.
RIGHT — Full React Machine-Coding Example

This implementation demonstrates the core virtualization algorithm using fixed-height rows. It intentionally avoids a third-party library so you can explain the mechanics in an interview.

import React, { useMemo, useState } from "react";

const ITEM_HEIGHT = 50;
const CONTAINER_HEIGHT = 500;
const OVERSCAN = 5;

const items = Array.from(
  { length: 10000 },
  (_, index) => ({
    id: index + 1,
    name: `Item ${index + 1}`,
  })
);

function VirtualList() {
  const [scrollTop, setScrollTop] = useState(0);

  // How many items can fit inside the viewport?
  const visibleCount = Math.ceil(
    CONTAINER_HEIGHT / ITEM_HEIGHT
  );

  // Find the first item that should appear near the viewport.
  const firstVisibleIndex = Math.floor(
    scrollTop / ITEM_HEIGHT
  );

  // Render a few extra items before the viewport.
  // This is called overscan and helps prevent blank gaps
  // during fast scrolling.
  const startIndex = Math.max(
    0,
    firstVisibleIndex - OVERSCAN
  );

  // Render extra items after the viewport as well.
  const endIndex = Math.min(
    items.length,
    firstVisibleIndex + visibleCount + OVERSCAN
  );

  // Only this small slice is rendered.
  const visibleItems = useMemo(
    () => items.slice(startIndex, endIndex),
    [startIndex, endIndex]
  );

  const totalHeight = items.length * ITEM_HEIGHT;

  return (
    <div
      style={{
        height: CONTAINER_HEIGHT,
        overflowY: "auto",
        border: "1px solid #ccc",
      }}
      onScroll={(event) => {
        setScrollTop(event.currentTarget.scrollTop);
      }}
    >
      {/*
        This element represents the height of the complete list.
        The browser therefore gives us a scrollbar for all items
        even though only a small slice is mounted.
      */}
      <div
        style={{
          height: totalHeight,
          position: "relative",
        }}
      >
        {visibleItems.map((item, index) => {
          const actualIndex = startIndex + index;

          return (
            <div
              key={item.id}
              style={{
                position: "absolute",

                // Place the virtual row at its real position
                // inside the complete virtual list.
                top: actualIndex * ITEM_HEIGHT,

                height: ITEM_HEIGHT,
                width: "100%",
                boxSizing: "border-box",
                borderBottom: "1px solid #ddd",
                padding: "14px",
                background: "#fff",
              }}
            >
              {item.name}
            </div>
          );
        })}
      </div>
    </div>
  );
}

export default VirtualList;
Important: This is the core algorithm, not a production-grade virtualization library. Real applications may need support for variable row heights, keyboard navigation, accessibility, resize handling, horizontal lists, sticky rows, and more.

RIGHT — Why Do We Need the Large Spacer?

A common question in interviews is:

“If you're rendering only 20 items, how does the scrollbar know that there are 10,000?”

We create a container whose height represents the complete virtual list:

const totalHeight =
  items.length * ITEM_HEIGHT;

For 10,000 items at 50px:

10,000 × 50
= 500,000px

Then the visible rows are positioned inside that large virtual space.

Result: The browser thinks the scrollable area is huge, while React mounts only a small number of actual rows.
RIGHT — What is Overscan?

Overscan means rendering a few extra items before and after the visible area.

Before viewport
5 extra rows
Viewport
Visible rows
After viewport
5 extra rows
Why? If the user scrolls quickly, the nearby rows are already mounted, reducing the chance of seeing blank space.
RIGHT — Common Mistakes Explained
1. Rendering the entire array
If you call items.map() over 100,000 items and mount every row, you are not virtualizing.
2. Forgetting the virtual total height
Without the spacer/virtual height, the scrollbar only represents the small rendered window.
3. No overscan
Fast scrolling can expose blank gaps while new rows are being rendered.
4. Variable-height assumption
The simple scrollTop / itemHeight calculation works naturally for fixed-height rows. Variable heights require more sophisticated measurement/index calculations.
5. Bad keys
Use a stable unique item ID when available, not a random value generated on each render.
6. Heavy scroll work
A complex scroll handler can become expensive. Keep the calculation lightweight and consider batching or scheduling updates where appropriate.
RIGHT — Virtualization + Infinite Scrolling

These techniques solve different problems and can be combined.

Infinite scrolling
“Do I need more data?”

Fetch the next page when the user approaches the end.
Virtualization
“Which loaded data should be in the DOM?”

Render only the visible window.
Strong architecture: Fetch data in pages + keep the loaded data + virtualize the large rendered collection.

RIGHT — Interview Follow-Up Answers
  1. What is windowing?
    Another common name for list virtualization: render a moving window of items instead of the whole list.
  2. Why use overscan?
    To render nearby rows so fast scrolling is less likely to reveal blank space.
  3. Does virtualization reduce API calls?
    No. Pagination/infinite scrolling can reduce initial data fetching. Virtualization controls what gets mounted in the DOM.
  4. Can I virtualize variable-height rows?
    Yes, but it is more complex because the implementation must measure or estimate item sizes and maintain accurate positions.
  5. When should I not virtualize?
    For small lists where normal rendering is fast and the added implementation complexity provides little benefit.
